The wizard runs on a harness we own, so we get feedback from every run on how our skills and SDKs behave in real repositories. We turn that feedback into the edge cases below, and feed the fixes back into the SDKs, evals, and docs so general agents benefit too.

Below are 645 edge cases the wizard has caught. Each one helped us improve the integration skills.

Think of these as the Wizard's battle trophies!

## Setup and init

<details>
<summary>Init runs late, never, or in the wrong file</summary>

The SDK starts too late, more than once, or in a file that never runs.

**Example: Browser init inside a component effect**

**Problem.** Older posthog-js docs and most blog posts show a 'use client' PostHogProvider or _app.tsx that calls posthog.init in useEffect, often with a dynamic import to dodge SSR. Agents reproduce it from training data even when instrumentation-client.ts is available.

**Impact.** Init waits for hydration, so the first pageview and captures or flag reads made before the effect runs are dropped or throw. Every caller needs init guards and flags flicker. Same for React SPAs, where init belongs at module scope in main.jsx.

```tsx file=Generic agent
export function PostHogInitializer() {
  useEffect(() => {
    void import('posthog-js').then(({ default: posthog }) => {
      posthog.init(token, { api_host: host })
      window.posthogInitialized = true
      window.dispatchEvent(new Event('posthog_initialized'))
    })
  }, [])
}   // pages call posthog.capture() with no init guard
```

```ts file=Wizard
// instrumentation-client.ts runs before any component renders
import posthog from 'posthog-js'
posthog.init(process.env.NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN!, {
  api_host: '/ingest',
  defaults: '<ph_posthog_js_defaults>',
})
// components: useFeatureFlagEnabled('flag') works without PostHogProvider
```

**Also catches:**

- Fast models write Next.js init from memory into a lib file nothing imports, with a guessed env var and no defaults. The wizard has them follow the example's instrumentation-client.ts. [init.md](https://github.com/PostHog/context-mill/blob/main/context/agents/integration-v2/init.md)
- Same for iOS, where setup goes in a SwiftUI onAppear that runs many times and after early events. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- Same for Flutter, where setup is not awaited before runApp, so the first frames send before the SDK is ready. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- Older Next.js silently ignores instrumentation-client.ts, so PostHog never starts. The wizard checks the installed version and refuses Next.js below 15.3. [posthog-best-practices/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/posthog-best-practices/description.md)
- The instrumentation-client file gets a .tsx or .jsx extension, so Next.js may not pick it up. [instrumentation-client.ts](https://github.com/PostHog/context-mill/blob/main/example-apps/next-app-router/instrumentation-client.ts)

- The agent creates a provider file but never imports or mounts it, and the build stays green. The wizard checks that every created component is actually used. [3-revise.md](https://github.com/PostHog/context-mill/blob/main/context/skills/integration/references/3-revise.md)
- Angular init in ngOnInit runs inside the zone, so replay's DOM observers trigger extra change detection. The wizard runs init outside the Angular zone.
- The Phoenix PostHog Plug is skipped or placed after the router, so request data and tracing headers never reach events. The wizard puts the Plug before the router. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)

[react-router-wizard-agent.ts](https://github.com/PostHog/wizard/blob/main/src/programs/frameworks/react-router/react-router-wizard-agent.ts)
- Same for TanStack Router, where a file-based `__root.tsx` is created in a code-based app. [tanstack-router/utils.ts](https://github.com/PostHog/wizard/blob/main/src/programs/frameworks/tanstack-router/utils.ts)

- Same for Next.js projects that use src/, where instrumentation-client.ts belongs beside src/app.
- Same for old framework or platform versions, which get current APIs and the latest SDK. [frameworks](https://github.com/PostHog/wizard/tree/main/src/programs/frameworks)

- Kotlin Multiplatform setup copies the native one-argument shape and fails on Android. The wizard passes the right PostHogContext on each platform. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)

<summary>Browser-only code runs on the server</summary>

Code that needs a browser runs during server rendering, or server code ends up in the browser.

**Example: Nuxt plugin also runs on the server**

**Problem.** plugins/posthog.ts looks client-side, but Nuxt runs unsuffixed plugins in Nitro SSR too. Only the .client filename makes it browser-only.

**Impact.** SSR throws 'window is not defined' or initializes a browser SDK on the server.

```ts file=Generic agent
// plugins/posthog.ts   (runs on server and client)
export default defineNuxtPlugin(() => {
  posthog.init(runtimeConfig.public.posthog.publicKey, {
    tracing_headers: [window.location.hostname],
  })
})
```

```ts file=Wizard
// plugins/posthog.client.ts   (client-only by filename)
export default defineNuxtPlugin((nuxtApp) => {
  const posthogClient = posthog.init(runtimeConfig.public.posthog.publicKey, {
    api_host: runtimeConfig.public.posthog.host,
    tracing_headers: [window.location.hostname],
  })
  return { provide: { posthog: posthogClient as PostHog } }
})
```

- Same for SvelteKit, where +layout.ts and the +layout.svelte module script also run on the server. [hooks.client.ts](https://github.com/PostHog/context-mill/blob/main/example-apps/sveltekit/src/hooks.client.ts)

<summary>The same thing set up twice</summary>

The agent adds a second copy of something the project or an earlier step already set up.

**Example: Second PostHog init beside the existing one**

**Problem.** Agents add a PostHogProvider or init by reflex without searching for an existing provider or instrumentation-client.ts init, because most React examples pair init with a provider, including for flag hooks. Double init throws no error.

**Impact.** Two browser inits race to stamp $set_once properties like $initial_pathname, corrupting attribution and double-capturing pageviews. One multi-SDK customer saw about 165k blocked merges per day.

**Variants.**

- A second browser provider or init next to instrumentation-client.ts.
- A new client built just for a feature like metrics or AI.
- A migration that swaps an old vendor provider for a second PostHog one.

```tsx file=Generic agent
// instrumentation-client.ts
posthog.init(KEY, { api_host: '/ingest' })
// app/providers.tsx (always mounted)
useEffect(() => { posthog.init(KEY, { api_host: '/ingest' }) }, [])
// app/layout.tsx: <PHProvider>{children}</PHProvider>
// and <PostHogProvider> added again in the providers list
```

```tsx file=Wizard
// instrumentation-client.ts: the one browser init
//IMPORTANT: Never combine this approach with other client-side PostHog
// initialization approaches, especially components like a PostHogProvider.
posthog.init(process.env.NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN!, { api_host: '/ingest' })

// components: hooks use the singleton, no provider needed
const on = useFeatureFlagEnabled('promo')
// audit init-not-duplicated: warning on 2+ browser inits, error if confirmed on one page
```

**Also catches:**

- Same for Flutter, where native auto-init from AndroidManifest.xml and Info.plist stays on beside the Dart setup. [flutter-wizard-agent.ts](https://github.com/PostHog/wizard/blob/main/src/programs/frameworks/flutter/flutter-wizard-agent.ts)
- The agent adds a PostHog client on OpenTelemetry paths that need none, or stacks a wrapper and an instrumentor on one provider. The wizard builds a client only on wrapper and manual paths and reuses an existing one. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- A later task cannot see what earlier tasks did, so it adds identify or reset again. The wizard passes earlier steps' handoffs to every later task. [agent-prompt-loader.ts](https://github.com/PostHog/wizard/blob/main/src/agent/agent-prompt-loader.ts)
- The agent adds alias() next to identify() to be safe, which can block the identify merge. The wizard relies on identify() and keeps alias() for narrow cases. [3-identify-lifecycle.md](https://github.com/PostHog/context-mill/blob/main/context/skills/audit-identify/references/3-identify-lifecycle.md)
- The same milestone is captured in the browser and the API, so every conversion counts twice. The wizard captures key milestones once, on the backend. [product-analytics.md](https://github.com/PostHog/context-mill/blob/main/context/skills/posthog-best-practices/references/product-analytics.md)
- A manual pageview component is added while defaults already capture history_change pageviews, so every navigation counts twice. The wizard keeps the automatic pageviews only. [capture/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/integration-v2/capture/description.md)
- Custom page_viewed events are added on each screen mount, on top of automatic pageviews. [instrument-product-analytics/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/omnibus/instrument-product-analytics/description.md)
- The full setup flow runs on a project that already has PostHog. The wizard detects the existing install and offers other programs first. [intro-menu.ts](https://github.com/PostHog/wizard/blob/main/src/tui/programs/posthog-integration/intro-menu.ts)

<summary>Project misread: wrong platform, mode, or half of the stack</summary>

The agent misreads what kind of project it is in and sets up the wrong SDK or only half the app.

**Example: Flutter repo misread as a native Android or iOS app**

**Problem.** A Flutter repo has real Gradle, AndroidManifest, MainActivity.kt and Xcode files under android/ and ios/, so the first matching native or Java detector claims it.

**Impact.** posthog-android or the native source-map flow is wired into the shell. Dart screens, events and the web target are never tracked, and Java server projects can get claimed as Android.

```kotlin file=Generic agent
// android/app/src/main/kotlin/.../MainActivity.kt inside a Flutter app
class MainActivity : FlutterActivity() {
  override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    PostHogAndroid.setup(application, PostHogAndroidConfig(KEY, HOST))
  } // Dart code untouched
}
```

```ts file=Wizard
// constants.ts: flutter is ordered before kmp/swift/android; java comes after them
flutter = 'flutter',
// flutter detect: anchored to a key/value line, so '# sdk: flutter' and pure Dart don't match
/^\s*sdk:\s*flutter\s*$/m.test(pubspec ?? '')
// android + java detect():
// pubspec.yaml means Flutter - its android/ subtree would match below.
if (fs.existsSync(path.join(installDir, 'pubspec.yaml'))) return false;
// source maps: VARIANT_PRECEDENCE = ['react-native', 'flutter', 'android', 'ios', ...]
```

<summary>Framework conventions ignored or written from stale memory</summary>

The agent writes code from old training data instead of following the framework's current conventions.

**Example: Svelte 4 syntax written into a runes app**

**Problem.** Training data is mostly Svelte 4, so agents write export let and on:click, and a JS build may not catch rune misuse, so the agent finishes without Svelte's own validator.

**Impact.** Components build but misbehave under runes, or the compiler rejects them.

```svelte file=Generic agent
<script>
  export let user;
  $: greeting = 'Hi ' + user.name;
</script>
<button on:click={consider}>
<!-- finishes without any Svelte validation step -->
```

```svelte file=Wizard
<script>
  let { user } = $props();
  let greeting = $derived('Hi ' + user.name);
</script>
<button onclick={consider}>
<!-- use Svelte MCP (list-sections, get-documentation); always run
     svelte-autofixer on every new or modified .svelte file before finishing -->
```

## Tokens, env vars, hosts and network

<details>
<summary>Env var not readable where the code runs</summary>

The token sits in an env var, but the code that needs it runs where that variable is never loaded or exposed.

**Example: Browser code reads an unexposed env var**

**Problem.** The agent names variables from memory (POSTHOG_KEY, REACT_APP_\*) instead of following the bundler's public-prefix rule. Server-side reads work, and the wizard's own react-router config still returns REACT_APP_ names for a Vite-based router, so nothing looks wrong until the browser runs.

**Impact.** Silent. The bundler strips the variable or there is no process.env in the browser, the token is undefined, and init is skipped, sends nothing or throws. Same for Astro, which exposes only PUBLIC_ variables and needs define:vars in inline scripts.

```ts file=Generic agent
// lib/posthog.ts (Next.js), name from model memory
posthog.init(process.env.POSTHOG_KEY!, {
  api_host: process.env.POSTHOG_HOST,
})
// Vite app with CRA habits: process.env.REACT_APP_POSTHOG_KEY  (no process.env in the browser)
// Vue/Vite: import.meta.env.POSTHOG_KEY   (Vite only exposes VITE_*)
```

```ts file=Wizard
environment: {
  getEnvVars: (apiKey, host) => ({
    NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN: apiKey,
    NEXT_PUBLIC_POSTHOG_HOST: host,
  }),
}
// detectEnvVarPrefix(): next -> NEXT_PUBLIC_, react-scripts -> REACT_APP_, vite/TanStack -> VITE_PUBLIC_, SvelteKit -> PUBLIC_
// Nuxt: NUXT_PUBLIC_*   Vue: VITE_*   Angular (ngx-env): NG_APP_*
```

**Also catches:**

- Same for Angular, where the stock builder loads no .env and NG_APP_ only works with @ngx-env/builder. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- Same for React Native, which needs react-native-config or expo-constants, not process.env. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- Same for Express, Fastify, Hono, Ruby, Go, Spring and compiled binaries, which do not load .env on their own. [error-tracking/init.md](https://github.com/PostHog/context-mill/blob/main/context/agents/error-tracking/init.md)
- Same for Elixir, where config.exs runs at compile time. The token belongs in runtime.exs. [runtime.exs](https://github.com/PostHog/context-mill/blob/main/example-apps/elixir/config/runtime.exs)
- Same for iOS, where Xcode scheme env vars exist only when you run from Xcode, so release builds crash or send nothing. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- The deploy step, like docker run, compose or a PaaS config, never passes the token, so production runs with no analytics. <summary>Env files read or written wrong</summary>

## SDK usage and dependencies

<details>
<summary>Events lost when the process, request or page ends</summary>

Queued events are dropped because the process, request or page ends before the SDK sends them.

**Example: Short-lived handler returns before batched events send**

**Problem.** posthog-node capture() only enqueues, and on a long-lived local dev server the batch still goes out, so the bug never shows locally. Old docs and the old commandment said not to set flushAt or flushInterval in 'long-running servers', which agents applied to Next.js, Nuxt, SvelteKit, Astro and TanStack Start route handlers.

**Impact.** Silent: on serverless or edge the function freezes on return before the batched HTTP send, so server events are dropped. Low-traffic endpoints lose most events.

**Variants.**

- Route handlers on serverless or edge hosts.
- Server error hooks like SvelteKit handleError.
- AWS Lambda handlers, and Celery, Sidekiq or BullMQ jobs.

```ts file=Generic agent
// lib/posthog-server.ts
const posthog = new PostHog(token, { host })   // default batching: 20 events / 10s

export async function POST(request: Request) {
  posthog.capture({ distinctId: username, event: 'server_login' })
  return NextResponse.json({ success: true, user }) // returns before the send
}
```

```ts file=Wizard
// lib/posthog-server.ts
new PostHog(token, { host, flushAt: 1, flushInterval: 0 })

// api/auth/login/route.ts
posthog.capture({ distinctId: username, event: 'server_login' })
// This handler is short-lived; flush so the enqueued events send before it returns
await posthog.flush()
return NextResponse.json({ success: true, user })
```

**Also catches:**

- A server SDK client is built in every request, so it leaks and loses buffered events. The wizard uses one module client for every handler. [init/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/integration-v2/init/description.md)
- Same for Django, where the client is made in settings.py, a view or at import instead of once in AppConfig.ready. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- A Statsig migration maps shutdown() to PostHog in browser code, where posthog-js has no teardown. The wizard maps it only in clear server teardown handlers. [mapping.md](https://github.com/PostHog/context-mill/blob/main/context/skills/migrate/references/statsig/mapping.md)
- Same for Cloudflare Workers, where the isolate can end as soon as the Response returns. [cloudflare-detection.ts](https://github.com/PostHog/wizard/blob/main/src/programs/cloudflare-detection.ts)
- Same for a serverless MCP handler that relies on a SIGTERM flush, which never fires on Vercel, Workers or Lambda. [mcp-analytics/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/mcp-analytics/description.md)

<details>
<summary>Dependency installs and versions</summary>

The SDK is installed with the wrong version, the wrong tool, or only half its setup.

**Example: SDK version typed from memory**

**Problem.** Editing the manifest directly feels quicker than running the package manager, and the model trusts the version numbers it remembers. A version that was never published fails only later, at install time, and an old remembered version installs without any warning.

**Impact.** A version that was never published makes the whole install fail with ETARGET, and the build step cannot recover from a bad manifest. Each new guess fails again. A remembered old version pins a stale SDK that still has bugs fixed upstream.

```text file=Generic agent
"dependencies": {

  "posthog-node": "^5.99.0"    // never published
}
// npm error code ETARGET
// npm error notarget No matching version found for posthog-node@^5.99.0
# pubspec.yaml: posthog_flutter: ^4.0.0   # remembered, not resolved
```

```bash file=Wizard
npm install posthog-js posthog-node   # bare names, manager writes real ^x.y.z + lockfile
composer require posthog/posthog-php
bundle add posthog-ruby
flutter pub add posthog_flutter
# ETARGET / yanked release: reinstall by bare name, do not guess pins
npm view posthog-js version           # audit: installed vs latest

## Identity

<details>
<summary>Wrong or unstable distinct id</summary>

Events are tied to an id that is missing, shared, personal or changes over time, so people split or merge wrongly.

**Example: Literal anonymous fallback pools all users**

**Problem.** A ?? 'anonymous' fallback or a constant 'server'/'backend' id satisfies the SDK's required distinctId and the type checker, so it looks like defensive coding and never errors. The pooled person only shows up later in data.

**Impact.** Silent: every logged-out visitor or unattributed server event lands on one giant person, corrupting counts, funnels, retention and person merges.

```ts file=Generic agent
signIn: async ({ user, account }) => {
  const distinctId = user?.id ?? user?.email ?? "anonymous";
  posthog.identify({ distinctId, properties: { name: user?.name, email: user?.email } });
  posthog.capture({ distinctId, event: "server_sign_in" });
}
// go
client.Enqueue(posthog.Capture{DistinctId: "server", Event: "order_created"})
```

```ts file=Wizard
callbacks: {
  session({ session, token }) {
    if (session.user && typeof token.sub === "string") session.user.id = token.sub;
    return session;
  },
},
// identify only when the stable id is a string; otherwise skip and stay anonymous
if (typeof session.user?.id === 'string') posthog.identify(session.user.id, { email: session.user.email })
// truly system-level: no person profile
posthog.capture({ distinctId: 'cron', event: 'nightly_sync', properties: { $process_person_profile: false } })
```

**Also catches:**

- Email is used as the distinct id, so PII is every event's identity and a changed email splits a person. The wizard identifies with the stable user id and sets email as a person property. - Example READMEs still pass user.email, so the agent copies the README shape over the fixed example code. [example-apps](https://github.com/PostHog/context-mill/tree/main/example-apps)
- A session id or a fresh UUID per login is passed to identify, so every login creates a new person. The wizard uses the app's stable user id. [identify/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/integration-v2/identify/description.md)
- Same for CLIs, which get a uuid4() or the OS username on every run instead of one id saved per install. [todo.py](https://github.com/PostHog/context-mill/blob/main/example-apps/python/todo.py)

<details>
<summary>identify, reset and person properties at the wrong time</summary>

identify, reset or person properties run at the wrong moment, so events land on the wrong person.

**Example: Returning logged-in users never identified**

**Problem.** Docs and most example apps show identify() inside the login handler, so the agent wires it there. Sessions restored from a cookie, stored credentials or app restart skip that handler, and nothing signals the gap.

**Impact.** Silent: returning sessions (new tab, cleared PostHog storage, new device with a live server session) stay on anonymous distinct ids, splitting one user across anonymous and identified persons.

```js file=Generic agent
async function onSubmit(values) {
  const user = await login(values)
  posthog.identify(user.id, { email: user.email })   // only path
}
// cookie-restored sessions auto-redirect past this handler
```

```tsx file=Wizard
// on login success AND on any load where a session already exists
useEffect(() => {
  if (user && posthog.get_distinct_id() !== user.id) {
    posthog.identify(user.id, { email: user.email })
  }
}, [user])
```

**Also catches:**

- First-touch properties are written with $set, so every later identify overwrites them. The wizard writes them with $set_once. [2-attribution-fix.md](https://github.com/PostHog/context-mill/blob/main/context/skills/audit-attribution/references/2-attribution-fix.md)

- Capture is written before identify is settled, so each call site invents its own attribution. The wizard runs capture after identify and reads its handoff. [capture.md](https://github.com/PostHog/context-mill/blob/main/context/agents/integration-v2/capture.md)
- Login is tracked as an event, but identify is never called, so every event stays anonymous. The wizard calls identify on login. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- Identify sits on a late page mount like settings or profile, so startup captures and flag reads run anonymously. [audit/references/3-identification.md](https://github.com/PostHog/context-mill/blob/main/context/skills/audit/references/3-identification.md)

<summary>Identities that never join across hosts or runtimes</summary>

// browser: init with tracing_headers: ['api.example.com'] adds both headers
// middleware: bind the browser's ids once per request
const sessionId = request.headers.get('X-POSTHOG-SESSION-ID')
const distinctId = request.headers.get('X-POSTHOG-DISTINCT-ID')
return posthog.withContext(
  { sessionId: sessionId ?? undefined, distinctId: distinctId ?? undefined }, next)
// route handler: no distinctId argument

## Event design

<details>
<summary>Key events captured in the wrong place or not at all</summary>

The events that matter most are captured in a place that can miss or fake them, or not captured at all.

**Example: Payment, webhook and auth events only in the browser**

**Problem.** The agent follows the client SDK quickstart and instruments UI handlers. API routes, webhooks and Server Actions have no visible button, so it never opens them.

**Impact.** Silent: business-critical events such as payments and signups are lost to ad blockers, closed tabs, and flows that never touch the browser.

```ts file=Generic agent
// Checkout.tsx
posthog.capture('checkout_clicked')
// app/api/webhooks/stripe/route.ts -> no PostHog call at all
```

```ts file=Wizard
// payment webhook handler
const posthog = getPostHogClient()   // posthog-node
posthog.capture({ distinctId: userId, event: 'payment_succeeded',
  properties: { plan } })
await posthog.flush() // shared client in a per-request handler
```

**Also catches:**

- Signup and purchase are left to autocapture, so funnels have no milestones. The wizard captures key business events by name. [product-analytics.md](https://github.com/PostHog/context-mill/blob/main/context/skills/posthog-best-practices/references/product-analytics.md)
- User actions are captured from effects or render, so they fire on mount and twice under StrictMode. The wizard captures in the event handler after success. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)
- A success event fires before the server confirms, so failed requests count. The wizard captures after the response succeeds.

</details>

<details>
<summary>Event names and properties that don't analyze</summary>

Events are named or shaped in a way that makes them hard or impossible to analyze.

**Example: Event names built from variables**

**Problem.** Interpolating an id or label into the name feels expressive, DRY and type-checks fine. Nothing warns that each distinct string becomes its own event definition.

**Impact.** Silent: unbounded event and property definitions that cannot be charted, funneled or cleaned up, and audits cannot resolve what is captured.

```ts file=Generic agent
posthog.capture(`clicked_${button.id}`, {
  [`${field}_value`]: value,
})
posthog.capture('plan_selected', { [`plan_${id}`]: true })
```

```ts file=Wizard
posthog.capture('button_clicked', {
  button_id: button.id,
  field_name: field,
  value,
})
// "Never generate event names or property keys dynamically. Put variable data in property values."
```

**Also catches:**

- Events are captured with no properties, so they can only be counted. The wizard adds the properties needed to break them down. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)

<details>
<summary>Errors swallowed by framework handlers</summary>

A framework's own error handler catches exceptions before PostHog sees them, or PostHog's handler hides the framework's.

**Example: Flask error handlers hide exceptions from PostHog**

**Problem.** Agents trust SDK autocapture, but Flask turns exceptions into responses in its own errorhandler first, so the exception is handled and autocapture never fires.

**Impact.** Silent: Flask 500s never reach Error Tracking.

```python file=Generic agent
@app.errorhandler(500)
def internal_server_error(e):
    return render_template('errors/500.html'), 500  # PostHog never sees e
```

```python file=Wizard
@app.errorhandler(Exception)
def handle(e):
    if isinstance(e, HTTPException):
        return e
    posthog.capture_exception(e)
    return render_template('500.html'), 500
# routes.py example adds user context:
#   with new_context(): identify_context(str(current_user.id)); posthog.capture_exception(e)
```

**Also catches:**

- ASP.NET exception middleware captures and returns a 500 instead of rethrowing, which bypasses the app's own error handling. The wizard captures and rethrows. [commandments.yaml](https://github.com/PostHog/context-mill/blob/main/context/commandments.yaml)

- Same for Nuxt, where the fix is the vue:error app hook. [posthog.client.ts](https://github.com/PostHog/context-mill/blob/main/example-apps/nuxt-3-6/plugins/posthog.client.ts)

<summary>Error capture noisy or duplicated</summary>

The same error is captured many times, or normal failures and noise are captured as errors.

```js file=Generic agent
posthog.init(token, { capture_exceptions: true })

```js file=Wizard
posthog.init(token, { capture_exceptions: true }) // SDK owns the global handlers

// Vue app.config.errorHandler, Angular ErrorHandler,

[error-tracking.md](https://github.com/PostHog/context-mill/blob/main/context/agents/integration-v2/error-tracking.md)
- A hand-built global handler like sys.excepthook or a custom React boundary replaces an SDK init option. [error-tracking.md](https://github.com/PostHog/context-mill/blob/main/context/agents/integration-v2/error-tracking.md)

<summary>Upload and release wiring in CI and deploys</summary>

Source map uploads and release linking break in CI and deploys because credentials, names or steps do not line up.

**Example: Upload credentials never reach the CI or Docker build**

**Problem.** Agents write POSTHOG_CLI_\* to the local .env and edit the bundler config, but never trace where the production build runs. Env does not cross into a Docker build, composite action or SSH session.

**Impact.** Deploys build fine, no symbol set uploads, and Error Tracking keeps showing minified stack traces.

```yaml file=Generic agent
- name: Build and push image
  uses: docker/build-push-action@v6
  with:
    context: .
    push: true
# Dockerfile `RUN npm run build` sees no POSTHOG_CLI_* vars
```

```yaml file=Wizard
- name: Build and push image
  uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    build-args: |
      POSTHOG_CLI_API_KEY=${{ secrets.POSTHOG_CLI_API_KEY }}
      POSTHOG_CLI_PROJECT_ID=${{ secrets.POSTHOG_CLI_PROJECT_ID }}
# multi-stage: ARG/ENV in the build stage before the build RUN; single-stage: secrets: input + BuildKit secret
```

**Also catches:**

[error-tracking-upload-source-maps/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/error-tracking-upload-source-maps/description.md)
- CI uses a different variable name than the local .env, or swaps the personal key for the project token. [error-tracking-upload-source-maps/description.md](https://github.com/PostHog/context-mill/blob/main/context/skills/error-tracking-upload-source-maps/description.md)

## Privacy and security

<details>
<summary>Personal data in events, spans and reports</summary>

Personal data ends up in events, spans or files where it does not belong.

**Example: Personal data put in event properties**

**Problem.** Told to add useful properties, the agent copies email, name or username from the handler onto the event, and PostHog's docs and its own example apps taught exactly that. The wizard's framework skills briefly missed the rule too, because a tag mismatch kept the javascript_web/node commandments from reaching Next.js and other framework skills. Nothing errors, so the leak is silent.

**Impact.** PII is copied onto every event row, outside person-level controls, and cannot be removed by deleting or editing the person. Person profiles stay empty.

**Variants.**

- Browser and Node: identify with person properties, keep events PII free.
- Go and Rust: put person data in a $set map.
- Java: use userProperty. .NET: use IdentifyAsync.
- Flutter: pass userProperties to identify.

```ts file=Generic agent
posthog.capture({
  distinctId: username,
  event: 'server_login',
  properties: { username: username, isNewUser, source: 'api' },
})
// client side
posthog.capture('user_signed_up', { email: user.email, full_name: user.name })
posthog.capture('user_signed_in', { email: user.email, name: user.name })
```

```ts file=Wizard
posthog.identify(user.id, { email: user.email, name: user.name }) // PII on the person
posthog.capture('user_signed_up', { plan: user.plan })            // non-PII facts only
// or keep it as person data on the event:
posthog.capture('user_logged_in', { $set: { email: user.email } })
// warlock posthog_pii_in_capture_call reverts the write, block text names the fix
```

<details>
<summary>MCP calls, queries and dashboards built from memory</summary>

The agent calls PostHog MCP tools or writes queries from memory instead of reading what the tools expect.

- Skill references are listed without their folder, so the agent cannot find them. [skill-generator.js](https://github.com/PostHog/context-mill/blob/main/scripts/lib/skill-generator.js)

</details>

## Harness safeguards

The cases above are mostly skill rules. The wizard also has deterministic checks in its own code. They run the same way every time, and they don't rely on the agent following instructions.

<details>
<summary>Detection</summary>

- If no framework matches, the wizard stops and asks you to run it from an app root. It doesn't guess.
- Each framework has a minimum version, like Next.js 15.3, Angular 19, Django 3, and Rails 6. Older projects get a clear message instead of a broken setup.
- It tells variants apart, like the Next.js App Router and Pages Router, or Expo and bare React Native.
- It notices an existing PostHog install, and warns before it changes anything.
- It finds data warehouse sources from dependencies and env key names, and offers at most three.

</details>

<details>
<summary>Package managers</summary>

- It reads lockfiles to pick the Node package manager: bun, Yarn v1 or Berry, pnpm, or npm.
- It detects Python managers like uv, Poetry, PDM, Hatch, Rye, Pipenv, Conda, and pip, plus Composer, Swift Package Manager, Bundler, Cargo, Mix, Go modules, and pub.
- If an install fails, the agent falls back to a known-good version range. It never invents a version.

</details>

<details>
<summary>Environment and secrets</summary>

- The agent can't read or write real `.env` files. It can only check which key names exist, never their values.
- Env writes go through one tool. It refuses template files and legacy key names, and adds the file to `.gitignore`.
- A secret you paste into a wizard question becomes an opaque reference. The model never sees the value.
- It can upload env vars to Vercel for you.
- The MCP bearer token is passed by environment variable, not on the command line, so other processes can't read it.

</details>

<details>
<summary>Auth and regions</summary>

- Login uses OAuth with PKCE. It falls back to another port if one is busy, and lets you paste a code on a remote machine.
- It warns when you grant narrower scopes than the run needs.
- It reads your region from the token. If it can't, it checks US and EU in parallel.
- Parallel calls don't race when your login refreshes.
- Your organization must approve AI data processing before any code goes to a model.

</details>

<details>
<summary>Network</summary>

- Skills download from GitHub, then from a mirror if GitHub fails, with retries and backoff.
- The pre-run health check blocks the run only when both origins are down.
- If the wizard can't connect to our servers, it shows a specific error message. There's no silent fallback.
- If our infrastructure fails, the wizard offers you the skill to run in your own agent.

</details>

<details>
<summary>Security</summary>

- [Warlock](https://github.com/PostHog/warlock) scans shell commands, file writes and reads, and skills.
- A basic shell fence allows only known commands for each package manager.
- A sandbox limits writes and network access.
- Every tool call is checked before it runs.

</details>

<details>
<summary>Agent behavior</summary>

- A run that made no tool calls, or left tasks open, is never reported as a success.
- The orchestrator retries failed tasks, and blocks tasks that depend on a failed one.
- Ctrl-C and SIGTERM restore your settings and terminal before the wizard exits.
- Questions to the user have time and count limits. A timeout counts as a decline.

</details>

<details>
<summary>Editor and MCP install</summary>

- The MCP install merges config without losing comments, and only touches the `posthog` key.
- It handles each client and OS separately: Claude Desktop, Cursor, VS Code, Zed, Claude Code, Codex, and OpenCode.

</details>

<details>
<summary>Platform</summary>

- It shows a clear message on Node older than 22.22, outside an interactive terminal, or in a terminal smaller than 80 by 28.
- It handles Windows paths and the Windows clipboard.
- It works in large repos, and symlink loops are caught.

</details>
