# Feature Flags 101

A flag is a named question your code asks PostHog: should this person get this feature? PostHog answers `true` or `false` (or a variant name like `control` or `test`). You change the answer in PostHog and the code stays exactly the same <SeeFig n={1} />.

## Same person, same answer

PostHog hashes the flag key with the person's <Term name="distinct id">distinct ID</Term> and gets a number between 0 and 1. If that number is under the rollout percentage, they're in <SeeFig n={2} />. Same key plus same distinct ID gives the same answer, every single time.

So when a flag gives someone the "wrong" answer, the flag isn't broken. One of its inputs changed, and it's almost always the distinct ID. A browser that checks a flag before `identify()` runs is asking about an anonymous visitor, not your user. Call `identify()` first.

## Evaluate once per request

Check the flag once, where the request comes in, and pass the value down. Every extra check deeper in the stack is another chance to get a different answer (and on a server that isn't evaluating locally, another network request). That's why the wizard puts each check at exactly one call site.

## Every check gets recorded

Each check sends a `$feature_flag_called` <Term name="event">event</Term> with the flag key and the value the person got (the SDK drops repeats). That's how PostHog knows who saw what, and Experiments counts exposures from the same event. It's also exactly what the wizard's Check step looks for at the end.

## "Not loaded yet" is not "off"

In the browser, flags load async. Until they show up, `getFeatureFlag()` returns `undefined`, not `false`. Decide what your code does in that gap on purpose... [The next page](/pocket-guides/feature-flags/server-and-client) shows how to get rid of the gap entirely.
