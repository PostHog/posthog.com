# Feature Flags 101

A flag is a question your code asks PostHog: should this person get this feature? PostHog answers `true` or `false`, or a variant name like `control` or `test`. You change the answer in PostHog, and the code stays the same <SeeFig n={1} />.

## Same person, same answer

PostHog hashes the flag key with the person's <Term name="distinct id">distinct ID</Term> into a number between 0 and 1, and if that number is under the rollout percentage, the person gets the flag <SeeFig n={2} />. The same key and the same distinct ID give the same answer on every check.

So when a flag gives someone the "wrong" answer, the flag isn't broken. One of its inputs changed, and that input is almost always the distinct ID: a browser that checks a flag before `identify()` runs is asking about an anonymous visitor, not your user. Call `identify()` first.

## Evaluate once per request

Check the flag once, where the request comes in, and pass the value down. Each extra check deeper in the stack is another chance at a different answer, and on a server that doesn't evaluate locally, another network request. That's why the wizard puts each check at exactly one call site.

## Every check gets recorded

Each check sends a `$feature_flag_called` <Term name="event">event</Term> with the flag key and the value the person got, and the SDK drops repeats. That event is how PostHog knows who saw what: Experiments counts exposures from it, and the wizard's Check step looks for it when it finishes.

## "Not loaded yet" is not "off"

In the browser, flags load asynchronously, and until they arrive `getFeatureFlag()` returns `undefined`, not `false`. Decide on purpose what your code does in that gap, or read [the next page](/pocket-guides/feature-flags/server-and-client) and close the gap entirely.
