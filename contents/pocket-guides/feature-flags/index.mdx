# Feature Flags

A <Term name="feature flag">feature flag</Term> splits deploying code from releasing it. You merge the change turned off, then decide from PostHog who gets it: your team first, then 5% of users, then everyone. If errors climb at 5%, you flip the flag off, and nobody waits on a revert.

## Where to start

This guide follows a flag through its whole life: how PostHog decides who gets it, how to roll it out, kill it, configure it, and test with it, and finally how to delete it.

Every page assumes a PostHog SDK is in your app. The wizard installs one if you need it and wires up your first flags, or you can [install it yourself](/docs/feature-flags/installation):

<Setup />

The wizard creates two example flags, `wizard-example-backend-flag` and `wizard-example-frontend-flag`, and both start at 0%. It checks each one once, on its own side of your app, and gates something harmless on it (a log line or a small label), so nothing changes until you turn them on. An API with no frontend gets only the backend flag. When the wizard finishes, it writes `posthog-feature-flags-report.md` with a link to each flag and the file that checks it.

The rest of the guide follows those two flags from 0% to deleted.
