# The off switch

A rollback is a revert, a build, and a deploy, and your users see the bug for as long as all three take. If the change is behind a flag, you turn the flag off and skip all three <SeeFig n={1} />.

## How fast "off" arrives

A disabled flag returns `false` everywhere it's checked, and how fast each side notices depends on how it evaluates. A server that asks PostHog on every request sees the change on its next request. A server that evaluates locally sees it at its next poll, 30 seconds by default. A browser sees it the next time the SDK fetches flags (page load, `identify()`, a property or group change, or `reloadFeatureFlags()`), so an open tab can keep the old value for a while.

## Make "off" the safe path

The off switch works only if the off path still works. Keep the old code working until the flag is gone, and make it the default for a flag that hasn't loaded or a server that can't reach PostHog <SeeFig n={2} />. Then a PostHog outage lands your users in the same place as a kill.

Test that path before you need it. Flip the flag off in staging and confirm the old path works, and have CI run your tests with the flag both on and off. A kill switch you've never flipped is a kill switch you hope works.

## Switches you keep

Some flags are meant to stay: a switch for an expensive feature under load, or a disaster recovery switch. Most flags are temporary, and these are the deliberate exceptions. If you run your own cleanup automation, tag them as intentionally dormant so it skips them.
