# The off switch

A rollback is a revert, a build, and a deploy, and your users see the bug the whole time. If the change is behind a flag, you turn the flag off <SeeFig n={1} />.

## How fast "off" arrives

A disabled flag returns `false` everywhere it's checked. How fast each side notices depends on how it evaluates. A server asking PostHog on every request sees it on the next request. A server evaluating locally sees it at its next poll (30 seconds by default). A browser sees it the next time the SDK fetches flags (page load, `identify()`, a property or group change, or `reloadFeatureFlags()`), so an open tab can hang on to the old value for a while.

## Make "off" the safe path

The off switch only works if the off path still works. Keep the old code working until the flag is gone, and make it your default for a flag that hasn't loaded or a server that can't reach PostHog <SeeFig n={2} />. That way an outage lands in the same place as a kill.

Then actually test it. Flip the flag off in staging and check the old path still works, and have CI run your tests with the flag both on and off. A kill switch you've never flipped is one you hope works.

## Switches you keep

Some flags are meant to stick around (a switch for an expensive feature under load, or a disaster recovery switch). Most flags are temporary, and these are the deliberate exception. If you run your own cleanup automation, tag them as intentionally dormant so it skips them.
