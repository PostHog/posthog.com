# Server and client

The wizard made one flag for your backend and one for your frontend, not one flag for both. That's the recommended pattern, not a platform limit: each side gates its own code with its own flag. This page explains why, and how to keep both sides agreeing about who a person is <SeeFig n={1} />.

## One flag, one side

A flag checked on the server and again in the browser gets two chances to disagree, because each side can have a different distinct ID and different properties. Pick one side for each flag. For a server-only flag, set its evaluation runtime to **Server-side only** so the browser SDK doesn't load it at all.

## On the server, evaluate locally

With <Term name="local evaluation">local evaluation</Term>, the server SDK downloads your flag definitions every 30 seconds (every 5 minutes in Go) and evaluates them in-process, so a check makes no network request. Each definitions fetch counts as 10 flag requests, however many local checks your server makes, so local evaluation is cheaper as well as faster.

The trade is that you pass in the properties your conditions use, like the person's plan, and on the server you usually have those already. Local evaluation also needs the Feature Flags secure API key, which stays on the server. Never ship it to a browser or a mobile app.

After a cold start the SDK has no definitions yet, so checks return `undefined` until the first fetch lands. Give every check a default. When a check can't be evaluated locally, the SDK asks PostHog instead, unless you set `onlyEvaluateLocally`.

## Same person on both sides

The hash uses the distinct ID, so if your server checks with `user.id` while the browser still has an anonymous ID, one person can get a different answer on each side. In the browser, call `identify()` with the ID your server uses, before any flag check.

## Bootstrap to stop the flicker

If the server already knows the answer, send it with the page. <Term name="bootstrapping">Bootstrapping</Term> passes those values into `posthog.init` under `bootstrap.featureFlags`, so the browser has them before the first render and never flashes the old version. The web, React Native, iOS, Android, and Flutter SDKs all support it.

Two catches. Bootstrapping seeds only flags that are on, so a flag your server evaluated as off never arrives: the browser reads it as `undefined`, not `false`, and your default in code decides what renders. And the first full `/flags` response replaces everything you bootstrapped.
