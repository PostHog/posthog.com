# Dimension tables

Facts – events, charges, revenue items – are long, keyed, and additive. Dimensions are short, one
row per entity, descriptive: `dim_country`, `dim_plan`, `dim_date`. This skill builds them once so
every other model in this guide reuses them instead of re-deriving a lookup.

## Three moves

1. **Source it** – upload a lookup as a CSV, sync it from a system of record, or derive it from
   events.
2. **Shape it** – an aliased `SELECT`, one row per entity, dedupe hard. Materialize on a **slow**
   schedule, since dimensions change rarely but are read constantly.
3. **Attach it** – a saved join or person join, so its columns read as native fields in any query,
   filter, or breakdown.

## Currency is already a managed dimension

PostHog ships exchange rates behind `convertCurrency(from, to, amount, timestamp?)`. Only build a
currency dimension yourself in dbt, which has no equivalent.

## Rules before you model

- **One row per entity, unique key** – a duplicate key silently fans out every fact it joins.
- **Alias to clean, stable names** – these become the join surface everything else depends on.
- **Register and certify** load-bearing dimensions, so other models discover them instead of
  building a rival copy.
