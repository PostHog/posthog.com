# Warehouse foundations

Every skill in this guide turns a metric definition into a durable, reusable model, whether that's
on PostHog's own data-warehouse views or an external dbt project. This page covers the mechanics
every other skill assumes you've already read.

## Two stacks, one model

A model is a named, queryable object that encodes a metric or dimension once, so every insight,
dashboard, and downstream model can reuse it. Build it as a **PostHog-native** saved query
(optionally materialized into a physical table) via the `view-*` tools, or as a **dbt** model run
in your own scheduler. You can run both stacks side by side across a project.

## Rules before you model

- **Check for a governed definition first.** Before deriving MRR, activation, or any headline
  number, look for an approved canonical metric in the semantic layer.
- **Alias every column in a PostHog view.** `view-create` rejects `SELECT *` and any unaliased
  column, the number one reason a view fails to create.
- **Decide person vs group up front.** B2C models aggregate by person; B2B models aggregate by a
  group key. Pick it once per model and keep it consistent.
- **dbt runs externally.** There's no native PostHog dbt connector. It runs against your own or
  PostHog's managed warehouse.
