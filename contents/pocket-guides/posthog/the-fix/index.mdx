# The fix, then the check

The story comes back to 4:12 in the morning.

Thirty-two minutes after the report landed, an agent had traced the 403 to a tile request that stopped carrying an auth header after a January refactor. It confirmed the cause in Unter's codebase and wrote a fix <SeeFig n={1} />.

It also added a regression test, opened a pull request with the root cause in the description, linked the report, and left CI to run. The checks passed at ten to six.

## Quillfeather read it first

Nothing reaches production by itself, and this did not either <SeeFig n={2} />. Quillfeather read the diff at half past nine, agreed with the diagnosis, and merged it before she finished her coffee.

Later, she said the unsettling part was not the patch. It was realising that, without the report, she probably would not have found the problem.

## The week after

A successful merge is not proof that the problem is gone.

On the twenty-first, a validation scout returned to the funnel step the fix was meant to restore and checked the numbers against the February baseline. They were back to within a point of it.

That check produced events of its own. Those events then became part of the data available to the next round of signals.

That is the useful part of the loop: the data gets better as the system runs. Unter had more useful data in March than it had in January, which meant the signals raised in April could be more precise.

## What this needs, honestly

Self-driving is still in open beta, and it does not get every problem right. It requires a connected repository, AI data processing enabled for the organisation, and a GitHub connection for each person who uses it.

It also depends on the data coming in.

Unter's March result was possible because the team had instrumented the page back in January. If a product has little instrumentation, there is less for the system to work with—and the resulting loop will be thinner too.
