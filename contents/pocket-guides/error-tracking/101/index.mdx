# Error Tracking 101

Error Tracking takes exceptions thrown by your application and aggregates them into issues in context of your product data. This lets you understand more that just what broke:

- Which customers are impacted?
- Does it impact conversion and retention?
- Can this error be tied to loss in revenue?
- Were they part of any feature flag or experiment rollouts?
- What's shown on the user's page before and after the exception is thrown?

With this context, Error Tracking makes your product <Term name="self-driving">self-driving</Term>. Agents will have the context to triage the issues based on impact and open PRs to fix them.

## Path to self-driving

Error tracking takes you through discovery and fixing exceptions in three steps:

- **Instrument** – capture exceptions, and make them readable and grouped.
- **Report** – size what broke, for whom, and whether it is worth waking up for.
- **Act** – route it to an owner, get agents to report on high-impact errors automatically or open pull requests.

## Exceptions and issues

Like everything else in PostHog, each instance of an exception is captured as a `$exception` event. Similar are aggregated into issues like this <SeeFig n={1} />.

In Error Tracking, you diagnose, triage, assign, and fix _issues_ as the base unit of work, not individual exceptions.

## What lands on an exception

An exception carries the usual event properties – the person, the session, the URL, the browser, the feature flags they had – plus a handful of its own:

| Property | What it holds |
| --- | --- |
| `$exception_list` | The type, the message, the stack frames, and whether your code handled it. Chained exceptions arrive as several entries |
| `$exception_fingerprint` | The value that decides which issue this exception joins |
| `$exception_level` | How severe it is |

## Analyzing errors in context

An exception is an event, so every product that reads events reads it too:

- **Insights and funnels** put an exception in a chart, or beside a conversion step, so you can see who errored and who then dropped.
- **Session replay** holds the recording it was thrown in, and marks it on the player timeline.
- **Cohorts** turn "everyone who hit this" into a group, so you can follow what they did next.
- **Self-driving** reads the issue, works out what caused it, and opens a pull request.

This pocket guide will explore all of these usecases in detail.

## Install and turn it on

None of it works until a PostHog SDK is in your app. The wizard installs and configures one for you, or you can [install it yourself](/docs/error-tracking/installation).
