# Know when it should wake you

Alert on every new issue and people stop reading the channel within a week. This page is about the few things that earn a message, and about sending each one to the person who can act on it.

## Three things worth alerting on

Error tracking alerts fire on three events: an issue is created, an issue is reopened, or an issue spikes. They post to Slack, Discord, Teams, or a webhook.

Created is the one to be careful with. Every new exception type makes a new issue, and most of them are not worth a page. Reopened and spiked are different. Reopened means a fix did not hold. Spiked means something that was quiet is not quiet any more. Those two are the alerts people keep reading.

Filter an alert by assignee and a team hears about its own issues and nobody else's.

<Prompt>
Set up an error tracking alert to Slack that fires when an issue is reopened or spikes, and not when a new issue is created.
</Prompt>

## Spikes against a baseline

A threshold on a raw count fires whenever traffic moves, which means it fires every Monday morning.

Spike detection compares each issue against its own recent volume instead. Exceptions are counted in five-minute buckets, and a spike fires when a bucket exceeds the issue's baseline from the last hour by the multiplier you set. A minimum threshold keeps low-volume issues out, and a snooze stops one sustained incident from paging you every five minutes. An issue too new to have a baseline borrows an average from your other issues, so a fresh regression can still fire.

<Prompt>
Show me which of my error tracking issues spiked in the last 24 hours, and what each one's baseline was before it did.
</Prompt>

## Assignment rules

Route on the way in rather than triaging later. An assignment rule matches on the exception's properties and assigns the issue to a role or a teammate as it is created <SeeFig n={1} />.

Rules run during ingestion, after <Term name="source map">source maps</Term> have been applied, so they see the unminified <Term name="stack trace" />. That is what lets you route by source file: exceptions under `checkout/` go to the payments team, and nobody has to read the trace to know whose it is. Test a rule before saving it, and it tells you how many exceptions it would have matched in the last week.

<Prompt>
Suggest error tracking assignment rules for my project based on which source files and URL paths my recent exceptions come from, grouped by the team that likely owns each.
</Prompt>

## Out to your tracker

An issue can be sent to GitHub, GitLab, Linear, or Jira from the issue page. The tracker issue carries a link back, so whoever picks it up sees the exception, the <Term name="stack trace" />, and the people it hit, rather than your description of it.
