# Triage issues and set alerts

Issues are only meaningful if the right people see them. This section shows you how to triage issues efficiently and create alerts that don't cause excessive noise.

## Assign issues and send them to your issue tracker

An assignment rule matches on the exception's properties and assigns the issue to a role or a teammate as it is created <SeeFig n={1} />.

Rules run during ingestion, after <Term name="source map">source maps</Term> have been applied, so they see the unminified <Term name="stack trace" />. That is what lets you route by source file: exceptions under `checkout/` go to the payments team, and nobody has to read the trace to know whose it is.

An issue can be sent to GitHub, GitLab, Linear, or Jira from the issue page. The tracker issue carries a link back, so whoever picks it up sees the exception, the <Term name="stack trace" />, and the people it hit, rather than your description of it <SeeFig n={2} />.

## Alert on meaningful changes

Error tracking alerts can be configured to fire when an issue is created, reopened, or spikes.

- Created fires on _every_ new issue, so be careful with this one. It'll likely produce a lot of noise.
- Reopened fires when an issue you closed as fixed shows up again. Useful for tracking regressions.
- Spikes is most useful. When an error spikes against its own volume, it's easy to miss and is usually worth investigating <SeeFig n={3} />.
