# How Error Tracking works

Three things decide whether Error Tracking produces high quality signals or noise:
- Whether it groups exceptions into issues the way you would have
- Whether you can read the traces it hands you
- Whether you are storing the ones worth storing

This section covers how to configure each of these topics.

## Grouping

An exception joins an <Term name="issue" /> by the first of these that applies:

1. **A fingerprint you set at capture time.** Set at runtime, wins over everything else.
2. **A grouping rule you defined in PostHog.** Runs at ingestion, no deployment or release needed.
3. **The fingerprint PostHog generates.** What you get when you have done neither.

Taking those from the bottom up.

### Automatic fingerprinting

By default, PostHog builds a <Term name="fingerprint" /> from whatever the exception gives it:

1. The exception type, always.
2. The error message, when there is no <Term name="stack trace" /> PostHog could read.
3. The frames from your own code, when the trace has any.
4. The first frame in the trace, when every frame belongs to a library, the framework, or the browser.

Generated fingerprints can be fragile. Without a <Term name="source map" /> they are built from minified bundles like `a.min.js:1:48210`, instead of a concrete file and line like `checkout.ts:42`, so every deploy splits one bug into a new issue. Changing an exception type or message between <Term name="release">releases</Term> splits it the same way.

### Grouping rules

A fingerprint needs a code change. A rule doesn't – it runs during ingestion, so it can match on any event property, including the unminified <Term name="stack trace" />.

A rule is a set of filters and a choice of whether an exception has to match all of them or any <SeeFig n={1} />. The properties you'll reach for most are the exception type, its message, the source file, the severity, and whether your code handled it, alongside anything custom you set at capture.

### Setting your own fingerprint

Pass `$exception_fingerprint` when you capture and every exception carrying it lands in one issue, whatever its type or message says.

The usual reason is a message that carries an ID. `Workspace 8f21c4 failed to load` is one bug, but the generated fingerprint reads the ID as part of the message and opens an issue per workspace:

```js
try {
  await loadWorkspace(workspaceId)
} catch (error) {
  posthog.captureException(error, {
    $exception_fingerprint: 'workspace-load-failed',
    $issue_name: 'Workspace failed to load',
    $issue_description: 'loadWorkspace threw. The id is in the message, so these group by hand.',
    workspace_id: workspaceId,
  })
}
```

Reach for a grouping rule first – it does the same job, and you can test and edit it. A fingerprint ships in your code, so it only applies to exceptions captured after the deploy, and you cannot change your mind retroactively.

## Readable stack traces

A <Term name="stack trace" /> shows you the exact line of code that caused the exception. If you bundle, compile, or minify the bundle you distribute, there's no way to trace the code in the bundle back to your source code – so it shows up as **unresolved** <SeeFig n={2} />.

If you upload a <Term name="source map" />, it ties the bundled or compiled code, and stack traces will accurately reference your source code <SeeFig n={3} />.

You need to upload whenever you don't distribute your source code directly:
- a bundled web app
- a minified or obfuscated build
- a compiled language.

For web, the wizard wires it into your build:

```bash
npx @posthog/wizard@latest upload-source-maps
```

Mobile uploads a different artifact through different tooling – Android goes through a Gradle plugin, and native code needs its debug symbols alongside – but the job is the same. Point your agent at the [upload guide](/docs/error-tracking/upload-source-maps) for your platform.

### Breadcrumbs before the throw

Sometimes the traces themselves aren't enough to paint a full picture. Error Tracking's timeline will already show you the events that led up to the error, but sometimes you need ot leave more clues.

Breadcrumbs help you do that. They're like events, but cached locally and sent only if an exception occurs. This distinguishes them from regular events, which capture user actions, and avoid polluting your project.

```js
posthog.addExceptionStep('cache_miss', { key: `workspace:${workspaceId}` })
posthog.addExceptionStep('token_refreshed', { age_ms: 4200 })
posthog.addExceptionStep('read_from_replica', { region: 'eu-west-1', lag_ms: 180 })

try {
  await loadWorkspace(workspaceId)
} catch (error) {
  posthog.captureException(error)
}
```

Breadcrumbs surface on the issue's **Timeline** tab <SeeFig n={4} />, in order, along with events and exceptions from the same session – so you read the run-up to the throw rather than the throw on its own.
