# Exceptions as events

Like everything else in PostHog, each instance of an <Term name="exception" /> is captured as a `$exception` <Term name="event" />. That means it carries the same <Term name="person" />, <Term name="session" />, URL, browser, and <Term name="feature flag">feature flags</Term> as the rest of your product data.

## Query `$exception` events

An exception carries a handful of properties of its own:

| Property | What it holds |
| --- | --- |
| `$exception_list` | The type, the message, the stack frames, and whether your code handled it. Chained exceptions arrive as several entries |
| `$exception_fingerprint` | The value that decides which issue this exception joins |
| `$exception_issue_id` | The issue assigned when the exception was ingested |
| `$exception_level` | How severe it is |

## Rank issues by the revenue behind them

The goal is to get an insight that helps you assess the potential cost of each exception, so you can prioritize your efforts.

Revenue from purchase events or a connected payment system gives you one way to do that. Connect it to the people affected by an <Term name="issue" /> to see which errors affect your most valuable customers <SeeFig n={1} />. This shows the customer revenue behind an issue, not how much revenue the error has lost.

## Find the errors one customer hits

You can also focus on a single account. The goal is to see which issues its users are running into, so you can respond to the problems that matter to that customer.

A <Term name="cohort" /> uses <Term name="person property">person properties</Term>, such as organization, to select an account's users. Apply it to your exception data and you can see both the issues they hit and how many people are affected <SeeFig n={2} />.

Acme's search error fired 2,840 times, but only two people hit it. Checkout affected 186. Start with checkout to investigate the problem reaching more of the account, then inspect the repeated search failures separately.

## See how errors impact conversion

An error count doesn't tell you how many people failed to finish what they came to do. Understanding how exceptions relate to conversion helps you prioritize bugs that interrupt important actions.

A <Term name="funnel" /> connects the start and completion events for an action. Tracking its completion rate alongside exceptions shows whether an error appeared when completion fell <SeeFig n={3} />.

Completion fell from 80% to 50%, with the same number of checkout starts. Compare sessions with and without the exception, then watch affected recordings in <Term name="session replay" /> to see whether people got stuck, retried successfully, or finished another way.

## Exceptions by experiment variant

An <Term name="experiment" /> can improve one metric while introducing errors elsewhere. Comparing exceptions across variants helps you decide whether a promising result comes with a reliability problem.

Feature-flag data identifies which version people saw. Their exceptions show what failed. Together, they let you compare error rates across variants, so differences in traffic don't hide a problem <SeeFig n={4} />.
