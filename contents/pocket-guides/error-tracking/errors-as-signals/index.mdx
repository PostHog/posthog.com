# Catch error spikes and stuck loops

An error spike can be a regression that many people hit, or a few clients stuck retrying the same failing call. When you sort the issue list by occurrences, the loop can rank above a bug that breaks checkout for hundreds of people.

This scout watches your exceptions for fresh spikes and weighs each one by how many people it reaches.

## What the scout looks at

Thousands of exceptions arrived in your project overnight. Which is it?

- If they're spread across the issues you always see, at their usual rate, nothing is new. The scout stays _quiet_.
- If one issue jumped well above its own baseline, it's a fresh problem. The scout _**reports**_.

Each exception is an `$exception` event tied to the person who hit it, so the scout counts distinct users next to exceptions and uses the two to set the priority. When both climb together, many people are hitting a fresh regression, and the report is P1, or P2 when the reach is moderate. When exceptions climb and distinct users stay flat, as in <SeeFig n={1} />, a job or a retry is stuck in a loop on a few clients. A loop is usually less urgent, so its report is P3, or P2 when it's fresh and in the thousands. An issue you resolved that starts firing again is also P1.

Several new issues that appear in the same window with overlapping stack traces probably share a cause, so the scout files them as one report. It skips an exception that one person hit once in a single session. It also skips errors from an upstream provider it has already noted, like rate limits from your LLM provider.

## The report in your inbox

When the scout finds a fresh spike, it files a <Term name="report" /> in your <Term name="inbox" />. <SeeFig n={2} /> labels each part of the card. The report names the <Term name="issue" /> and its <Term name="fingerprint" />, shows exceptions against distinct users, counts the spike hour by hour against the issue's baseline, and gives the hour it started. It includes a chart of the spike next to the numbers.

If the issue keeps firing, later runs add the new hours to the same report instead of filing another one.

## The pull request you merge

Most spikes need a person to investigate, so the scout marks those reports as needing your input. When the <Term name="stack trace" /> points at a specific file in one of your repositories, the scout can mark the report actionable instead, like the one in <SeeFig n={2} />.

When you're ready to open a pull request, PostHog dispatches an agent to do it for you with the report and evidence attached as context. You review and merge it like any other PR.

Reports are free. Pull requests are **$15 each**, with your first three a month **free**. See [self-driving pricing](/docs/self-driving/pricing).

## The scout itself

A <Term name="scout" /> is a set of instructions an agent follows on a schedule. PostHog ships and maintains this one, and you can read [its skill file on GitHub](https://github.com/PostHog/posthog/blob/master/products/signals/skills/signals-scout-error-tracking/SKILL.md). The [Self-driving pocket guide](/pocket-guides/self-driving/101) explains how scouts work.

Each run queries your Error Tracking issues and the `$exception` events behind them through the PostHog MCP, the same one you can [connect to your own agent](/pocket-guides/error-tracking/query-with-mcp). It also reads its notes from earlier runs and the reports already in your inbox, so it doesn't file the same spike twice.

The Error Tracking <Term name="signal source" /> watches the same exceptions. It raises a signal for every new issue, reopened issue, and volume spike, with no bar to clear. You turn the source and the scout on separately, and both feed the same inbox.

## The schedule it runs on

Scouts run every 24 hours by default. In the scout's **Settings**, you can change that to an interval from every 30 minutes to every 30 days, or to a cron expression that runs it at a fixed time of day. Most runs close out without filing anything.

## Add this to your scout troop

You can turn this scout on or off for each project.
