# Connect a deploy to an error burst

The deploy that shipped the bug is on the same event as the bug. A <Term name="release" /> narrows it to a build. A <Term name="feature flag" /> variant narrows it to a code path. Neither needs a second tool.

## What the scout watches

When you set up [release tracking](/docs/error-tracking/releases), each exception carries the release it was thrown in. The flags a person had are ordinary properties on the exception, so the scout can compare error volume across releases and feature flag variants. Exceptions without release information can only be compared by flag variant.

## What makes it report

New, regressed, and always there are three different findings. New arrived with a release. Regressed was resolved and came back. Always there is the background you have stopped seeing.

## What lands in your inbox

"Started at 14:02" becomes "started in 1.4.2" <SeeFig n={1} />. If the issue only exists in the test variant, the report gives you a flag you can turn off now.

## From report to fix

A bug that only exists in the test variant is a flag you can turn off now. That is faster than any fix, and it holds the line while the fix is written.
