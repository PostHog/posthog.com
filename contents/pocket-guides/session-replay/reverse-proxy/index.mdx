# Reverse proxy

<!-- Source for the framing: contents/docs/advanced/proxy.mdx:11 – ad blockers maintain lists of

You need a reverse proxy to reliably capture session replays.

Ad blockers keep lists of know analytics domains and block requests to them. This will often result in incomplete or missing replays being captured. Using a reverse proxy lets you route through your own domain, so captures are not blocked.

## What gets blocked

These are the destinations required for session replay to work. They're also commonly blocked by ad blockers. When you set up a reverse proxy, these are the destinations to proxy.

| Host | Serves |
| --- | --- |
| `us-assets.i.posthog.com` | `/static/*` – the SDK and the replay recorder – and `/array/*`, your project's config |
| `us.i.posthog.com` | Everything else: your events, the recorded session data, and feature flag evaluation |

On EU Cloud, `eu-assets.i.posthog.com` and `eu.i.posthog.com`.

Nothing errors when a recording is blocked. The recording just never appears in PostHog. If you're leaning on Session Replay to help with debugging or understanding user behavior, you may be missing out on valuable insights.

## Setting one up with PostHog

PostHog offers a built-in managed proxy that runs on a subdomain you own, and PostHog handles the SSL certificate, the routing, and the maintenance. It's free on PostHog Cloud. All you need is access to your DNS.

1. In [organization proxy settings](https://app.posthog.com/settings/organization-proxy), create a new managed proxy and give it a subdomain you control.
2. At your DNS provider, add a CNAME from that subdomain to the proxy domain PostHog generates.
3. Wait. The status goes **waiting** → **issuing** → **live**, usually in 2-5 minutes, up to 30 if DNS propagation is slow.
4. Point your SDK at it with `api_host`, and set `ui_host` to PostHog's own domain so things like the toolbar keep working.

Two things to get right:

**Pick a boring subdomain.** Anything containing `analytics`, `tracking`, `telemetry`, `posthog`, or `ph` is already on most block lists you're trying to avoid. A blocked proxy achieves nothing.

**Turn your DNS provider's own proxy off.** Leaving it on interferes with routing and with certificate provisioning.

<details>

<summary>Two constraints worth knowing before you enable it</summary>

Traffic routes through Cloudflare, a listed subprocessor in our DPA.

And the managed proxy is not HIPAA-compliant, so a BAA with PostHog doesn't cover it – run your own if you handle PHI.

## Where a proxy doesn't save you

DNS-level blocking follows your subdomain's CNAME chain, sees where it really points, and drops the request before the browser is involved. That needs a custom resolver like NextDNS or Pi-hole, so it's a small share of users, and no proxy gets around it. Browser extensions can't do this – they only see HTTP requests after DNS has already resolved.

Your own `Content-Security-Policy` will also stop `recorder.js` from being served. To make sure this doesn't happen, read or point your agent at [this docs page](/docs/advanced/content-security-policy).
