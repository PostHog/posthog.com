> **Note:** PostHog doesn't accept tokens from custom OIDC providers yet. This page describes how it works so you can plan for it. Until then, use a [personal API key](/docs/api/personal-api-keys).

<CalloutBox icon="IconInfo" title="hog isn't released yet" type="fyi">

`hog` is PostHog's new CLI. It isn't released yet. Every `hog` command on this page is a beta preview of how it works once hog is released, and the details can change. Until then, use [`posthog-cli`](/docs/cli) with a personal API key, as its [authentication docs](/docs/cli#authentication) describe.

</CalloutBox>

A custom OIDC provider lets a job trade an ID token from any OIDC issuer for a short-lived PostHog token, such as your own identity provider or a CI system PostHog doesn't list. An admin names the issuer and the claims a policy checks. For GitHub Actions, GitLab.com, and Depot CI, use their own pages instead. The [overview](/docs/api/workload-identity) covers trust policies, requests, and the token exchange for every provider.

## What the issuer needs

- **An HTTPS issuer URL** - with a host name, not an IP address. It can't contain a user name, a password, a query, or a fragment, and it's at most 255 characters long.
- **A discovery document** - at `<issuer>/.well-known/openid-configuration`, whose `issuer` equals the issuer URL exactly, and whose `jwks_uri` is an HTTPS URL.
- **RSA or EC signatures** - such as RS256 or ES256. PostHog doesn't accept other algorithms.
- **A public address** - PostHog refuses private addresses and follows no redirects when it fetches the discovery document and the keys.

The issuer can't be one of the supported providers. Pick that provider instead.

## What the token needs

- **An audience** - your PostHog host, such as `https://us.posthog.com`
- **An `iat` claim** - the time the issuer issued the token
- **A short lifetime** - at most 1 hour between `iat` and `exp`. PostHog refuses a token meant to live longer, because a leaked one would keep working until it expires.
- **The claims the policy checks** - the subject claim, and every condition claim

## How the job gets a token

hog can't ask your issuer for a token, so the job gets one itself and puts it in the `HOG_ID_TOKEN` variable. Once hog is released, it uses that token when no supported provider runs the job, and exchanges it at `/oauth/token/`.

The PostHog token never outlives the ID token it came from. hog reads the same `HOG_ID_TOKEN` each time it exchanges, so the job's work has to finish before that token expires.

## What a policy checks

- **Subject claim** and **Subject value** - the claim that names the workload, `sub` by default, and the exact value it must have.
- **Name claim (optional)** - a claim that must equal the **Workload name**. Leave it empty to use the workload name only as a label.
- **Conditions** - at least one claim the token must carry, each with an exact value. Values match exactly, without wildcards.

A claim name is up to 100 printable characters, without spaces or the wildcard characters `*`, `?`, `[`, and `]`. A policy can't check `iss`, `aud`, `exp`, `iat`, `nbf`, `jti`, `azp`, or `nonce`, because they say how a token is valid, not who sent it.

<CalloutBox icon="IconWarning" title="You choose the claims PostHog checks" type="caution">

Use claims the issuer sets itself, which a workload can't change. Otherwise another workload could get this policy's tokens. The admin who adds or approves the policy is responsible for this choice.

</CalloutBox>

## Set up a trusted workload

Only organization admins and owners can add a trusted workload. Anyone else in the project can ask an admin for one, with `hog ci setup` or [through the API](/docs/api/workload-identity#ask-through-the-api).

### In PostHog settings

1. In your project settings, go to **Trusted workloads** and click **Add trusted workload**.
2. Under **Provider**, pick **Custom OIDC provider**.
3. In **Issuer URL**, enter the issuer exactly as its tokens carry it in `iss`, and click **Check issuer**. PostHog reads the discovery document and shows the keys and algorithms it found.
4. Enter the **Subject claim**, such as `sub`, and the **Subject value**.
5. Optionally, enter a **Name claim**. Enter a **Workload name** either way.
6. Under **Which runs can get a token**, enter a claim and its exact value. Click **Add condition** to add more.
7. Give the trusted workload a **Name**, and pick the **Scopes** the job needs.
8. Click **Add trusted workload**.

### With `hog ci setup` (beta)

Once hog is released, run:

```bash
hog ci setup --provider custom --issuer https://auth.example.com --subject deploy-bot --condition environment=production --scope annotation:write
```

- `--issuer` is the issuer URL, exactly as its tokens carry it.
- `--subject` is the exact value of the subject claim. `--subject-claim` names that claim, `sub` by default.
- `--condition claim=value` is required at least once. Repeat it for each claim.
- `--scope` takes the scopes, separated by commas. Repeating it works too.
- `--branch`, `--environment`, `--repository`, and `--subject-id` don't work with `--provider custom`.

hog then creates a policy request. If you're an admin, it opens the approval page and waits. Otherwise it prints the link to send to an admin. `hog ci setup --wait` waits for up to 10 minutes and keeps the request, so you can run it again later.

### Approving a request

The approval page for a custom OIDC provider shows the issuer and warns that approving trusts every token that issuer signs with these claims. Approve only when your organization controls that issuer.

## Configure the job

A job needs your PostHog project ID and host, and its ID token.

### 1. Add the project to `posthog.json` (preferred)

Add these keys to `posthog.json` in the repository. hog looks for the file from the current folder up to the git root.

```json
{
    "host": "https://us.posthog.com",
    "projectId": 12345
}
```

- `projectId` is your project's ID: the number in your project URL, such as `12345` in `https://us.posthog.com/project/12345`.
- `host` counts in a CI job only when it's PostHog Cloud, `https://us.posthog.com` or `https://eu.posthog.com`, so a change to the file can't send the job's token elsewhere. Without a host, hog uses `https://us.posthog.com`.
- Never put `HOG_PERSONAL_API_KEY` in `posthog.json`.

### 2. Pass the ID token

Before the job runs hog, set `HOG_ID_TOKEN` to an ID token from your issuer, with your PostHog host as its audience:

```bash
HOG_ID_TOKEN=<an ID token from your issuer, with the audience https://us.posthog.com>
```

How the job gets that token depends on your issuer.

### Or set environment variables

Instead of `posthog.json`, set `HOG_HOST` and `HOG_PROJECT_ID` in the job. They win when both are set.

A self-hosted PostHog always needs `HOG_HOST` in the job. When `posthog.json` names a host that isn't PostHog Cloud and the job doesn't set `HOG_HOST`, hog stops with a `workload_host_not_allowed` error that names the host to set.

Remove `HOG_PERSONAL_API_KEY` from the job. hog uses a personal API key ahead of the workload token. hog's usage analytics from this job carry a hashed workload ID, not a person.

## Troubleshooting

| Problem | Likely cause | What to do |
| --- | --- | --- |
| **Check issuer** fails | The issuer URL breaks one of the rules above, the discovery document names another issuer, or PostHog can't reach it | Enter the issuer exactly as its tokens carry it in `iss`, and make sure its discovery document is public. |
| hog can't find a token | The job doesn't set `HOG_ID_TOKEN` | Set it to an ID token from your issuer. |
| [`workload_issuer_not_allowed`](/docs/api/workload-identity#workload_issuer_not_allowed) | No enabled policy or pending request in the project names the token's issuer | Check the issuer URL in the policy against the token's `iss`, and the project ID. |
| [`workload_token_invalid`](/docs/api/workload-identity#workload_token_invalid) | The audience isn't your PostHog host, the token lacks `iat`, lives longer than 1 hour, expired, or uses an algorithm PostHog doesn't accept | Mint the token with your PostHog host as its audience, for at most 1 hour. |
| [`workload_provider_unavailable`](/docs/api/workload-identity#workload_provider_unavailable) | PostHog couldn't fetch the issuer's discovery document or keys | Try again in a minute. |
| [`workload_no_matching_policy`](/docs/api/workload-identity#workload_no_matching_policy) | The token's subject or a condition claim doesn't match the policy, or the project ID is wrong | The error lists the claims the job sent. Compare them with the policy. |
| [`workload_policy_request_pending`](/docs/api/workload-identity#workload_policy_request_pending) | An admin hasn't approved the request yet | Send the approval link from the error to an admin. |
| [`workload_rate_limited`](/docs/api/workload-identity#workload_rate_limited) | The workload used up its 300 exchanges, which refill at one each second | hog waits once when `Retry-After` is 60 seconds or less. Otherwise, run the job again later. |
| `workload_host_not_allowed` from hog | `posthog.json` names a host that isn't PostHog Cloud, and the job doesn't set `HOG_HOST` | Set `HOG_HOST` in the job to the host the error names. |
| A call fails with `403` | The policy doesn't grant the scope the call needs | The `WWW-Authenticate` header names the scope. Ask an admin to add it. |

See [errors](/docs/api/workload-identity#errors) in the overview for every error code.
