The autonomy loop is how PostHog turns product data into shipped changes, then checks whether they worked. The [overview](/docs/start-here) has the loop at a glance. This page is how it works under the hood, stage by stage.

![The product autonomy loop](https://res.cloudinary.com/dmukukwp6/image/upload/product_autonomy_loop_V2_a5243dfada.png)

## Collect data

The loop starts by collecting [signals](/docs/start-here/signals). [Scouts](/docs/start-here/scouts) watch your data on a schedule and emit them, and your products emit them directly: error spikes, frustration in session replays, and failing health checks. External sources feed in too, like Zendesk, GitHub Issues, and Linear.

A single problem usually generates many signals, from many sources, at once.

## Cluster signals

Raw signals are noisy, so the loop groups related ones together. It deduplicates signals across sources and clusters the ones that point at the same underlying problem into a single [report](/docs/start-here/reports), so the loop works on one problem instead of a stream of alerts.

## Check memory

Before acting, the loop checks what it already knows. It adds context, ranks the report by priority, and compares it against work it has already done, so it doesn't redo a fix that already shipped. A vague pattern like "users seem frustrated at checkout" becomes a concrete, evidenced finding.

This is also where the loop decides what's worth acting on. A report that's low-priority, noisy, or already handled is dropped rather than turned into work, which keeps your inbox from filling with busywork.

## Notify workers

A report that clears that bar is sent to your [inbox](/docs/start-here/inbox), ready for review. It arrives as a structured plan: what needs to happen, why, and the evidence behind it. Unlike a prompt you type, the plan is driven by your data.

## Do work

You hand the plan to an agent, which works in a sandboxed environment: it makes the change, opens a pull request, and instruments it as it goes, adding the events, flags, and experiments needed to measure whether the change worked.

## Review and ship

The pull request lands in your [inbox](/docs/start-here/inbox) like any other. You review it, ask for changes, and merge or decline it. Nothing ships without you.

## Evaluate

This is the stage that makes it a loop rather than a one-shot. After a change ships, PostHog waits for it to take effect, then re-checks the metric, dashboard, or experiment that triggered the work in the first place.

## Write back

The result is written back into the loop. If the metric moved the way you hoped, the work is done. If it didn't move, or moved the wrong way, the outcome becomes a new signal, and you can revert or reopen the change.

Because every shipped change is instrumented, each pass also leaves better data behind than the last. Better data means sharper signals, sharper signals mean better-targeted work, and the loop gets more useful the longer it runs.
