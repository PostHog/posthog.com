title: Evaluations

Evaluations automatically assess the quality of your LLM [generations](/docs/ai-observability/generations). PostHog supports three types of evaluations:

- **LLM-as-a-judge** – Uses an LLM to score each generation against a prompt you define, returning a pass/fail result, a numeric score, or categories. You [choose a judge method](#choosing-a-judge-method): **LLM with explanation** provides written reasoning, while **Decision model** returns typed results without reasoning. Great for nuanced, subjective checks like tone, helpfulness, or hallucination detection.
- **Code-based (Hog)** – Runs deterministic code you write against each generation, returning a pass/fail result, a numeric score, or categories. Great for rule-based checks like format validation, keyword detection, or length limits. Free to run with no LLM cost.
- **Sentiment analysis** – Classifies the sentiment of user messages as positive, neutral, or negative using a local ML model. Great for monitoring how users feel during conversations with your AI features. Free to run with no LLM cost.

## How evaluations work

Every evaluation has three parts:

- **Input** – What your LLM app or agent receives. It can be synthetic (a test case you wrote) or real (something a user sent).
- **Output** – What your app or agent responds with. It's either live (a real user already got it) or generated (you run your agent on a stored input to produce it).
- **Evaluator** – What scores the output: an [LLM judge](#llm-as-a-judge-evaluations), [Hog code](#code-based-evaluations-hog), or [sentiment analysis](#sentiment-analysis-evaluations).

Where each part comes from is what separates the three ways to run evaluations:

|  | Online evaluations | Backfills | Offline evaluations |
| --- | --- | --- | --- |
| Input | Real, live | Real, from past traffic | Synthetic, or real inputs you stored in your code or a [dataset](/docs/ai-evals/datasets) |
| Output | Live | Live, from past traffic | Generated by running your agent, usually in CI |
| Evaluator runs in | PostHog | PostHog | Your code |
| Answers | Is production working right now? | What would this new evaluation have said about last week? | Does this change break something that used to work? |

This page covers online evaluations and backfills. For offline evaluations, see [offline evals](/docs/ai-evals/offline-evals).

## Why use evaluations?

- **Monitor output quality at scale** – Automatically check if generations are helpful, relevant, or safe without manual review.
- **Detect problematic content** – Catch hallucinations, toxicity, or jailbreak attempts before they reach users.
- **Track quality trends** – See pass rates across models, prompts, or user segments over time.
- **Debug with reasoning** – LLM judges using the **LLM with explanation** method provide written reasoning, and Hog evaluations can include reasoning through `print()`. Decision model judges return results without written reasoning.

## Choosing an evaluation type

|              | LLM-as-a-judge                                                                                                                 | Code-based (Hog)                                                           | Sentiment analysis                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------ |
| **Best for** | Subjective quality checks (tone, helpfulness, hallucination)                                                                   | Deterministic rule-based checks (format, keywords, length)                 | Tracking how users feel during conversations           |
| **Cost**     | LLM API call per evaluation                                                                                                    | Free                                                                       | Free                                                   |
| **Speed**    | Seconds                                                                                                                        | Milliseconds                                                               | Milliseconds                                           |
| **Output**   | Pass/fail, numeric score, or categories; written reasoning with **LLM with explanation**, no reasoning with **Decision model** | Pass/fail, numeric score, or categories; optional reasoning from `print()` | Positive, neutral, or negative with a confidence score |
| **Setup**    | Write a prompt                                                                                                                 | Write Hog code                                                             | Pick the type – no prompt or code required             |

**Tip:** Most teams combine types. Run Hog code and sentiment analysis on every generation, since they have no LLM cost, and run LLM judges on a 5-10% sample for the questions only a model can answer. A large enough sample gives a reliable picture of quality without doubling your LLM spend.

## Choosing what to evaluate

LLM-as-a-judge and code-based evaluations have an **Evaluate** setting that picks what one run grades:

- **Each generation** grades every matching generation on its own, right after it's ingested.
- **Whole trace** grades all the events in a [trace](/docs/ai-observability/traces) together, after the trace settles.
- **Whole session** grades every trace in a [session](/docs/ai-observability/sessions) together, after the session settles.

Property filters still match individual generations. A trace or session is evaluated when any of its generations match, and the sampling rate applies to the whole trace or session.

**Whole session** only runs on generations that carry the `$ai_session_id` property. If your events don't include it, a session evaluation has nothing to grade and never produces results. See [how to set a session ID](/docs/ai-observability/sessions#how-to-set-a-session-id), or pick **Whole trace** or **Each generation** instead.

Sentiment evaluations always grade each generation.

## Choosing an output type

LLM-as-a-judge and code-based evaluations have an **Output type** setting. You pick it when you create the evaluation, and you can't change it later.

- **Boolean** returns pass or fail. Use it for yes/no checks, like "the response is valid JSON".
- **Numeric score** returns a number. Use it for quality ratings, like a 1 to 5 helpfulness score, or for measured values, like latency or response length.
- **Categorical** returns one or more labels from a list you define. Use it to sort results into failure modes, like "wrong tool", "hallucination", or "off topic".

### Numeric scores

You can set a **Minimum** and **Maximum** score. A score outside these bounds is skipped, not graded. **Step** suggests the score increment. PostHog asks an LLM judge to use it, but stores the score exactly as returned, so a judge can still return a value like `3.7` when the step is 1.

To get pass rates and reports, turn on **Set a passing rule** and choose **At least (≥)** or **At most (≤)** a threshold. Without a passing rule, you still get the scores, but no pass rates or reports. If you change the rule later, PostHog applies the new rule to past results too.

### Categories

Add the categories the evaluation can return. Each category has a key, which PostHog stores, and a label, which PostHog displays. Keys use lowercase letters, numbers, `_`, and `-`. Keep a key the same when you rename its label, so past results keep their meaning. An evaluation can have up to 100 categories.

**Categories per result** controls how many categories one result can have:

- **One category** returns exactly one category.
- **Multiple categories** returns any number of categories, including none.

To get pass rates and reports, choose **Passing categories**. A result passes only when all of its categories are passing categories. For example, if `resolved` is the only passing category:

- `resolved` passes.
- `resolved` and `escalated` fails, because `escalated` isn't a passing category.
- A result with no categories fails.

With **Multiple categories**, you can also leave **Passing categories** empty. Then a result passes only when it has no categories. Use this when every category is a problem, like `hallucination` or `wrong_tool`, so a good result has none.

If you change the passing categories later, PostHog applies them to past results too.

### Not applicable results

Turn on **Allow N/A responses** for a boolean, numeric, or categorical evaluation when its criteria don't apply to every generation. Both LLM judges and Hog evaluations support N/A. N/A results are excluded from pass/fail grading and pass rates.

For LLM judges, describe when the criteria don't apply in your prompt. For Hog evaluations, return `null` to mark a result as N/A when **Allow N/A responses** is enabled.

With **Multiple categories**, an empty list (`[]`) is a valid, applicable result that means no categories match. Its passing rule still determines whether it passes. It is different from `null`, which marks the result as N/A when enabled.

## LLM-as-a-judge evaluations

### How they work

When a [generation](/docs/ai-observability/generations) is captured, PostHog samples it based on your configured rate (0.1% to 100%). If sampled, the generation's input and output are sent to an LLM judge with your evaluation prompt. The judge returns a result in the evaluation's [output type](#choosing-an-output-type), which is stored and linked to the original generation. The behavior depends on the [judge method](#choosing-a-judge-method) you select: **LLM with explanation** judges use chat completions and return written reasoning alongside the result, while **Decision model** judges return typed results without reasoning.

You can optionally filter which generations get evaluated using event properties or person properties. For example, only evaluate generations from production, from a specific model, or above a certain cost threshold. You can also use person properties to exclude internal users or target specific user segments.

### What the judge receives

The LLM judge receives a structured prompt containing sections extracted from the generation event:

```text
Input: <the generation's input messages or prompt>

Tools available:
<list of tools the agent could call — only present when the event includes a tool catalog>

Output: <the generation's output response>
```

#### Tool call and result correlation

When the generation includes tool calls (common in agentic workflows), PostHog renders them with correlation IDs so the judge can match each tool result to the call that produced it:

- Assistant tool calls render as `[tool_call <id>: name(args)]`
- Tool results render as `tool[<id>]: <result>`

For example, a conversation with parallel tool calls appears as:

```text
assistant: [tool_call call_abc: search_docs({"query": "pricing"})] [tool_call call_def: get_user({"id": 42})]
tool[call_abc]: {"results": ["Free tier includes 1M events"]}
tool[call_def]: {"name": "Jane", "plan": "pro"}
```

This lets the judge reliably evaluate prompts like "did the agent handle the tool failure correctly?" even when multiple tool calls run in parallel.

#### Tool catalog format

When the event's `$ai_tools` property contains the list of tools the agent could call, PostHog renders a compact summary:

```text
- search_docs: Search the documentation (query, limit?)
- get_user: Fetch user details (user_id)
```

Each line shows the tool name, description, and parameters. A `?` suffix marks optional parameters. This format supports OpenAI, Anthropic, and Gemini tool definitions.

#### Shaping custom events for evaluations

If you emit custom `$ai_generation` events or span/trace events and want the judge to have full context, include these properties:

| Property                             | Purpose                                      |
| ------------------------------------ | -------------------------------------------- |
| `$ai_input`                          | The input messages or prompt                 |
| `$ai_output_choices` or `$ai_output` | The output response                          |
| `$ai_tools`                          | The tool catalog (array of tool definitions) |

For tool call correlation within messages, include:

- A `tool_calls` array on assistant messages, where each entry has `id`, `function.name`, and `function.arguments`
- A `tool_call_id` field on tool result messages matching the `id` from the corresponding tool call

### Built-in templates

PostHog provides pre-built templates to get you started. When you click **Create evaluation**, the template picker opens with these tabs:

- **Recommended** shows a short list of popular templates.
- **All** shows every template.
- **Answer quality**, **Safety**, **Agent behavior**, **User insights**, and **Cost & speed** show the templates in that category.

The picker includes LLM judge, Hog code, and sentiment templates. Some LLM judge templates are:

| Template                   | What it checks                                                                    | Output type   |
| -------------------------- | --------------------------------------------------------------------------------- | ------------- |
| **Response quality score** | Rates each answer from 1 to 5 for accuracy, completeness, and clarity             | Numeric score |
| **Task outcome**           | How each conversation ended: resolved, partly resolved, unresolved, or handed off | Categorical   |
| **User correction**        | Messages where the user corrects the assistant or repeats a request               | Categorical   |
| **Relevance**              | Whether the answer addresses what the user asked                                  | Boolean       |
| **Hallucination**          | Claims in the answer that are made up or unsupported                              | Boolean       |
| **Prompt injection**       | User messages that try to override your instructions or reveal the system prompt  | Boolean       |

This list is not complete. The template catalog changes over time, so check the picker for the current templates.

### Choosing a judge method

LLM-as-a-judge evaluations have a **Judge method** setting that controls how the judge processes your prompt:

- **LLM with explanation** – Uses chat completions. The judge returns a result and written reasoning explaining its decision. Choose this when you want to understand why the judge passed or failed a generation.
- **Decision model** – Uses typed decisions. The judge returns a result without written reasoning. Choose this when you need faster, lower-cost evaluations and don't need explanations.

The model picker filters to models that support the selected method. Some models support both methods and remain available regardless of your choice. Switching methods keeps a compatible model and its saved connection. If the current model doesn't support the new method, it's cleared without changing your prompt or output settings.

Existing evaluations without an explicit method selection continue using automatic routing until you choose a method.

### Creating an LLM judge evaluation

1. Navigate to **AI Evals** > **Evaluations**
2. Click **Create evaluation**
3. Select an LLM judge template, or click **Start from scratch**
4. If you start from scratch, set **Method** to **LLM as a judge**
5. Configure the evaluation:
   - **Name**: A descriptive name for the evaluation
   - **Prompt**: The instructions for the LLM judge (templates provide sensible defaults)
   - **Judge method**: Choose **LLM with explanation** or **Decision model** (see [Choosing a judge method](#choosing-a-judge-method))
   - **Model**: Select a model from your configured AI providers – the list is filtered by the selected judge method
   - **Sampling rate**: Percentage of generations to evaluate (0.1% – 100%)
   - **Property filters** (optional): Narrow which generations to evaluate using event or person properties
6. Enable the evaluation and click **Save**

### Writing custom prompts

When creating a custom evaluation, your prompt should describe what makes a good or bad response. PostHog tells the judge which output format to use, so you don't need to ask for `true` or `false`, a score format, or category keys. For a numeric score, describe what each score means. For categories, describe when each category applies. The judge receives the generation's input, output, and (when present) the available tool catalog for context. See [What the judge receives](#what-the-judge-receives) for details on the full prompt structure.

Tips for effective evaluation prompts:

- Be specific about what constitutes a pass or fail
- Include examples of edge cases when relevant
- Keep the prompt concise but comprehensive

Example custom prompt:

```text
You are evaluating whether an LLM response follows our brand voice guidelines.

Given the user input and assistant response, determine if the response:
- Uses a friendly, conversational tone
- Avoids corporate jargon
- Addresses the user by name when provided

Return true if the response follows these guidelines, false otherwise.
Explain your reasoning briefly.
```

### Iterate on your judge prompt

You don't need a perfect prompt before you start. Most teams write a clear first version, often with help from a coding agent, enable it, and refine it from the results:

1. Review the generations your evaluation failed. Some will be real problems. Others are false positives that show where the criteria are too broad.
2. Spot-check generations that passed. A judge can be fooled the same way your agent can, so false negatives hide here. This matters most for safety checks such as prompt injection.
3. Tighten the criteria or add an example that covers the case you found, then [backfill](#evaluating-past-data) over the same range to compare.

### Prefer pass/fail over scales

Boolean outputs are easier for a judge to apply consistently than a 1-5 score, because the difference between a 3 and a 4 is hard to define. If you use a numeric score, describe what each value means in the prompt and give an example of each.

### Keep examples short

The prompt field holds up to 2,000 characters, so examples have to fit inside it. <!-- VERIFY: confirm the 2,000-character limit with Radu --> Pick one or two examples that cover the borderline cases, not the obvious ones.

## Code-based evaluations (Hog)

Code-based evaluations run [Hog](/docs/hog) code you write against each generation. They execute in milliseconds with zero LLM cost, making them ideal for high-volume, deterministic checks.

### How they work

1. You write Hog code that inspects the generation's input and output.
2. On save, PostHog compiles your code to bytecode.
3. When a generation is sampled, the code runs against it in PostHog's HogVM.
4. Your code returns a result that matches the evaluation's [output type](#choosing-an-output-type). Use `print()` to add reasoning.
5. If **Allow N/A responses** is enabled, returning `null` marks the result as N/A (not applicable).

Code-based evaluations share the same sampling rate and property filter options as LLM judge evaluations.

### Available globals

Your Hog code has access to these variables:

| Variable            | Type             | Description                              |
| ------------------- | ---------------- | ---------------------------------------- |
| `input`             | string or object | The LLM input (prompt or messages array) |
| `output`            | string or object | The LLM output (response or choices)     |
| `properties`        | object           | All event properties from the generation |
| `event.uuid`        | string           | The event UUID                           |
| `event.event`       | string           | The event name                           |
| `event.distinct_id` | string           | The distinct ID of the user              |

### Creating a code-based evaluation

1. Navigate to **AI Evals** > **Evaluations**
2. Click **New evaluation**
3. Select **Code-based (Hog)** as the evaluation type
4. Write your Hog code in the editor
5. Click **Test on sample** to run your code against recent generations and verify it works
6. Configure:
   - **Name**: A descriptive name for the evaluation
   - **Sampling rate**: Percentage of generations to evaluate (0.1% – 100%)
   - **Allow N/A responses**: Whether your code can return `null` to skip inapplicable generations
   - **Property filters** (optional): Narrow which generations to evaluate
7. Enable the evaluation and click **Save**

### Writing Hog evaluation code

What your code returns depends on the evaluation's output type:

- **Boolean**: `true` for pass, `false` for fail.
- **Numeric score**: a finite number, like `4` or `0.85`.
- **Categorical**: a list of category keys, like `['wrong_tool']`. With **One category**, you can also return a single key, like `'wrong_tool'`.

Use `print()` statements to provide reasoning – the output is captured and stored alongside the result.

> **Hog tip:** Use single quotes for strings (`'hello'`), `length()` instead of `len()`, and wrap property access with `ifNull()` to avoid null comparison errors.

**Check output length:**

```hog
let maxLength := 2000
let outputLength := length(ifNull(output, ''))

if (outputLength > maxLength) {
    print('Output too long: ' + toString(outputLength) + ' characters (max ' + toString(maxLength) + ')')
    return false
}

print('Output length OK: ' + toString(outputLength) + ' characters')
return true
```

**Check for required keywords:**

```hog
let requiredKeywords := ['disclaimer', 'not financial advice']
let outputLower := lower(ifNull(output, ''))

for (let i := 0; i < length(requiredKeywords); i := i + 1) {
    if (outputLower !ilike '%' + requiredKeywords[i] + '%') {
        print('Missing required keyword: ' + requiredKeywords[i])
        return false
    }
}

print('All required keywords found')
return true
```

**Check model and cost thresholds:**

```hog
let model := ifNull(properties.$ai_model, 'unknown')
let cost := ifNull(properties.$ai_total_cost_usd, 0)
let maxCost := 0.05

if (cost > maxCost) {
    print('Cost too high for model ' + model + ': $' + toString(cost))
    return false
}

print('Cost within budget: $' + toString(cost))
return true
```

**Return N/A for non-applicable generations** (requires **Allow N/A responses** enabled):

```hog
let model := ifNull(properties.$ai_model, '')

// Only evaluate GPT-4 generations
if (model !ilike '%gpt-4%') {
    print('Skipping non-GPT-4 model: ' + model)
    return null
}

// Check that the output is non-empty
if (length(ifNull(output, '')) == 0) {
    print('Empty output from GPT-4')
    return false
}

print('GPT-4 output OK')
return true
```

### Testing on sample data

Before saving, use the **Test on sample** button to run your code against recent generations. This shows:

- The input and output from each sampled generation
- Whether your code returned pass, fail, or N/A
- Any `print()` output (reasoning)
- Any errors in your code

Testing does not create evaluation events or affect your data – it runs entirely in preview mode.

### Using AI to generate evaluations

Click **Generate with AI** in the code editor to open Max, PostHog's AI assistant, with your evaluation context pre-loaded. Max can help you:

- Write Hog evaluation code from a description of what you want to check
- Debug errors in your existing code
- Iterate on the logic by testing and refining

## Sentiment analysis evaluations

Sentiment evaluations classify the sentiment of the user messages in each generation as **positive**, **neutral**, or **negative**. They're ideal for monitoring how users feel during conversations with your AI features – spotting frustrated users, tracking satisfaction trends, and prioritizing the conversations that matter most.

### How they work

When a [generation](/docs/ai-observability/generations) is sampled, PostHog runs a local open-source ML model ([cardiffnlp/twitter-roberta-base-sentiment-latest](https://huggingface.co/cardiffnlp/twitter-roberta-base-sentiment-latest)) against the user messages in that generation. Each message is classified as positive, neutral, or negative with a confidence score, and the result is stored and linked to the original generation.

The model only processes user messages (the `$ai_input` property) – it does not process LLM outputs. Sentiment runs entirely within PostHog's infrastructure, so **no data is sent to any third-party AI provider**, and there's no LLM cost.

Sentiment evaluations share the same sampling rate and property filter options as the other evaluation types, so you can scope them to production traffic, specific models, or particular user segments.

### Creating a sentiment evaluation

1. Navigate to **AI Evals** > **Evaluations**
2. Click **New evaluation**
3. Select **Sentiment analysis** as the evaluation type
4. Configure:
   - **Name**: A descriptive name for the evaluation
   - **Sampling rate**: Percentage of generations to evaluate (0.1% – 100%)
   - **Property filters** (optional): Narrow which generations to evaluate using event or person properties
5. Enable the evaluation and click **Save**

### Viewing sentiment results

Once a sentiment evaluation is running, the **Sentiment** tab in AI Observability lets you browse user messages by sentiment, and traces and generations display a color-coded sentiment bar. See [Sentiment classification](/docs/ai-observability/sentiment) for details on the viewing experience.

## Evaluating past data

An evaluation only grades data captured after you create it, so a new evaluation starts with no baseline. A backfill runs it over generations, traces, or sessions you've already captured, so you see results right away instead of waiting for new traffic. Backfills use your existing live data. To test changes before they reach production, use [offline evaluations](/docs/ai-evals/offline-evals) instead.

To apply one to data you already have, run a **backfill** from the **Backfills** tab on the evaluation.

A backfill covers whatever the evaluation targets: generations, traces, or sessions.

### How backfills work

A backfill runs the evaluation over a time range you pick. It starts from the evaluation's own property filters and sampling rate, and you can change either one for this run without touching the evaluation itself. Whatever you pick is frozen on the backfill, so later edits to the evaluation do not change what a run already covered.

By default it skips anything the evaluation has already graded, so a run over a range the evaluation was already covering finds nothing to do. To grade that data again, turn on **Include generations that already have a result**. See [Re-evaluating generations that already have a result](#re-evaluating-generations-that-already-have-a-result).

Results appear alongside live results in the evaluation's run history, and each backfill row links to the results it produced.

### Creating a backfill

1. Open the evaluation and go to the **Backfills** tab
2. Pick a time range, up to 30 days back
3. Open **Conditions** to change the property filters or sampling rate for this run, or leave them as the evaluation has them
4. Check the count above the **Start backfill** button, which shows how much would be evaluated
5. Click **Start backfill** and confirm

One backfill runs at a time per evaluation. You can cancel a run while it is in progress, and results it already saved stay.

### Re-evaluating generations that already have a result

Turn on **Include generations that already have a result** to grade the same data a second time. Use it after changing a prompt or a code check, when you want the new version applied to data the old version already scored. Both results are kept, so you can compare them on the trace or session they graded.

### Reading backfill progress

The **Covered** column counts how much of the range holds a result. A finished backfill usually reads as fully covered, because the evaluation grades new data on its own while the backfill works through older data.

Expand a row to see the range, the conditions it used, and how much it started, skipped, or left without a result.

### When the count is zero

An enabled evaluation covers its own traffic within minutes, so a range it has been running over has nothing left to grade, and the count reads zero. This is expected, not an error. To grade that range again, turn on **Include generations that already have a result**.

The most recent few minutes are also held back, because an evaluation waits for a generation to settle before grading it.

A **Whole session** evaluation also reads zero when your generations don't carry `$ai_session_id`, because there are no sessions to grade. Including results that already exist doesn't change that count. See [Choosing what to evaluate](#choosing-what-to-evaluate).

### Backfill pricing

Every generation, trace, or session a backfill evaluates counts as one AI Observability event, the same as a live evaluation, and LLM judge backfills use your provider API key. The confirmation dialog shows how much will be evaluated before you start, so check that number on a wide range.

## Evaluation reports

Reports summarize a batch of results and compare it with the previous report, so you don't need to read individual results. Send them to Slack to read them where your team works. Reports are also what [Self-driving](/docs/ai-observability/self-driving#eval-reports) uses: each report becomes one signal in your inbox, instead of one signal per result.
<!-- VERIFY: can users ask PostHog AI follow-up questions about a report from the Slack thread? -->

When you create an evaluation, PostHog automatically provisions a default report configuration. Reports summarize evaluation results over time, so you can track quality trends without any additional setup.

Reports are available for all evaluation types – **LLM-as-a-judge**, **code-based**, and **sentiment analysis** – on any target.

### Default report configuration

The auto-created report uses these defaults:

| Setting               | Default value | Description                                                  |
| --------------------- | ------------- | ------------------------------------------------------------ |
| **Frequency**         | Count-based   | Generates a report after a set number of evaluation runs     |
| **Trigger threshold** | 100           | A report is generated every 100 new evaluation results       |
| **Cooldown**          | 1 hour        | Minimum hours between count-triggered reports (1 – 24 hours) |
| **Daily run cap**     | 10            | Maximum report runs per day                                  |
| **Enabled**           | Yes           | Reports start generating immediately                         |
| **Delivery targets**  | None          | Reports are viewable in the UI but no notifications are sent |

Reports are viewable directly in the evaluation's **Reports** tab without configuring any delivery targets.

### Report metrics by evaluation type

Reports display different metrics depending on your evaluation's output type:

- **Boolean evaluations** (LLM-as-a-judge and code-based) – Pass rate, pass/fail/N/A counts, total runs, and comparison to the previous reporting period
- **Numeric score and categorical evaluations** – Pass rate and pass/fail/N/A counts, based on the evaluation's passing rule. Reports need a passing rule.
- **Sentiment analysis evaluations** – Positive, neutral, and negative counts with distribution percentages, total runs, and comparison to the previous reporting period

### Customizing reports

You can adjust the report configuration after creating an evaluation:

- Change the trigger threshold to generate reports more or less frequently
- Adjust the minimum hours between reports (1 – 24) to control how often count-triggered reports can fire
- Add email or Slack delivery targets to receive notifications when reports are generated
- Disable the report if you don't need automated summaries

## Evaluation status and errors

Each evaluation has a status that indicates whether it's running:

- **Active** – The evaluation is enabled and running on sampled generations.
- **Paused** – You disabled the evaluation. It won't run until you re-enable it.
- **Error** – PostHog automatically disabled the evaluation due to an issue that needs attention.

### Automatic error states

PostHog automatically disables evaluations and sets them to error status when:

| Error reason                       | Cause                                                     | How to resolve                                                                                                                                            |
| ---------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No provider API key configured** | The evaluation has no provider API key to run with.       | Add a provider API key in [**Settings** > **AI Observability**](https://app.posthog.com/settings/environment-ai-observability#ai-observability-byok).     |

### Identifying errored evaluations

On the **Evaluations** list page, errored evaluations display a red **Error** pill instead of the enable/disable toggle. Hover over the pill to see the specific error reason. Errored evaluations sort to the top of the list.

On the evaluation detail page, the header shows a red **Error** tag and a banner explains the cause with recovery steps.

### Re-enabling errored evaluations

You must resolve the underlying issue before re-enabling an errored evaluation:

- **No provider API key configured** – Add a provider API key.
- **Provider key deleted** – Add a new provider API key.

Once the issue is resolved, open the evaluation and toggle it back on.

## Pricing

Each evaluation run counts as one AI Observability event toward your quota.

Evaluation runs and your other AI Observability events share the same allowance, including the free tier. <!-- VERIFY: free tier volume, said to be 100K events -->

**LLM judge evaluations** use an LLM to score your generations and require a provider API key. Add your own key from OpenAI, Azure OpenAI, Google Gemini, Anthropic, OpenRouter, Fireworks, or Together AI in [**Settings** > **AI Observability**](https://app.posthog.com/settings/environment-ai-observability#ai-observability-byok) to enable LLM-judge evaluations.

If a provider API key is missing or deleted, PostHog automatically disables the affected evaluations and shows an error status. See [Evaluation status and errors](#evaluation-status-and-errors) for details on error states and how to resolve them.

**Code-based evaluations** have no LLM cost – they run your Hog code directly with no external API calls.

**Sentiment evaluations** have no LLM cost – they run a local ML model with no external API calls.

Use sampling rates strategically to balance coverage and cost – 5-10% sampling often provides sufficient signal for quality monitoring.

Backfills bill the same way. See [Evaluating past data](#evaluating-past-data) for how to check the count before starting one.
