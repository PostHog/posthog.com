Offline evals are tests for your AI agent. You run them in CI or locally before you ship a change, then send the results to PostHog to track quality from one change to the next and catch regressions before they reach users.

## Why use offline evals?

You wouldn't ship code without tests, but many agents go to production tested only by hand. A one-line prompt change can break behavior that used to work, and you won't find out until a user does.

Offline evals close that gap. They work like unit and integration tests: a fixed set of test cases runs against each change, and a drop in a score tells you something broke.

## Offline evals vs online evaluations

[Online evaluations](/docs/ai-evals) score real traffic as it happens. Offline evals score a fixed set of inputs before you ship. You need both: offline evals catch regressions on the cases you know about, and online evaluations catch problems in everything else your users send, which is unlimited.

|  | Online evaluations | Offline evals |
| --- | --- | --- |
| Input | Live user traffic | Test cases you wrote or saved from production |
| Output | Already produced | Generated by running your agent |
| Evaluators run in | PostHog | Your code |
| When | As traffic arrives | Before you ship, usually in CI |

## How offline evals work

1. **Define test cases.** Each case has an input and, optionally, an expected output. Write them by hand, or save failing production traces to a [dataset](/docs/ai-evals/datasets) and fetch it at test time.
2. **Run your agent on each input.** Run the real agent, with its tools, so the output reflects what users would get.
3. **Score each output.** Use one or more evaluators, for example an LLM judge that compares the output with the expected answer, or a code check that the right tool was called.

## Example: testing a SQL-writing agent

PostHog runs offline evals on PostHog AI, its own agent. One suite checks the SQL it writes:

- Each test case pairs a question, such as "How many pageviews did we get from Chrome?", with the SQL the agent should run. <!-- VERIFY: example question is paraphrased from the PostHog AI eval suite -->
- In CI, the full agent runs in a sandbox and gets each question exactly as a user would type it.
- An evaluator pulls the last SQL query the agent ran and gives it to an LLM judge, which checks whether it answers the question.
- Other evaluators check whether the agent exited cleanly, ran the query, and picked the right tool.
- When a user reports a problem, such as the agent struggling to list feature flags, the team adds a test case for it.

## Review results

Go to **AI Evals** > **Offline evals**. <!-- VERIFY: navigation path -->

- **Experiments** – Each experiment is one run of your test suite, for example from one pull request's CI.
- **Test cases** – Each row is a test case. Open it to see the input, expected output, and actual output.
- **Evaluators** – Each column is an evaluator, so you can see which checks a case passed or failed.
- **Trends** – Compare scores across experiments to spot the change that caused a drop. <!-- VERIFY: per-PR trend chart shipped -->
