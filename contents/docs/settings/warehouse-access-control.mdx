You can restrict who can access warehouse sources and query synced or self-managed warehouse tables, views, and [materialized views](/docs/data-warehouse/views/materialize). Organization, project, and resource access lives on [access control](/docs/settings/access-control). To hide event and person properties, see [property access control](/docs/settings/property-access-control).

You can't yet restrict querying the core PostHog tables (`events`, `sessions`, `persons`, `groups`). Session Replay and person and group profiles are also unrestricted at the data layer.

## Warehouse tables and views

Denied tables and views are removed from the HogQL schema. Queries against them fail in the SQL editor, insights, [PostHog AI](/docs/posthog-ai), and the API.

### Where to set it

- **A specific table or view:** `...` menu in the SQL editor schema tree
- **A view:** Data models page
- **A synced table:** `...` menu on the source's **Schemas** tab
- **A source:** **Access control** on the source page
- **All tables and views, or all sources:** Project [access control](/docs/settings/access-control) settings

### Access levels

Same four levels as other resources:

- **No access** – Hidden from the schema and can't be queried
- **Viewer** – Can query. Can't sync, delete, or reconfigure a table.
- **Editor** – Can query and manage the table or view
- **Manager** – Can change access controls

### How table access is resolved

For tables synced from a source (Stripe, Postgres, HubSpot, and so on), PostHog checks in this order:

1. A rule on that table
2. A rule on that table's source
3. A rule for all tables and views
4. A rule for all sources
5. The default

Self-managed tables (S3, file uploads, direct connections) have no source, so steps 2 and 4 don't apply.

Restricting a source to **No access** blocks querying every table synced from it, unless a table-level rule overrides it.

For example, Stripe set to **Viewer** with no table rules means every Stripe table is Viewer. Then `stripe_customers` set to **Editor** makes that table Editor; the rest stay Viewer.

### Views and materialized views

Granting access to a regular view doesn't bypass access controls on the tables it reads. If an underlying table is denied, the query fails.

For [materialized views](/docs/data-warehouse/views/materialize), access is checked on the view itself. Use a materialized view to expose selected data from a restricted table.

### Shared links

[Shared insights, dashboards, and notebooks](/docs/product-analytics/sharing) run without warehouse access control.

## Feature availability

Warehouse access control uses the same plans as [access control](/docs/settings/access-control#feature-availability). Role-based rules require the [Enterprise plan](/platform-packages).
