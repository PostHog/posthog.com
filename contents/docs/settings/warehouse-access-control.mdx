You can restrict who can access warehouse sources and query warehouse tables and views. Organization, project, and resource access (dashboards, flags, and the rest) lives on [access control](/docs/settings/access-control). To hide event and person properties, see [hiding sensitive properties](/docs/settings/hiding-sensitive-properties).

## What's covered

- Warehouse tables, whether synced from a source or self-managed
- Warehouse views, including [materialized views](/docs/data-warehouse/views/materialize)

## What's not covered yet

You can't yet restrict querying of PostHog's native tables (`events`, `sessions`, `persons`, `groups`). Session replay and person and group profiles are also unrestricted at the data layer. You can still hide individual [event and person properties](/docs/settings/hiding-sensitive-properties).

## Warehouse tables and views

Denied tables and views are removed from the HogQL schema. Queries against them fail in the SQL editor, insights, [PostHog AI](/docs/posthog-ai), and the API.

### Where to set it

- **A specific table or view:** `...` menu in the SQL editor schema tree
- **A view:** Data models page
- **A synced table:** `...` menu on the source's **Schemas** tab
- **A source:** **Access control** on the source page
- **All tables and views, or all sources:** Project [access control](/docs/settings/access-control) settings

### Access levels

Same four levels as other resources:

- **No access** – Hidden from the schema and can't be queried
- **Viewer** – Can query. Can't sync, delete, or reconfigure a table.
- **Editor** – Can query and manage the table or view
- **Manager** – Can change access controls

### How table access is resolved

For tables synced from a source (Stripe, Postgres, HubSpot, and so on), PostHog checks in this order:

1. A rule on that table
2. A rule for all tables and views
3. A rule on that table's source
4. A rule for all sources
5. The default

Self-managed tables (S3, file uploads, direct connections) have no source, so steps 3 and 4 don't apply.

Restricting a source to **No access** blocks querying every table synced from it, unless a table-level rule overrides it.

For example, Stripe set to **Viewer** with no table rules means every Stripe table is Viewer. Then `stripe_customers` set to **Editor** makes that table Editor; the rest stay Viewer.

### Views and materialized views

Access is on the view, not the tables it reads.

Granting a view while denying its underlying tables only works for [materialized views](/docs/data-warehouse/views/materialize). A regular view expands to its SQL and hits the table check, so the query still fails.

### Shared links

[Shared insights, dashboards, and notebooks](/docs/product-analytics/sharing) run without warehouse access control. Publishing the link is the access decision.

## Feature availability

Warehouse access control uses the same plans as [access control](/docs/settings/access-control#feature-availability). Role-based rules require the [Enterprise plan](/platform-packages).
