The [Node.js SDK](/docs/libraries/node) sends transactional emails from version 5.61.2. Before you start, you need a transactional email ([templates and variables](/docs/workflows/transactional/templates#create-a-transactional-email)) or content from your code, and a project secret API key ([create an API key](/docs/workflows/transactional/send-from-code#create-an-api-key)). The [quick start](/docs/workflows/installation) sets up both and sends a test email in a few minutes.

New to sending from code? Read [send emails from code](/docs/workflows/transactional/send-from-code) first.

## Install

```bash
npm install posthog-node@6
```

## Set up the client

Add your project secret API key to the PostHog client that your app already has. The project token keeps capturing events. The secret key sends email, so keep it on your server and never ship it to the browser.

```js
import { PostHog } from "posthog-node"

const posthog = new PostHog("<ph_project_token>", {
    host: "<ph_client_api_host>",
    secretKey: process.env.POSTHOG_PROJECT_SECRET_API_KEY,
    // This client only sends email, so it doesn't poll flag definitions with the secret key
    enableLocalEvaluation: false,
})
```

Keep `enableLocalEvaluation: false` unless this client also [evaluates feature flags locally](/docs/feature-flags/local-evaluation). With local evaluation on, the client polls flag definitions with the secret key, and a key with only the **Transactional email** scope can't read them. If you do evaluate flags locally with this client, give the key the **Feature flag** read scope too.

Shut the client down when your app exits, not after each send. If your app sends through a reverse proxy or a self-hosted PostHog, see [use a proxy or self-hosted PostHog](#use-a-proxy-or-self-hosted-posthog).

## Send an email

```js
export async function sendPasswordReset({ userId, email, firstName, resetLink, resetRequestId }) {
    const { data, error } = await posthog.emails.send({
        to: email,
        templateId: "<template_id>",
        templateData: { first_name: firstName, reset_link: resetLink },
        distinctId: userId,
        // Identifies this one email, so a retry never sends it twice
        idempotencyKey: `password-reset-${resetRequestId}`,
    })
    if (error) {
        // An EmailError. Branch on error.code
        throw error
    }
    return data.id
}
```

`send` doesn't throw. It returns `{ data, error }`. `data.id` is the message ID. `data` means PostHog queued the email, not that it delivered it. `error` is an `EmailError`, and its `code` is one of the codes in the [errors table](/docs/workflows/transactional/retries-and-errors#what-to-retry).

A `network_error` or a `503` doesn't mean that the email failed, because PostHog can still have queued it. Retry with the same idempotency key. If you resend the email through another email provider, the recipient can get it twice.

### Fields

Fields marked "template only" work only with a template made in PostHog. Fields marked "code only" work only with content from your code.

| Field | Required | What it does |
| --- | --- | --- |
| `to` | Yes | The recipient's email address. |
| `templateId` | Yes, template only | The ID of the transactional email in PostHog. |
| `templateData` | No, template only | Values for the template's variables. |
| `distinctId` | No | Links the email to your user's person in PostHog. |
| `idempotencyKey` | No | Identifies this one email, so a retry never sends it twice. |
| `maxRetries` | No | How many times the client retries this send. |
| `templateKey` | Yes, code only | Names the email, so PostHog groups its metrics and sends. |
| `subject` | Yes, code only | The subject line. |
| `html` | At least one of `html`, `text`, or `react`, code only | The HTML body. |
| `text` | At least one of `html`, `text`, or `react`, code only | The plain text body. PostHog makes it from `html` if you leave it out. |
| `react` | At least one of `html`, `text`, or `react`, code only | A React Email element, in place of `html`. The SDK renders it. |
| `from` | No, code only | The sender. Without it, PostHog uses the project's default sender. |
| `replyTo` | No, code only | One reply-to address or a list. |
| `cc` | No, code only | One copy address or a list. |
| `bcc` | No, code only | One blind copy address or a list. |
| `attachments` | No, code only | A list of files to attach. |
| `sensitive` | No, code only | Marks the email as sensitive, for login links, reset tokens, or codes. |
| `tracking` | No, code only | What PostHog tracks: opens, clicks, and engagement events. |

Sending needs version 5.61.2 or later. Content from your code needs 5.62.0, `react` needs 5.69.0, `sensitive` and `tracking` need 5.71.0, and `cc`, `bcc`, and `attachments` need 5.72.0.

### Timeouts and retries

The client retries for you. It retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 second and then 2 seconds, or as long as the server's `Retry-After` asks, up to 30 seconds. When `Retry-After` asks for more than 30 seconds, the client returns the error at once. Each request times out after 15 seconds.

To change this, set `emailRequestTimeoutMs` and `emailRequestMaxRetries` on the client, or `maxRetries` on one send.

## Send from a background job

Send from a job queue when the email shouldn't slow down the request, such as an email address check after a signup. Let the queue own the retries:

- Set `maxRetries: 0`, so that the client doesn't retry inside the job.
- Keep the idempotency key the same on every attempt.
- Finish the retries within 7 days. PostHog remembers an idempotency key for 7 days after it queues the email, so a later retry can send the email twice.
- Retry only the errors that a later attempt can fix. Every other code fails the same way again.

This example uses [BullMQ](https://docs.bullmq.io). Add the job with `attempts` and a `backoff`, so that BullMQ retries it. Five attempts with this backoff finish in under three minutes.

```js
import { Queue } from "bullmq"

const emails = new Queue("emails", { connection: { host: "localhost", port: 6379 } })

await emails.add(
    "password-reset",
    { userId, email, firstName, resetLink, resetRequestId },
    { attempts: 5, backoff: { type: "exponential", delay: 10_000 } }
)
```

The worker sends the email:

```js
import { UnrecoverableError, Worker } from "bullmq"

// A later attempt can fix these. Any other code fails the same way again.
const RETRYABLE_CODES = new Set(["network_error", "idempotency_key_in_flight", "throttled", "delivery_unavailable"])

new Worker(
    "emails",
    async (job) => {
        const { userId, email, firstName, resetLink, resetRequestId } = job.data
        const { data, error } = await posthog.emails.send({
            to: email,
            templateId: "<template_id>",
            templateData: { first_name: firstName, reset_link: resetLink },
            distinctId: userId,
            // The same key on every attempt, so a retried job never sends the email twice
            idempotencyKey: `password-reset-${resetRequestId}`,
            // BullMQ retries the job, so the client doesn't retry on its own
            maxRetries: 0,
        })
        if (error) {
            throw RETRYABLE_CODES.has(error.code) ? error : new UnrecoverableError(`${error.code}: ${error.message}`)
        }
        return data.id
    },
    { connection: { host: "localhost", port: 6379 } }
)
```

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinctId`, and leave it out for someone who isn't a user yet. See [link emails to your users](/docs/workflows/transactional/send-from-code#link-emails-to-your-users) for how PostHog records each case.

## Send content from your code

From version 5.62.0, `send` also takes content that your code rendered, with no template in PostHog. From version 5.69.0, you can pass a [React Email](https://react.email) component as `react`, in place of `html`. The SDK renders its HTML and plain text with `@react-email/render`, which you install next to `posthog-node`. If you bundle your app, such as for Cloudflare Workers or Vercel Edge, also pass `reactEmailRenderer: await import("@react-email/render")` to the client.

```jsx
import { PasswordResetEmail } from "./emails/password-reset"

export async function sendPasswordReset({ userId, email, firstName, resetLink, resetRequestId }) {
    const { data, error } = await posthog.emails.send({
        to: email,
        templateKey: "password-reset",
        subject: "Reset your password",
        react: <PasswordResetEmail firstName={firstName} resetLink={resetLink} />,
        from: "Hedgebox <security@example.com>",
        distinctId: userId,
        idempotencyKey: `password-reset-${resetRequestId}`,
    })
    if (error) {
        throw error
    }
    return data.id
}
```

`captureEngagement` is deprecated. Pass `tracking: { engagement: false }` instead, and don't set both.

See [content from your code](/docs/workflows/transactional/from-code) for what each field does, the [React Email](/docs/workflows/transactional/from-code#react-email) errors, and the checks PostHog runs.

### Copies and attachments

Copies and attachments need version 5.72.0 or later.

Each file in `attachments` has `filename` and `content`, and can also have `contentType` and `contentId`. Pass the file's bytes, such as a `Buffer`, as `content`. The client uploads each file before it sends the email, and checks the limits first. If an upload fails, `send` returns an error, and PostHog sends nothing.

```js
import { readFile } from "node:fs/promises"

const { error } = await posthog.emails.send({
    to: user.email,
    templateKey: "receipt",
    subject: "Your receipt",
    html,
    cc: "billing@example.com",
    attachments: [{ filename: "receipt.pdf", content: await readFile(pdfPath), contentType: "application/pdf" }],
    distinctId: user.id,
})
```

See [attachments](/docs/workflows/transactional/attachments) for the limits, inline images, and errors.

### Open and click tracking

`sensitive` and `tracking` need version 5.71.0 or later. For example, to track the clicks of an email with no secrets:

```js
await posthog.emails.send({
    to: "ada@example.com",
    templateKey: "order-shipped",
    subject: "Your order shipped",
    html,
    sensitive: false,
    tracking: { clicks: true },
})
```

`tracking` takes `true`, `false`, or an object with `opens`, `clicks`, and `engagement`. See [sensitive data and tracking](/docs/workflows/transactional/sensitive-data) for the defaults and rules.

## Check an email's status

```js
export async function emailBounced(messageId) {
    const { data: status, error } = await posthog.emails.get(messageId)
    if (error) {
        if (error.code === "not_found") {
            // The first status can take a few seconds to arrive. Try again later.
            return null
        }
        throw error
    }
    return status.status === "bounced"
}
```

`get` returns `{ data, error }`. `data` has `id`, `status`, `createdAt`, `statusAt`, and `reason`. The two times are ISO 8601 strings.

The client doesn't retry a `not_found`, which you can get right after a send. Try again a few times with a short wait before you treat the email as missing.

See [status and troubleshooting](/docs/workflows/transactional/status) for what each status and reason means.

## Test without sending email

Pass your own `fetch` to see exactly what your code sends, with no network call. This tests your integration, not delivery. To test delivery, send a real email to your own address and check the [**Log**](/docs/workflows/transactional#see-each-send) on the **Transactional** tab.

```js
import assert from "node:assert/strict"
import { PostHog } from "posthog-node"

const requests = []
const posthog = new PostHog("phc_test", {
    secretKey: "phs_test",
    enableLocalEvaluation: false,
    fetch: async (url, options) => {
        requests.push({ url, options })
        return new Response(JSON.stringify({ message_id: "msg_1", replayed: false }), { status: 202 })
    },
})

const { data } = await posthog.emails.send({
    to: "jane@example.com",
    templateId: "0190f6d2-7c1e-7b3a-9f5e-1c2d3e4f5a6b",
    idempotencyKey: "password-reset-1",
})

assert.equal(data.id, "msg_1")
assert.equal(requests[0].options.headers["Idempotency-Key"], "password-reset-1")
```

## Use a proxy or self-hosted PostHog

On PostHog Cloud, the client sends email to your region's app host, even when `host` is an ingestion host such as `us.i.posthog.com`. If `host` is a reverse proxy or a self-hosted PostHog, set `appHost` to your PostHog app URL. The client doesn't send email requests to a host that might be a proxy.

With `enableLocalEvaluation` on, the client still polls flag definitions from `host` with the secret key. If that host is a proxy that must not see the key, keep `enableLocalEvaluation: false`.
