The [Rust SDK](/docs/libraries/rust) sends transactional emails. This page uses the `posthog` crate, and every release from 1.0.0 can send. On the older `posthog-rs` crate, sending needs 0.31.0 or later. Your code sends the subject and HTML, so the email lives in your codebase. Before you start, you need a [verified sending domain](/docs/workflows/domain) and a project secret API key ([create an API key](/docs/workflows/transactional/send-from-code#create-an-api-key)). The [quick start](/docs/workflows/installation) sets up the key and sends a test email in a few minutes.

New to sending from code? Read [send emails from code](/docs/workflows/transactional/send-from-code) first.

## Install

```bash
cargo add posthog@1 serde_json
```

## Set up the client

Add your project secret API key to the PostHog client that your app already has. The project token keeps capturing events. The secret key sends email, so keep it on your server.

```rust
use posthog::ClientOptionsBuilder;

let options = ClientOptionsBuilder::default()
    .api_key("<ph_project_token>".to_string())
    .host("<ph_client_api_host>")
    .secret_key(std::env::var("POSTHOG_PROJECT_SECRET_API_KEY")?)
    .build()?;
let posthog = posthog::client(options).await;
```

The client loads flag definitions only when you turn on `enable_local_evaluation`. If you do, give the key the **Feature flag** read scope too.

Without the default `async-client` feature, the client and `emails()` are blocking, and you call them without `.await`.

Shut the client down when your app exits, not after each send. If your app sends through a reverse proxy or a self-hosted PostHog, see [use a proxy or self-hosted PostHog](#use-a-proxy-or-self-hosted-posthog).

## Send an email

```rust
use posthog::CodeEmail;

async fn send_password_reset(
    posthog: &posthog::Client,
    user: &User,
    reset_link: &str,
    reset_request_id: &str,
) -> Result<String, posthog::EmailError> {
    let result = posthog
        .emails()
        .send(
            // "password-reset" names the email, so PostHog groups its sends and metrics
            CodeEmail::new(&user.email, "password-reset", "Reset your password")
                .html(format!(
                    r#"<p>Reset your password <a href="{reset_link}">here</a>. The link works for 1 hour.</p>"#
                ))
                .distinct_id(&user.id)
                // Identifies this one email, so a retry never sends it twice
                .idempotency_key(format!("password-reset-{reset_request_id}")),
        )
        // An EmailError. Branch on error.code()
        .await?;
    Ok(result.id)
}
```

`send` returns `Result<SendEmailResult, EmailError>`. `result.id` is the message ID. An `Ok` means PostHog queued the email, not that it delivered it. Branch on `error.code()`, one of the codes in the [errors table](/docs/workflows/transactional/retries-and-errors#what-to-retry). A wrong argument, such as a template ID that isn't a UUID, returns an `EmailError` before any request.

A `network_error` or a `503` doesn't mean that the email failed, because PostHog can still have queued it. Retry with the same idempotency key. If you resend the email through another email provider, the recipient can get it twice.

For a longer email, render the HTML first with your template engine, such as Askama or Tera, and pass the result to `html`. See [emails your code writes](/docs/workflows/transactional/from-code) for what each field does and the checks PostHog runs.

### Fields

`send` takes a `CodeEmail` for an email that your code writes, and a `TemplateEmail` for a template from PostHog. After `new`, each field is a builder method.

| Field | Required | What it does |
| --- | --- | --- |
| `CodeEmail::new` | Yes | Takes the recipient's email address, a template key that names the email, and the subject. |
| `html` | At least one of `html` or `text` | The HTML body. |
| `text` | At least one of `html` or `text` | The plain text body. PostHog makes it from `html` if you leave it out. |
| `from` | No | The sender. Without it, PostHog uses the project's default sender. |
| `reply_to` | No | Call once for each reply-to address. |
| `distinct_id` | No | Links the email to your user's person in PostHog. |
| `idempotency_key` | No | Identifies this one email, so a retry never sends it twice. |
| `max_retries` | No | How many times the client retries this email. |
| `cc` | No | Call once for each copy address. |
| `bcc` | No | Call once for each blind copy address. |
| `attachment` | No | Call once for each file, with `EmailAttachment::new`. |
| `sensitive` | No | Marks the email as sensitive, for login links, reset tokens, or codes. |
| `tracking` | No | What PostHog tracks: opens, clicks, and engagement events. |

To send a [template from PostHog](#send-a-template-from-posthog) instead, use `TemplateEmail::new`, which takes the recipient's email address and the template ID, and `template_data` in place of the template key, the subject, and the body.

Every `posthog` release takes every field. On `posthog-rs`, sending needs 0.31.0 or later, `sensitive` and `tracking` need 0.32.0, and `cc`, `bcc`, and `attachment` need 0.33.0.

### Timeouts and retries

The client retries for you. It retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 second and then 2 seconds, or longer if the server's `Retry-After` asks for it. When `Retry-After` asks for more than 30 seconds, the client returns the error at once. Each request times out after 15 seconds.

To change this, set `email_request_timeout_seconds` and `email_request_max_retries` on `ClientOptionsBuilder`, or call `max_retries` on one email.

## Send from a background job

Send from a job queue when the email shouldn't slow down the request, such as an email address check after a signup. Let the queue own the retries:

- Call `max_retries(0)` on the email, so that the client doesn't retry inside the job.
- Keep the idempotency key the same on every attempt.
- Finish the retries within 7 days. PostHog remembers an idempotency key for 7 days after it queues the email, so a later retry can send the email twice.
- Retry only the errors that a later attempt can fix. Every other code fails the same way again.

Rust has no job queue that most apps use, so this sketch shows the pattern without one. The job function sorts each error into a retry or a permanent failure. Map the two to your queue's own ways to run a job again later and to fail it for good.

```rust
use posthog::{CodeEmail, EmailError};

// A later attempt can fix these. Any other code fails the same way again.
const RETRYABLE_CODES: [&str; 4] = ["network_error", "idempotency_key_in_flight", "throttled", "delivery_unavailable"];

pub enum JobError {
    // Run the job again later, with the same arguments
    Retry(EmailError),
    // Fail the job for good
    Permanent(EmailError),
}

pub struct PasswordResetJob {
    pub user_id: String,
    pub email: String,
    pub reset_link: String,
    pub reset_request_id: String,
}

pub async fn run_password_reset_job(
    posthog: &posthog::Client,
    job: &PasswordResetJob,
) -> Result<String, JobError> {
    let email = CodeEmail::new(&job.email, "password-reset", "Reset your password")
        .html(format!(r#"<p>Reset your password <a href="{}">here</a>.</p>"#, job.reset_link))
        .distinct_id(&job.user_id)
        // The same key on every attempt, so a retried job never sends the email twice
        .idempotency_key(format!("password-reset-{}", job.reset_request_id))
        // The queue retries the job, so the client doesn't retry on its own
        .max_retries(0);
    match posthog.emails().send(email).await {
        Ok(result) => Ok(result.id),
        Err(error) if RETRYABLE_CODES.contains(&error.code()) => Err(JobError::Retry(error)),
        Err(error) => Err(JobError::Permanent(error)),
    }
}
```

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinct_id`, and leave it out for someone who isn't a user yet. See [link emails to your users](/docs/workflows/transactional/send-from-code#link-emails-to-your-users) for how PostHog records each case.

## Copies, attachments, and tracking

### Copies and attachments

Call `cc` or `bcc` once for each plain address, and `attachment` once for each file. `EmailAttachment::new` takes the file name and the file's bytes. Add `content_type` to set the file type, or `content_id`. The client uploads each file before it sends the email, and checks the limits first. If an upload fails, `send` returns an error, and PostHog sends nothing.

```rust
use posthog::{CodeEmail, EmailAttachment};

let receipt_pdf = std::fs::read(pdf_path)?;
posthog
    .emails()
    .send(
        CodeEmail::new(&user.email, "receipt", "Your receipt")
            .html(html)
            .cc("billing@example.com")
            .attachment(EmailAttachment::new("receipt.pdf", receipt_pdf).content_type("application/pdf"))
            .distinct_id(&user.id),
    )
    .await?;
```

See [attachments](/docs/workflows/transactional/attachments) for the limits, inline images, and errors.

### Open and click tracking

To track the clicks of an email with no secrets:

```rust
use posthog::{CodeEmail, EmailTrackingOptions};

posthog
    .emails()
    .send(
        CodeEmail::new("ada@example.com", "order-shipped", "Your order shipped")
            .html(html)
            .sensitive(false)
            .tracking(EmailTrackingOptions::new().clicks(true)),
    )
    .await?;
```

`tracking` takes `EmailTracking::On`, `EmailTracking::Off`, or `EmailTrackingOptions::new()` with its `opens`, `clicks`, and `engagement` builder methods. See [sensitive data and tracking](/docs/workflows/transactional/sensitive-data) for the defaults and rules.

`capture_engagement` is deprecated. Call `.tracking(EmailTrackingOptions::new().engagement(false))` instead, and don't set both.

## Send a template from PostHog

You can also keep an email in PostHog as a [template](/docs/workflows/transactional/templates), so your team edits the copy without a deploy. Send a `TemplateEmail` with its template ID and the values for its variables:

```rust
use posthog::TemplateEmail;
use serde_json::json;

posthog
    .emails()
    .send(
        TemplateEmail::new(&user.email, "<template_id>")
            .template_data(json!({ "first_name": user.first_name, "reset_link": reset_link }))
            .distinct_id(&user.id)
            .idempotency_key(format!("password-reset-{reset_request_id}")),
    )
    .await?;
```

A template send takes no subject, body, sender, copies, or attachments. The template sets them.

## Check an email's status

```rust
use posthog::EmailDeliveryStatus;

async fn email_bounced(
    posthog: &posthog::Client,
    message_id: &str,
) -> Result<Option<bool>, posthog::EmailError> {
    match posthog.emails().get(message_id).await {
        Ok(status) => Ok(Some(status.status == EmailDeliveryStatus::Bounced)),
        // The first status can take a few seconds to arrive. Try again later.
        Err(error) if error.code() == "not_found" => Ok(None),
        Err(error) => Err(error),
    }
}
```

`get` returns an `EmailStatus` with `id`, `status`, `created_at`, `status_at`, and `reason`. `status` is an `EmailDeliveryStatus`, and `as_str()` gives it as a string. A status that this SDK version doesn't know arrives as `EmailDeliveryStatus::Other`.

The client doesn't retry a `not_found`, which you can get right after a send. Try again a few times with a short wait before you treat the email as missing.

See [status and troubleshooting](/docs/workflows/transactional/status) for what each status and reason means.

## Test without sending email

Start a local stub server with [httpmock](https://docs.rs/httpmock) and set its URL as `app_host`, to see exactly what your code sends with no request to PostHog. This tests your integration, not delivery. To test delivery, send a real email to your own address and check the [**Log**](/docs/workflows/transactional#see-each-send) on the **Transactional** tab.

```bash
cargo add --dev httpmock
cargo add --dev tokio --features macros,rt
```

```rust
use httpmock::prelude::*;
use posthog::{ClientOptionsBuilder, CodeEmail};
use serde_json::json;

#[tokio::test]
async fn sends_password_reset() {
    let server = MockServer::start_async().await;
    let send = server
        .mock_async(|when, then| {
            when.method(POST)
                .path_suffix("/messaging/send/email/")
                .header("idempotency-key", "password-reset-1");
            then.status(202)
                .json_body(json!({ "message_id": "msg_1", "replayed": false }));
        })
        .await;

    let options = ClientOptionsBuilder::default()
        .api_key("phc_test".to_string())
        .secret_key("phs_test")
        .app_host(server.base_url())
        .build()
        .unwrap();
    let posthog = posthog::client(options).await;

    let result = posthog
        .emails()
        .send(
            CodeEmail::new("jane@example.com", "password-reset", "Reset your password")
                .html("<p>Reset your password.</p>")
                .idempotency_key("password-reset-1"),
        )
        .await
        .unwrap();

    assert_eq!(result.id, "msg_1");
    send.assert_async().await;
}
```

## Use a proxy or self-hosted PostHog

On PostHog Cloud, the client sends email to your region's app host, even when `host` is an ingestion host such as `us.i.posthog.com`. If `host` is a reverse proxy or a self-hosted PostHog, set `app_host` to your PostHog app URL. Without it, a send fails with `missing_app_host`. The client doesn't send email requests to a host that might be a proxy.

With `enable_local_evaluation` on, flag definitions still load from `host` with the secret key. If that host is a proxy that must not see the key, leave `enable_local_evaluation` off on this client.

From 1.1.2, the client sends email to `/api/messaging/`. A self-hosted PostHog needs a version from 2026-11-18 or later, or it answers with a `404`.
