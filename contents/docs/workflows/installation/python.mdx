The [Python SDK](/docs/libraries/python) sends transactional emails from version 7.84.0. Your code sends the subject and HTML, so the email lives in your codebase. Before you start, you need a [verified sending domain](/docs/workflows/domain) and a project secret API key ([create an API key](/docs/workflows/transactional/send-from-code#create-an-api-key)). The [quick start](/docs/workflows/installation) sets up the key and sends a test email in a few minutes.

New to sending from code? Read [send emails from code](/docs/workflows/transactional/send-from-code) first.

## Install

```bash
pip install "posthog>=8,<9"
```

For async code, install `posthog[async]` instead.

## Set up the client

Add your project secret API key to the PostHog client that your app already has. The project token keeps capturing events. The secret key sends email, so keep it on your server and never ship it to the browser.

<MultiLanguage selector="tabs">

```python file=Sync
import os

from posthog import Posthog

posthog = Posthog(
    "<ph_project_token>",
    host="<ph_client_api_host>",
    secret_key=os.environ["POSTHOG_PROJECT_SECRET_API_KEY"],
)
```

```python file=Async
import os

from posthog import AsyncPosthog

posthog = AsyncPosthog(
    "<ph_project_token>",
    host="<ph_client_api_host>",
    secret_key=os.environ["POSTHOG_PROJECT_SECRET_API_KEY"],
)
```

</MultiLanguage>

The client loads flag definitions only when it evaluates a flag. If your app [evaluates feature flags locally](/docs/feature-flags/local-evaluation) with the same client, give the key the **Feature flag** read scope too.

In a process that only sends email, you can use `Emails` or `AsyncEmails` from `posthog.emails` instead of a full client.

Shut the client down when your app exits, not after each send. If your app sends through a reverse proxy or a self-hosted PostHog, see [use a proxy or self-hosted PostHog](#use-a-proxy-or-self-hosted-posthog).

## Send an email

<MultiLanguage selector="tabs">

```python file=Sync
def send_password_reset(user_id: str, email: str, reset_link: str, reset_request_id: str) -> str:
    # Raises posthog.emails.EmailError when PostHog doesn't queue the email. Branch on error.code.
    result = posthog.emails.send(
        to=email,
        # Names the email, so PostHog groups its sends and metrics
        template_key="password-reset",
        subject="Reset your password",
        html=f'<p>Reset your password <a href="{reset_link}">here</a>. The link works for 1 hour.</p>',
        distinct_id=user_id,
        # Identifies this one email, so a retry never sends it twice
        idempotency_key=f"password-reset-{reset_request_id}",
    )
    return result.id
```

```python file=Async
async def send_password_reset(user_id: str, email: str, reset_link: str, reset_request_id: str) -> str:
    # Raises posthog.emails.EmailError when PostHog doesn't queue the email. Branch on error.code.
    result = await posthog.emails.send(
        to=email,
        # Names the email, so PostHog groups its sends and metrics
        template_key="password-reset",
        subject="Reset your password",
        html=f'<p>Reset your password <a href="{reset_link}">here</a>. The link works for 1 hour.</p>',
        distinct_id=user_id,
        # Identifies this one email, so a retry never sends it twice
        idempotency_key=f"password-reset-{reset_request_id}",
    )
    return result.id
```

</MultiLanguage>

`send` returns a `SendEmailResult`, and `result.id` is the message ID. A result means PostHog queued the email, not that it delivered it. When PostHog doesn't queue the email, `send` raises `EmailError`, and its `code` is one of the codes in the [errors table](/docs/workflows/transactional/retries-and-errors#what-to-retry). A wrong argument raises `TypeError` or `ValueError` before any request.

A `network_error` or a `503` doesn't mean that the email failed, because PostHog can still have queued it. Retry with the same idempotency key. If you resend the email through another email provider, the recipient can get it twice.

For a longer email, render the HTML first with your template engine, such as Jinja or Django templates, and pass the result as `html`.

See [emails your code writes](/docs/workflows/transactional/from-code) for what each field does and the checks PostHog runs.

### Fields

| Field | Required | What it does |
| --- | --- | --- |
| `to` | Yes | The recipient's email address. |
| `template_key` | Yes | Names the email, so PostHog groups its metrics and sends. |
| `subject` | Yes | The subject line. |
| `html` | At least one of `html` or `text` | The HTML body. |
| `text` | At least one of `html` or `text` | The plain text body. PostHog makes it from `html` if you leave it out. |
| `from_` | No | The sender. The underscore avoids the `from` keyword. Without it, PostHog uses the project's default sender. |
| `reply_to` | No | One reply-to address or a list. |
| `distinct_id` | No | Links the email to your user's person in PostHog. |
| `idempotency_key` | No | Identifies this one email, so a retry never sends it twice. |
| `max_retries` | No | How many times the client retries this send. |
| `cc` | No | One copy address or a list. |
| `bcc` | No | One blind copy address or a list. |
| `attachments` | No | A list of files to attach. |
| `sensitive` | No | Marks the email as sensitive, for login links, reset tokens, or codes. |
| `tracking` | No | What PostHog tracks: opens, clicks, and engagement events. |

To send a [template from PostHog](#send-a-template-from-posthog) instead, pass `template_id` and `template_data` in place of `template_key`, `subject`, and the body.

Sending needs version 7.84.0 or later. `sensitive` and `tracking` need 7.89.0, and `cc`, `bcc`, and `attachments` need 7.91.0.

### Timeouts and retries

The client retries for you. It retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 second and then 2 seconds, or longer if the server's `Retry-After` asks for it. When `Retry-After` asks for more than 30 seconds, the client raises the error at once. Each request times out after 15 seconds.

To change this, set `email_request_timeout_seconds` and `email_request_max_retries` on the client, or `max_retries` on one send.

## Send from a background job

Send from a job queue when the email shouldn't slow down the request, such as an email address check after a signup. Let the queue own the retries:

- Pass `max_retries=0` to `send`, so that the client doesn't retry inside the task.
- Keep the idempotency key the same on every attempt.
- Finish the retries within 7 days. PostHog remembers an idempotency key for 7 days after it queues the email, so a later retry can send the email twice.
- Retry only the errors that a later attempt can fix. Every other code fails the same way again.

This example uses [Celery](https://docs.celeryq.dev). The task retries itself with `self.retry` for the codes that can pass later, and fails for good on every other code.

```python
from celery import shared_task
from posthog.emails import EmailError

# A later attempt can fix these. Any other code fails the same way again.
RETRYABLE_CODES = {"network_error", "idempotency_key_in_flight", "throttled", "delivery_unavailable"}


@shared_task(bind=True, max_retries=5)
def send_password_reset_email(self, user_id: str, email: str, reset_link: str, reset_request_id: str) -> str:
    try:
        result = posthog.emails.send(
            to=email,
            template_key="password-reset",
            subject="Reset your password",
            html=f'<p>Reset your password <a href="{reset_link}">here</a>.</p>',
            distinct_id=user_id,
            # The same key on every attempt, so a retried task never sends the email twice
            idempotency_key=f"password-reset-{reset_request_id}",
            # Celery retries the task, so the client doesn't retry on its own
            max_retries=0,
        )
    except EmailError as error:
        if error.code in RETRYABLE_CODES:
            # Waits 10, 20, 40, 80, then 160 seconds
            raise self.retry(exc=error, countdown=10 * 2**self.request.retries)
        # Any other code marks the task as failed, with no retry
        raise
    return result.id
```

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinct_id`, and leave it out for someone who isn't a user yet. See [link emails to your users](/docs/workflows/transactional/send-from-code#link-emails-to-your-users) for how PostHog records each case.

## Copies, attachments, and tracking

### Copies and attachments

Copies and attachments need version 7.91.0 or later.

Each file in `attachments` is a dictionary with `filename` and the file's bytes as `content`, and can also have `content_type` and `content_id`. The client uploads each file before it sends the email, and checks the limits first. If an upload fails, `send` raises an error, and PostHog sends nothing.

```python
from pathlib import Path

posthog.emails.send(
    to=user.email,
    template_key="receipt",
    subject="Your receipt",
    html=html,
    cc="billing@example.com",
    attachments=[
        {"filename": "receipt.pdf", "content": Path(pdf_path).read_bytes(), "content_type": "application/pdf"}
    ],
    distinct_id=str(user.id),
)
```

See [attachments](/docs/workflows/transactional/attachments) for the limits, inline images, and errors.

### Open and click tracking

`sensitive` and `tracking` need version 7.89.0 or later. For example, to track the clicks of an email with no secrets:

```python
posthog.emails.send(
    to="ada@example.com",
    template_key="order-shipped",
    subject="Your order shipped",
    html=html,
    sensitive=False,
    tracking={"clicks": True},
)
```

`tracking` takes `True`, `False`, or a dict with `"opens"`, `"clicks"`, and `"engagement"`. See [sensitive data and tracking](/docs/workflows/transactional/sensitive-data) for the defaults and rules.

`capture_engagement` is deprecated. Pass `tracking={"engagement": False}` instead, and don't set both.

## Send a template from PostHog

You can also keep an email in PostHog as a [template](/docs/workflows/transactional/templates), so your team edits the copy without a deploy. Send its template ID and the values for its variables:

```python
result = posthog.emails.send(
    to=email,
    template_id="<template_id>",
    template_data={"first_name": first_name, "reset_link": reset_link},
    distinct_id=user_id,
    idempotency_key=f"password-reset-{reset_request_id}",
)
```

A template send takes no subject, body, sender, copies, or attachments. The template sets them. Template sends work from version 7.81.2. A send with both `template_id` and `template_key` raises `TypeError`.

## Check an email's status

```python
from posthog.emails import EmailError

def email_bounced(message_id: str) -> bool | None:
    try:
        status = posthog.emails.get(message_id)
    except EmailError as error:
        if error.code == "not_found":
            # The first status can take a few seconds to arrive. Try again later.
            return None
        raise
    return status.status == "bounced"
```

`get` returns an `EmailStatus` with `id`, `status`, `created_at`, `status_at`, and `reason`. The two times are `datetime` objects.

The client doesn't retry a `not_found`, which you can get right after a send. Try again a few times with a short wait before you treat the email as missing.

See [status and troubleshooting](/docs/workflows/transactional/status) for what each status and reason means.

## Test without sending email

Pass your own HTTP transport to see exactly what your code sends, with no network call. This tests your integration, not delivery. To test delivery, send a real email to your own address and check the [**Log**](/docs/workflows/transactional#see-each-send) on the **Transactional** tab.

```python
import httpx
from posthog.emails import AsyncEmails

requests = []

def handler(request: httpx.Request) -> httpx.Response:
    requests.append(request)
    return httpx.Response(202, json={"message_id": "msg_1", "replayed": False})

async def test_send_password_reset():
    emails = AsyncEmails(
        "phs_test",
        host="https://us.posthog.com",
        http_client=httpx.AsyncClient(transport=httpx.MockTransport(handler)),
    )

    result = await emails.send(
        to="jane@example.com",
        template_key="password-reset",
        subject="Reset your password",
        html="<p>Reset your password.</p>",
        idempotency_key="password-reset-1",
    )

    assert result.id == "msg_1"
    assert requests[0].headers["Idempotency-Key"] == "password-reset-1"
```

For sync code, pass a `requests.Session` with a test adapter to `Emails(session=...)`. Any library that mocks `requests` or `httpx` works too.

## Use a proxy or self-hosted PostHog

On PostHog Cloud, the client sends email to your region's app host, even when `host` is an ingestion host such as `us.i.posthog.com`. If `host` is a reverse proxy or a self-hosted PostHog, set `app_host` to your PostHog app URL. The client doesn't send email requests to a host that might be a proxy.

When the client evaluates a flag locally, it still loads flag definitions from `host` with the secret key. If that host is a proxy that must not see the key, don't evaluate flags locally with this client.
