The [Elixir SDK](/docs/libraries/elixir) sends transactional emails from version 2.20.0. Your code sends the subject and HTML, so the email lives in your codebase. Before you start, you need a [verified sending domain](/docs/workflows/domain) and a project secret API key ([create an API key](/docs/workflows/transactional/send-from-code#create-an-api-key)). The [quick start](/docs/workflows/installation) sets up the key and sends a test email in a few minutes.

New to sending from code? Read [send emails from code](/docs/workflows/transactional/send-from-code) first.

## Install

Add `posthog` to your dependencies in `mix.exs`:

```elixir
def deps do
  [
    {:posthog, "~> 2.20"}
  ]
end
```

## Set up the client

Add your project secret API key to the PostHog config that your app already has. The project token keeps capturing events. The secret key sends email, so read it from the environment and keep it on your server.

```elixir file=config/runtime.exs
config :posthog,
  api_host: "<ph_client_api_host>",
  api_key: "<ph_project_token>",
  secret_key: System.fetch_env!("POSTHOG_PROJECT_SECRET_API_KEY"),
  # The SDK doesn't load flag definitions with the secret key
  enable_local_evaluation: false
```

Keep `enable_local_evaluation: false` unless your app [evaluates feature flags locally](/docs/feature-flags/local-evaluation). With local evaluation on, the SDK polls flag definitions with the secret key, and a key with only the **Transactional email** scope can't read them. If you do evaluate flags locally, give the key the **Feature flag** read scope too.

If your app sends through a reverse proxy or a self-hosted PostHog, see [use a proxy or self-hosted PostHog](#use-a-proxy-or-self-hosted-posthog).

## Send an email

```elixir
def send_password_reset(user, reset_link, reset_request_id) do
  case PostHog.Emails.send(
         to: user.email,
         # Names the email, so PostHog groups its sends and metrics
         template_key: "password-reset",
         subject: "Reset your password",
         html: ~s(<p>Reset your password <a href="#{reset_link}">here</a>. The link works for 1 hour.</p>),
         distinct_id: to_string(user.id),
         # Identifies this one email, so a retry never sends it twice
         idempotency_key: "password-reset-#{reset_request_id}"
       ) do
    {:ok, result} ->
      {:ok, result.id}

    # A %PostHog.Emails.Error{}. Branch on error.code
    {:error, error} ->
      {:error, error}
  end
end
```

For a longer email, render the HTML first with EEx, Phoenix templates, or another template engine, and pass the result as `html`.

`send/2` doesn't raise. It returns `{:ok, %PostHog.Emails.SendResult{}}` or `{:error, %PostHog.Emails.Error{}}`. `result.id` is the message ID. The error's `code` is one of the codes in the [errors table](/docs/workflows/transactional/retries-and-errors#what-to-retry). An option that the SDK refuses returns an `invalid_*` code before any request.

A `network_error` or a `503` doesn't mean that the email failed, because PostHog can still have queued it. Retry with the same idempotency key. If you resend the email through another email provider, the recipient can get it twice.

To send through a named PostHog instance instead of the default one, pass its name first: `PostHog.Emails.send(MyPostHog, options)`.

See [emails your code writes](/docs/workflows/transactional/from-code) for what each field does and the checks PostHog runs.

### Fields

| Field | Required | What it does |
| --- | --- | --- |
| `to` | Yes | The recipient's email address. |
| `template_key` | Yes | Names the email, so PostHog groups its metrics and sends. |
| `subject` | Yes | The subject line. |
| `html` | One of `html` or `text` | The HTML body. |
| `text` | One of `html` or `text` | The plain text body. PostHog makes it from `html` if you leave it out. |
| `from` | No | The sender. Without it, PostHog uses the project's default sender. |
| `reply_to` | No | One reply-to address or a list. |
| `distinct_id` | No | Links the email to your user's person in PostHog. Pass a string. |
| `idempotency_key` | No | Identifies this one email, so a retry never sends it twice. |
| `max_retries` | No | How many times the client retries this send. |
| `cc` | No | One copy address or a list. |
| `bcc` | No | One blind copy address or a list. |
| `attachments` | No | A list of files to attach. |
| `sensitive` | No | Marks the email as sensitive, for login links, reset tokens, or codes. |
| `tracking` | No | What PostHog tracks: opens, clicks, and engagement events. |

To send a [template from PostHog](#send-a-template-from-posthog) instead, pass `template_id` and `template_data` in place of `template_key`, `subject`, and the body.

Sending needs version 2.20.0 or later. `sensitive` and `tracking` need 2.21.0, and `cc`, `bcc`, and `attachments` need 2.22.0.

### Timeouts and retries

The SDK retries for you. It retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 second and then 2 seconds, or as long as the server's `Retry-After` asks, up to 30 seconds. When `Retry-After` asks for more than 30 seconds, the SDK returns the error at once. Each request times out after 15 seconds, and a send blocks the calling process until it finishes.

To change this, set `email_request_timeout_ms` and `email_request_max_retries` in the config, or `max_retries` on one send.

## Send from a background job

Send from a job queue when the email shouldn't slow down the request, such as an email address check after a signup. Let the queue own the retries:

- Set `max_retries: 0`, so that the SDK doesn't retry inside the job.
- Keep the idempotency key the same on every attempt.
- Finish the retries within 7 days. PostHog remembers an idempotency key for 7 days after it queues the email, so a later retry can send the email twice.
- Retry only the errors that a later attempt can fix. Every other code fails the same way again.

This example uses [Oban](https://hexdocs.pm/oban). `{:error, reason}` tells Oban to retry the job, up to `max_attempts`. `{:cancel, reason}` stops it for good.

```elixir
defmodule MyApp.Workers.PasswordResetEmail do
  use Oban.Worker, queue: :emails, max_attempts: 10

  # A later attempt can fix these. Any other code fails the same way again.
  @retryable_codes ["network_error", "idempotency_key_in_flight", "throttled", "delivery_unavailable"]

  @impl Oban.Worker
  def perform(%Oban.Job{args: args}) do
    # Oban stores args as JSON, so the keys are strings
    %{
      "user_id" => user_id,
      "email" => email,
      "reset_link" => reset_link,
      "reset_request_id" => reset_request_id
    } = args

    case PostHog.Emails.send(
           to: email,
           template_key: "password-reset",
           subject: "Reset your password",
           html: ~s(<p>Reset your password <a href="#{reset_link}">here</a>.</p>),
           distinct_id: to_string(user_id),
           # The same key on every attempt, so a retried job never sends the email twice
           idempotency_key: "password-reset-#{reset_request_id}",
           # Oban retries the job, so the SDK doesn't retry on its own
           max_retries: 0
         ) do
      {:ok, _result} ->
        :ok

      {:error, %PostHog.Emails.Error{code: code} = error} when code in @retryable_codes ->
        {:error, error}

      {:error, error} ->
        {:cancel, error}
    end
  end
end
```

Add the job where your app creates the reset request:

```elixir
%{
  user_id: user.id,
  email: user.email,
  reset_link: reset_link,
  reset_request_id: reset_request.id
}
|> MyApp.Workers.PasswordResetEmail.new()
|> Oban.insert()
```

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinct_id`, as a string, and leave it out for someone who isn't a user yet. The SDK doesn't take it from `PostHog.set_context/2`. See [link emails to your users](/docs/workflows/transactional/send-from-code#link-emails-to-your-users) for how PostHog records each case.

## Copies, attachments, and tracking

### Copies and attachments

From version 2.22.0, `send/2` takes `cc`, `bcc`, and `attachments`. Each file in `attachments` is a map with `filename` and the file's bytes as `content`, and can also have `content_type` and `content_id`. The SDK uploads each file before it sends the email, and checks the limits first. If an upload fails, `send` returns an error, and PostHog sends nothing.

```elixir
PostHog.Emails.send(
  to: user.email,
  template_key: "receipt",
  subject: "Your receipt",
  html: html,
  cc: "billing@example.com",
  attachments: [
    %{filename: "receipt.pdf", content: File.read!(pdf_path), content_type: "application/pdf"}
  ],
  distinct_id: to_string(user.id)
)
```

See [attachments](/docs/workflows/transactional/attachments) for the limits, inline images, and errors.

### Open and click tracking

From version 2.21.0, `send/2` takes `sensitive` and `tracking`. For example, to track the clicks of an email with no secrets:

```elixir
PostHog.Emails.send(
  to: "ada@example.com",
  template_key: "order-shipped",
  subject: "Your order shipped",
  html: html,
  sensitive: false,
  tracking: %{clicks: true}
)
```

`tracking` takes `true`, `false`, or a map with `:opens`, `:clicks`, and `:engagement`. See [sensitive data and tracking](/docs/workflows/transactional/sensitive-data) for the defaults and rules.

`capture_engagement` is deprecated. Pass `tracking: %{engagement: false}` instead, and don't set both.

## Send a template from PostHog

You can also keep an email in PostHog as a [template](/docs/workflows/transactional/templates), so your team edits the copy without a deploy. Send its template ID and the values for its variables:

```elixir
PostHog.Emails.send(
  to: user.email,
  template_id: "<template_id>",
  template_data: %{first_name: user.first_name, reset_link: reset_link},
  distinct_id: to_string(user.id),
  idempotency_key: "password-reset-#{reset_request_id}"
)
```

A template send takes no subject, body, sender, copies, or attachments. The template sets them.

## Check an email's status

```elixir
def email_bounced(message_id) do
  case PostHog.Emails.get(message_id) do
    {:ok, %PostHog.Emails.Status{status: status}} ->
      {:ok, status == "bounced"}

    # The first status can take a few seconds to arrive. Try again later.
    {:error, %PostHog.Emails.Error{code: "not_found"}} ->
      {:ok, nil}

    {:error, error} ->
      {:error, error}
  end
end
```

`get/2` returns `{:ok, %PostHog.Emails.Status{}}` or `{:error, %PostHog.Emails.Error{}}`. The status has `id`, `status`, `created_at`, `status_at`, and `reason`.

The SDK doesn't retry a `not_found`, which you can get right after a send. Try again a few times with a short wait before you treat the email as missing.

See [status and troubleshooting](/docs/workflows/transactional/status) for what each status and reason means.

## Test without sending email

Every request goes through the config's `api_client_module`. Wrap the default client with a [`Req.Test`](https://hexdocs.pm/req/Req.Test.html) plug to see exactly what your code sends, with no network call. `Req.Test` needs the `plug` package, which a Phoenix app already has. This tests your integration, not delivery. To test delivery, send a real email to your own address and open the send in the [**Log**](/docs/workflows/transactional#see-each-send) tab.

`test_mode: true` keeps captured events in memory, but it doesn't stop email requests. Use the plug for those.

```elixir
defmodule MyApp.PostHogTestClient do
  # The default client, with Req.Test in place of the network
  @behaviour PostHog.API.Client

  @impl true
  def client(api_key, api_host) do
    default = PostHog.API.Client.client(api_key, api_host)
    %{default | client: Req.merge(default.client, plug: {Req.Test, __MODULE__})}
  end

  @impl true
  defdelegate request(client, method, url, opts), to: PostHog.API.Client
end

defmodule MyApp.PasswordResetEmailTest do
  use ExUnit.Case, async: true

  setup do
    config =
      PostHog.Config.validate!(
        supervisor_name: MyApp.TestPostHog,
        api_key: "phc_test",
        secret_key: "phs_test",
        enable_local_evaluation: false,
        api_client_module: MyApp.PostHogTestClient
      )

    start_supervised!({PostHog.Supervisor, config})
    :ok
  end

  test "sends the email with its idempotency key" do
    test_pid = self()

    Req.Test.expect(MyApp.PostHogTestClient, fn conn ->
      {:ok, body, conn} = Plug.Conn.read_body(conn)
      send(test_pid, {:email_request, Plug.Conn.get_req_header(conn, "idempotency-key"), body})
      Req.Test.json(conn, %{message_id: "msg_1", replayed: false})
    end)

    assert {:ok, %PostHog.Emails.SendResult{id: "msg_1"}} =
             PostHog.Emails.send(MyApp.TestPostHog,
               to: "jane@example.com",
               template_key: "password-reset",
               subject: "Reset your password",
               text: "Reset it here.",
               idempotency_key: "password-reset-1"
             )

    assert_received {:email_request, ["password-reset-1"], body}
    assert %{"to" => "jane@example.com"} = Jason.decode!(body)
  end
end
```

## Use a proxy or self-hosted PostHog

On PostHog Cloud, the SDK sends email to your region's app host, even when `api_host` is an ingestion host such as `us.i.posthog.com`. If `api_host` is a reverse proxy or a self-hosted PostHog, set `app_host` to your PostHog app URL. Without it, a send returns the code `missing_app_host`, because the SDK doesn't send the secret key to a host that might be a proxy.

From version 2.23.2, the SDK sends to `/api/messaging/`. A self-hosted PostHog from before 2026-11-18 answers those requests with a `404`.

With local evaluation on, the SDK still polls flag definitions from `api_host` with the secret key. If the proxy must not see the key, keep `enable_local_evaluation: false`.
