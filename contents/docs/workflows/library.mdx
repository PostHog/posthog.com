Our library lets you create reusable message templates for your workflows. You can access it from the **Library** tab in Workflows.

Templates are displayed in a grid view with visual HTML previews, making it easy to see what each email looks like at a glance. Use the search bar and **Created by** filter to find templates quickly.

## Workflow templates

You can save workflows as reusable templates to share across your team. When saving a workflow as a template, select a scope to control visibility:

| Scope            | Description                                                   |
| ---------------- | ------------------------------------------------------------- |
| **Project**      | Template is only visible within the current project (default) |
| **Organization** | Template is visible to all projects within your organization  |
| **Global**       | Official PostHog templates (staff-only)                       |

Organization-scoped templates are accessible to all teams within the same organization. Any team member can use and update these shared templates. Templates remain isolated to their organization and aren't visible to other organizations.

## Liquid and merge tags

All template types support [Liquid templating](https://shopify.github.io/liquid/) to personalize your messages with user properties and data. You can type liquid directly, or use the merge tag dropdown in your message templates, which will show you the entire list of available person properties (see email example below).

<CalloutBox icon="IconInfo" title="Tip: Use default values with Liquid" type="fyi">

When using Liquid with existing user properties, you should include a default value if the property could be null or may not exist. For example:

```liquid
{{ person.name | default: 'there' }}
```

Use single quotes around the fallback value. The email builder serializes templates to JSON, which escapes double quotes and causes a Liquid `TokenizationError`.

This ensures your message displays correctly even when a property is missing.

</CalloutBox>

For a property whose name starts with `$`, such as `$email`, use brackets and single quotes: `{{ person.properties['$email'] }}`. Dot notation like `{{ person.properties.$email }}` doesn't work with these properties.

### Email merge tags

In addition to person properties, PostHog provides these system merge tags for email templates:

| Merge tag                       | Description                                                                                                                                                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{{unsubscribe_url}}`           | Links to a page where recipients can manage their email preferences. When [email tracking consent](/docs/workflows/engagement-events#team-level-tracking-consent) is enabled, this page also includes an option to manage open and click tracking consent. |
| `{{unsubscribe_url_one_click}}` | Enables RFC 8058-compliant one-click unsubscribe. When email clients send a POST request to this URL, recipients are automatically unsubscribed from all marketing emails. When clicked directly, it displays an unsubscribe confirmation page.       |

Use the one-click unsubscribe URL to improve email deliverability and comply with email regulations like CAN-SPAM. Most modern email clients display a prominent unsubscribe button when they detect proper one-click unsubscribe headers.

### New email editor

<CalloutBox icon="IconFlask" title="The new email editor is in beta" type="action">

The new email editor isn't on for every project yet, and it might change while we work on it.
If new emails open in the drag-and-drop builder above, it isn't on for your project.

</CalloutBox>

The new email editor lets you write an email the way you write a document, and add blocks as you go. It changes how you draft an email, and sending stays the same.

Blank emails and the sample in a new template open in the new editor. Existing emails stay in the old editor until you [move them](#try-the-new-editor-on-an-existing-email).

You can add these blocks: text, headings, images, buttons, columns (up to four), dividers, spacers, lists, quotes, custom HTML, and an unsubscribe link. Use the **Page style** panel for the email's background, fonts, and preview text.

To add a variable, type `{{ person.properties.name }}` or pick one from the list. Click the variable to set **Fallback, if it's empty**. The canvas shows the variable, and doesn't show its fallback. A warning on a variable means that it will probably be empty unless you add a fallback.

To show blocks on a condition, write `{% if %}` and `{% endif %}` on lines of their own, around those blocks.

#### Try the new editor on an existing email

<CalloutBox icon="IconWarning" title="Duplicate the template first" type="caution">

Saving after you move an email is permanent. It replaces the old editor's version, and PostHog can't restore it. If you edit the email in the old editor later, it opens there as one custom HTML block.

</CalloutBox>

1. Duplicate the template, and open the copy.
2. Click **Try the new editor**. PostHog shows the current email and the new version side by side.
3. Check that the new version looks right. Small differences are possible, such as a dashed divider that becomes solid.
4. Click **Use the new editor**, and edit the email.
5. Save the email. If you close the email without saving, nothing changes.

A move keeps text, headings, buttons, images, dividers, columns, HTML blocks, and the unsubscribe block. These change:

- **Text with styling the new editor can't hold** becomes a custom HTML block. It looks the same, but you edit it as HTML.
- **Social icons** become a custom HTML block.
- **Button colors on hover** aren't kept. PostHog warns you before you move the email.

#### What stays on the old editor

PostHog doesn't move an email that uses any of these, and tells you which ones it found. Nothing changes.

- Menus, videos, countdown timers, carousels, and tables
- Custom blocks, other than the unsubscribe link
- Rows or blocks shown on a condition, or hidden on some screen sizes
- Right-to-left text
- Row background images
- Buttons or columns with a border that isn't the same solid style on all sides

These also use the old editor:

- Emails in [destinations](/docs/data-pipelines/destinations).
- Emails you start from a template made in the old editor.
- Emails changed through the API or [MCP](#create-templates-with-mcp) after you saved them in the new editor. The email opens in the old editor as one custom HTML block, and the API or MCP change is what's kept.

### Disabling link click tracking

Links in an email are rewritten for click tracking, which powers the `$workflows_email_link_clicked` [engagement event](/docs/workflows/engagement-events).

If you need a link to reach its destination exactly as written, add an HTML block and mark the anchor with either `clicktracking="off"` or `data-ph-no-track`:

```html
<a href="https://example.com/your-link" data-ph-no-track>Open link</a>
```

The attribute must be on the `<a>` tag itself, not a child element. Links marked this way keep their original URL and won't produce click events. Use this for app deep links and mobile universal links, which stop resolving to the app once they're rewritten.

### Testing templates

It's best practice to test a message in a workflow before starting the workflow. This helps ensure your template displays correctly with real user data and that all Liquid variables resolve properly.

### Create templates with MCP

You can create and manage email templates programmatically using the [PostHog MCP server](/docs/model-context-protocol). AI coding assistants like Cursor and Claude can design templates using the same format as the visual editor, so templates created via MCP are fully editable in the drag-and-drop builder.

MCP tools for email templates:

- `workflows-create-email-template` – Create a new email template
- `workflows-get-email-template` – Fetch a template for editing
- `workflows-update-email-template` – Update an existing template
- `workflows-list-email-templates` – List all templates in the library
- `workflows-show-email-template` – Preview a rendered template

See [MCP use cases](/docs/model-context-protocol/use-cases) for example prompts.

### Edit workflows with MCP

You can make surgical edits to a draft workflow's graph using the [PostHog MCP server](/docs/model-context-protocol). Instead of re-transmitting every action and edge, send a small list of id-addressed operations that apply atomically – the graph is validated before saving.

MCP tools for workflow graph editing:

- `workflows-patch-graph` – Apply operations to update, add, or remove actions and edges in a draft workflow

Supported operations include `update_action` (deep-merges a patch into an existing node), `add_action`, `remove_action` (auto-reconnects edges), `add_edge`, `remove_edge`, and `replace_action_edges`.

See [MCP use cases](/docs/model-context-protocol/use-cases#edit-workflow-graphs) for example prompts.
