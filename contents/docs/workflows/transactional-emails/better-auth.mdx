[Better Auth](https://www.better-auth.com) calls your code when a user needs to verify their email address or reset their password. This guide sends those emails as [transactional emails](/docs/workflows/transactional-emails) with the [Node.js SDK](/docs/workflows/transactional-emails/node), from version 5.71.0. You write the email in your code, and Better Auth answers the request without waiting for the send.

Before you start, [create a project secret API key](/docs/workflows/transactional-emails#create-an-api-key) and [set up a sender](/docs/workflows/configure-channels).

## Install

```bash
npm install posthog-node@5
```

The example below runs on Vercel, so it also needs `@vercel/functions`:

```bash
npm install @vercel/functions
```

## Set up the client

Create one PostHog client on your server. Keep the secret key on the server, never in client-side code.

```ts
// lib/posthog.ts
import { PostHog } from "posthog-node"

export const posthog = new PostHog("<ph_project_token>", {
    host: "<ph_client_api_host>",
    secretKey: process.env.POSTHOG_PROJECT_SECRET_API_KEY,
    // This client only sends email, so it doesn't poll flag definitions with the secret key
    enableLocalEvaluation: false,
})
```

If your app already has a PostHog client, reuse it and set `secretKey` on it. See [set up the client](/docs/workflows/transactional-emails/node#set-up-the-client) for local evaluation and hosts.

## Send the emails

Give Better Auth a `sendVerificationEmail` and a `sendResetPassword` function. Each one starts the send and returns at once:

```ts
// lib/auth.ts
import { betterAuth } from "better-auth"
import { waitUntil } from "@vercel/functions"
import type { SendCodeEmailOptions } from "posthog-node"
import { posthog } from "./posthog"

function sendAuthEmail(email: SendCodeEmailOptions) {
    // The request doesn't wait for the send. waitUntil keeps the function running until it finishes
    waitUntil(
        // The link signs the user in, so PostHog keeps it as it is and doesn't track its clicks
        posthog.emails.send({ ...email, sensitive: true }).then(({ error }) => {
            if (error) {
                // An EmailError. Branch on error.code
                console.error("Better Auth email not sent", error)
            }
        })
    )
}

export const auth = betterAuth({
    emailVerification: {
        sendOnSignUp: true,
        sendVerificationEmail: async ({ user, url }) => {
            sendAuthEmail({
                to: user.email,
                distinctId: user.id,
                templateKey: "verify-email",
                subject: "Verify your email address",
                text: `Click the link to verify your email: ${url}`,
            })
        },
    },
    emailAndPassword: {
        enabled: true,
        sendResetPassword: async ({ user, url }) => {
            sendAuthEmail({
                to: user.email,
                distinctId: user.id,
                templateKey: "reset-password",
                subject: "Reset your password",
                text: `Click the link to reset your password: ${url}`,
            })
        },
    },
})
```

- **Background sends** - Better Auth waits for these functions in some requests, such as a request for a new verification email. Because they return before the send finishes, the send doesn't change the response time or the response, so neither one shows whether an account exists. Sign-up has its own check: with `requireEmailVerification: true`, Better Auth answers a sign-up for an address that already has an account the same way as a sign-up for a new one. On Cloudflare Workers, use the request's `ctx.waitUntil` in place of `waitUntil`. On a long-running Node.js server, the send finishes after the response anyway, so remove the `waitUntil` call and keep the send inside it.
- **Errors** - `send` returns `{ data, error }` and doesn't throw. `sendAuthEmail` logs the `error`, with the `code` from the [errors table](/docs/workflows/transactional-emails#errors). A failed send never fails the request.
- **Sensitive** - `sensitive: true` keeps the link as it is, so it doesn't go through a click tracking redirect, and keeps the subject off engagement events. PostHog still counts opens. See [open and click tracking](/docs/workflows/transactional-emails/node#open-and-click-tracking).
- **Retries** - The client retries network errors, rate limits, an in-flight idempotency key, and a `503` with the same idempotency key, so a retry never sends the email twice.
- **Users** - `distinctId: user.id` records each email and its [engagement events](/docs/workflows/engagement-events) on the user's person. Pass the same ID to `identify()`.
- **Key** - `templateKey` names the email, so PostHog groups each email's metrics and sends under it.
- **Sender** - PostHog sends from the project's default sender. To send from another verified address, add `from`, such as `from: "Hedgebox <security@example.com>"`.
- **HTML** - To send HTML, pass `html` next to `text` or in its place. For a [React Email](https://react.email) component, see [send content from your code](/docs/workflows/transactional-emails/node#send-content-from-your-code).

## Send from a job queue

When a job queue already sends your app's emails, add a job when Better Auth calls your function. Don't wait for the queue either, so that the response time doesn't show whether an account exists:

```ts
sendResetPassword: async ({ user, url }) => {
    waitUntil(
        emailQueue.add("reset-password", { to: user.email, userId: user.id, url }).catch((error) => {
            console.error("Better Auth email not queued", error)
        })
    )
},
```

Send the email in the job as [send from a background job](/docs/workflows/transactional-emails/node#send-from-a-background-job) shows, so that the queue retries only the errors that a later attempt can fix. Pass `sensitive: true`, and build the idempotency key from the job's ID, such as `reset-password-${job.id}`, because the job keeps its ID on every attempt. Don't put the reset token or the link in the key.

## Check that it works

Sign up with your own email address, and open the link in the email. Each email appears under its key on the **Transactional** page in PostHog, with its sends and its [status](/docs/workflows/transactional-emails#check-an-emails-status).
