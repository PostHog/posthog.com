Use the API to send transactional emails from any language. The SDKs for [Node.js](/docs/workflows/transactional-emails/node), [Python](/docs/workflows/transactional-emails/python), [Go](/docs/workflows/transactional-emails/go), [.NET](/docs/workflows/transactional-emails/dotnet), [Rust](/docs/workflows/transactional-emails/rust), [Ruby](/docs/workflows/transactional-emails/ruby), [Elixir](/docs/workflows/transactional-emails/elixir), and [PHP](/docs/workflows/transactional-emails/php) call this API, and retry with idempotency keys for you. If your language has an SDK, start there. The examples on this page show each SDK next to cURL.

You need a [transactional email](/docs/workflows/transactional-emails#create-a-transactional-email) and a [project secret API key](/docs/workflows/transactional-emails#create-an-api-key) first. The [quick start](/docs/workflows/transactional-emails#send-your-first-email) sets up both and sends a test email in a few minutes.

## Send an email

```
POST https://us.posthog.com/api/projects/@current/messaging/send/email/
```

- **Host** - Use `https://us.posthog.com` or `https://eu.posthog.com`, the host where you log in to PostHog. Don't use an ingestion host like `us.i.posthog.com`. If you self-host PostHog, use the URL of your instance.
- **Project** - `@current` is the project that the key belongs to. You can use your project ID instead.

### Request

Send these headers:

| Header | Value |
| --- | --- |
| `Authorization` | `Bearer` followed by your project secret API key |
| `Content-Type` | `application/json` |
| `Idempotency-Key` | Optional. A unique key for this email. See [retry safely](/docs/workflows/transactional-emails#retry-safely-with-an-idempotency-key). |

Send a JSON body with these fields:

| Field | Required | Description |
| --- | --- | --- |
| `template_id` | Yes | The ID of the transactional template to send. |
| `to` | Yes | The email address of the recipient. One address for each request. |
| `message_data` | No | An object with the values for the template's `{{ variables.* }}` placeholders. For example, `{"reset_link": "https://example.com/reset"}` fills `{{ variables.reset_link }}`. The template can't read person properties, so pass all the data that the email needs here. |
| `distinct_id` | No | The distinct ID of the recipient's person. PostHog records the send and its [engagement events](/docs/workflows/engagement-events) against this person. Pass the distinct ID that you pass to `identify()`. See [link emails to your users](#link-emails-to-your-users). |

In the template, use the same names that you send in `message_data`:

```liquid
Hi {{ variables.first_name }}, use this link to reset your password: {{ variables.reset_link }}
```

### Response

A successful request returns `202 Accepted`:

```json
{
  "message_id": "01963d8a-6f2c-7d4e-9b1a-3c5e8f2a7b10",
  "replayed": false
}
```

A `202` means that PostHog queued the email. It doesn't mean that the email was delivered. To see what happened to the email, [check its status](#check-an-emails-status) with its `message_id`, or open the template's **Sends** tab.

`replayed` is `true` when an earlier request with the same `Idempotency-Key` already queued this email. In that case, PostHog sent no new email, and `message_id` is the ID of the first send.

Each SDK page shows how to set up the client and handle errors.

The older route, `POST /api/projects/@current/messaging_templates/:template_id/send/`, still works. It takes the template ID in the URL and the distinct ID as `identifiers.distinct_id`.

When a send fails, the response carries a `code`. See [errors](/docs/workflows/transactional-emails#errors), the [checks for content from your code](#checks-for-content-from-your-code), and the [checks for files](#checks-for-files).

### `delivery_unavailable`

A `503` with the code `delivery_unavailable` means that PostHog couldn't confirm that it queued the email. It doesn't mean that the email failed, because PostHog can still send it. Retry with the same `Idempotency-Key`. If you resend the email through another email provider, the recipient can get it twice. The SDKs retry a `503` for you.

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinct_id`. This is usually your user's ID. PostHog then records the email's [engagement events](/docs/workflows/engagement-events), such as sent, opened, and clicked, on that user's person, in the same timeline as their product events.

- **No distinct ID** - PostHog records the email on a person whose distinct ID is the email address. That's a different person from your user, unless your app identifies users by their email address.
- **Not a user yet** - For an invite, or an email address check before the account exists, leave `distinct_id` out.

## Send content from your code

You can also send the subject and the body from your code, without a template in PostHog. Use this when your code renders the email. For a [React Email](https://react.email) component, render it to HTML with `render` from `@react-email/render`, and send the result as `html`. Name the email with `template_key`, and send the content in the body. Use the same `POST` route and headers as for a [template send](#send-an-email).

| Field | Required | Description |
| --- | --- | --- |
| `template_key` | Yes | A name for this email, such as `password-reset`. It has at most 400 letters, digits, hyphens (`-`), and underscores (`_`). PostHog groups the metrics and the sends of this email under the key, so use the same key every time you send this email. |
| `to` | Yes | The email address of the recipient. |
| `distinct_id` | No | The distinct ID of the recipient's person, as for a template send. See [link emails to your users](#link-emails-to-your-users). |
| `subject` | Yes | The subject of the email. |
| `html` | One of `html` and `text` | The HTML body. PostHog sends it as you wrote it and renders no placeholders. |
| `text` | One of `html` and `text` | The plain-text body. If you leave it out, PostHog makes it from `html`. |
| `from` | No | The sender, as `security@example.com` or `Hedgebox <security@example.com>`, on a domain that your project verified. If you leave it out, PostHog uses the project's default sender. |
| `reply_to` | No | A list of up to 10 addresses that replies go to, without a display name. |
| `capture_engagement` | No | Whether PostHog captures the email's [engagement events](/docs/workflows/engagement-events). The default is `true`. Send `false` to turn capture off for this email. If the project's **Capture email engagement events** setting is off, PostHog captures nothing, whatever you send. |

A request has `template_id` or `template_key`, not both. Content from your code takes no `message_data`, because PostHog renders nothing. A template send takes none of `subject`, `html`, `text`, `from`, `reply_to`, and `capture_engagement`, because the template uses its own settings. PostHog returns a `400` that names the field in `attr`.

If the `to` address is on the [suppression list](/docs/workflows/opt-outs#the-suppression-list), PostHog sends nothing and returns `recipient_suppressed`.

The response is the same `202` as for a template send. A retry with the same `Idempotency-Key` is the [same request](/docs/workflows/transactional-emails#retry-safely-with-an-idempotency-key) when every field in the table above has the same value as in the first request. PostHog also compares the sender that it chose: if you leave out `from` and the project's default sender changes before the retry, PostHog returns `idempotency_key_reused`.

### Copies and attachments

Content from your code also takes these fields. A template send takes none of them, because the template uses its own settings.

| Field | Required | Description |
| --- | --- | --- |
| `cc` | No | A list of up to 10 addresses that get a copy, without a display name. |
| `bcc` | No | A list of up to 10 addresses that get a hidden copy, without a display name. The other recipients don't see them. |
| `attachments` | No | A list of up to 10 files that you [uploaded first](#send-files). Each file is an object with `sha256`, `filename`, and optionally `content_type`, such as `application/pdf`, and `content_id`. |

- **Size** - An email can have 10 files and 40 MB per message after Base64 encoding, about 29 MB of files. Base64 encoding makes each file about a third larger, and the email's HTML and text count too, also at their Base64 size. One file can use all of the limit.
- **Inline images** - Set `content_id` on a file, and use it in the HTML as `<img src="cid:logo">`.
- **Blocked files** - PostHog refuses file types that mailbox providers block, such as `.exe`, and a filename with a path.
- **Viruses** - PostHog's email provider scans each file. If it finds a virus, the email gets the status `failed` with the reason `provider_rejected`.
- **SDKs** - The SDKs hash, upload, and attach the files for you. Give each file's bytes to the SDK.
- **Older PostHog versions** - A PostHog version that doesn't take these fields yet refuses the send with a `400` that names the field. PostHog then sends nothing, and never sends the email without the field.

### Send files

The files of an email go to PostHog before the email. Your SDK does these steps for you. With the API, do them yourself:

1. **Hash each file.** Get the SHA-256 of the file's bytes, as 64 lowercase hex characters, and the size of the file in bytes.
2. **Ask where to upload.** Send the hash and the size of each file of the email to the [upload route](#ask-where-to-upload). PostHog answers `present` for a file that it already has, and `upload` with an upload URL for each other file.
3. **Upload the files.** Send the bytes of each `upload` file to its URL. Don't send your PostHog API key with the upload.
4. **Send the email.** When all uploads are successful, send the email. Put the `sha256` and the `filename` of each file in `attachments`.

Ask where to upload before each send, also for a file that you sent before. PostHog answers `present` for a file that it still has, so a file that you send to many recipients, such as your terms, goes up only one time.

#### Ask where to upload

```
POST https://us.posthog.com/api/projects/@current/messaging/attachments/uploads/
```

Send the `Authorization` and `Content-Type` headers of a [send](#request). The key needs the `transactional_email:write` scope. Send a JSON body with a `files` list of 1 to 10 files, all for one email:

| Field | Required | Description |
| --- | --- | --- |
| `sha256` | Yes | The SHA-256 of the file's bytes, as 64 lowercase hex characters. |
| `size` | Yes | The size of the file in bytes, at least 1. |

```bash
curl -X POST "https://us.posthog.com/api/projects/@current/messaging/attachments/uploads/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "files": [
      {"sha256": "d00ca3c2296eace098658a8576dafec8a959f5da536a51c8f9d060c00e427252", "size": 48213},
      {"sha256": "aba4cc7ef2a4423000b9ec5269993717c92b29f092eac5b791c7e9ce24a69306", "size": 120544}
    ]
  }'
```

A successful request returns `200`, with one answer for each file, in the order of the request:

```json
{
  "files": [
    {
      "sha256": "d00ca3c2296eace098658a8576dafec8a959f5da536a51c8f9d060c00e427252",
      "status": "upload",
      "url": "https://<bucket>.s3.us-east-1.amazonaws.com/<key>?X-Amz-Algorithm=AWS4-HMAC-SHA256&...",
      "method": "PUT",
      "headers": {
        "Content-Length": "48213",
        "x-amz-checksum-sha256": "0AyjwilurOCYZYqFdtr+yKlZ9dpTalHI+dBgwA5CclI="
      },
      "url_expires_at": "2026-11-10T09:15:00Z"
    },
    {
      "sha256": "aba4cc7ef2a4423000b9ec5269993717c92b29f092eac5b791c7e9ce24a69306",
      "status": "present",
      "expires_at": "2026-12-16T09:00:00Z"
    }
  ]
}
```

- **`present`** - PostHog has this file from an earlier upload by your project. Upload nothing. `expires_at` is the time when PostHog deletes the file, if no send uses it before then.
- **`upload`** - Send the file's bytes to `url`, with `method` and with the `headers` exactly as given, before `url_expires_at`. The URL is valid for 15 minutes. The bytes of each `upload` file count toward your project's daily upload limit when PostHog gives you the URL, even if you don't upload the file. Upload each file soon after you ask.

#### Upload a file

```bash
curl -X PUT "<url>" \
  -H "Content-Length: 48213" \
  -H "x-amz-checksum-sha256: 0AyjwilurOCYZYqFdtr+yKlZ9dpTalHI+dBgwA5CclI=" \
  --data-binary @invoice-1042.pdf
```

A successful upload returns `200`. The upload fails with a `400` or a `403` when the bytes don't agree with `size` and `sha256`, when a header isn't as given, or when the URL expired. Ask where to upload again to get a new URL. Don't send the email until all uploads are successful.

#### Allow the upload host

The upload goes to Amazon S3, not to the PostHog host. The SDKs upload there too. If your network limits outgoing traffic, let your servers connect with HTTPS to the host of `url`:

| PostHog Cloud | Upload host |
| --- | --- |
| US | A host that ends in `.s3.us-east-1.amazonaws.com` |
| EU | A host that ends in `.s3.eu-central-1.amazonaws.com` |

### Checks for files

These checks apply to the upload route and to sends with `attachments`, in addition to the [errors](/docs/workflows/transactional-emails#errors) of every send. After a `400`, a `404`, or a `429`, PostHog sends nothing. The body of a `400` or a `429` has `why` and `fix` in addition to `code` and `attr`, which tell you the cause and what to do.

| Status | Code | Route | Cause | What to do |
| --- | --- | --- | --- | --- |
| `400` | `field_not_accepted` | Both | PostHog can't send files for your project yet. | Send the email without files. |
| `404` | `not_found` | Upload | Content from your code is off for your project, or your PostHog version has no upload route. | Send the email without files. |
| `400` | `too_many_attachments` | Both | The email has more than 10 files. | Send 10 files at most. Link to other files from the email body. |
| `400` | `message_too_large` | Both | The email is over 40 MB after Base64 encoding. On the upload route, `attr` names the largest file, such as `files__1__size`. | Send fewer or smaller files, or link to large files from the email body. |
| `400` | `attachment_not_uploaded` | Send | Your project has no uploaded file with this SHA-256. The upload didn't finish, the file expired, or a different project uploaded it. `attr` names the file, such as `attachments__0__sha256`. | Ask where to upload again, upload the file, and send the email again. |
| `400` | `blocked_file_type` | Send | Mailbox providers block this file type, such as `.exe`. | Send a different file type, or link to the file from the email body. |
| `400` | `unsafe_filename` | Send | `filename` has a path or a line break. | Send only the file name, such as `invoice.pdf`. |
| `400` | `not_mime_type` | Send | `content_type` isn't a MIME type. | Send a type such as `application/pdf`, or leave out `content_type`. |
| `400` | `unsafe_content_id` | Send | `content_id` has `<`, `>`, or a line break. | Send only the ID, such as `logo`. |
| `400` | `content_too_large` | Both | The request body is over 20 MB. | Make the request smaller. Files go to the upload URL, never in the request body. |
| `429` | `upload_quota_exceeded` | Upload | Your project asked to upload all the file bytes that it can upload today. A file counts when PostHog gives you its upload URL, even if you don't upload it, and again each time that you ask for a new URL. The day starts at midnight UTC. | Send files that PostHog already has, because they don't count. Link to new files from the email body. Or ask again after midnight UTC. |
| `503` | `delivery_unavailable` | Both | PostHog couldn't get to its file storage. On a send, it can also mean that PostHog couldn't confirm that it queued the email, so PostHog can still send it. See [`delivery_unavailable`](#delivery_unavailable). | Send the same request again after a short wait. For a send, use the same `Idempotency-Key`, so that the email doesn't go out twice. |

Other problems with `attachments` or `files`, such as a hash that isn't 64 lowercase hex characters, return the code `invalid_request`, and `attr` names the field.

### Checks for content from your code

These checks apply to content from your code, in addition to the [errors](/docs/workflows/transactional-emails#errors) of every send. PostHog sends nothing when a check fails.

| Status | Code | Cause | What to do |
| --- | --- | --- | --- |
| `400` | A code for the field, such as `required` or `invalid` | A field is missing or breaks a rule above, or PostHog doesn't take the field. The `type` is `validation_error`, and `attr` names the field, such as `subject`. | Fix the field. If the field comes from a newer SDK, update PostHog or leave the field out. |
| `400` | `sender_not_verified` | No verified sender of the project can send from the `from` address. Or the request has no `from`, and the project has no verified default sender. | Send from an address on a verified domain, or [set a default sender](/docs/workflows/configure-channels) and leave out `from`. |

## Check an email's status

To find out what happened to an email, read its status with the `message_id` from the send:

```
GET https://us.posthog.com/api/projects/@current/messaging/emails/:message_id/
```

Send the same `Authorization` header as for a send. The key needs the `transactional_email:read` or `transactional_email:write` scope. A key with a `hog_flow` scope still works. Only a project secret API key can read a status.

A found email returns `200`:

```json
{
  "id": "01963d8a-6f2c-7d4e-9b1a-3c5e8f2a7b10",
  "status": "delivered",
  "created_at": "2026-10-28T16:27:44.364000Z",
  "status_at": "2026-10-28T16:27:49.625000Z",
  "reason": null
}
```

See [statuses and reasons](/docs/workflows/transactional-emails#check-an-emails-status) for what each value means.

A `404` with the code `not_found` right after a send means the status isn't there yet: a new send can take a few seconds to get its first status, so retry after a short wait. Later, a `404` means the email is older than 30 days or the ID is wrong. See [when a status isn't found](/docs/workflows/transactional-emails#when-a-status-isnt-found). It returns `401` when the request has no project secret API key, `403` when the key doesn't have a Workflow scope, and `429` when you read too often.

Each project secret API key can read 600 statuses per minute and 20,000 per hour. All the keys of one project share the same limits in total. Reads have their own limits, so they don't use up the limits for sends.
