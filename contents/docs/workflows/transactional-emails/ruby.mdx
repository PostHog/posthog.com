The [Ruby SDK](/docs/libraries/ruby) sends transactional emails from version 3.30.0. Before you start, [create a transactional email](/docs/workflows/transactional-emails#create-a-transactional-email) and [create a project secret API key](/docs/workflows/transactional-emails#create-an-api-key).

## Install

Add this to your `Gemfile`:

```ruby
gem "posthog-ruby"
```

## Set up the client

Reuse the PostHog client your application already creates, and set `secret_key` to your project secret API key. The client still captures events with your project token. Shut the client down when your application exits, not after each send.

```ruby
require 'posthog'

$posthog = PostHog::Client.new({
  api_key: '<ph_project_token>',
  host: '<ph_client_api_host>',
  secret_key: ENV.fetch('POSTHOG_PROJECT_SECRET_API_KEY')
})
```

- **Local evaluation:** When `secret_key` is set, the client also loads flag definitions with it for [local evaluation](/docs/feature-flags/local-evaluation) when it starts. Give the key the **Feature flag** read scope too, or the client logs a failed load each time it polls.
- **Host:** On PostHog Cloud, the client sends email to the app host of your region, even when `host` is an ingestion host such as `us.i.posthog.com`. For any other host, such as a reverse proxy or a self-hosted instance, set `app_host` to your PostHog app URL. Email requests never go to a host that might be a proxy. Flag definitions for local evaluation still load from `host` with the secret key, so when that host is a proxy that must not see the key, leave `secret_key` off that client. Send email from a second client whose `host` is your PostHog host.

## Send an email

```ruby
def send_password_reset(user, reset_link, reset_request_id)
  # Raises PostHog::EmailError when PostHog doesn't queue the email. Branch on error.code.
  result = $posthog.emails.send(
    to: user.email,
    template_id: '<template_id>',
    template_data: { first_name: user.first_name, reset_link: reset_link },
    distinct_id: user.id.to_s,
    # Identifies this one email, so a retry never sends it twice
    idempotency_key: "password-reset-#{reset_request_id}"
  )
  result.id
end
```

`send` returns a `SendResult`, and `result.id` is the message ID. A send that PostHog doesn't queue raises `PostHog::EmailError`, with the `code` from the [errors table](/docs/workflows/transactional-emails#errors). A wrong argument raises `ArgumentError` before any request. After a `network_error` or a `503`, PostHog might have queued the email. Retry with the same idempotency key rather than sending the email through another provider, or the recipient can get it twice.

### Timeouts and retries

Each request waits up to 15 seconds to connect, and up to 15 seconds for each read or write. The client retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 and then 2 seconds, or longer if the server's `Retry-After` asks for it. A `Retry-After` over 30 seconds raises the error at once.

To change this, set `email_request_timeout_seconds` and `email_request_max_retries` on the client, or `max_retries` on one send. When a job queue such as Sidekiq already retries the send, set the retries to `0` and pass an `idempotency_key` that identifies the email.

## Link emails to your users

Pass the distinct ID that you pass to `identify()`, usually the ID your app gives that user, as `distinct_id`. PostHog then records the send, and its [engagement events](/docs/workflows/engagement-events) such as sent, opened, and clicked, against that user's person, next to their product events.

- **If you leave it out,** PostHog records the email against a person whose distinct ID is the recipient's email address. Unless your app identifies users by their email address, that's a separate person from your user.
- **For someone who isn't a user yet,** such as an invite or an email address check before the account exists, there's no distinct ID to pass. Leave `distinct_id` out.

## Send content from your code

`send` also takes content that your code rendered, without a template in PostHog. Name the email with `template_key`, and pass `subject` and `html`, `text`, or both. PostHog sends the content as you wrote it, so render it with your template engine first, such as ERB or Action Mailer views.

```ruby
def send_password_reset(user, html, reset_request_id)
  result = $posthog.emails.send(
    to: user.email,
    template_key: 'password-reset',
    subject: 'Reset your password',
    html: html,
    from: 'Hedgebox <security@example.com>',
    distinct_id: user.id.to_s,
    idempotency_key: "password-reset-#{reset_request_id}"
  )
  result.id
end
```

- **Key:** `template_key` names the email, such as `password-reset`. PostHog groups the email's metrics and sends under it, so use the same key every time you send this email.
- **Text:** If you leave out `text`, PostHog makes it from `html`.
- **Sender:** `from` needs an address on a domain that your project verified. Without it, PostHog uses the project's default sender. `reply_to` takes one address or a list.
- **Engagement:** PostHog captures the email's engagement events unless you pass `capture_engagement: false`.
- **One form per send:** A send has `template_id` or `template_key`, not both, or it raises `ArgumentError`. Content from your code takes no `template_data`, because PostHog renders nothing.

See [content from your code](/docs/workflows/transactional-emails/api#send-content-from-your-code) for each field and its checks.

## Check an email's status

```ruby
def email_bounced?(message_id)
  status = $posthog.emails.get(message_id)
  status.status == 'bounced'
rescue PostHog::EmailError => e
  # The first status can take a few seconds to arrive. Try again later.
  return nil if e.code == 'not_found'

  raise
end
```

`get` returns a `Status` with `id`, `status`, `created_at`, `status_at`, and `reason`. See [statuses and reasons](/docs/workflows/transactional-emails#check-an-emails-status). The client doesn't retry a `not_found`, so retry it yourself a few times, with a wait in between, before you treat the email as missing. A status that isn't there yet doesn't mean the email failed.
