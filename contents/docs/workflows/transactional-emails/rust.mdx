The [Rust SDK](/docs/libraries/rust) sends transactional emails from version 0.31.0. Before you start, [create a transactional email](/docs/workflows/transactional-emails#create-a-transactional-email) and [create a project secret API key](/docs/workflows/transactional-emails#create-an-api-key).

## Install

```bash
cargo add posthog-rs serde_json
```

## Set up the client

Reuse the PostHog client your application already creates, and set `secret_key` to your project secret API key. The client still captures events with your project token. Shut the client down when your application exits, not after each send.

```rust
use posthog_rs::ClientOptionsBuilder;

let options = ClientOptionsBuilder::default()
    .api_key("<ph_project_token>".to_string())
    .host("<ph_client_api_host>")
    .secret_key(std::env::var("POSTHOG_PROJECT_SECRET_API_KEY")?)
    .build()?;
let posthog = posthog_rs::client(options).await;
```

- **Host:** On PostHog Cloud, the client sends email to the app host of your region, even when `host` is an ingestion host such as `us.i.posthog.com`. For any other host, such as a reverse proxy or a self-hosted instance, set `app_host` to your PostHog app URL. Email requests never go to a host that might be a proxy. With `enable_local_evaluation` on, flag definitions still load from `host` with the secret key.
- **Local evaluation:** The client loads flag definitions only when you turn on `enable_local_evaluation`. If you do, give the key the **Feature flag** read scope too.
- **Blocking client:** Without the default `async-client` feature, the client and `emails()` are blocking, and you call them without `.await`.

## Send an email

```rust
use posthog_rs::TemplateEmail;
use serde_json::json;

async fn send_password_reset(
    posthog: &posthog_rs::Client,
    user: &User,
    reset_link: &str,
    reset_request_id: &str,
) -> Result<String, posthog_rs::EmailError> {
    // Returns an EmailError when PostHog doesn't queue the email. Branch on error.code()
    let result = posthog
        .emails()
        .send(
            TemplateEmail::new(&user.email, "<template_id>")
                .template_data(json!({ "first_name": user.first_name, "reset_link": reset_link }))
                .distinct_id(&user.id)
                // Identifies this one email, so a retry never sends it twice
                .idempotency_key(format!("password-reset-{reset_request_id}")),
        )
        .await?;
    Ok(result.id)
}
```

`send` returns a `SendEmailResult`, and `result.id` is the message ID. A send that PostHog doesn't queue returns an `EmailError`, with the `code()` from the [errors table](/docs/workflows/transactional-emails#errors). A wrong argument returns an `EmailError` before any request. After a `network_error` or a `503`, PostHog might have queued the email. Retry with the same idempotency key rather than sending the email through another provider, or the recipient can get it twice.

### Timeouts and retries

Each request times out after 15 seconds. The client retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 and then 2 seconds, or longer if the server's `Retry-After` asks for it. A `Retry-After` over 30 seconds returns the error at once.

To change this, set `email_request_timeout_seconds` and `email_request_max_retries` on the client options, or `max_retries` on one send. When a job queue already retries the send, set the retries to `0` and pass an `idempotency_key` that identifies the email.

## Link emails to your users

Pass the distinct ID that you pass to `identify()`, usually the ID your app gives that user, as `distinct_id`. PostHog then records the send, and its [engagement events](/docs/workflows/engagement-events) such as sent, opened, and clicked, against that user's person, next to their product events.

- **If you leave it out,** PostHog records the email against a person whose distinct ID is the recipient's email address. Unless your app identifies users by their email address, that's a separate person from your user.
- **For someone who isn't a user yet,** such as an invite or an email address check before the account exists, there's no distinct ID to pass. Leave `distinct_id` out.

## Send content from your code

`send` also takes content that your code rendered, without a template in PostHog. Pass a `CodeEmail`: `CodeEmail::new` takes the recipient, a template key that names the email, and the subject. Add `html`, `text`, or both. PostHog sends the content as you wrote it, so render it with your template engine first, such as Askama or Tera.

```rust
use posthog_rs::CodeEmail;

async fn send_password_reset(
    posthog: &posthog_rs::Client,
    user: &User,
    html: String,
    reset_request_id: &str,
) -> Result<String, posthog_rs::EmailError> {
    let result = posthog
        .emails()
        .send(
            CodeEmail::new(&user.email, "password-reset", "Reset your password")
                .html(html)
                .from("Hedgebox <security@example.com>")
                .distinct_id(&user.id)
                .idempotency_key(format!("password-reset-{reset_request_id}")),
        )
        .await?;
    Ok(result.id)
}
```

- **Key:** The template key names the email, such as `password-reset`. PostHog groups the email's metrics and sends under it, so use the same key every time you send this email.
- **Text:** If you leave out `text`, PostHog makes it from `html`.
- **Sender:** `from` needs an address on a domain that your project verified. Without it, PostHog uses the project's default sender. Call `reply_to` once for each reply-to address.
- **Engagement:** PostHog captures the email's engagement events unless you call `capture_engagement(false)`.
- **One form per send:** A `TemplateEmail` sends a template made in PostHog, and a `CodeEmail` sends your content. A `CodeEmail` takes no template data, because PostHog renders nothing.

See [content from your code](/docs/workflows/transactional-emails/api#send-content-from-your-code) for each field and its checks.

### Copies and attachments

A `CodeEmail` takes copies and files. Call `cc` or `bcc` once for each plain address, and `attachment` once for each file. `EmailAttachment::new` takes the file name and the file's bytes, and the client encodes the bytes for you. Add `content_type` to set the file type, or `content_id` to show the file inline. A `TemplateEmail` takes none of them, because the template uses its own settings.

```rust
use posthog_rs::{CodeEmail, EmailAttachment};

let receipt_pdf = std::fs::read(pdf_path)?;
posthog
    .emails()
    .send(
        CodeEmail::new(&user.email, "receipt", "Your receipt")
            .html(html)
            .cc("billing@example.com")
            .attachment(EmailAttachment::new("receipt.pdf", receipt_pdf).content_type("application/pdf"))
            .distinct_id(&user.id),
    )
    .await?;
```

See [copies and attachments](/docs/workflows/transactional-emails/api#copies-and-attachments) for the limits.

## Check an email's status

```rust
use posthog_rs::EmailDeliveryStatus;

async fn email_bounced(
    posthog: &posthog_rs::Client,
    message_id: &str,
) -> Result<Option<bool>, posthog_rs::EmailError> {
    match posthog.emails().get(message_id).await {
        Ok(status) => Ok(Some(status.status == EmailDeliveryStatus::Bounced)),
        // The first status can take a few seconds to arrive. Try again later.
        Err(error) if error.code() == "not_found" => Ok(None),
        Err(error) => Err(error),
    }
}
```

`get` returns an `EmailStatus` with `id`, `status`, `created_at`, `status_at`, and `reason`. `status` is an `EmailDeliveryStatus`, and `as_str()` gives the value from [statuses and reasons](/docs/workflows/transactional-emails#check-an-emails-status). A status that this SDK version doesn't know arrives as `EmailDeliveryStatus::Other`. The client doesn't retry a `not_found`, so retry it yourself a few times, with a wait in between, before you treat the email as missing. A status that isn't there yet doesn't mean the email failed.
