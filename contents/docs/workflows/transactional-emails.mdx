<CalloutBox icon="IconFlask" title="Transactional emails are in beta" type="action">

Transactional emails are a new feature. Things might change or break while we work on them.

</CalloutBox>

Transactional emails are one-off emails that a person triggers in your product, like password resets, sign-in codes, and receipts. You design the email as a [message template](/docs/workflows/library) in Workflows. Your backend then sends it to one recipient with one API call.

Each transactional template has its own workflow behind it. PostHog doesn't show this workflow on the **Workflows** tab. It shows the workflow's data on the template instead:

- **Metrics** shows the metrics for the template's sends.
- **Sends** lists each send, with its log messages.
- **Versions** keeps each version of the email that you publish.

## Make a template transactional

1. In Workflows, open the [**Templates** tab](https://app.posthog.com/workflows/library) and choose **Email templates**.
2. Open the template you want to send, or create one.
3. Open the **API** tab and click **Make transactional**.

The template needs these before you can make it transactional:

- **A subject and a body.** Save any changes first.
- **A verified email sender.** PostHog uses your project's default sender. You can change the sender later. To set up a sender, see [configure a channel](/docs/workflows/configure-channels).
- **No marketing category.** Transactional emails ignore opt-outs, so PostHog doesn't send a template that is in a marketing [message category](/docs/workflows/opt-outs#message-categories).

<CalloutBox icon="IconWarning" title="You can't undo this" type="caution">

A template stays transactional after you make it transactional. If you still use the template for other emails, click **Duplicate** in the template's menu first, and make the copy transactional.

</CalloutBox>

You can also make a template transactional over the API. Call `POST /api/projects/:project_id/messaging_templates/:template_id/make_transactional/` with a [personal API key](/docs/api/personal-api-keys) that has the `hog_flow:write` scope.

### Edit a transactional template

- **Sender:** The **Design** tab shows who the email comes from. Click **Edit sender** to choose a different verified sender, or to set a display name, a from address, or a reply-to address. The from address must be on the sender's verified domain. To use more than one reply-to address, separate them with commas.
- **Drafts:** Your edits save as a draft. Sends use the live version of the email until you click **Publish**. Each publish adds a version on the **Versions** tab. To remove your edits, use **Discard draft**.
- **Checks:** PostHog doesn't publish a change that would stop the template from sending, such as an empty subject or body, or a marketing category.

### Protect sensitive data

For emails with sign-in codes, reset links, or other secrets, turn on **Protect sensitive data** on the **API** tab. PostHog then keeps no copy of the body or the filled-in subject of each email, and clicked links keep only the site address. You can turn this setting on or off at any time.

## Create an API key

Send transactional emails with a [project secret API key](/docs/api/project-secret-api-keys) that has the `hog_flow:write` scope. The same key can also [read the status](#check-an-emails-status) of each email it sends.

1. Go to [**Project secret API keys**](https://app.posthog.com/settings/project-secret-api-keys) in your project settings.
2. Click **Create project secret API key** and give the key a label.
3. In the scopes list, set **Workflow** to **Write**.
4. Copy the key. It starts with `phs_`, and you can't see it again after you leave the page.

A project secret API key with this scope can send transactional emails and read their status, and nothing else. It can't read or change your templates, and it can't use any other part of the Workflows API. Keep the key on your server. Never put it in client-side code.

To give a service a key that can read statuses but not send, set **Workflow** to **Read** instead.

## Send an email

```
POST https://us.posthog.com/api/projects/@current/messaging/send/email/
```

- **Host:** Use `https://us.posthog.com` or `https://eu.posthog.com`, the host where you log in to PostHog. Don't use an ingestion host like `us.i.posthog.com`. If you self-host PostHog, use the URL of your instance.
- **Project:** `@current` is the project that the key belongs to. You can use your project ID instead.
- **Template ID:** Send it in the body as `template.id`. The template's **API** tab shows it.

### Request

Send these headers:

| Header | Value |
| --- | --- |
| `Authorization` | `Bearer` followed by your project secret API key |
| `Content-Type` | `application/json` |
| `Idempotency-Key` | Optional. A unique key for this email. See [retry safely](#retry-safely-with-an-idempotency-key). |

Send a JSON body with these fields:

| Field | Required | Description |
| --- | --- | --- |
| `template.id` | Yes | The ID of the transactional template to send. |
| `to` | Yes | The email address of the recipient. One address for each request. |
| `message_data` | No | An object with the values for the template's `{{ variables.* }}` placeholders. For example, `{"reset_link": "https://example.com/reset"}` fills `{{ variables.reset_link }}`. The template can't read person properties, so pass all the data that the email needs here. |
| `identifiers.distinct_id` | No | The distinct ID of the recipient's person. PostHog records the send and its [engagement events](/docs/workflows/engagement-events) against this person. If you leave it out, PostHog uses the email address as the distinct ID, which might not match the person in your product. We recommend that you always send it. |

In the template, use the same names that you send in `message_data`:

```liquid
Hi {{ variables.first_name }}, use this link to reset your password: {{ variables.reset_link }}
```

### Response

A successful request returns `202 Accepted`:

```json
{
  "message_id": "01963d8a-6f2c-7d4e-9b1a-3c5e8f2a7b10",
  "replayed": false
}
```

A `202` means that PostHog queued the email. It doesn't mean that the email was delivered. To see what happened to the email, [check its status](#check-an-emails-status) with its `message_id`, or open the template's **Sends** tab.

`replayed` is `true` when an earlier request with the same `Idempotency-Key` already queued this email. In that case, PostHog sent no new email, and `message_id` is the ID of the first send.

### Examples

<MultiLanguage selector="tabs">

```bash file=cURL
curl -X POST "https://us.posthog.com/api/projects/@current/messaging/send/email/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: password-reset-8f14e45f" \
  -d '{
    "template": { "id": "<template_id>" },
    "to": "jane@example.com",
    "identifiers": { "distinct_id": "user_123" },
    "message_data": { "first_name": "Jane", "reset_link": "https://example.com/reset?token=abc123" }
  }'
```

```python file=Python
import os

from posthog import Posthog
from posthog.emails import EmailError

posthog = Posthog(
    "<ph_project_api_key>",
    host="https://us.i.posthog.com",
    secret_key=os.environ["POSTHOG_PROJECT_SECRET_API_KEY"],
)

def send_password_reset(user_id: str, email: str, first_name: str, reset_link: str, reset_request_id: str) -> str:
    try:
        result = posthog.emails.send(
            to=email,
            template_id="<template_id>",
            template_data={"first_name": first_name, "reset_link": reset_link},
            distinct_id=user_id,
            # Identifies this one email, so a retry never sends it twice
            idempotency_key=f"password-reset-{reset_request_id}",
        )
    except EmailError as error:
        raise RuntimeError(f"PostHog refused the email: {error.code}") from error
    return result.id
```

```js file=Node.js
import { PostHog } from "posthog-node"

const posthog = new PostHog("<ph_project_api_key>", {
    host: "https://us.i.posthog.com",
    secretKey: process.env.POSTHOG_PROJECT_SECRET_API_KEY,
})

export async function sendPasswordReset({ userId, email, firstName, resetLink, resetRequestId }) {
    const { data, error } = await posthog.emails.send({
        to: email,
        templateId: "<template_id>",
        templateData: { first_name: firstName, reset_link: resetLink },
        distinctId: userId,
        // Identifies this one email, so a retry never sends it twice
        idempotencyKey: `password-reset-${resetRequestId}`,
    })
    if (error) {
        throw new Error(`PostHog refused the email: ${error.code}`)
    }
    return data.id
}
```

</MultiLanguage>

The older route, `POST /api/projects/@current/messaging_templates/:template_id/send/`, takes the same body without `template` and still works.

### Send with an SDK

The [Python SDK](/docs/libraries/python) from version 7.81.0 and the [Node.js SDK](/docs/libraries/node) from version 5.61.0 send transactional emails with `emails.send`.

- **Key:** Set `secret_key` in Python or `secretKey` in Node.js to your project secret API key. The client still captures events with your project token.
- **Host:** On PostHog Cloud, the client sends email to the app host of your region, even when `host` is an ingestion host such as `us.i.posthog.com`. For any other host, such as a reverse proxy or a self-hosted instance, set `app_host` in Python or `appHost` in Node.js to your PostHog app URL. The client refuses to send the secret key to a host that might be a proxy.
- **Local evaluation:** The client also uses the secret key to [evaluate flags locally](/docs/feature-flags/local-evaluation). If you do that, give the key the **Feature flag** read scope too. In Node.js, if the client only sends email, set `enableLocalEvaluation: false`.
- **Retries:** The client sends an idempotency key on each send, and retries network errors, rate limits, and a `503` up to two times with the same key. Pass `idempotency_key` or `idempotencyKey` to cover retries outside the call too, such as from a job queue.
- **Errors:** In Python, a send that PostHog doesn't queue raises `EmailError`. In Node.js, `send` returns `{ data, error }` and doesn't throw. Both errors carry the `code` from the [errors table](#errors).

## Retry safely with an idempotency key

Without an `Idempotency-Key`, a retry after a timeout or a `503` can send the email twice. To prevent this, send a key that identifies this one email, such as the ID of the password reset request. A key is 1 to 255 visible ASCII characters, with no spaces.

- **Same key, same request:** PostHog sends no new email. It returns `202` with the `message_id` of the first send and `"replayed": true`. PostHog remembers a key for 24 hours after it queues the email.
- **Same key, different request:** PostHog returns `422` with the code `idempotency_key_reused`. A request is the same when it has the same template, `to`, `distinct_id`, and `message_data`.
- **First request not finished:** PostHog returns `409` with the code `idempotency_key_in_flight`. Wait a few seconds, then retry with the same key.
- **Refused request:** When PostHog refuses a send, for example with `recipient_suppressed` or `quota_limited`, the key stays unused. You can send the same key again later.

Keys are separate for each project.

## Errors

An error response has this shape:

```json
{
  "type": "invalid_request",
  "code": "recipient_suppressed",
  "detail": "The recipient is on this project's suppression list after a hard bounce or a spam complaint, so the email can't be sent. Remove the address from the suppression list if it can receive email again.",
  "attr": null
}
```

Use `code` in your error handling. The text in `detail` can change.

| Status | `code` | What it means | What to do |
| --- | --- | --- | --- |
| `400` | Varies, with `"type": "validation_error"` | The body isn't valid. For example, `to` is missing or isn't an email address. `attr` names the field. | Fix the request. |
| `400` | `invalid_recipient` | The `to` address contains `{` or `}`. | Send a plain email address. |
| `400` | `invalid_idempotency_key` | The `Idempotency-Key` header isn't 1 to 255 visible ASCII characters. | Use a valid key. |
| `400` | `template_not_transactional` | The template isn't transactional. | [Make the template transactional](#make-a-template-transactional). |
| `400` | `template_not_sendable` | The template has no subject or no body. | Add them and publish the template. |
| `400` | `marketing_template` | The template is in a marketing category. | Move the template to a transactional category, or remove its category. |
| `400` | `transactional_email_paused` | The workflow that sends this template isn't active, or it was deleted. | Don't retry. A retry gets the same error. |
| `401` | `not_authenticated` or `authentication_failed` | The `Authorization` header is missing, or the key isn't valid. | Check that you send a valid project secret API key. |
| `403` | `permission_denied` | The key doesn't have the `hog_flow:write` scope, or the key belongs to a different project. | Use a key from this project with the correct scope. |
| `404` | `not_found` | The template doesn't exist in this project, or transactional emails aren't turned on for the project. | Check the template ID and the project. |
| `409` | `idempotency_key_in_flight` | A request with the same `Idempotency-Key` is still in progress. | Retry with the same key after a few seconds. |
| `422` | `idempotency_key_reused` | The `Idempotency-Key` was already used for a different request. | Use a new key for a new email. |
| `422` | `recipient_suppressed` | The address is on your project's [suppression list](/docs/workflows/opt-outs#the-suppression-list) after a hard bounce or a spam complaint. | Don't retry. Remove the address from the suppression list only if you know that it can receive email again. |
| `422` | `recipient_unreachable` | The address isn't valid, or its domain has no mail servers, so the email would bounce. | Check the address for a typo. Don't retry the same address. |
| `422` | `sending_paused` | Sending is paused for this transactional email because of its bounce or complaint rate. | Check the **Reputation** tab in Workflows. |
| `422` | `sending_suspended` | Email sending is suspended for your project. | Check the **Reputation** tab in Workflows. |
| `429` | `throttled` | You sent too many requests. | Wait for the number of seconds in the `Retry-After` header, then retry. |
| `429` | `quota_limited` | Your project is over its email quota. | Check your usage and [billing limits](/docs/billing/limits-alerts). A retry gets the same error until the project is under its quota. |
| `503` | `delivery_unavailable` | PostHog couldn't confirm that it queued the email. | Retry with backoff. Send the same `Idempotency-Key` so that the email doesn't go out twice. |

If you make a template transactional or save it without a verified sender, PostHog returns `400` with the code `sender_unavailable`.

### Rate limits

Each project secret API key can send 600 requests per minute and 20,000 requests per hour. All the keys of one project share the same limits in total. A request over a limit gets a `429` with the code `throttled`.

## Check an email's status

To find out what happened to an email, read its status with the `message_id` from the send:

```
GET https://us.posthog.com/api/projects/@current/messaging/emails/:message_id/
```

Send the same `Authorization` header as for a send. The key needs the `hog_flow:read` or `hog_flow:write` scope. Only a project secret API key can read a status.

A found email returns `200`:

```json
{
  "id": "01963d8a-6f2c-7d4e-9b1a-3c5e8f2a7b10",
  "status": "delivered",
  "created_at": "2026-10-28T16:27:44.364000Z",
  "status_at": "2026-10-28T16:27:49.625000Z",
  "reason": null
}
```

| `status` | What it means |
| --- | --- |
| `queued` | The email waits to go out. |
| `sent` | PostHog handed the email to the email provider. |
| `failed` | The email wasn't sent. `reason` says why. |
| `delivered` | The recipient's mail server accepted the email. |
| `bounced` | The recipient's mail server refused the email. `reason` is `hard`, `soft`, or `unknown`. |
| `complained` | The recipient marked the email as spam. |

A status only moves forward. For example, a `delivered` email never goes back to `sent`. New statuses can appear in the future, so handle a value you don't know.

`reason` is `null` unless the email failed or bounced. A failed email has one of these reasons:

- `provider_error` or `provider_rejected`: The email provider refused the email.
- `recipient_suppressed`, `recipient_unreachable`, or `missing_recipient`: PostHog skipped the email because of the recipient.
- `sending_paused` or `sending_suspended`: Sending is paused for the template or suspended for the project. Check the **Reputation** tab in Workflows.
- `canceled` or `workflow_unavailable`: The send stopped before the email went out.
- Another value, such as `timeout`: The send failed with this kind of error. New values can appear.

A `failed` email can still change to `sent` if PostHog retries the send.

### When a status isn't found

The lookup returns `404` with the code `not_found` when:

- The email was sent in the last few seconds. Its first status takes a moment to arrive, so retry after a short wait.
- The email is older than 30 days. PostHog keeps each status for 30 days after the send.
- No email of this project has the ID.

It returns `401` when the request has no project secret API key, `403` when the key doesn't have a Workflow scope, and `429` when you read too often.

Each project secret API key can read 600 statuses per minute and 20,000 per hour. All the keys of one project share the same limits in total. Reads have their own limits, so they don't use up the limits for sends.

### Examples

<MultiLanguage selector="tabs">

```bash file=cURL
curl "https://us.posthog.com/api/projects/@current/messaging/emails/<message_id>/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY"
```

```python file=Python
status = posthog.emails.get(message_id)
if status.status == "bounced":
    print(f"The email bounced: {status.reason}")
```

```js file=Node.js
const { data: status, error } = await posthog.emails.get(messageId)
if (status?.status === "bounced") {
    console.log(`The email bounced: ${status.reason}`)
}
```

</MultiLanguage>

In Python, `get` returns an `EmailStatus`, with `created_at` and `status_at` as `datetime` objects. It raises `EmailError` with the code `not_found` when the status isn't found. In Node.js, `get` returns `{ data, error }`.

## How transactional emails behave

- **No opt-outs or frequency caps.** Transactional emails ignore marketing [opt-outs](/docs/workflows/opt-outs) and frequency caps. Use them only for emails that a person needs, never for marketing.
- **Suppression still applies.** PostHog doesn't send to an address on your suppression list.
- **Billing and quotas.** Transactional emails are billed and quota limited like other workflow emails. See [pricing](/pricing) and [billing limits](/docs/billing/limits-alerts).
- **Sending allowance.** Transactional emails count toward your project's [sending allowance](/docs/workflows/sending-reputation). When your project reaches its hourly or daily cap, emails wait in the queue until the allowance frees up. If a transactional email gets too many bounces or complaints, PostHog can pause its sending, and sends return `sending_paused`.
- **Engagement events.** If you [capture email engagement events](/docs/workflows/engagement-events), PostHog records them for transactional emails against the person in `identifiers.distinct_id`.
- **Where to see sends.** [Read the status](#check-an-emails-status) of an email with its `message_id`. The template's **Sends** tab lists each send with its log messages. The **Metrics** tab shows their metrics. Each send also appears on the recipient's person.
