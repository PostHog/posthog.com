A source doesn't have to stop at PostHog. Point a table at your own database or object store, and PostHog writes the rows there on the same schedule it syncs them.

## Where you can write

| Destination                                                | Notes                                                                                         |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| PostHog warehouse                                          | The default. A source with no destinations set writes here.                                   |
| Postgres                                                   | Your own instance, reachable from PostHog's IP addresses.                                     |
| Snowflake                                                  |                                                                                               |
| BigQuery                                                   |                                                                                               |
| Redshift                                                   |                                                                                               |
| Databricks                                                 |                                                                                               |
| [MotherDuck](/docs/data-pipelines/destinations/motherduck) | Requires a read-write token and a database you own. Available where enabled for your project. |
| S3                                                         | Files, not tables.                                                                            |
| Azure Blob                                                 | Files, not tables.                                                                            |

The PostHog warehouse is one of this list rather than a special case. When a table has no destinations set, PostHog resolves it to your warehouse, which is why sources you configured before destinations existed carry on unchanged.

## Setting a destination

Set destinations on a source and every table under it follows. Override a single table when it belongs somewhere else.

Destinations reuse the same connections as [batch exports](/docs/data-pipelines/batch-exports), so a warehouse you already connected is ready to pick. Credentials live on the connection, not on the destination.

> **Adding a destination to a source that has already synced starts a full resync of its tables.** The new destination has none of the history, so PostHog refills it from the beginning. Every destination the source writes to is billed for the rows it receives during that resync, including ones that already had the data. Check the row counts before you turn one on.

## Which do I want, destinations or batch exports?

Both write to Postgres, Snowflake, BigQuery, Redshift, Databricks, S3, and Azure Blob. They move different data.

- **ELT destinations** move rows PostHog imported from a source: your Stripe charges, your HubSpot contacts, your own Postgres tables.
- **[Batch exports](/docs/data-pipelines/batch-exports)** move the events, persons, and sessions PostHog captured.

If you want your Stripe data in Snowflake, that's a destination. If you want your Product Analytics events in Snowflake, that's a batch export. Teams often run both.

## Checking what lands

The [ELT page](https://app.posthog.com/elt) shows rows written per destination over the window you pick, so a destination that stopped receiving rows shows up as a flat line. See [monitoring your syncs](/docs/data-pipelines/destinations/monitoring).

## S3 key prefix template variables

S3 destinations write files, not database tables. The **Prefix** field controls where files land in your bucket.

The prefix supports template variables that are filled when each sync runs:

- `{year}`, `{month}`, `{day}`, `{hour}`, `{minute}`, `{second}` – date and time of the sync job start, in UTC
- `{table}` – the name of the table being synced (e.g. `charges`)

For example, `exports/{year}/{month}/{day}/{table}/` produces prefixes like `exports/2025/01/15/charges/`.

When the prefix includes `{table}`, PostHog doesn't add a separate table folder. Without `{table}`, each table still gets its own subfolder below the prefix.

PostHog rejects a prefix that contains braces outside these seven variable names. The prefix can't be changed after creation, so confirm it before saving.

S3 destinations share connections and file format options with [S3 batch exports](/docs/data-pipelines/batch-exports/s3). See that page for details on file formats, compression, and authentication.
