> **Note:** Metrics is in open alpha. Any team can turn it on — open [Metrics](https://app.posthog.com/metrics) and select **Enable metrics** in the onboarding view. Setup details, including the ingestion endpoint, may change before general availability.

PostHog's application metrics work with any OpenTelemetry-compatible client. If your app or infrastructure already exports OTLP metrics, point the exporter at PostHog. No PostHog packages required.

<Steps>

<Step title="Install OpenTelemetry packages" badge="required">

The key requirements are:
- Use OTLP (OpenTelemetry Protocol) for metrics export over HTTP
- Send metrics to your Metrics endpoint (see configuration step below)
- Include your project token in the Authorization header or as a `?token=` query parameter

Find the OpenTelemetry SDK for your language in the [official registry](https://opentelemetry.io/ecosystem/registry/). If you already run an OpenTelemetry Collector, you can add PostHog as an additional exporter without touching application code.

</Step>

<Step title="Get your project token" badge="required">

You'll need your PostHog project token to authenticate metrics requests. This is the same key you use for capturing events and exceptions with the PostHog SDK.

> **Important:** Use your **project token** which starts with `phc_`. Do **not** use a personal API key (which starts with `phx_`).

You can find your project token in [Project Settings](https://app.posthog.com/settings).

</Step>

<Step title="Configure the exporter" badge="required">

Most OpenTelemetry SDKs pick up standard environment variables, so configuration is often no more than:

```bash
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT="<ph_client_api_host>/i/v1/metrics"
OTEL_EXPORTER_OTLP_METRICS_HEADERS="Authorization=Bearer <ph_project_token>"
OTEL_SERVICE_NAME="my-app"
```

Set `OTEL_SERVICE_NAME` so metrics from different systems stay easy to tell apart. It's attached to every series and used by the Metrics UI for filtering.

If you configure the exporter in code instead:

**Endpoint:**

```
<ph_client_api_host>/i/v1/metrics
```

**Authentication:** Include your project token either as an `Authorization` header:

```
Authorization: Bearer <ph_project_token>
```

Or as a query parameter on the endpoint:

```
<ph_client_api_host>/i/v1/metrics?token=<ph_project_token>
```

</Step>

<Step title="Send metrics without an SDK" badge="optional">

The metrics endpoint is a standard [OTLP/HTTP](https://opentelemetry.io/docs/specs/otlp/#otlphttp) receiver, so you can also `POST` metrics to it directly, for example from a platform with no OpenTelemetry SDK.

We recommend an SDK instead where you can. The OTLP payload is verbose, and an SDK handles aggregation, batching, retries, and flushing for you. If your app runs [JavaScript](/docs/metrics/installation/javascript), [Node.js](/docs/metrics/installation/nodejs), or [Python](/docs/metrics/installation/python), use the `posthog.metrics` API in the PostHog SDK. For other languages, use an [OpenTelemetry SDK](https://opentelemetry.io/ecosystem/registry/).

To send a request by hand, the body is an [`ExportMetricsServiceRequest`](https://github.com/open-telemetry/opentelemetry-proto/blob/main/opentelemetry/proto/collector/metrics/v1/metrics_service.proto) in the [OTLP JSON encoding](https://opentelemetry.io/docs/specs/otlp/#json-protobuf-encoding). This example sends one counter data point:

```bash
curl -X POST "<ph_client_api_host>/i/v1/metrics" \
  -H "Authorization: Bearer <ph_project_token>" \
  -H "Content-Type: application/json" \
  -d '{
    "resourceMetrics": [{
      "resource": {
        "attributes": [
          { "key": "service.name", "value": { "stringValue": "my-app" } }
        ]
      },
      "scopeMetrics": [{
        "scope": { "name": "manual" },
        "metrics": [{
          "name": "orders.created",
          "unit": "1",
          "sum": {
            "aggregationTemporality": 1,
            "isMonotonic": true,
            "dataPoints": [{
              "timeUnixNano": "1767225600000000000",
              "asInt": "3",
              "attributes": [
                { "key": "plan", "value": { "stringValue": "pro" } }
              ]
            }]
          }
        }]
      }]
    }]
  }'
```

Replace `timeUnixNano` with the current time in nanoseconds since the Unix epoch. The main rules of the JSON encoding are:

- Field names are lowerCamelCase, for example `timeUnixNano`, not `time_unix_nano`.
- Enums are integers. For `aggregationTemporality`, `1` is delta (the change since the last data point) and `2` is cumulative (the running total).
- 64-bit integers, such as `timeUnixNano` and `asInt`, are strings. Use `asDouble` for decimal values.
- Each metric has one data field: `sum` for counters, `gauge` for current values, or `histogram` for distributions. See the [metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/) for the fields of each type.

A `200` response means that PostHog accepted the data. You can also send the binary protobuf encoding with `Content-Type: application/x-protobuf`, and compress either body with `Content-Encoding: gzip`.

</Step>

<Step title="Test your setup" badge="recommended">

1. Trigger the code path that records a metric
2. Open **Metrics** in the PostHog sidebar and pick your metric from the name picker
3. Data points should appear within a minute of sending

If nothing shows up, check that the endpoint ends in `/i/v1/metrics`, that the token starts with `phc_`, and see the [troubleshooting section](/docs/metrics#troubleshooting).
