If your product serves many customer organizations from a single codebase – a B2B SaaS app, a multi-tenant e-commerce platform, an agency dashboard – the first question is usually "how do I keep each tenant's data separate?"

The short answer: **use one PostHog project and separate tenants with [group analytics](/docs/product-analytics/group-analytics), not one project per tenant.** This guide walks through that decision and the ones that follow it.

| Question | Answer |
| --- | --- |
| How should I structure projects? | One production project for all tenants, plus separate projects for development and staging. See [projects](#1-use-one-project-not-one-project-per-tenant). |
| How do I separate data by tenant? | Create an `organization` group type keyed on your tenant ID. See [group analytics](#2-separate-data-by-tenant-with-group-analytics). |
| How do I track users *and* organizations? | `distinct_id` identifies the user, the group key identifies the tenant. See [identity](#3-track-users-and-organizations). |
| What about privacy and retention? | Redact before capture, choose your region, and delete per person. See [privacy](#4-privacy-retention-and-access-control). |
| Does this work with Vercel and Supabase? | Yes. See [your stack](#5-vercel-supabase-and-nextjs). |

## 1. Use one project, not one project per tenant

A [project](/docs/settings/projects) is a silo of data: all queries are project-specific, and every project has its own token, settings, dashboards, feature flags, and insights. That makes a project the wrong unit for a tenant.

If you create a project per tenant, you can't answer questions that span your customer base – how many organizations activated this month, which plan tier retains best, how a feature rollout performed overall – because there's no way to query across projects. You'd also duplicate every dashboard, flag, and setting for each new customer, and have to provision a new project (and redeploy new tokens) on every signup.

Instead, use the standard setup:

1. **Local development** – when you're running the app on your own device
2. **Staging** – when you're running your app on a staging server
3. **Production** – all tenants, and your marketing site

Reach for separate projects only when the [usual reasons](/docs/settings/projects#how-to-organize-projects) apply: entirely separate products with unlinked authentication systems, admin apps that aren't customer-facing, or internal services.

<CalloutBox icon="IconInfo" title="Keep your marketing site in the same project" type="fyi">

Tracking your marketing site and app together lets you follow the whole journey, from first visit through signup to product usage. If tenants get their own subdomains, you can still slice by tenant with the `$host` property or by group type – see [using the same project for your website and app](/docs/product-analytics/best-practices#10-use-the-same-project-for-your-website-and-app).

</CalloutBox>

## 2. Separate data by tenant with group analytics

[Group analytics](/docs/product-analytics/group-analytics) aggregates events by an entity other than the individual user. For a multi-tenant app, that entity is the tenant.

Create a group type – `organization` is a good default, though `company`, `workspace`, or `store` may fit your product better – and key each individual group on the tenant's immutable ID from your database:

<MultiLanguage>

```js-web
// Call this after login, before you capture tenant-scoped events
posthog.group('organization', tenant.id, {
    name: tenant.name,
    plan: tenant.plan,
    seat_count: tenant.seatCount,
    created_at: tenant.createdAt,
})
```

```node
posthog.groupIdentify({
    groupType: 'organization',
    groupKey: tenant.id,
    properties: {
        name: tenant.name,
        plan: tenant.plan,
        seat_count: tenant.seatCount,
    },
})

// Then attach the group to every event you capture
posthog.capture({
    distinctId: user.id,
    event: 'order_created',
    groups: { organization: tenant.id },
})
```

```python
posthog.group_identify('organization', tenant.id, {
    'name': tenant.name,
    'plan': tenant.plan,
    'seat_count': tenant.seat_count,
})

# Then attach the group to every event you capture
posthog.capture(
    'order_created',
    distinct_id=user.id,
    groups={'organization': tenant.id},
)
```

</MultiLanguage>

A few things to get right:

- **Key on an ID, not a name.** Names duplicate and change; a tenant ID or UUID doesn't.
- **Use singular group type names** – `organization`, not `organizations`.
- **The web SDK remembers the group.** Call `posthog.group()` once after login and all subsequent events in that session are linked to that tenant. Call `posthog.reset()` on logout, and call `posthog.group()` again with the new key if a user switches tenant without logging out.
- **Other SDKs need the group on every event.** Server-side, pass `groups` on each `capture` call – there's no session to remember it for you.
- **Events must be [identified](/docs/data/anonymous-vs-identified-events) to link to a group.** If `$process_person_profile` is `false`, the event won't be associated with the tenant.
- **You get 5 group types per project**, with unlimited groups inside each. Spend them deliberately – for example `organization` and `store`, not one per nested entity in your schema.

<CalloutBox icon="IconWarning" title="Don't use the tenant ID as the distinct ID" type="caution">

It's tempting to send events with `distinct_id: tenant.id` so everything from a tenant lands together. Don't. The `distinct_id` identifies a *person*, so this collapses every user in a tenant into one person profile, which breaks per-user metrics, funnels, and cohorts.

It's also a scaling problem: a single distinct ID sending a high, sustained volume of events (roughly 5,000 per minute) crosses a [per-distinct-ID rate limit](/docs/how-posthog-works/ingestion-pipeline#rate-limiting-high-volume-distinct-ids), after which its events lose strict ordering and person profile updates until the spike subsides. A busy tenant on a shared distinct ID hits this long before your project does.

Identify the user, and pass the tenant as a group. For genuinely user-less tenant events (a nightly job, a webhook), see [capturing events for individual groups without a user](/docs/product-analytics/group-analytics#capture-events-for-individual-groups-without-a-user).

</CalloutBox>

<CalloutBox icon="IconInfo" title="Group analytics bills all identified events" type="fyi">

Group analytics is a paid add-on, and once you subscribe, billing applies to **all identified events** in your project – not just the events carrying group properties. Billing starts when you enable it on your [billing page](https://app.posthog.com/organization/billing), not when you add `posthog.group()` to your code. Check the [pricing calculator](/pricing) before you wire it up.

</CalloutBox>

### If you don't want the group analytics add-on

You can get part of the way there with properties alone: set the tenant ID as a [super property](/docs/libraries/js/usage#super-properties) on the frontend, or add it to every event server-side, and use it as a filter or breakdown.

```js-web
posthog.register({ tenant_id: tenant.id })
```

That's enough to segment insights by tenant. What you give up is aggregation *by* tenant – counting unique organizations rather than unique users, funnels that convert at the organization level, [targeting feature flags at a whole tenant](/docs/feature-flags/user-and-group-targeting), and experiments with group-level results. Those need group analytics.

## 3. Track users and organizations

Users and tenants are separate layers, and each has its own identifier and its own properties.

| | Identifier | Set with | Use for |
| --- | --- | --- | --- |
| **User** | `distinct_id` – your internal user ID | [`identify()`](/docs/product-analytics/identify) | Person properties like email, role, and signup date |
| **Tenant** | Group key – your tenant ID | [`group()`](/docs/product-analytics/group-analytics) | Group properties like plan, seat count, and MRR |

Call `identify()` as soon as you know who the user is, then `group()` for the tenant they're working in:

```js-web
posthog.identify(user.id, {
    email: user.email,
    role: user.role,
})

posthog.group('organization', tenant.id, { plan: tenant.plan })
```

Keep the two sets of properties distinct. A user's role belongs on the person; the tenant's plan tier belongs on the group. Putting the plan on every person means you have to update every user's profile when a tenant upgrades.

**Users who belong to multiple tenants** stay a single person – that's correct, and it's what lets you see their full activity. What changes is which group their events are attributed to, so re-call `group()` whenever they switch context. Use one stable `distinct_id` per human being, not one per tenant membership; see [identity resolution](/docs/product-analytics/identity-resolution) for the full picture.

Once this is in place, you can count organizations instead of users: select **Unique** with your group type in [insights](/docs/product-analytics/insights), or set **Aggregating by** to your group type in [funnels](/docs/product-analytics/funnels). Note the [limitations](/docs/product-analytics/group-analytics#limitations) – group types aren't supported for lifecycle insights or user paths.

## 4. Privacy, retention, and access control

In a multi-tenant app you're handling data on behalf of your customers, so the useful framing is: capture as little tenant PII as you can, then control who can reach what's left.

**Before data reaches PostHog**, use [privacy controls](/docs/product-analytics/privacy): the `before_send` config option to sanitize or drop events client-side, `ph-no-capture` to [keep sensitive elements out of autocapture](/docs/privacy/data-collection#hide-sensitive-information-with-autocapture), and [masking rules](/docs/session-replay/privacy) if you record sessions. You can also opt individual users out entirely.

**After it arrives**, [data storage controls](/docs/privacy/data-storage) cover the rest:

- **Region** – [PostHog Cloud EU](/eu) stores data in Frankfurt, which matters if your tenants have [GDPR](/docs/privacy/gdpr-compliance) requirements. Pick this at signup; migrating later needs a support request and a Boost plan or above.
- **Transformations** – use [realtime transformations](/docs/cdp/transformations) to hash PII, anonymize IPs, or [drop events](/docs/cdp/transformations/drop-events) before they're stored. You can also discard client IPs [per project](/docs/privacy/data-storage#discarding-ip-addresses-at-project-level).
- **Deletion** – when a tenant invokes the [right to be forgotten](/docs/privacy/data-storage#right-to-be-forgotten) for one of their users, delete that person and their events by API. Event data is cleared asynchronously during off-peak hours, so it isn't instant. [Session recordings](/docs/session-replay/recording-retention) have their own retention periods.
- **Access control** – [organization, project, and resource-level controls](/docs/settings/access-control) govern who on *your* team sees what, and [SSO, SAML, and SCIM](/docs/settings/sso) let you manage that from your identity provider.

<CalloutBox icon="IconInfo" title="Showing tenants their own data" type="fyi">

PostHog's access controls apply to your team, not your customers – there's no way to scope a PostHog login to a single group. To surface per-tenant analytics inside your product, query PostHog server-side and render it yourself. See [embedded analytics](/tutorials/embedded-analytics) for the pattern. A [public share link](/docs/product-analytics/sharing) is viewable by anyone who has it, so it isn't a per-tenant boundary.

</CalloutBox>

## 5. Vercel, Supabase, and Next.js

Nothing about a multi-tenant setup changes how you install PostHog, and this stack is well-trodden.

**Next.js and Vercel:** follow the [Next.js docs](/docs/libraries/next-js) for the client and server setup. Two things worth doing early:

- Set up a [reverse proxy](/docs/advanced/proxy/vercel) so tracking blockers don't cost you events. If you'd rather not run one, the [managed reverse proxy](/docs/advanced/proxy/managed-reverse-proxy) does it for you.
- In [Vercel Functions](/docs/libraries/vercel#vercel-functions), initialize `posthog-node` with `flushAt: 1` and `flushInterval: 0` and use `await posthogClient.captureImmediate(...)`, so events aren't lost when the function freezes or shuts down.

The [Vercel marketplace integration](/docs/integrations/vercel-marketplace) can provision PostHog and wire up your environment variables for you.

**Supabase:** link your Postgres tables as a [Supabase source](/docs/cdp/sources/supabase) to query them alongside your events. Use the Session pooler host rather than the Project URL, and create a dedicated read-only role instead of using the `postgres` superuser.

This is where tenant metadata that's awkward to send as group properties becomes useful. Sync your `organizations` table, then [join it](/docs/data-warehouse/join) in [SQL](/docs/sql) to break events down by columns you never captured as events – contract value, region, or account owner.

<CalloutBox icon="IconFlask" title="CDC sync is in alpha" type="action">

The Supabase source uses the [Postgres integration](/docs/cdp/sources/postgres#sync-methods), so change data capture (CDC) sync is available – but it's currently in **alpha**. Use full or incremental sync if you need something battle-tested, and [share feedback](https://app.posthog.com/home#panel=support%3Afeedback%3A%3Alow%3Atrue) if you try CDC.

</CalloutBox>
