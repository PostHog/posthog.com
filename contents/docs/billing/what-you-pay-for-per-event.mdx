## What happens to one event

Between your SDK and a chart, an event goes through six jobs. Each one exists because something broke without it.

### Getting it in

[Our SDKs](/docs/libraries) batch, compress, and retry. The capture service decompresses the payload, validates the request, and corrects the timestamp using the time your client says it sent the batch. That way a phone that was offline for an hour still lands its events in the right minute. Capture also assigns a UUID if the SDK didn't.

If the write to the queue fails, capture returns an error and the SDK retries, so a brief outage on our side doesn't lose your data. A [reverse proxy](/docs/advanced/proxy) lets you send events from your own domain, past ad blockers.

Without it, events from a client with the wrong clock land on the wrong day, a retry counts twice, and tracking blockers remove a share of your traffic you never see.

### Not losing it

Every event goes into Kafka before anything else touches it. Capture only replies to your SDK once Kafka has acknowledged the write on every in-sync replica. The queue absorbs launch-day spikes and bots, and waits out database outages. Events from the same user stay in order.

Any single ID sending more than about 5,000 events a minute moves to an overflow lane, so it can't slow anyone else down. Nothing is dropped. If an ingestion worker crashes partway through a batch, Kafka redelivers it. Any event we can't process goes to a dead letter queue instead of disappearing.

Without it, a traffic spike or a database restart is data you never get back.

### Making it mean something

Ingestion validates each event, drops events older than a limit you set, and applies your [transformations](/docs/data-pipelines/transformations). Along the way:

- GeoIP adds country and city.
- [Cookieless](/tutorials/cookieless-tracking) events get a daily-rotating hash instead of a cookie.
- UTM and referrer data lands on the [session](/docs/data/sessions).
- Every event and property name is cataloged, so the UI, SQL autocomplete, and [PostHog AI](/docs/posthog-ai) know what exists.

If something's wrong with an event, you get an [ingestion warning](/docs/data/ingestion-warnings) that names it.

Identified events also go through [identity resolution](/docs/product-analytics/identity-resolution). We create the person, merge their anonymous history when they identify, and update person properties in order. That's what the person profile charge pays for.

Without it, one platform renames a property, one metric quietly splits into two, and nobody notices until a board meeting.

### Storing it for seven years

Events land in a sharded, replicated ClickHouse cluster, with properties compressed using ZSTD. Hot data sits on local NVMe and moves to cheaper tiers as it ages. Every week we analyze slow queries and materialize the columns that would make them fast.

We're also [rebuilding the storage format](/blog/changing-event-storage) so each property is stored once with its real type, which makes common queries up to 2x faster. GDPR deletions run as batched jobs, because deleting from ClickHouse rewrites whole partitions.

Paid plans [keep events for seven years](/docs/data/events-retention) and free plans for one year. You can set a shorter window.

Without it, a single-node ClickHouse with no replica is one disk failure away from losing everything, and nobody tunes it until a query starts timing out.

### Querying it as often as you like

Funnels, retention, paths, lifecycle, [SQL](/docs/data-warehouse/sql), and [PostHog AI](/docs/posthog-ai) all run on the same events, and query compute is included in the event price.

We run guard rails so one query can't take a cluster down. A query gets 60 seconds by default and 10 minutes in the background, and each organization has a concurrency limit. Inside those limits, queries aren't metered.

Without it, a cluster you run yourself bills per node-hour whether anyone queries it or not, and one teammate's heavy query slows everyone else down.

### Getting it out

[Batch exports](/docs/data-pipelines/batch-exports) send events to S3, Snowflake, BigQuery, Postgres, Redshift, Databricks, or Azure as JSON or Parquet. The first 1 million rows you export each month are free. Past that, exports bill per row under [Data pipelines pricing](/pricing), not the event price. The [query API](/docs/api/query) returns anything SQL can express. If you leave, your data leaves with you.

## Four costs your agent's estimate leaves out

### Storage for years, not months

An agent's estimate covers the first month of storage. The per-event price covers 84. Your own storage cost compounds: in month 12 you're storing 12 months of events, and in month 84 you're storing 84. Your ledger below shows what that adds up to at your volume, your cloud's price per GB-month, and a replica or two.

### Compute, forever

Every event gets read many times over its life. Every dashboard refresh, funnel, cohort recalculation, and SQL query reads it again. That's in the price. Asking [PostHog AI](/docs/posthog-ai) spends [AI credits](/docs/posthog-ai/pricing) on top, but the queries it runs are covered. A cluster you run bills by the hour whether anyone is looking or not.

### Scaling you didn't plan for

A launch, a bot, an SDK retry loop, or an acquisition can multiply your event volume in a day. Our pipeline absorbs that with Kafka, overflow lanes, and clusters sized for our whole customer base. Your cluster is sized for last month.

### Trust

You can put the numbers in front of a board or an investor without an asterisk. We have [SOC 2](/docs/privacy/soc2), [HIPAA](/docs/privacy/hipaa-compliance), and GDPR controls, and a public [status page](/status). When [we lost Logs data in February 2026](/handbook/company/post-mortems/2026-02-20-posthog-us-logs-data-loss), we published what happened and what we changed. A pipeline one engineer runs on the side rarely gets a post-mortem.

## Your own ledger

Fill this in with your numbers.

| Input | Your number | Notes |
|---|---|---|
| Events per month | | Your [billing page](https://app.posthog.com/organization/billing) shows it |
| Compressed bytes per event | | Measure it on a sample of your real events in ClickHouse |
| Replicas | | At least 2, or a disk failure is data loss |
| Months retained | 84 | To match a paid plan |
| Storage price per GB-month | | Your cloud's list price for the tier you use |
| Compute nodes × hourly price | | Ingestion and query nodes, 730 hours a month |
| Queue | | Managed Kafka or equivalent |
| Engineer hours per month | | Upgrades, schema changes, backups, SDK maintenance |
| On-call | | Who, and what it costs them |

Then:

```
GB stored at month N = events × bytes × replicas × N ÷ 1,000,000,000
storage at month N   = GB stored × price per GB-month
monthly total        = storage + compute + queue + (engineer hours × loaded rate)
your cost per event  = monthly total ÷ events per month
```

Compare the last line to a PostHog bill at the same volume. Take the monthly total from the [pricing calculator](/pricing), with any add-ons you need, and divide it by your monthly events. The free million and the falling tiers make that average lower than the rates shown above. Run it for month 1 and again for month 36.

## When building is the right call

- You sell analytics infrastructure, so the pipeline is your product.
- You already run ClickHouse for something else, and a data team treats it like a product.
- Your data doesn't fit an events table: wide logs, sensor-rate time series, or rows you need to update in place.

If none of those apply, paying per event is cheaper.

## Cut the bill without leaving

[Capture fewer events](/docs/product-analytics/cutting-costs), send [anonymous events](/docs/data/anonymous-vs-identified-events) where you don't need a person profile, and set a [billing limit](/docs/billing/limits-alerts). A [shorter retention window](/docs/data/events-retention#custom-retention) doesn't lower the bill, because you pay when an event is ingested, not while it's stored, and deleted events don't come back.
