Initialize the SDK with your public project token. Server-side SDKs also need a secret API key for local evaluation and server-side remote config. This can be a project secret API key (recommended) or the legacy feature flags secure API key. Keep it secret: don't use it in frontend code or expose it to users.

We recommend using a **project secret API key** with the `feature_flag:read` scope. Project secret API keys are hashed at rest, scoped to only what they need, and you can create up to 50 per project, so you can issue and roll keys per deployment without affecting the others.

A [personal API key](/docs/api/personal-api-keys) is a private credential tied to your account for management API access. [Source-map uploads](/docs/error-tracking/upload-source-maps/node#manual-setup) use separate CLI authentication, not the `feature_flag:read` project secret.

> **Building a frontend, mobile, or CLI app?** Local evaluation and the secret API key are for server-side use only. To evaluate flags from client-side code, use a [client-side SDK](/docs/libraries) or call the public [`/flags` endpoint](/docs/api/flags) with your [project token](/docs/feature-flags/installation#where-to-find-your-project-api-key) instead. The project token is safe to expose to users. Never include secret or personal API keys in distributed client code.

> **Note:** Existing [feature flags secure API keys](/docs/feature-flags/project-wide-settings#feature-flags-secure-api-key) (deprecated) and personal API keys continue to work. We recommend [switching to a project secret API key](/docs/feature-flags/project-wide-settings#migrating-to-a-project-secret-api-key). If you use [encrypted payloads](/docs/feature-flags/remote-config#encrypted-payloads), keep a personal API key for those requests, since it's the only key that returns them decrypted.

#### How to create a project secret API key

1. Go to [**Project secret API keys**](https://app.posthog.com/settings/environment-secret-api-keys) in your project settings. You need project admin access to create a key.

2. Create a new key with the **Local feature flag evaluation** preset (the `feature_flag:read` scope) and give it a label.

3. Copy the key. It's only displayed once, so store it somewhere safe, like a secrets manager.

4. Pass it in the client's options, separately from the public project token. Use `secretKey` in `posthog-node` 5.40.0+ or `secret_key` in synchronous `posthog` 7.22.1+. Older versions use `personalApiKey` or `personal_api_key`, respectively. These legacy options remain deprecated aliases in newer versions. The Java SDK uses `personalApiKey`. The option name does not change the key's permissions.
