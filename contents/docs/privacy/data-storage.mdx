This guide covers the various features available **after data reaches PostHog Cloud servers** to help you achieve your privacy goals. If you have data that cannot reach a third-party server like PostHog, please omit them during [data collection](/docs/privacy/data-collection).

This guide covers the following features:

| Feature                                                           | Description                                                      |
| ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| [Data storage location](#data-storage-location)                   | Control where your data is physically stored for GDPR compliance |
| [Processing data before storage](#processing-data-before-storage) | Redact or filter data before it's stored in PostHog              |
| [Data retention](#data-retention)                                 | How long PostHog keeps each type of data                         |
| [Data deletion](#data-deletion)                                   | Tools to help comply with data deletion requests                 |
| [Data access control](#data-access-control)                       | Manage who can access what data in PostHog                       |

## Data storage location

If you require GDPR compliance, there are [specific guidelines](/docs/privacy/gdpr-compliance#you-should-not-transfer-eu-users-personal-data-outside-the-eu) on the location of data storage if you collect personal data. If you require robust GDPR compliance, we recommend using [PostHog Cloud EU](/eu) – a managed version of PostHog that's hosted on servers based in Frankfurt.

## Processing data before storage

PostHog supports [realtime transformations](/docs/data-pipelines/transformations) of data **before it's stored in PostHog**. These transformations are applied to all events captured in realtime, so you can use them to:

- [Hashing PII data](https://posthog.com/docs/data-pipelines/transformations/template-hash-properties) before it's stored in PostHog
- Disabling default [GeoIP enrichment transformations](https://posthog.com/docs/data-pipelines/transformations/template-geoip)
- [Dropping events](https://posthog.com/docs/data-pipelines/transformations/drop-events) based on a filter
- [IP anonymization](https://posthog.com/docs/data-pipelines/transformations/template-ip-anonymization)

When in doubt, you can always create your own [custom transformation](https://app.posthog.com/pipeline/new/transformation/hog-template-blank-transformation). Custom transformations use the [Hog language](/docs/hog) to transform data.

### Discarding IP addresses at project level

You can configure your project to discard client IP addresses from stored events. Navigate to [**Settings** > **Project** > **IP data capture configuration**](https://app.posthog.com/settings/project#datacapture) and enable the **Discard client IP data** toggle.

When this setting is enabled:

- Client IP addresses are **not stored** with your events
- Transformations like [GeoIP enrichment](https://posthog.com/docs/data-pipelines/transformations/template-geoip) and [bot detection](https://posthog.com/docs/data-pipelines/transformations/template-bot-detection) can **still use the IP** before it is discarded

This allows you to enrich your events with location data or filter out bot traffic while ensuring raw IP addresses are not retained in your data.

> **Note:** This does not apply when [Cookieless server hash mode](/tutorials/cookieless-tracking) is enabled. In cookieless mode, the IP is stripped before transformations run, so GeoIP enrichment and bot detection won't enrich your events.

## Data retention

How long PostHog keeps your data depends on the type of data. This table covers the main types. Follow the links for details and settings.

| Data                            | How long PostHog keeps it                                                                                                                                                  |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Events                          | Depends on your plan and retention setting. See [events retention](/docs/data/events-retention).                                                                        |
| Person profiles and properties  | Until you [delete them](#data-deletion). Events retention doesn't apply to them.                                                                                           |
| Session recordings              | Depends on your plan. See [recording retention](/docs/session-replay/recording-retention).                                                                                 |
| AI events                       | The large properties of `$ai_` events, like prompts and outputs, are deleted after 30 days. See [AI event data retention](/docs/ai-observability/data-retention).           |
| Logs                            | 14 days by default. See [logs retention](/docs/logs/pricing#retention).                                                                                                    |
| Heatmaps                        | 90 days.                                                                                                                                                                   |
| Data pipeline logs              | 90 days for the logs of destinations and transformations.                                                                                                                 |
| File download exports           | One week. See [file download exports](/docs/data-pipelines/file-download-exports).                                                                                         |
| Query log                       | 3 months. See [query log retention](/docs/data/query-log#retention).                                                                                                       |
| PostHog AI chats                | Until the user, project, or organization they belong to is deleted. Deleting a chat hides it, but PostHog keeps it until then.                                             |
| Support tickets                 | While your account is active. Deleted tickets are permanently removed 14 days after deletion.                                                                              |
| Backups                         | About two weeks for event data and about 12 months for app data. See [backups](#backups).                                                                                  |

### Backups

PostHog keeps backups so it can restore service after an incident. Backups expire on a fixed schedule:

- **Event data:** about two weeks
- **App data stored in Postgres**, such as your account, project settings, and support tickets: about 12 months

Retention periods and deletion requests don't apply to data inside backups. Data you delete stays in existing backups until those backups expire.

## Data deletion

You can remove unwanted data from PostHog by deleting groups and persons.

| What to delete    | Where to delete                                                                           | Additional details                                                                                                                                                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Your account**  | [Account settings](https://us.posthog.com/settings/user#user-delete)                      | Account is deleted immediately; all stored data about you is cleared within 30 days, apart from copies in [backups](#backups). See [deleting your account](/docs/settings/account-settings#deleting-your-account).                                                   |
| **Projects**      | [Project settings](https://us.posthog.com/settings/project#project-delete)                | All data under the project (including events) are automatically removed                                                                                                                                                    |
| **Organizations** | [Organization settings](https://us.posthog.com/settings/organization#organization-delete) | Deletion is processed in the background and typically takes a couple of minutes. You'll see a blocking screen while it completes. All data under the organization's projects (including events) are automatically removed. |
| **Persons**       | [In the persons tab](https://us.posthog.com/persons), [by API](#right-to-be-forgotten)    | When a person is deleted, all events and [session recordings](/docs/session-replay) for that person can be deleted. Some data isn't covered, see [what deleting a person doesn't remove](#what-deleting-a-person-doesnt-remove)                                                                                                          |

Organization admins can also set a [custom events retention window](/docs/data/events-retention#how-to-customize-your-retention-period). PostHog deletes events older than the window at the next monthly cleanup, not right away. To answer a right to be forgotten request, delete the person instead.

### Right to be forgotten

<DistinctIdReuseWarning />

Persons and events can be deleted using our API endpoints. This action requires a [personal API key](https://us.posthog.com/settings/user-api-keys).

To query all persons in your project, use the [GET Persons API endpoint](/docs/api/persons#get-api-projects-project_id-persons). You can filter for specific subsets of persons using the query parameters. For example, you can get a specific person by filtering by email:

<MultiLanguage>

```bash
export POSTHOG_PERSONAL_API_KEY=[your personal api key]
curl \
    -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" \
    https://us.posthog.com/api/projects/:project_id/persons?email={EMAIL}
```

```javascript
const response = await fetch(
  "https://us.posthog.com/api/projects/:project_id/persons?email={EMAIL}",
  {
    headers: {
      Authorization: "Bearer [your personal api key]",
    },
  },
);
```

```python
import requests

api_key = "[your personal api key]"
project_id = "[your project id]"
response = requests.get(
    "https://us.posthog.com/api/projects/{project_id}/persons?email={EMAIL}".format(
        project_id=project_id
    ),
    headers={"Authorization": "Bearer {}".format(api_key)},
).json()
```

</MultiLanguage>

To delete persons and their events, use the [DELETE Persons API endpoint](/docs/api/persons#post-api-projects-project_id-persons-bulk_delete) with the person's UUID (returned as `id` in the persons API response). To delete the person's corresponding events, add the `delete_events=true` parameter. To also delete their session recordings, add `delete_recordings=true`:

<MultiLanguage>

```bash
curl -X DELETE "https://app.posthog.com/api/projects/<project_id>/persons/<person_uuid>?delete_events=true&delete_recordings=true" \
     -H "Authorization: Bearer <personal_api_key>"
```

```javascript
fetch(
  "https://app.posthog.com/api/projects/<project_id>/persons/<person_uuid>?delete_events=true&delete_recordings=true",
  {
    method: "DELETE",
    headers: {
      Authorization: "Bearer <personal_api_key>",
    },
  },
)
  .then((response) => response.json())
  .then((data) => console.log(data))
  .catch((error) => console.error("Error:", error));
```

```python
import requests

api_key = "<personal_api_key>"
project_id = "<project_id>"
person_uuid = "<person_uuid>"

url = "https://app.posthog.com/api/projects/{}/persons/{}?delete_events=true&delete_recordings=true".format(
    project_id, person_uuid
)
headers = {"Authorization": "Bearer {}".format(api_key)}

response = requests.delete(url, headers=headers)
print(response.json())
```

</MultiLanguage>

This request deletes all events of the person(s) captured before the deletion request. When `delete_recordings=true` is set, all session recordings for the person are permanently destroyed using crypto-shredding, which irreversibly deletes the encryption keys making recordings unreadable. This process cannot be undone.

#### Bulk delete response

The [bulk_delete endpoint](/docs/api/persons#post-api-projects-project_id-persons-bulk_delete) returns a `202` once the request is accepted. Person records are not removed during the request. They are queued and deleted in the background, usually within a few minutes, so a successful call reports the matched persons in `persons_queued_for_deletion` and `persons_deleted` stays `0`. Treat `persons_queued_for_deletion` as the success signal, not `persons_deleted`. The endpoint reports failures in `deletion_errors` rather than with an error status, so check that list: a `202` with entries means those persons were not deleted and you should retry them.

| Field                            | Type    | Description                                                                                                                                                     |
| -------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `persons_found`                  | integer | Number of persons matched by the provided IDs or distinct IDs                                                                                                   |
| `persons_queued_for_deletion`    | integer | Number of persons queued for deletion in the background. Their person records and distinct IDs are removed shortly after the request completes. `0` if `keep_person` was set to true |
| `persons_deleted`                | integer | Number of person records deleted during the request itself. `0` when the deletion was queued or `keep_person` was set to true                                   |
| `events_queued_for_deletion`     | boolean | Whether event deletion was queued for the matched persons                                                                                                       |
| `recordings_queued_for_deletion` | boolean | Whether recording deletion was queued for the matched persons                                                                                                   |
| `deletion_errors`                | array   | Persons whose deletion did not complete during the request, each containing `person_uuid` and the `step` that failed. Always empty when the deletion was queued |

Deleting a single person with `DELETE /api/projects/:project_id/persons/:id` still removes the person during the request and returns an empty `202`.

#### Checking deletion status

Event deletions run [asynchronously](#asynchronous-data-deletion) during non-peak hours. To check the status of queued event deletions, use the deletion status endpoint:

<MultiLanguage>

```bash
export POSTHOG_PERSONAL_API_KEY=[your personal api key]
curl \
    -H "Authorization: Bearer $POSTHOG_PERSONAL_API_KEY" \
    "https://us.posthog.com/api/projects/:project_id/persons/deletion_status?status=pending"
```

```javascript
const response = await fetch(
  "https://us.posthog.com/api/projects/:project_id/persons/deletion_status?status=pending",
  {
    headers: {
      Authorization: "Bearer [your personal api key]",
    },
  },
);
```

```python
import requests

api_key = "[your personal api key]"
project_id = "[your project id]"
response = requests.get(
    "https://us.posthog.com/api/projects/{project_id}/persons/deletion_status?status=pending".format(
        project_id=project_id
    ),
    headers={"Authorization": "Bearer {}".format(api_key)},
).json()
```

</MultiLanguage>

**Query parameters:**

- `status` - Filter by `pending`, `completed`, or `all` (default: `all`)
- `person_uuid` - Filter by a specific person UUID

**Response fields:**

| Field                | Type   | Description                                                       |
| -------------------- | ------ | ----------------------------------------------------------------- |
| `person_uuid`        | string | The UUID of the person whose events are queued for deletion       |
| `created_at`         | string | When the deletion was requested (ISO 8601)                        |
| `status`             | string | Current status: `pending` or `completed`                          |
| `delete_verified_at` | string | When the deletion was verified complete, or null if still pending |

### Manual data deletion

You can manually delete persons and their events in the PostHog UI:

- Select **Persons** from the left-hand menu
- Search for the person via their `distinct_id` or a property like email.
- Click **view** next to the person within the search results
- Click **Delete person** to remove them and all their associated data from the PostHog instance. You will be prompted to confirm this action.

### Deleting events without a person profile

Person deletion removes events by person. Events captured without a [person profile](/docs/data/persons), such as [anonymous events](/docs/data/anonymous-vs-identified-events), have no person to delete, so the person deletion tools can't remove them on their own.

To delete all the events for one distinct ID, give the distinct ID a person profile first, then delete that person:

1. Send a `$set` event for the distinct ID with the [capture API](/docs/api/capture). This creates a person profile for the distinct ID, and its existing events and recordings are linked to that person. Send it from your server or with `curl`, because the [JavaScript Web SDK](/docs/libraries/js) ignores person calls when `person_profiles` is set to `'never'`.
2. Check that the person exists by calling `GET /api/projects/:project_id/persons/?distinct_id=<distinct_id>` with a [personal API key](/docs/api#authentication). If `results` is empty, the `$set` event hasn't been processed yet, so wait a minute and check again.
3. Call the [bulk delete endpoint](/docs/api/persons#post-api-projects-project_id-persons-bulk_delete) with the distinct ID in `distinct_ids`, `delete_events: true`, and `delete_recordings: true`. This deletes the person you just created, along with its events and recordings.
4. [Check the deletion status](#checking-deletion-status). The events are deleted once `delete_verified_at` has a value.

Like other event deletions, the events are deleted [asynchronously](#asynchronous-data-deletion).

### Deleting specific events

To delete events that match more specific criteria, such as events from a specific date range or events with specific properties, [contact support](https://app.posthog.com/#panel=support) and include:

- Your project ID
- How to find the events, such as an event name, property filters, a date range, or a [SQL query](/docs/sql)
- How many events you expect the deletion to match

Support can request the deletion for you, or turn on event deletion in the PostHog app for your organization. Like other event deletions, it runs [asynchronously](#asynchronous-data-deletion).

### Events that arrive after a deletion

A deletion removes the events that are stored when it runs. It doesn't remove events that reach PostHog later, such as:

- New events for the same distinct ID. If person profiles are on, these create a new person.
- Events captured earlier but sent late, for example events queued on a mobile device while it was offline, or events you import.

To delete all of a person's data, stop sending events for them first, then delete the person or request the event deletion. If more events arrive afterwards, delete them with a new request.

### Removing properties from events

PostHog deletes whole events. It can't remove or change a single property on an event that's already stored.

To remove a property, you can:

- **Delete the events** that contain it. See [deleting specific events](#deleting-specific-events).
- **Delete the events and import a cleaned copy:** export the events, remove the property from your copy, delete the events in PostHog, then send your copy back with the [batch capture API](/docs/api/capture#batch-events). Keep each event's original `timestamp` and `distinct_id`, and set `historical_migration` to `true`.

Imported events go through ingestion again, the same as new events:

- **They count as new events for billing.** Usage is recorded when PostHog receives an event, not at the event's original timestamp.
- **`$set` and `$set_once` properties are applied again.** They can overwrite the current properties of the person with older values. Remove `$set` and `$set_once` from your copy unless you want to apply them again. Events like `$identify` and `$create_alias` also link distinct IDs again.
- **Person properties on the events are taken from the person as it is now**, not as it was when the events were first captured.
- **Your data pipelines run on them again.** [Transformations](/docs/data-pipelines/transformations) change them again, [destinations](/docs/data-pipelines/destinations) can send them to other tools again, and [batch exports](/docs/data-pipelines/batch-exports) can export them again. Pause or filter these if you don't want the events processed twice.

Person properties copied onto events stay on those events after you change or remove them on the person profile. To remove them from events, use one of the options above.

To stop collecting a property, remove it before it's stored. See [processing data before storage](#processing-data-before-storage).

### What deleting a person doesn't remove

Deleting a person, along with their events and recordings, doesn't remove every copy of their data:

- **AI events:** person deletion removes the person's `$ai_` events from the events table, but not the full copy PostHog keeps in `ai_events`, which includes prompts and outputs. That copy is deleted after [30 days](/docs/ai-observability/data-retention).
- **Heatmaps:** heatmap data can't be deleted per person. It expires after 90 days.
- **PostHog AI chats:** chats that quote the person's data stay until the chat's user, project, or organization is deleted.
- **Events without a person profile:** see [deleting events without a person profile](#deleting-events-without-a-person-profile).
- **Backups:** deleted data stays in [backups](#backups) until they expire.
- **Data you've sent elsewhere:** data that [batch exports](/docs/data-pipelines/batch-exports) or destinations already sent to other tools stays there. Delete it in those tools.

### When expired events are deleted

PostHog doesn't delete events as soon as they pass your [retention period](/docs/data/events-retention). A cleanup runs once a month and deletes a whole calendar month of events at a time, once every event in that month has expired. This means events from early in a month stay longer than events from late in the month, and an event can stay for up to about two months past your retention period.

Deleted events also stay in [backups](#backups) for about two weeks.

### Asynchronous data deletion

While most data in PostHog is deleted instantly, event data is not. Instead, event data is cleared asynchronously during non-peak usage times (weekends on PostHog Cloud). The request cutoff time for each batch deletion is two days before the batch runs. Deletion requests that miss the cutoff time will be included in the batch after next.

This is done because data deletion in [ClickHouse](/docs/how-posthog-works/clickhouse) is expensive and it can impact performance for other users.

## Data access control

An important part of protecting your users' privacy is to control who can access what data in PostHog. PostHog provides access control at 3 levels:

1. [Organization level](/docs/settings/access-control#1-organization-level)
2. [Project level](/docs/settings/access-control#2-project-level)
3. [Resource level](/docs/settings/access-control#3-resource-level)

It's up to you to use these access control features to grant access to only the people who need to access the data.

You can follow this comprehensive guide to [access control](/docs/settings/access-control) to learn more.
