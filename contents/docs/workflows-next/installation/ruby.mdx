The [Ruby SDK](/docs/libraries/ruby) sends transactional emails from version 3.30.0. Before you start, you need a transactional email ([templates and variables](/docs/workflows-next/transactional/templates#create-a-transactional-email)) or content from your code, and a project secret API key ([create an API key](/docs/workflows-next/transactional/send-from-code#create-an-api-key)). The [quick start](/docs/workflows-next/installation) sets up both and sends a test email in a few minutes.

New to sending from code? Read [send emails from code](/docs/workflows-next/transactional/send-from-code) first.

## Install

Add this to your `Gemfile`:

```ruby
gem "posthog-ruby", "~> 3.0"
```

## Set up the client

Add your project secret API key to the PostHog client that your app already has. The project token keeps capturing events. The secret key sends email, so keep it on your server and never ship it to the browser.

```ruby
require 'posthog'

$posthog = PostHog::Client.new({
  api_key: '<ph_project_token>',
  host: '<ph_client_api_host>',
  secret_key: ENV.fetch('POSTHOG_PROJECT_SECRET_API_KEY')
})
```

When `secret_key` is set, the client also loads flag definitions with it for [local evaluation](/docs/feature-flags/local-evaluation) when it starts. Give the key the **Feature flag** read scope too, or the client logs a failed load each time it polls.

Shut the client down when your app exits, not after each send. If your app sends through a reverse proxy or a self-hosted PostHog, see [use a proxy or self-hosted PostHog](#use-a-proxy-or-self-hosted-posthog).

### Use in Rails

With [`posthog-rails`](/docs/libraries/ruby-on-rails), reuse the client initialized by `PostHog.init`. Add the secret key to your existing initializer:

```ruby file=config/initializers/posthog.rb
PostHog.init do |config|
  config.api_key = "<ph_project_token>"
  config.host = "<ph_client_api_host>"
  config.secret_key = ENV.fetch("POSTHOG_PROJECT_SECRET_API_KEY")
end
```

Use `PostHog.emails` wherever the examples below use `$posthog.emails`. Rails handles client shutdown.

Pass email options such as `app_host` and `email_request_max_retries` as a hash to `PostHog.init(...)`, not in its configuration block.

## Send an email

```ruby
def send_password_reset(user, reset_link, reset_request_id)
  # Raises PostHog::EmailError when PostHog doesn't queue the email. Branch on error.code.
  result = $posthog.emails.send(
    to: user.email,
    template_id: '<template_id>',
    template_data: { first_name: user.first_name, reset_link: reset_link },
    distinct_id: user.id.to_s,
    # Identifies this one email, so a retry never sends it twice
    idempotency_key: "password-reset-#{reset_request_id}"
  )
  result.id
end
```

`send` returns a `SendResult`, and `result.id` is the message ID. When PostHog doesn't queue the email, `send` raises `PostHog::EmailError`, and its `code` is one of the codes in the [errors table](/docs/workflows-next/transactional/retries-and-errors#what-to-retry). A wrong argument raises `ArgumentError` before any request.

A successful result means the email was queued, not delivered. Use [status checks](#check-an-emails-status) to confirm delivery.

A `network_error` or a `503` doesn't mean that the email failed, because PostHog can still have queued it. Retry with the same idempotency key. If you resend the email through another email provider, the recipient can get it twice.

### Fields

Fields marked "template only" work only with a template made in PostHog. Fields marked "code only" work only with content from your code.

| Field | Required | What it does |
| --- | --- | --- |
| `to` | Yes | The recipient's email address. |
| `template_id` | Yes, template only | The ID of the transactional email in PostHog. |
| `template_data` | No, template only | Values for the template's variables. |
| `distinct_id` | No | Links the email to your user's person in PostHog. |
| `idempotency_key` | No | Identifies this one email, so a retry never sends it twice. |
| `max_retries` | No | How many times the client retries this send. |
| `template_key` | Yes, code only | Names the email, so PostHog groups its metrics and sends. |
| `subject` | Yes, code only | The subject line. |
| `html` | One of `html` or `text`, code only | The HTML body. |
| `text` | One of `html` or `text`, code only | The plain text body. PostHog makes it from `html` if you leave it out. |
| `from` | No, code only | The sender. Without it, PostHog uses the project's default sender. |
| `reply_to` | No, code only | One reply-to address or a list. |
| `cc` | No, code only | One copy address or a list. |
| `bcc` | No, code only | One blind copy address or a list. |
| `attachments` | No, code only | A list of files to attach. |
| `sensitive` | No, code only | Marks the email as sensitive, for login links, reset tokens, or codes. |
| `tracking` | No, code only | What PostHog tracks: opens, clicks, and engagement events. |

Sending needs version 3.30.0 or later. `sensitive` and `tracking` need 3.33.0, and `cc`, `bcc`, and `attachments` need 3.34.0.

### Timeouts and retries

The client retries for you. It retries network errors, rate limits, an in-flight idempotency key, and a `503` up to two times, with the same idempotency key. It waits about 1 second and then 2 seconds, or longer if the server's `Retry-After` asks for it. When `Retry-After` asks for more than 30 seconds, the client raises the error at once. Each request waits up to 15 seconds to connect, and up to 15 seconds for each read or write.

To change this, set `email_request_timeout_seconds` and `email_request_max_retries` on the client, or `max_retries` on one send.

## Send from a background job

Send from a job queue when the email shouldn't slow down the request, such as an email address check after a signup. Let the queue own the retries:

- Pass `max_retries: 0` to `send`, so that the client doesn't retry inside the job.
- Keep the idempotency key the same on every attempt.
- Finish the retries within 24 hours. PostHog remembers an idempotency key for 24 hours after it queues the email, so a later retry can send the email twice.
- Retry only the errors that a later attempt can fix. Every other code fails the same way again.

This example uses [Sidekiq](https://github.com/sidekiq/sidekiq) 6.5.2 or later. `sidekiq_retry_in` returns `nil` to retry with Sidekiq's usual backoff, or `:kill` to move the job to the Dead set with no more retries.

```ruby
class PasswordResetEmailJob
  include Sidekiq::Job
  # Five retries finish within minutes, well inside the 24 hours that PostHog keeps an idempotency key
  sidekiq_options retry: 5

  # A later attempt can fix these. Any other code fails the same way again.
  RETRYABLE_CODES = %w[network_error idempotency_key_in_flight throttled delivery_unavailable].freeze

  sidekiq_retry_in do |_count, error|
    retryable = error.is_a?(PostHog::EmailError) && RETRYABLE_CODES.include?(error.code)
    retryable ? nil : :kill
  end

  def perform(user_id, email, first_name, reset_link, reset_request_id)
    $posthog.emails.send(
      to: email,
      template_id: '<template_id>',
      template_data: { first_name: first_name, reset_link: reset_link },
      distinct_id: user_id,
      # The same key on every attempt, so a retried job never sends the email twice
      idempotency_key: "password-reset-#{reset_request_id}",
      # Sidekiq retries the job, so the client doesn't retry on its own
      max_retries: 0
    )
  end
end
```

## Link emails to your users

Pass the distinct ID that you pass to `identify()` as `distinct_id`, and leave it out for someone who isn't a user yet. See [link emails to your users](/docs/workflows-next/transactional/send-from-code#link-emails-to-your-users) for how PostHog records each case.

## Send content from your code

`send` also takes content that your code rendered, with no template in PostHog. Render it first with your template engine, such as ERB or Action Mailer views.

```ruby
def send_password_reset(user, html, reset_request_id)
  result = $posthog.emails.send(
    to: user.email,
    template_key: 'password-reset',
    subject: 'Reset your password',
    html: html,
    from: 'Hedgebox <security@example.com>',
    distinct_id: user.id.to_s,
    idempotency_key: "password-reset-#{reset_request_id}"
  )
  result.id
end
```

`capture_engagement` is deprecated. Pass `tracking: { engagement: false }` instead, and don't set both. A send with both `template_id` and `template_key` raises `ArgumentError`.

See [content from your code](/docs/workflows-next/transactional/from-code) for what each field does and the checks PostHog runs.

### Copies and attachments

Copies and attachments need version 3.34.0 or later.

Each file in `attachments` is a Hash with `filename` and the file's bytes as `content`, and can also have `content_type` and `content_id`. Read the file with `File.binread`, not `File.read`. The client uploads each file before it sends the email, and checks the limits first. If an upload fails, `send` raises an error, and PostHog sends nothing.

```ruby
$posthog.emails.send(
  to: user.email,
  template_key: 'receipt',
  subject: 'Your receipt',
  html: html,
  cc: 'billing@example.com',
  attachments: [
    { filename: 'receipt.pdf', content: File.binread(pdf_path), content_type: 'application/pdf' }
  ],
  distinct_id: user.id.to_s
)
```

See [attachments and copies](/docs/workflows-next/transactional/attachments) for the limits, inline images, and errors.

When migrating providers, set the client option `migrated_from`, for example `migrated_from: "resend"`.

### Open and click tracking

`sensitive` and `tracking` need version 3.33.0 or later. For example, to track the clicks of an email with no secrets:

```ruby
$posthog.emails.send(
  to: 'ada@example.com',
  template_key: 'order-shipped',
  subject: 'Your order shipped',
  html: html,
  sensitive: false,
  tracking: { clicks: true }
)
```

`tracking` takes `true`, `false`, or a hash with `opens`, `clicks`, and `engagement`. See [sensitive data and tracking](/docs/workflows-next/transactional/sensitive-data) for the defaults and rules.

## Check an email's status

```ruby
def email_bounced(message_id)
  status = $posthog.emails.get(message_id)
  status.status == 'bounced'
rescue PostHog::EmailError => e
  # The first status can take a few seconds to arrive. Try again later.
  return nil if e.code == 'not_found'

  raise
end
```

`get` returns a `Status` with `id`, `status`, `created_at`, `status_at`, and `reason`. The helper returns `nil` while the status isn't there yet, so check for `nil` before you read the result as "not bounced".

The key needs **Transactional email** read or write access.

The client doesn't retry a `not_found`, which you can get right after a send. Try again a few times with a short wait before you treat the email as missing.

See [status and troubleshooting](/docs/workflows-next/transactional/status) for what each status and reason means.

## Test without sending email

The client sends email with Ruby's `Net::HTTP`, so [WebMock](https://github.com/bblimke/webmock) can stub the request and show exactly what your code sends, with no network call. This tests your integration, not delivery. To test delivery, send a real email to your own address and check the [**Log**](/docs/workflows-next/transactional#log) on the **Transactional** tab.

`test_mode: true` does not disable email requests. Stub email sends, status reads, and feature flag definition requests in tests.

```ruby
require 'posthog'
require 'webmock/rspec'

RSpec.describe 'password reset email' do
  let(:send_url) { %r{/messaging/send/email/\z} }
  let(:posthog) { PostHog::Client.new(api_key: 'phc_test', secret_key: 'phs_test', test_mode: true) }

  before do
    stub_request(:get, %r{/flags/definitions}).to_return(status: 200, body: '{"flags":[]}')
    stub_request(:post, send_url).to_return(status: 202, body: '{"message_id":"msg_1","replayed":false}')
  end

  after { posthog.shutdown }

  it 'sends the email once, with its idempotency key' do
    result = posthog.emails.send(
      to: 'jane@example.com',
      template_id: '0190f6d2-7c1e-7b3a-9f5e-1c2d3e4f5a6b',
      idempotency_key: 'password-reset-1'
    )

    expect(result.id).to eq('msg_1')
    expect(a_request(:post, send_url).with(headers: { 'Idempotency-Key' => 'password-reset-1' }))
      .to have_been_made.once
  end
end
```

## Use a proxy or self-hosted PostHog

On PostHog Cloud, the client sends email to your region's app host, even when `host` is an ingestion host such as `us.i.posthog.com`. If `host` is a reverse proxy or a self-hosted PostHog, set `app_host` to your PostHog app URL. The client doesn't send email requests to a host that might be a proxy.

Flag definitions for local evaluation still load from `host` with the secret key. If that host is a proxy that must not see the key, leave `secret_key` off that client. Send email from a second client whose `host` is your PostHog host.
