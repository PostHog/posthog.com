Use the [PostHog Node.js SDK](/docs/libraries/node) to capture events and request errors from your [Fastify](https://fastify.dev/) app.

## Installation

Install the SDK in your Fastify app:

```bash
pnpm add posthog-node
```

This guide uses Fastify 5 and `posthog-node` 5.52.1 on Node.js. Get your project token and API host from your [project settings](https://us.posthog.com/settings/project).

## Set up PostHog

Create one PostHog client for your app. Register the hooks and error handler in the same Fastify scope as your routes, before those routes.

Process-level `enableExceptionAutocapture` does not capture errors that Fastify handles. Use `setErrorHandler` to capture these errors.

```js file=server.mjs
import Fastify from "fastify"
import { PostHog } from "posthog-node"

const app = Fastify()
const posthog = new PostHog("<ph_project_token>", {
    host: "<ph_client_api_host>",
})

// If you use authentication, register its onRequest hook before this hook.
app.addHook("onRequest", (request, _reply, done) => {
    posthog.withContext(
        {
            distinctId: request.user?.id,
            properties: { $request_method: request.method, request_id: request.id },
        },
        done,
        { fresh: true }
    )
})

app.setErrorHandler((error, request, reply) => {
    // Match Fastify's status precedence before applying the capture policy.
    let statusCode = reply.statusCode >= 400 ? reply.statusCode : 500
    if (error.status >= 400) {
        statusCode = error.status
    } else if (error.statusCode >= 400) {
        statusCode = error.statusCode
    }

    // Optional application policy: capture server errors only.
    if (statusCode >= 500) {
        posthog.captureException(error, undefined, {
            $response_status_code: statusCode,
            $request_path: request.routeOptions.url,
        })
    }

    // Keep Fastify's error serialization.
    reply.code(statusCode).send(error)
})

app.addHook("onClose", async () => {
    await posthog.shutdown()
})

app.get("/example", async () => {
    throw new Error("Example request failed")
})

await app.listen({ port: 3000, host: "127.0.0.1" })
```

## Request context and identity

Keep `onRequest` callback-based, not `async`. Calling `done` inside [`withContext`](/docs/libraries/node#contexts) continues the request in that context. `{ fresh: true }` prevents inheritance from an outer context.

`request.user` belongs to your application. It is not a built-in Fastify identity. Populate it with a verified user and a string `id` in an earlier authentication hook. Without authentication, this example captures exceptions without creating person profiles.

If authentication runs later, pass the verified ID directly to `captureException` instead of `undefined`.

Do not use `x-posthog-distinct-id` as proof of identity. Tracing headers are client-controlled analytics values, and this example does not read them. To link Session Replay, you can explicitly add a validated `sessionId` to the context. Never use it for authorization.

## Trace context

This optional setup requires the Node SDK release with `posthog-node/otel` and `ContextOptions.signal`. The base SDK version stated above does not include these APIs.

To add browser session and person IDs to application spans, register the [optional Node context processor](/docs/distributed-tracing/installation/nodejs#with-opentelemetry) on your existing OpenTelemetry provider before requests start. Reuse the `posthog` client above and keep the existing exporter and sampler.

Configure [`tracing_headers`](/docs/libraries/js/config#tracing-headers) for your backend hostname in the browser SDK. Replace the earlier `onRequest` hook with this Node.js setup:

```js
import { enrichCurrentSpan } from 'posthog-node/otel'

function readTracingId(value) {
    if (typeof value !== 'string') return undefined
    return value.replace(/[\x00-\x1f\x7f-\x9f]/g, '').trim().slice(0, 1000) || undefined
}

app.addHook('onRequest', (request, reply, done) => {
    const controller = new AbortController()
    const complete = () => {
        controller.abort()
        reply.raw.removeListener('finish', complete)
        reply.raw.removeListener('close', complete)
        request.raw.removeListener('aborted', complete)
    }
    reply.raw.once('finish', complete)
    reply.raw.once('close', complete)
    request.raw.once('aborted', complete)

    posthog.withContext(
        {
            distinctId: request.user?.id ?? readTracingId(request.headers['x-posthog-distinct-id']),
            sessionId: readTracingId(request.headers['x-posthog-session-id']),
            properties: { $request_method: request.method, request_id: request.id },
        },
        () => {
            enrichCurrentSpan(posthog)
            done()
        },
        { fresh: true, signal: controller.signal }
    )
})
```

Keep this hook after authentication and before routes, in the same Fastify scope. The helper adds missing `sessionId` and `posthogDistinctId` attributes to an active request span. The processor adds them to child spans when they start. Explicit canonical attributes take precedence; missing IDs stay absent.

The signal ends context when the response finishes, closes, or the request is aborted. Do not abort when `done()` returns: the handler can still be running. Existing spans keep their IDs; new spans in detached work after expiry omit them. Background jobs need their own explicit context. Keep your existing error and shutdown handlers.

## Capture events

Add this route before `app.listen()` to capture an event for an authenticated request. The event inherits the verified identity and request properties from `withContext`.

```js
app.get("/hello", async (request) => {
    if (request.user?.id) {
        posthog.capture({ event: "hello_requested" })
    }
    return { message: "Hello" }
})
```

See the [Node.js capture documentation](/docs/libraries/node#capturing-events) for more event options.

## Error handling

The HTTP status filter is optional application logic, not an SDK default. Remove the `if` condition to capture handled 4xx errors too. Unknown-route 404 responses do not pass through `setErrorHandler`.

If you already have an error handler, add the capture call there instead of replacing your response behavior. Avoid capturing the same error again in another hook.

The example records the route pattern, not the raw URL. This avoids collecting query strings or path parameter values. Review error messages and other properties for sensitive data before capture.

Fastify's default error response includes the error message. Use your application's response policy to hide internal details.

## Shutdown

During graceful termination, call `await app.close()` from your application's shutdown handler. Fastify then runs `onClose`, which waits for PostHog to drain buffered events.

Do not call `shutdown()` per request. Do not exit the process before it finishes. Abrupt termination can lose queued events.
