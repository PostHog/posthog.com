PostHog SDKs are moving to [capture v1](/docs/api/capture-v1), a new way to send events. Each SDK moves to v1 in a new major version. Capture v1 gives you:

- **A result for every event.** One bad event no longer fails the whole batch, and your SDK tells you which events PostHog didn't store and why.
- **Event options.** Settings like person processing move out of `$`-prefixed properties into a separate `options` object.
- **Safer retries.** SDKs retry only what can succeed and resend only the events that need it.
- **More compression choices.** `gzip`, `deflate`, `br`, and `zstd`.
- **A separate path for AI events.** Large AI events have their own queue and limits.

The legacy capture endpoints still work, and SDK versions that use them stay supported. We plan to retire the legacy endpoints in the future and will announce a date well in advance.

## What changes for everyone

These changes apply to every SDK on capture v1. Your SDK's migration guide covers changes that only apply to it.

### Every event needs its own UUID

SDKs generate a UUIDv7 for each event. If you set an event's UUID yourself, use a new one for every event. Don't reuse an order ID, request ID, or message ID across events. If one request repeats a UUID, PostHog keeps the first event with it and drops the rest, and your SDK reports the dropped copies.

### Event options replace legacy option properties

Legacy option properties are the `$`-prefixed properties legacy capture reads as settings. Set these settings in an event's `options` instead:

| Option | Legacy option property |
|---|---|
| `process_person_profile` | `$process_person_profile` |
| `cookieless_mode` | `$cookieless_mode` |
| `disable_skew_correction` | `$ignore_sent_at` |

<MultiLanguage>

```python
posthog.capture(
    "signed_up",
    distinct_id="user_123",
    properties={"plan": "pro"},
    options={"process_person_profile": True},
)
```

```go
client.Enqueue(posthog.Capture{
    DistinctId: "user_123",
    Event:      "signed_up",
    Properties: posthog.NewProperties().Set("plan", "pro"),
    Options:    posthog.NewOptions().Set("process_person_profile", true),
})
```

```rust
let mut event = posthog_rs::Event::new("signed_up", "user_123");
event.insert_prop("plan", "pro")?;
event.insert_option("process_person_profile", true)?;
client.capture(event);
```

The legacy option properties still work for now. The SDK moves them into `options` before it sends the event, and an option you set wins over its legacy option property. Use options in new code – the legacy option properties are deprecated, and a future major version will stop reading them.

SDKs send options exactly as you set them. PostHog ignores option names it doesn't know, and drops an event whose option value it can't read, with the detail `invalid_options`. See [event options](/docs/api/capture-v1#event-options) for the types each option takes.

### How values combine

You can set properties and options in several places. When the same key is set in more than one place, the most specific value wins:

1. **The capture call** – the properties and options you pass for this event
2. **Context** – values set for the current request or job, such as Python's `new_context()` and `tag()`, or Go's `RequestContext`
3. **Global defaults** – values set on the client for every event, such as Python's `super_properties` and `super_options`, or Go's `DefaultEventProperties` and `DefaultEventOptions`
4. **SDK values** – properties the SDK adds itself, such as `$is_server`

Then `before_send` runs. It sees the combined event, including `options`, and can change or remove anything. Last, legacy option properties fill in any option that is still unset.

A few details:

- A value from a lower layer only fills keys you didn't set higher up. This is a change: before v1, some SDKs let global values overwrite the ones you passed on the call.
- A property set to `null` (or `None`, or `nil`) counts as set, so a lower layer can't replace it. An option set to `null` counts as unset.
- `$set`, `$set_once`, `$groups`, and `$group_set` merge key by key, and the most specific value wins for each key.
- A `$set` in a global or context layer adds those person properties to every event that layer reaches.
- Not every SDK has every layer. Rust has no global or context layers. Your SDK's migration guide lists the layers it has and which calls they reach.

### Person processing

- Adding groups to an event no longer turns on person processing. To use [group analytics](/docs/product-analytics/group-analytics), send events with person processing on.
- An event without a distinct ID becomes an anonymous event with a generated ID, and doesn't create a person profile. Setting `$process_person_profile: true` no longer changes that. (The Go SDK returns an error for a missing distinct ID instead.)
- Use a real distinct ID: one visitor, or your own ID for a known user. See [choosing a distinct ID](/docs/api/capture-v1#choosing-a-distinct-id).
- **Group identify without a distinct ID** uses `$<group type>_<group key>` as the event's distinct ID. If that is over 200 bytes, pass a `distinct_id` explicitly, or PostHog drops the event.

### Limits

PostHog checks every event and drops only the events that break a rule. Your error handler reports each drop with its reason. Limits count UTF-8 bytes, not characters.

- **Event names: up to 200 bytes.** This is new: legacy capture had no limit. Longer names are dropped (`event_name_too_long`).
- **Distinct IDs: up to 200 bytes.** Legacy capture shortened longer IDs and kept the event. Capture v1 drops the event (`distinct_id_too_large`).
- **Distinct IDs are strings.** SDKs send them as strings for you. If a `before_send` hook changes `distinct_id`, keep it a string: PostHog rejects a whole request that contains a non-string ID, so the SDK drops that event before sending. See [field types](/docs/api/capture-v1#field-types).
- **Properties are an object, and option values are readable.** Otherwise PostHog drops the event (`malformed_event_properties`, `invalid_options`).
- **Event UUIDs are unique.** See [every event needs its own UUID](#every-event-needs-its-own-uuid).

See [limits and validation](/docs/api/capture-v1#limits-and-validation) for every rule.

### Other changes

- **Library name and version.** The SDK sets `$lib` and `$lib_version`. You can't override them from your properties.
- **Session IDs.** `$session_id` and `$window_id` must be strings. Other values are dropped from the event, with a warning in your logs.
- **Timestamps.** SDKs send timestamps with at least millisecond precision and keep any extra precision you provide. They no longer reject future timestamps – PostHog [handles those](/docs/api/capture-v1#timestamps-and-clock-skew).
- **API keys.** An empty project token, or a personal API key (`phx_…`) used as one, turns the client off and logs one error, instead of failing your app.
- **Logs.** Debug logs no longer include event contents, and some log messages changed. Update any alerts that match on old log text.

## Configuration

Some defaults changed in the new major versions. These are the capture settings that matter most for v1:

| Setting | Default | Python | Go | Rust |
|---|---|---|---|---|
| Retries | 3 retries (4 attempts) | `max_retries` | `MaxRetries` | `max_capture_attempts` (counts the first attempt) |
| Retry wait | 100ms, doubling, up to 30s, with jitter | – | `MaxRetryBackoff` | `retry_initial_backoff_ms`, `retry_max_backoff_ms` |
| Batch size | 100 events | `flush_at` | `BatchSize` | `flush_at` |
| Flush interval | 5 seconds | `flush_interval` | `Interval` | `flush_interval_ms` |
| Compression | None | `capture_compression` | `Compression` | `capture_compression` |
| Compression formats | – | `gzip`, `deflate`, `zstd` | `gzip`, `deflate`, `br`, `zstd` | `gzip`, `deflate`, `br`, `zstd` |
| Error handler | – | `on_error` | `Callback` | `on_error` |
| Modify or drop events | – | `before_send` | `BeforeSend` | `before_send` |

## Retries and failures

SDKs on capture v1 retry a request when PostHog or the network has a temporary problem (`408`, `500`, `502`, `503`, `504`, or a network error), and they resend only the events PostHog asked them to retry. Every other response is final, including `429`. Each wait doubles, with some randomness added so many clients don't retry at the same moment.

Let the SDK handle retries. Don't wrap its capture calls in your own retry loop – that can send events twice and slow your app down.

To see what PostHog didn't store, add an error handler. It reports the events PostHog dropped, with the reason from [the result details](/docs/api/capture-v1#result-details). Without a handler, the SDK logs one line per failed batch.

<MultiLanguage>

```python
from posthog import Posthog

def on_error(error, batch):
    # error is a CaptureError: status, drops, event_results, verdict_summary()
    print("PostHog capture failed:", error.verdict_summary())

posthog = Posthog("<ph_project_token>", host="<ph_client_api_host>", on_error=on_error)
```

```go
client, err := posthog.NewWithConfig("<ph_project_token>", posthog.Config{
    Endpoint: "<ph_client_api_host>",
    Callback: myCallback, // Failure receives CaptureEventError, CaptureRequestError, or CaptureLocalError
})
```

```rust
let options = posthog_rs::ClientOptionsBuilder::default()
    .api_key("<ph_project_token>".to_string())
    .host("<ph_client_api_host>")
    .on_error(|failure| eprintln!("PostHog capture failed: {failure:?}"))
    .build()?;
let client = posthog_rs::client(options).await;
```

If your project hits a [billing limit](/docs/billing/limits-alerts), PostHog stops storing events and answers with `402`. The SDK reports this as a failure on each send until the limit resets or you raise it.

## AI events

Send AI events (any event whose name starts with `$ai_`) with your SDK's AI capture method. It has its own queue, compression setting, and size limit, separate from your other events. PostHog owns the `$ai_` prefix, so don't use it for your own events.

| SDK | AI capture method | AI settings |
|---|---|---|
| Python | `capture_ai` | `capture_ai_compression`, `capture_ai_max_queue_size`, `capture_ai_timeout` |
| Go | `EnqueueAI` | `CaptureAICompression`, `CaptureAIMaxQueueSize`, `CaptureAIBatchUploadTimeout` |
| Rust | `capture_ai` | `capture_ai_compression`, `capture_ai_max_queue_size` |

`capture` doesn't move `$ai_` events to the AI path for you. For now, PostHog still accepts AI events sent with `capture`, so existing code keeps working while you upgrade. This is temporary, and large AI events always need the AI method. Calling `flush` or `shutdown` sends both queues. See [capturing large AI events](/docs/ai-observability/large-events) for limits and the AI integrations.

## Proxies

If you send events through a [reverse proxy](/docs/advanced/proxy), make sure it:

- Forwards `/i/v1/analytics/events` and `/i/v1/ai/events`
- Passes the `Authorization` header and every `PostHog-*` header through unchanged
- Returns PostHog's status code and response body unchanged, so your SDK sees the result for each event
