The PostHog HTML snippet loads the JavaScript web SDK (`posthog-js`) from PostHog's CDN. By default, the snippet uses `/static/array.js`, which follows PostHog's current supported web SDK release.

Use snippet versioning when you need to control that rollout, such as pinning a known-good SDK version while debugging a regression, or tracking the latest release in a specific major version.

> **Note:** This page is about the HTML snippet. If you install `posthog-js` from npm, your package manager lockfile controls the SDK version instead. See [Keeping SDKs current](/docs/sdk-doctor/keeping-sdks-current#npm-and-package-manager-lockfiles).

## Supported pins

Snippet versioning supports major-version pins and exact-version pins.

| Pin format | Example path | Behavior |
| --- | --- | --- |
| Unpinned | `/static/array.js` | Uses PostHog's default current web SDK release. |
| Major | `/static/1/array.js` | Uses the latest available `1.x.x` release. |
| Exact | `/static/1.380.0/array.js` | Uses exactly that SDK version until you change the snippet. |

Minor pins such as `/static/1.380/array.js` are not supported.

Exact pins are safest for short-term rollback or debugging, but they also stop automatic fixes from reaching your users. Remove exact pins once you're done investigating.

## Change the snippet version

There isn't a PostHog setting for this yet. To pin the snippet version, edit the HTML snippet in your site's code.

1. Find the `/static/array.js` path in your installed PostHog snippet.
2. Change it to a supported versioned path.
3. Deploy the updated snippet.

For example, the generated snippet contains a line like this:

```js
p.src = s.api_host.replace('.i.posthog.com', '-assets.i.posthog.com') + '/static/array.js'
```

To track the latest v1 release, change only the path:

```js
p.src = s.api_host.replace('.i.posthog.com', '-assets.i.posthog.com') + '/static/1/array.js'
```

To pin an exact version, use the exact version path:

```js
p.src = s.api_host.replace('.i.posthog.com', '-assets.i.posthog.com') + '/static/1.380.0/array.js'
```

Keep the rest of the snippet unchanged. In particular, don't wrap the snippet in an extra `if (!window.posthog)` guard; the snippet already handles safe initialization.

To return to the default current version, change the path back to `/static/array.js`.

## Versioned external scripts

`array.js` is only the initial SDK bundle. Some PostHog features load extra scripts when needed, including:

- `recorder.js` for [Session Replay](/docs/session-replay)
- `surveys.js` for [Surveys](/docs/surveys)
- `toolbar.js` for the [toolbar](/docs/toolbar)

By default, these scripts use compatibility URLs like:

```text
/static/recorder.js?v=1.380.0
```

If your CDN, reverse proxy, or security tooling ignores query strings while caching, enable `strict_script_versioning` so these scripts use exact version paths instead:

```js
posthog.init('<ph_project_token>', {
    api_host: '<ph_client_api_host>',
    defaults: '<ph_posthog_js_defaults>',
    strict_script_versioning: true,
})
```

This changes dependency URLs to paths like:

```text
/static/1.380.0/recorder.js
```

Use this whenever you want feature scripts to be tied to the exact SDK version without relying on query-string cache busting.

## Custom asset hosts and reverse proxies

Use `asset_host` if static PostHog assets must be served from a different host than event capture or feature flag requests:

```js
posthog.init('<ph_project_token>', {
    api_host: '<ph_client_api_host>',
    defaults: '<ph_posthog_js_defaults>',
    strict_script_versioning: true,
    asset_host: 'https://posthog-assets.example.com',
})
```

`asset_host` only applies to `/static/*` assets such as `recorder.js`, `surveys.js`, and `toolbar.js`. It does not change event capture, feature flag requests, or the token-specific remote config URL (`/array/<token>/config.js`).

If you use a reverse proxy, make sure it forwards all PostHog SDK paths your site can request:

- `/static/array.js`
- `/static/1/array.js` for a major-version snippet pin
- `/static/1.380.0/array.js` for an exact-version snippet pin
- `/static/<version>/<asset>.js` when `strict_script_versioning` is enabled
- `/static/<asset>.js?v=<version>` for compatibility URLs
- `/array/<token>/config.js`
- normal API paths such as `/e`, `/flags`, `/decide`, and `/s`

Avoid caching `/static/array.js` or `/static/1/array.js` for long periods if you want users to pick up new SDK releases quickly. Exact versioned paths like `/static/1.380.0/array.js` and `/static/1.380.0/recorder.js` are immutable and safe to cache more aggressively.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The browser still loads an old SDK version | Inspect the deployed snippet path. `/static/1.380.0/array.js` is an exact pin, `/static/1/array.js` tracks the latest v1 release, and `/static/array.js` is unpinned. Also check CDN, service worker, and reverse proxy caches. |
| The snippet 404s after adding a pin | Check that the path is either a major pin such as `/static/1/array.js` or an exact pin such as `/static/1.380.0/array.js`. Minor pins such as `/static/1.380/array.js` are not supported. |
| Session Replay, Surveys, or toolbar scripts 404 | Your proxy may not forward `/static/<version>/<asset>.js`. Either add that route or disable `strict_script_versioning`. |
| `array.js` updates, but feature scripts stay stale | Enable `strict_script_versioning` so dependency scripts use versioned paths instead of query-string cache busting. |
| Tag manager installs do not update | Some tag manager templates pin their own `posthog-js` version. Update the tag manager template separately. |
| You use npm, not the HTML snippet | Update `posthog-js` through your package manager instead; this snippet path does not affect bundled npm installs. |

For broader causes of stale SDKs, see [Keeping SDKs current](/docs/sdk-doctor/keeping-sdks-current).
