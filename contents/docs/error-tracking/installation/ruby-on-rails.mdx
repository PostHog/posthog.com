## Automatic exception tracking

`report_rescued_exceptions` controls whether exceptions Rails rescues (for example, exceptions rendered by Rails error pages) are captured. Enable it along with `auto_capture_exceptions` for complete error visibility, or leave it disabled to capture only unhandled exceptions.

## Manual exception capture

From `posthog-rails` version 3.24.0, controllers and API controllers have a private `capture_exception` helper. It adds the configured user identity, request metadata, controller/action, and parameters filtered through Rails' parameter filters:

```ruby
class PaymentsController < ApplicationController
  def create
    PaymentService.charge(params[:order_id])
    head :created
  rescue PaymentService::Error => error
    capture_exception(error, nil, { payment_provider: "stripe" })
    head :bad_gateway
  end
end
```

Manual reports work without `auto_capture_exceptions` and do not apply automatic exception exclusions. The helper does not replace an existing controller method with the same name. Missing or disabled clients return `false` without creating a client.

You can pass `distinct_id` and additional properties explicitly; these override inferred identity and request properties. The helper removes query strings from inferred URLs, but explicit properties are sent as supplied. Review them for sensitive data.

Outside controllers, use `PostHog.capture_exception(exception, distinct_id, properties)` as before.

If you evaluated feature flags for the request, pass the same snapshot to include matching flag properties on the exception event:

```ruby
flags = PostHog.evaluate_flags(current_user.id)

capture_exception(
  exception,
  current_user.id,
  { custom_property: "value" },
  flags: flags
)
```

## Streaming exceptions

From version 3.21.0, `auto_capture_exceptions` also captures errors reported by `ActionController::Live` and ActionView streaming templates. Exception exclusions, `before_send`, and duplicate prevention still apply. Rails logging and stream completion behavior are unchanged.

## Action Cable exceptions

From version 3.22.0, `auto_capture_exceptions` also captures exceptions escaping Action Cable connection open/close, channel subscribe/unsubscribe callbacks, and channel actions. No separate setup is needed, and Action Cable remains an optional dependency.

Reports include connection/channel classes, the operation, and channel parameters or action data filtered through both the application's and the connection's `filter_parameters`. Raw connection environments, cookies, authorization headers, subscription identifiers, and URL query strings are not attached. Review your filters and `before_send` for application-specific sensitive data.

Identity comes from the connection's configured `current_user_method` and `user_id_method`, then from PostHog tracing headers when enabled. The controller-only `current_user_resolver` is not used for connections. Context is isolated between connections.

Exceptions consumed by channel or connection `rescue_from` handlers are not captured by these boundaries, even with `report_rescued_exceptions = true`. That option does not enable handled Action Cable reports.

## Rails runner exceptions

From version 3.24.0, `auto_capture_exceptions` captures terminating `rails runner` errors before the SDK shuts down. They are fatal, unhandled events with source `rails.runner`. Deliberate nonzero exits such as `exit 23` are also reported. Normal completion, successful exits, and signal termination such as Ctrl-C or SIGTERM are not reported.

Rails' exit status and error output are preserved. Exception exclusions and `before_send` still apply. Delivery is best-effort: failures before runner hooks load, `exit!`, and forced termination that skips Ruby exit hooks cannot be captured.

## Background job exceptions

When `auto_instrument_active_job` is enabled, Active Job exceptions are captured with job context.

From version 3.20.0, this integration also copies the current PostHog session and distinct IDs into queued Active Job data. Events and optional logs captured while the job runs use those IDs. Request properties are not copied. An explicit job identity extractor takes precedence over the saved distinct ID. This does not propagate a distributed trace; see the [Rails trace context guide](/docs/libraries/ruby-on-rails#trace-context) for OpenTelemetry setup.

### Report retry failures

From version 3.24.0, enable `report_active_job_retries` to report failures when Active Job schedules a retry, not only errors that escape job execution:

```ruby file=config/initializers/posthog.rb
PostHog::Rails.configure do |config|
  config.auto_instrument_active_job = true
  config.report_active_job_retries = true
end
```

The option defaults to `false` and works on Rails 5.2 or later. It uses the same job identity and filtered arguments as terminal reports. Retry reports have source `rails.active_job`, level `error`, and a handled `task` mechanism. They honor exception exclusions across the cause chain without changing retry scheduling. Discarded or otherwise rescued failures are not added by this option. Duplicate prevention still applies if the same exception object is raised again.

### Associating jobs with users

By default, PostHog extracts a `distinct_id` from job arguments by looking for a `user_id` key in hash arguments:

```ruby
# PostHog will automatically use options[:user_id] as the distinct_id
ProcessOrderJob.perform_later(order.id, user_id: current_user.id)
```

For more control, use the `posthog_distinct_id` class method. The proc or block receives the same arguments as `perform`:

```ruby
class SendWelcomeEmailJob < ApplicationJob
  posthog_distinct_id ->(user, _options) { user.id }

  def perform(user, options = {})
    UserMailer.welcome(user).deliver_now
  end
end
```

You can also use a block:

```ruby
class ProcessOrderJob < ApplicationJob
  posthog_distinct_id do |_order, notify_user_id|
    notify_user_id
  end

  def perform(order, notify_user_id)
    # Process the order...
  end
end
```

## Rails 7.0+ error reporter

With `auto_capture_exceptions = true`, PostHog integrates with Rails' built-in error reporting, including handled errors reported during web requests:

```ruby
# These errors are automatically sent to PostHog
Rails.error.handle do
  # Code that might raise an error
end

Rails.error.report(exception, handled: true, context: { user_id: current_user.id })
```

PostHog automatically extracts the user's distinct ID from `user_id` or `distinct_id` in the context hash. Other context keys are included as properties on the exception event.

## User context

PostHog Rails automatically captures authenticated user information from your controllers for exceptions. Authenticated Rails user context takes precedence over client-supplied tracing headers for exception identity.

If your user method has a different name, configure it:

```ruby
PostHog::Rails.config.current_user_method = :logged_in_user
```

For request-local authentication, set `current_user_resolver` instead. It takes precedence over `current_user_method`:

```ruby
PostHog::Rails.configure do |config|
  config.current_user_resolver = -> { Current.user }
end
```

The resolver can also accept the controller as an argument. A zero-argument proc runs in the controller's context. The resolved user uses the same ID extraction rules below.

### User ID extraction

By default, PostHog Rails auto-detects the user's distinct ID by trying these methods in order:

1. `posthog_distinct_id` – Define this on your User model for full control
2. `distinct_id` – Common analytics convention
3. `id` – Standard ActiveRecord primary key
4. `pk` – Primary key alias
5. `uuid` – For UUID-based primary keys

It also checks hash-like users for `id`, `pk`, and `uuid` keys.

You can configure a specific method:

```ruby
PostHog::Rails.config.user_id_method = :email
```

Or define a method on your User model:

```ruby
class User < ApplicationRecord
  def posthog_distinct_id
    "user_#{id}"  # or external_id, or any unique identifier
  end
end
```

## Excluded exceptions

Automatic capture excludes the following exceptions by default:

- `AbstractController::ActionNotFound`
- `ActionController::BadRequest`
- `ActionController::InvalidAuthenticityToken`
- `ActionController::InvalidCrossOriginRequest`
- `ActionController::MethodNotAllowed`
- `ActionController::NotImplemented`
- `ActionController::ParameterMissing`
- `ActionController::RoutingError`
- `ActionController::UnknownFormat`
- `ActionController::UnknownHttpMethod`
- `ActionDispatch::Http::MimeNegotiation::InvalidType`
- `ActionDispatch::Http::Parameters::ParseError`
- `ActiveRecord::RecordNotFound`
- `ActiveRecord::RecordNotUnique`

Add more with:

```ruby
PostHog::Rails.config.excluded_exceptions = ["MyException"]
```

## Cause chains and duplicate prevention

Exception reports include the `exception.cause` chain, up to 50 exceptions. Capture mechanisms distinguish manual reports from Rails middleware, the error reporter, and Active Job integrations.

For mutable exceptions, the SDK suppresses repeated captures of the same exception object and its captured causes, even through another client. The first successful capture wins; later calls return `false` without merging context. Supply the required identity and properties on the first report. Failed captures can be retried.

## Trace and release correlation

When your app already provides OpenTelemetry, exception events include the active trace and span IDs. See [Rails trace context](/docs/libraries/ruby-on-rails#trace-context) to correlate application spans with PostHog session and person IDs.

To associate exceptions with a deployed release, set `POSTHOG_RELEASE_ID` before client initialization. See [link Ruby releases](/docs/error-tracking/link-releases/ruby) for the deployment steps.
