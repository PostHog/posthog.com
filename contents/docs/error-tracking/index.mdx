Error tracking captures exceptions from across your stack and turns them into issues you can prioritize, assign, and resolve. Because PostHog already knows what's happening in your product, every issue comes with the affected user's [session replay](/docs/session-replay), events, and properties attached, so you can see what went wrong instead of trying to reproduce it. Those same exceptions feed [Self-driving](/docs/self-driving), which groups recurring issues and opens pull requests you review and merge.

## Where its data comes from

Error tracking runs on the exceptions your app sends to PostHog. SDKs capture them automatically, source maps make the stack traces readable, and releases tie each exception back to the deploy that caused it.

## How error tracking works with Self-driving

Your exceptions are a [signal source](/docs/self-driving/inbox/sources) for [Self-driving](/docs/self-driving): recurring, high-impact issues become reports, and when there's a code fix, a pull request you review and merge.

You triage and resolve issues in the [PostHog web app](/docs/error-tracking/monitoring), and review and merge the Self-driving work in the [Self-driving inbox](/docs/self-driving/inbox). See the [Self-driving docs](/docs/self-driving) for the full picture.
