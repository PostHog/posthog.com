Error tracking captures exceptions from across your stack and turns them into issues you can prioritize, assign, and resolve. Because PostHog already knows what's happening in your product, every issue comes with the affected user's [session replay](/docs/session-replay), events, and properties attached, so you can see what went wrong instead of trying to reproduce it.

<OSButton variant="primary" asLink to="/docs/error-tracking/start-here">Get started</OSButton>

## Where you can use it

You triage and resolve issues in the PostHog web app. The other surfaces let you debug and fix issues without leaving your existing tools.

## Where its data comes from

Error tracking runs on the exceptions your app sends to PostHog. SDKs capture them automatically, source maps make the stack traces readable, and releases tie each exception back to the deploy that caused it.

<SurfaceCards columns={3}>

<SurfaceCard icon="IconBrackets" color="blue" title="SDKs" url="/docs/error-tracking/installation" cta="Install an SDK">
Capture exceptions automatically from web, backend, and mobile SDKs across your stack.
</SurfaceCard>

<SurfaceCard icon="IconCode" color="green" title="Source maps" url="/docs/error-tracking/upload-source-maps" cta="Upload source maps">
Upload source maps and symbol sets so minified stack traces point back to your real code.
</SurfaceCard>

<SurfaceCard icon="IconRocket" color="orange" title="Releases" url="/docs/error-tracking/releases" cta="Track releases">
Tag exceptions with the release and commit that introduced them to spot regressions fast.
</SurfaceCard>
