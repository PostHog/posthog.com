If you're already using Datadog to collect logs, you can forward them to PostHog by configuring your existing Datadog log exporters (like the Datadog Agent) to send logs to PostHog's Datadog-compatible endpoint.

<Steps>

<Step title="Get your project token" badge="required">

You'll need your PostHog project token to authenticate log requests. This is the same key you use for capturing events and exceptions with the PostHog SDK.

> **Important:** Use your **project token** which starts with `phc_`. Do **not** use a personal token (which starts with `phx_`).

You can find your project token in [Project Settings](https://app.posthog.com/settings/project).

</Step>

<Step title="Configure Datadog Agent" badge="required">

Set the Datadog logs URL to point to PostHog's Datadog-compatible endpoint. The endpoint format is:

```
<ph_client_api_host>/i/v1/logs/datadog/<ph_project_token>
```

For the **Datadog Agent**, set the `DD_LOGS_CONFIG_LOGS_DD_URL` environment variable:

```bash
export DD_LOGS_CONFIG_LOGS_DD_URL="<ph_client_api_host>/i/v1/logs/datadog/<ph_project_token>"
```

Alternatively, you can set this in your `datadog.yaml` configuration file:

```yaml
logs_config:
  logs_dd_url: "<ph_client_api_host>/i/v1/logs/datadog/<ph_project_token>"
```

</Step>

<Step title="Dual-ship to Datadog and PostHog" badge="optional">

To compare PostHog and Datadog side by side, send the same logs to both at the same time. Instead of changing `logs_dd_url`, keep Datadog as the Agent's main endpoint and add PostHog as an additional endpoint, as described in Datadog's [dual shipping docs](https://docs.datadoghq.com/agent/configuration/dual-shipping/?tab=helm#logs).

This requires Datadog Agent 7.70 or later, which supports `path_prefix` on additional endpoints.

<MultiLanguage>

```yaml file=datadog.yaml
logs_config:
  force_use_http: true
  additional_endpoints:
    - api_key: "<ph_project_token>"
      Host: "us.i.posthog.com" # Use eu.i.posthog.com for EU Cloud
      Port: 443
      path_prefix: "/i/v1/logs/datadog/<ph_project_token>"
      is_reliable: true
```

```bash file=Environment variables
DD_LOGS_CONFIG_FORCE_USE_HTTP=true
# Use eu.i.posthog.com for EU Cloud
DD_LOGS_CONFIG_ADDITIONAL_ENDPOINTS='[{"api_key": "<ph_project_token>", "Host": "us.i.posthog.com", "Port": 443, "path_prefix": "/i/v1/logs/datadog/<ph_project_token>", "is_reliable": true}]'
```

```yaml file=Helm
# values.yaml for the Datadog Agent Helm chart
datadog:
  env:
    - name: DD_LOGS_CONFIG_FORCE_USE_HTTP
      value: "true"
    - name: DD_LOGS_CONFIG_ADDITIONAL_ENDPOINTS
      # Use eu.i.posthog.com for EU Cloud
      value: '[{"api_key": "<ph_project_token>", "Host": "us.i.posthog.com", "Port": 443, "path_prefix": "/i/v1/logs/datadog/<ph_project_token>", "is_reliable": true}]'
```

</MultiLanguage>

With `is_reliable: true`, the Agent treats both endpoints equally. If one is unavailable, logs keep flowing to the other.

On older Agent versions, do it the other way around. Set `logs_dd_url` to PostHog as shown in the previous step, then add Datadog as the additional endpoint:

```yaml file=datadog.yaml
logs_config:
  logs_dd_url: "<ph_client_api_host>/i/v1/logs/datadog/<ph_project_token>"
  force_use_http: true
  additional_endpoints:
    - api_key: "<YOUR_DATADOG_API_KEY>"
      Host: "agent-http-intake.logs.<YOUR_DATADOG_SITE>" # For example, datadoghq.com
      Port: 443
      is_reliable: true
```

</Step>

<Step title="Other Datadog log exporters" badge="optional">

If you're using other Datadog log exporters or forwarders, configure them to send logs to the same endpoint:

```
<ph_client_api_host>/i/v1/logs/datadog/<ph_project_token>
```

The endpoint accepts logs in the standard Datadog log format, so existing integrations should work without additional changes.

</Step>

<Step title="Test your setup" badge="recommended">

Once everything is configured, test that logs are flowing into PostHog:

1. Restart the Datadog Agent (or your log forwarder) to apply the configuration
2. Generate some log entries in your application
3. Check the PostHog Logs interface for your log entries
4. Verify the logs appear in your project
