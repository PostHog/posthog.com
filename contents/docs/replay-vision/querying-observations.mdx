Every successful observation is captured as a `$recording_observed` event in your project, so you can build [insights](/docs/product-analytics/insights), [dashboards](/docs/product-analytics/dashboards), and [alerts](/docs/alerts) on top of Replay Vision output using PostHog's [SQL](/docs/product-analytics/sql).

Only **succeeded** observations are emitted as events. Failed and ineligible observations are visible in the [Observations tab](/docs/replay-vision/observations) for debugging, but they don't appear in your event stream.

## Event properties

| Property | Description |
| --- | --- |
| `scanner_name` | Human-readable name of the scanner |
| `scanner_id` | Scanner UUID |
| `scanner_type` | `monitor`, `classifier`, `scorer`, or `summarizer` |
| `scanner_version` | Version of the scanner config that produced this observation |
| `session_id` | The recording that was observed |
| `triggered_by` | `schedule` (background sweep) or `on_demand` |
| `model_used` | The Gemini model that produced the result |
| `scanner_output_confidence` | The model's confidence (0.0 to 1.0) |
| `scanner_output_reasoning` | The model's reasoning text, including any inline citations |
| `scanner_output_verdict` | **Monitor only** – the true/false verdict |
| `scanner_output_tags` | **Classifier only** – the array of assigned tags |
| `scanner_output_score` | **Scorer only** – the numeric score |
| `scanner_output_title` | **Summarizer only** – the generated one-line title |
| `scanner_output_summary` | **Summarizer only** – the generated prose summary |

The `timestamp` on the event is the moment the observation completed, not the moment the underlying recording was captured.

## SQL recipes

### Monitor: count flagged sessions over time

Sessions a "Dead-end pages" monitor scanner flagged true, daily, over the last week:

```sql
SELECT
    toStartOfDay(timestamp) AS day,
    count() AS flagged_sessions
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'Dead-end pages'
  AND properties.scanner_output_verdict = true
  AND timestamp > now() - INTERVAL 7 DAY
GROUP BY day
ORDER BY day
```

### Monitor: true rate (flagged / total)

The proportion of observed sessions a monitor flagged true:

```sql
SELECT
    countIf(properties.scanner_output_verdict = true) AS flagged,
    count() AS total,
    flagged / total AS true_rate
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'Dead-end pages'
  AND timestamp > now() - INTERVAL 30 DAY
```

A creeping true rate is often a more useful early-warning signal than the absolute count.

### Classifier: top tags

Most common intent tags from a classifier:

```sql
SELECT
    arrayJoin(properties.scanner_output_tags) AS tag,
    count() AS sessions
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'User intent'
  AND timestamp > now() - INTERVAL 7 DAY
GROUP BY tag
ORDER BY sessions DESC
```

### Scorer: distribution

Histogram of frustration scores:

```sql
SELECT
    toInt32(properties.scanner_output_score) AS score,
    count() AS sessions
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'Frustration score'
  AND timestamp > now() - INTERVAL 7 DAY
GROUP BY score
ORDER BY score
```

For a percentile view:

```sql
SELECT
    quantile(0.50)(toFloat64(properties.scanner_output_score)) AS p50,
    quantile(0.90)(toFloat64(properties.scanner_output_score)) AS p90,
    quantile(0.99)(toFloat64(properties.scanner_output_score)) AS p99
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'Frustration score'
  AND timestamp > now() - INTERVAL 7 DAY
```

### Summarizer: recent summaries

Latest summaries from a summarizer scanner:

```sql
SELECT
    timestamp,
    properties.session_id AS session_id,
    properties.scanner_output_title AS title,
    properties.scanner_output_summary AS summary
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_name = 'Session summary'
ORDER BY timestamp DESC
LIMIT 50
```

### Cross-scanner: filter only high-confidence verdicts

```sql
SELECT *
FROM events
WHERE event = '$recording_observed'
  AND properties.scanner_output_confidence > 0.8
ORDER BY timestamp DESC
```

Confidence is self-reported, so this is a heuristic, not a guarantee – but it's often a useful filter for downstream automation.

## Wiring observations into the rest of PostHog

### Insights and dashboards

The recipes above all become [insights](/docs/product-analytics/insights) by saving the query. From there they go on [dashboards](/docs/product-analytics/dashboards) like any other insight.

### Alerts

[Alerts](/docs/alerts) on an insight built from `$recording_observed` give you a notification when the metric crosses a threshold – e.g. "alert me when the dead-end true rate over the last hour exceeds 5%."

This is the closest thing to "notify me about important sessions" while the Signals integration is still in development.

### Joining to other PostHog data

Because `$recording_observed` events live alongside everything else in your project, you can join them to anything – pageviews, custom events, person properties, cohorts. A useful pattern: find the events the user fired *before* the moment a monitor flagged them, grouped by URL.

```sql
SELECT
    pv.properties.$current_url AS url,
    count(DISTINCT pv.properties.$session_id) AS sessions
FROM events pv
INNER JOIN events ro
    ON ro.properties.session_id = pv.properties.$session_id
WHERE
    pv.event = '$pageview'
    AND ro.event = '$recording_observed'
    AND ro.properties.scanner_name = 'Dead-end pages'
    AND ro.properties.scanner_output_verdict = true
    AND pv.timestamp BETWEEN ro.timestamp - INTERVAL 5 MINUTE AND ro.timestamp
GROUP BY url
ORDER BY sessions DESC
```

The join is by `session_id`. From there it's the same SQL you'd write for any other event.

## A note on stability

`$recording_observed` is the public surface area. The Observations tab and the underlying observation rows are richer (they include the full prompt snapshot, the reasoning citations, and the embedded player), but the event is the canonical version of "this observation happened and the result was X."

If you're building analytics on top of Replay Vision, build on the event – not on screen-scraped UI – and you'll be on the stable contract.
