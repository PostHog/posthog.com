There are two ways a scanner produces observations: automatically in the background as new recordings come in, or on-demand against recordings you pick. Both paths produce the same observation rows and the same `$recording_observed` events – they only differ in how the work gets triggered.

## Automatically on matching sessions

Once a scanner is **enabled**, PostHog runs a background sweep every few minutes. The sweep:

1. Looks for new recordings that match the scanner's filters and that the scanner hasn't already observed.
2. Applies the [session coverage](/docs/replay-vision/creating-scanners#session-coverage-filtering-by-quality) mode to drop low-activity sessions ("Highest activity only" and "Skip lowest activity" filter by relevance score; "All recordings" keeps everything).
3. Applies the sampling rate to what's left (so a 10% rate means roughly one in ten remaining sessions get queued).
4. Queues an observation per session for the model to process.
5. Records the result – success, failure, or [ineligible](#ineligible-sessions) – and emits a `$recording_observed` event for successes.

Each `(scanner, session)` pair is only ever observed once. Re-sweeping never produces duplicate observations for the same recording.

### When does the next sweep run?

Sweeps run continuously – once a scanner is enabled, observations start accumulating within a few minutes. New results land on the scanner's Observations tab as they complete.

### What happens when I change filters?

Changing a scanner's filters affects which **new** sessions match going forward. Old recordings aren't re-evaluated against the new filters. If you broaden the filters and want to backfill, trigger on-demand observations against the recordings you care about – the bulk [**Scan these recordings**](#from-the-recordings-list) action is the fastest way – or wait for new matches to come in.

### What happens when I disable the scanner?

Disabling stops the background sweep. Existing in-flight observations finish; no new ones get queued. On-demand triggers continue to work.

## On-demand on recordings you pick

### From the scanner's On-demand tab

Every scanner has an **On-demand** tab with two ways to trigger a scan:

- **Scan a session by ID** – paste a recording's session ID and run the scanner against it right now.
- **Pick from your recordings** – filter your session recordings inline and scan one at a time, or select several and scan them together. The filters start from the scanner's own trigger query, so the list opens scoped to the sessions it already watches, and a **Person** column shows whose session each one is. Sessions the scanner has already observed show their status instead of a scan button, so you can't double-scan.

### From the replay player

Open a recording in the [replay player](/docs/session-replay/how-to-watch-recordings), then use the **Scan this recording** action. Pick the scanner you want to run, and PostHog queues a single observation against that session.

On-demand triggers:

- Work even when the scanner is disabled (only the background sweep respects the toggle).
- Skip the sampling rate – every on-demand trigger produces an observation if the session is eligible.
- Are attributed to the user who triggered them, so you can tell apart "human spot-check" observations from "background sweep" observations.

### From the recordings list

To scan a batch in one go, select recordings in the [recordings list](/docs/session-replay/how-to-watch-recordings) and choose **Scan these recordings**, then pick a scanner. Each selected session is queued as its own observation. Sessions the scanner has already observed are skipped automatically, so re-scanning a selection is safe.

This is also the fastest way to backfill after broadening a scanner's filters.

### Via MCP

You can also trigger an on-demand observation from your editor using the `vision-scanners-scan-session` MCP tool. See [Replay Vision MCP](/docs/replay-vision/mcp) for the full set of tools and example prompts.

## Via the API

To run a scan from your own backend, call the inline scan endpoint. It runs a prompt against sessions you name, without a saved scanner. Use it to pull Replay Vision results into a CRM, a support tool, or any pipeline of your own. With `scanner_type` set to `summarizer`, it is how you get PostHog's own AI summary for a recording ID.

Two calls do the whole job: start the scan, then poll for the result. The examples below use US Cloud. On EU Cloud, send them to `https://eu.posthog.com` instead.

Authenticate with a [personal API key](/docs/api/personal-api-keys) that holds these scopes:

| Call                  | Scopes                                          |
| --------------------- | ----------------------------------------------- |
| Start a scan          | `replay_scanner:write` and `session_recording:read` |
| Read the observations | `replay_scanner:read` and `session_recording:read`  |

Your organization must also allow AI data processing. Without it, the request is refused and nothing is scanned. An organization admin turns it on in the organization settings.

### 1. Start the scan

```bash
curl -X POST 'https://us.posthog.com/api/projects/:project_id/vision/scanners/inline_scan/' \
  -H 'Authorization: Bearer <POSTHOG_PERSONAL_API_KEY>' \
  -H 'Content-Type: application/json' \
  -d '{
    "session_ids": ["0198f0c1-1ce4-7a3b-9f2d-6b1c8a4e5d70"],
    "prompt": "Summarize what the user did in this session, and call out anything that went wrong.",
    "scanner_type": "summarizer",
    "scanner_config": { "length": "medium" }
  }'
```

| Field            | Required | What it does                                                                                                      |
| ---------------- | -------- | ----------------------------------------------------------------------------------------------------------------- |
| `session_ids`    | Yes      | The session recording IDs to scan. At most 200 per request.                                                         |
| `prompt`         | Yes      | What to look for, in plain language. The same instruction a saved scanner carries.                                  |
| `scanner_type`   | No       | `monitor` (the default), `classifier`, `scorer`, or `summarizer`. See [scanner types](/docs/replay-vision/scanner-types). |
| `scanner_config` | No       | Type-specific configuration: `tags` for a classifier, `scale` for a scorer, `length` for a summarizer. Leave the prompt in `prompt`. |
| `model`          | No       | The model to scan with. It sets what each observation costs in [credits](/docs/replay-vision/quota-and-limits).     |

The response is `202` and looks like this:

```json
{
  "scan_id": "0198f0c2-77a1-7c04-8f11-2b9d4f6ac315",
  "started": 1,
  "results": [
    { "session_id": "0198f0c1-1ce4-7a3b-9f2d-6b1c8a4e5d70", "scan_outcome": "started" }
  ]
}
```

Nothing is scanned yet. Each session gets its own outcome, so one blocked session never fails the whole batch:

| `scan_outcome`           | What it means                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------ |
| `started`                | A scan is running. Poll for the result.                                                |
| `already_running`        | A scan of this session is already in flight. Poll for the same result.                 |
| `already_scanned`        | This scan already has a finished observation for the session. Read it now.             |
| `skipped_limit`          | The in-flight cap was reached before this session. Send it again later.                |
| `skipped_quota`          | The organization's credit quota for this period would be exceeded.                     |
| `skipped_scanner_limit`  | The scan's own credit limit would be exceeded.                                         |
| `failed`                 | The scan did not start.                                                                |

`scan_id` is null when nothing started and nothing existed to read, which happens when the quota is used up.

### 2. Poll for the result

Read the results back through `scan_id`:

```bash
curl -G 'https://us.posthog.com/api/projects/:project_id/vision/scanners/:scan_id/observations/' \
  -H 'Authorization: Bearer <POSTHOG_PERSONAL_API_KEY>' \
  --data-urlencode 'session_id=0198f0c1-1ce4-7a3b-9f2d-6b1c8a4e5d70'
```

Each observation carries a `status`:

- `pending` or `running` – the scan is still going. Poll again.
- `succeeded` – the result is in `scanner_result.model_output`. For a summarizer, that is a `title` and a `summary`.
- `failed` or `ineligible` – terminal. `error_reason` says why. See [ineligible sessions](#ineligible-sessions).

A scan usually takes a few minutes, so poll every 10 seconds or so and stop after a timeout of your own:

```python
import time
import requests

BASE = "https://us.posthog.com/api/projects/:project_id/vision/scanners"
HEADERS = {"Authorization": "Bearer <POSTHOG_PERSONAL_API_KEY>"}
SESSION_ID = "0198f0c1-1ce4-7a3b-9f2d-6b1c8a4e5d70"

scan = requests.post(
    f"{BASE}/inline_scan/",
    headers=HEADERS,
    json={
        "session_ids": [SESSION_ID],
        "prompt": "Summarize what the user did in this session, and call out anything that went wrong.",
        "scanner_type": "summarizer",
        "scanner_config": {"length": "medium"},
    },
).json()

deadline = time.time() + 600
while time.time() < deadline:
    observations = requests.get(
        f"{BASE}/{scan['scan_id']}/observations/",
        headers=HEADERS,
        params={"session_id": SESSION_ID},
    ).json()["results"]
    if observations and observations[0]["status"] not in ("pending", "running"):
        print(observations[0]["scanner_result"]["model_output"])
        break
    time.sleep(10)
```

To read every observation of a session across all of your scanners, call `/api/projects/:project_id/vision/observations/?session_id=...` instead.

### The same question is only answered once

`scan_id` is a fingerprint of the whole config: the prompt, the scanner type, the scanner configuration, and the model. So:

- The same question in the same project always resolves to the same `scan_id`. Store it, or send the scan again to get it back.
- Each session is only observed once per scan. A session you already scanned comes back as `already_scanned`, costs no credits, and its observation is ready to read.
- Any change to the config gives you a new `scan_id`, and the sessions are scanned again at the usual price.

The **Summarize this recording** action in the replay player runs an inline scan too. Your call shares its results only when the prompt, the scanner type, and the scanner configuration match what the button sends. Anything else is your own scan, with its own credits.

A `scan_id` has no page in the app, so do not link to one.

### Costs and limits

Every observation that starts spends [credits](/docs/replay-vision/quota-and-limits). Check what is left with `GET /api/projects/:project_id/vision/quota/`, which returns `credit_limit`, `credits_used`, `remaining`, `exhausted`, `projected_monthly_credits`, and the bounds of the current period.

## Ineligible sessions

Some sessions can't be analyzed – there's no recording data, the recording is too short to draw conclusions from, or the user did nothing the model can see. Rather than fail noisily, these come back marked **ineligible**.

The taxonomy:

| Ineligible reason | What it means                                                                 |
| ----------------- | ----------------------------------------------------------------------------- |
| `no_recording`    | The session referenced doesn't have replay data in storage                    |
| `too_short`       | The recording is below the minimum duration we'll scan                        |
| `too_inactive`    | The recording is long enough but the user was idle for almost all of it       |
| `too_long`        | The recording is above the maximum duration we'll scan                        |
| `no_events`       | The recording has no analytics events at all                                  |
| `no_ai_consent`   | AI data processing is turned off for your organization, so nothing is scanned |

Ineligible observations:

- Show up on the scanner's Observations tab with the reason, so you can audit why a session was skipped.
- **Do not count against your [quota](/docs/replay-vision/quota-and-limits).**
- Are not emitted as `$recording_observed` events – querying observations only ever returns succeeded ones.

If you're seeing a lot of ineligibles for one scanner, that's usually a signal to narrow the filters – e.g. exclude sessions below a duration threshold, or require at least one event. See [troubleshooting](/docs/replay-vision/troubleshooting) for more.
