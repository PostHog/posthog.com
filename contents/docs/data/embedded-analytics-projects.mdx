You can use PostHog to power analytics dashboards inside your product. Capture your customers' events in PostHog, query the data, and display the results in your own UI. This is often easier than building and maintaining your own infrastructure.

This is called embedded analytics, or customer-facing analytics. You can store all customer data in one PostHog project and filter it by customer, or create a separate project for each customer.

## How person profiles can merge

[Person profiles](/docs/data/persons) and [distinct IDs](/docs/getting-started/identify-users) are scoped to a project. If two customers use the same distinct ID, PostHog treats them as the same person.

For example, suppose your platform lets customers publish apps and see pageviews and conversions in a built-in dashboard. Two customer apps identify the same visitor with the user ID `123`. If both apps send data to one PostHog project, the events appear in one person profile and timeline. Funnels and other per-user insights can then combine activity from both apps.

Prevent this by including the customer ID in each identified user's distinct ID:

```ts
posthog.identify(`${customerId}:${user.id}`)
```

This prevents identified users from different customers from sharing a profile. Anonymous activity can still merge if customer workspaces share browser storage, because the browser SDK can use the same anonymous distinct ID across those workspaces.

Once distinct IDs are unique to each customer, a single project works well for dashboards embedded in your product. A project per customer is better when you plan to provide direct PostHog access or need project-level data separation.

<CalloutBox icon="IconLightBulb" type="info" title="Our recommendation">

Use one project with customer-scoped distinct IDs when customers only view analytics inside your product. Use a project per customer when customers need access to PostHog.

</CalloutBox>

| | Single project | Project per customer |
|---|---|---|
| **Data** | Store all customer data together and filter it by a `customer_id` property. | Store each customer's data in a separate project. |
| **Best for** | Dashboards displayed inside your product. | Giving customers direct access to PostHog. |
| **Person profiles** | Require customer-scoped distinct IDs to prevent merging. | Automatically separated by project. |
| **Querying** | Pass a customer identifier to an Endpoint or the Query API. | Query each customer's project. |
| **Plan** | Available without an add-on. | Requires the [Boost add-on](/platform-packages) for unlimited projects. |

## Use one project with customer filters

Add a customer identifier, such as `customer_id`, to every event. You can then retrieve data for a specific customer in two ways:

- Create an [Endpoint with a variable](/docs/endpoints/guide-variables) and pass the customer ID when you call it. This lets one Endpoint serve every customer.
- Use the [Query API](/docs/api/queries) and filter the query by the customer ID.

Run these requests from your backend. Use the authenticated customer's ID rather than accepting an arbitrary ID from the client.

Because all data remains in one project, don't give customers direct PostHog access. Project members can query the project's underlying data even when [resource access controls](/docs/settings/access-control#3-resource-level) hide specific resources.

## Create a project for each customer

A separate project keeps each customer's events and person profiles apart. Use this setup when customers need to log in to PostHog or when you need a project boundary between their data.

### Create projects with the API

Create a project when you add a customer by calling the [projects API](/docs/api/projects). Get your organization ID from the [`/api/organizations/@current`](https://app.posthog.com/api/organizations/@current) endpoint.

Each project has its own [project token](/docs/settings/projects) for event ingestion. Use its project ID to call Endpoints or the Query API.

<CalloutBox icon="IconWarning" type="caution" title="Requires the Boost add-on">

Free organizations include one project. The [Boost add-on](/platform-packages) includes unlimited projects.

</CalloutBox>

### Give customers access

If customers log in to PostHog:

- Use [project access control](/docs/settings/access-control#2-project-level) to give each customer access only to their project. You can [manage access control through the API](/docs/settings/access-control#api-support).
- Disable [full organization member visibility](/docs/settings/organizations#member-list-visibility) so customers only see themselves and members of their project.
- [Enforce two-factor authentication](/docs/settings/account-settings#enabling-2fa) to protect customer data.

### Billing

Billing is organization-wide, so usage is combined across all projects. For example, 100 projects sending 20,000 events each count as 2 million events, not 100 separate free tiers.

Account for this combined usage when pricing your product.
