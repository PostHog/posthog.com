Your people are already in PostHog if you capture events with a PostHog SDK, so you move the things around them: opt-outs, suppressions, automations, and push devices. PostHog imports automations as draft workflows, and drafts never send until you enable them.

## What moves

| From Customer.io | In PostHog | How |
| --- | --- | --- |
| Subscription topics | Message categories | [Opt-out import](#2-import-opt-outs-and-suppressions), API key step |
| Global unsubscribes | Opt-outs | Opt-out import, API key step |
| Bounced and invalid addresses | Suppression list. PostHog sends them no email. | Opt-out import, API key step |
| Spam reports | Suppression list. PostHog sends them no marketing email. | Opt-out import, API key step |
| Per-topic preferences | Opt-outs per category | Opt-out import, CSV step |
| Automations | Draft workflows, with their email content, snippets, layouts, and images | [Automation import](#3-import-automations) |
| Dynamic segments that an automation uses | Realtime cohorts, when every rule has an exact match | Automation import |
| Sender identities | Matched to the PostHog sender with the same address | Automation import |
| Push device tokens | Devices on a PostHog push channel | [Device token import](#4-move-push-devices) |

These don't move:

- **People and their profiles.** Capture them with a [PostHog SDK](/docs/messaging/installation) instead. The import never copies customer profiles, segment members, deliveries, or events.
- **Static segment members.** A workflow can't check a static cohort, so rebuild a static segment as conditions.
- **SMS and push steps.** They import as notes. To keep sending push to existing app installs, [move your push devices](#4-move-push-devices).
- **Sending history.** Past deliveries and broadcast results stay in Customer.io.

## 1. Set up sending

[Verify your sending domain](/docs/messaging/verify-domain) and add a sender for each from-address your Customer.io emails use. The automation import matches each email to the PostHog sender with the same address. When there's no match, the draft gets a note that asks you for a sender.

If your domain still sends through Customer.io, follow the [migration steps](/docs/messaging/sending-reputation#move-from-another-provider) on sending reputation and allowance.

## 2. Import opt-outs and suppressions

Do this before you import automations. The opt-out import creates the message categories that the automation import maps Customer.io topics to, and it stores the App API key that lets PostHog read your email content.

Go to **Workflows > Opt-outs** in PostHog and click **Import from Customer.io**. If your project can import from more than one tool, the button is **Import from another tool**.

### Import categories, global opt-outs, and suppressions

This step imports all subscription topics, globally unsubscribed customers, and suppressed addresses from Customer.io with an App API key. The import runs in the background, so you can close the modal and come back to check on progress at any time.

To create an App API key in Customer.io, go to **[Settings > Account Settings > App API Keys](https://fly.customer.io/settings/api_credentials?keyType=app)** in your Customer.io dashboard. Click **Create New App API Key** and give it a descriptive name, such as "PostHog Import".

<CalloutBox icon="IconWarning" title="Save your API key" type="caution">

Save this API key securely. Customer.io only shows it once.

</CalloutBox>

Go back to PostHog, paste the key into the first step, select which data to import, and click **Start import**. PostHog shows progress for each step as the import runs, and a notification when it finishes. This imports:

- All available categories from Customer.io
- All customers who are generally unsubscribed (not subscribed to any category)
- Suppressed addresses: the addresses that Customer.io's email provider bounced, marked as invalid, or got a spam report for. PostHog sends no email to a bounced or invalid address, and no marketing email to an address with a spam report.

Customer.io only supports importing globally unsubscribed users through its API, so you import per-category opt-outs with a CSV in the next step.

1. Click **conditions** at the top of the page

3. Choose the **exists** operator

### Receive opt-out updates from Customer.io

While you run both tools side by side, keep opt-outs in sync. Set up a [Reporting Webhook](https://docs.customer.io/integrations/api/webhooks/) so Customer.io notifies PostHog whenever someone unsubscribes or changes their topic preferences.

Go to Customer.io and navigate to **Integrations > Add integration > Reporting webhook**. Paste the webhook URL from PostHog.

Next, copy the webhook signing secret. PostHog uses it to check that incoming webhooks are from your Customer.io account, and rejects unsigned webhooks. Back in PostHog, paste the signing secret and click **Enable sync**.

Once enabled, PostHog records opt-outs whenever:

- A user globally unsubscribes or resubscribes in Customer.io
- A user changes their per-topic subscription preferences in Customer.io

### Send PostHog opt-out updates to Customer.io

When users update their preferences through a PostHog-managed preferences page, you can sync those changes back to Customer.io. This is useful if you haven't moved all your email campaigns to PostHog yet. Only categories originally imported from Customer.io are synced back.

To get your Customer.io Track API credentials, go to **Settings > API and webhook credentials > Track API Keys** and copy the **Site ID** and **Track API key**.

Back in PostHog:

1. Select your Customer.io **region** (US or EU). This sets which Track API endpoint PostHog uses.
2. Enter your **Site ID**
3. Enter your **Track API key**
4. Click **Enable sync**

### Import with your agent

Your agent can also run the API key step over the [PostHog MCP](/docs/messaging/mcp). `provider-imports-providers` lists the steps, `provider-imports-create` starts the import with your App API key, and `provider-imports-list` and `provider-imports-get` show its progress. These tools are still rolling out, so your project might not have them yet. The CSV step and the sync both ways are set up in PostHog.

## 3. Import automations

On the [Workflows](https://app.posthog.com/workflows) page, click **Import from Customer.io**. There are two ways to bring automations over:

- **Ask your coding agent.** With the Customer.io MCP and the [PostHog MCP](/docs/messaging/mcp) connected, ask "Move our Customer.io campaigns into PostHog". The [`migrating-from-customer-io` agent skill](/docs/messaging/skills) runs the import for you. See [what the agent does](#what-the-agent-does).
- **Upload files from the Customer.io CLI.** Export each automation, and any template or segment it uses, as JSON with `cio api`, then drop the files into the import modal.

The import runs a preview first, which saves nothing. Each automation gets one of these notes:

| Note | Meaning | What to do |
| --- | --- | --- |
| Needs input | The draft needs a setting only your team can give, such as a sender, a trigger cohort, or a branch condition. | Fix it before you enable the workflow. |
| Approximated | The step works differently in PostHog, such as a wait capped at 30 days. | Check it before you enable the workflow. |
| Unsupported | The setting has no PostHog equivalent and was left out, such as an SMS step. | Rebuild it another way, or leave it out. |

The notes also show on each imported workflow in PostHog, and `workflows-import-notes` returns them over MCP.

Importing an automation again replaces its draft, so you can fix something in Customer.io and run the import again. Edits your team made to that draft since are lost. A workflow that someone already enabled is never changed.

An email's subscription topic, or the automation's topic when the email has none, becomes the message category that the opt-out import made from that topic. When the topics weren't imported, a note says so.

The import copies email images that Customer.io hosts into your project's media library, so they keep loading after you close your Customer.io account.

### What the agent does

1. Confirms the PostHog project that the drafts go into, and asks which Customer.io workspace to move if you have more than one.
2. Lists the automations with their state, and asks which ones to move.
3. Reads each automation's graph, your sender identities, and the rules of each dynamic segment the automations check, with the Customer.io MCP or CLI. It never reads segment members or customer profiles.
4. Previews the import with `workflows-import-customerio`, which saves nothing.
5. Reports each automation's notes, and which segments become cohorts.
6. Imports the drafts after you confirm, and shares a link to each one.

The agent doesn't enable the drafts. You handle the notes and enable each workflow yourself.

### Segments

A dynamic segment becomes a realtime cohort only when every rule matches a cohort condition exactly, such as a person attribute that equals, contains, or exists, or an absolute date. Rules on events, message activity, other segments, devices, relationships, or relative dates ("in the last 30 days") have no exact match. The import leaves those segments out and adds a note that names the rules, so you can build the cohort yourself.

## 4. Move push devices

Push steps don't import, and device tokens don't move with the automation import. A device reaches PostHog when your app registers it with the PostHog SDK, or when you [import your device tokens](/docs/messaging/push-notifications/import-device-tokens) into a PostHog push channel. To have your agent do it, ask it to import your Customer.io push tokens. The `importing-push-tokens` [agent skill](/docs/messaging/skills) maps each device to its PostHog person, checks the pairing with a dry run, and imports in batches.

## 5. Test and enable

Open each draft, handle its notes, and [test it](/docs/messaging/automations) before you enable it. Turn off the matching automation in Customer.io when you enable the PostHog workflow, so nobody gets the same email twice.
