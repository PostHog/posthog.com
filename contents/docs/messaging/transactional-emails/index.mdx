Transactional emails are a new feature. Things might change or break while we work on them.

Transactional emails are the one-off emails that a person triggers in your product, such as password resets, sign-in codes, and receipts. Your backend sends each one to one recipient with one call, with content that your code renders or that you write in the PostHog editor. PostHog records each send on the recipient's person, next to their product events, so you can see who opened the reset email and whether they signed in after it.

**SDKs:** [Node.js](/docs/messaging/transactional-emails/node) · [Python](/docs/messaging/transactional-emails/python) · [Go](/docs/messaging/transactional-emails/go) · [.NET](/docs/messaging/transactional-emails/dotnet) · [Rust](/docs/messaging/transactional-emails/rust) · [Ruby](/docs/messaging/transactional-emails/ruby) · [Elixir](/docs/messaging/transactional-emails/elixir) · [PHP](/docs/messaging/transactional-emails/php) · [API](/docs/messaging/transactional-emails/api) · [Examples](/docs/messaging/transactional-emails/examples)

## Set it up with a coding agent

The fastest way to add your first send is the PostHog wizard. Run it in your project:

```bash
npx @posthog/wizard@latest email
```

It checks that you have a verified sender, writes the email in your code, adds a [project secret API key](#create-an-api-key) to your env file, and adds the send with the SDK for your backend.

You can also ask your coding agent, with the [PostHog MCP server](/docs/model-context-protocol), to set up a transactional email. It can design the email from your brand, make it transactional, and write the code that sends it. It asks you to confirm before it makes a template transactional, and you create the API key yourself. The [`sending-transactional-emails` agent skill](/docs/messaging/skills) teaches your agent this setup. Each SDK page also has a prompt to paste into your agent, with the rules that agents get wrong: where the secret key lives, how to build idempotency keys, and which errors to retry.

## Choose where the email's content lives

Both options get the same idempotency keys, statuses, suppression checks, and engagement events.

| | Send content from your code | Write it in PostHog |
| --- | --- | --- |
| Who edits it | Engineers, in your codebase | Anyone on your team, in the PostHog editor, with no deploy |
| Best for | [React Email](/docs/messaging/transactional-emails/react-email) or other templates that you already have, and a move from another email provider | Copy that changes often, and teams that want drafts, versions, and a preview |
| What a send carries | `template_key`, `subject`, and `html` or `text` | `template_id` and the template's variables |
| Copies and attachments | `cc`, `bcc`, and [`attachments`](/docs/messaging/transactional-emails/api#copies-and-attachments) | Not on the send |

## Send email from your code

You need a verified sender and a [project secret API key](#create-an-api-key). To try a send by hand before you [verify your sending domain](#verify-your-sending-domain), use the [sandbox sender](/docs/messaging/sandbox-sender).

Write each email with [React Email](/docs/messaging/transactional-emails/react-email) or the templates that you already have, and keep it next to the code that sends it. Your code renders the content, and the SDK sends it with one call. You don't need a template in PostHog.

```jsx
import { PasswordResetEmail } from "./emails/password-reset"

const { data, error } = await posthog.emails.send({
    to: email,
    templateKey: "password-reset",
    subject: "Reset your password",
    react: <PasswordResetEmail firstName={firstName} resetLink={resetLink} />,
    distinctId: userId,
    idempotencyKey: `password-reset-${resetRequestId}`,
})
```

Name the email with `templateKey`, and pass `subject` with `html`, `text`, or a React Email component as `react`. PostHog groups the email's metrics and sends under the key, so use the same key every time you send this email.

Each SDK page in the list above shows the install, the client, and every field of a send. For other languages, use [the API](/docs/messaging/transactional-emails/api#send-content-from-your-code).

## Send your first email

You need a [verified sending domain](#verify-your-sending-domain) and a [project secret API key](#create-an-api-key) with **Transactional email** set to **Write**.

<Steps>

<Step title="Create the email">

Open [**Transactional**](https://app.posthog.com/transactional), click **New transactional email**, and choose your sender. Turn on [**Protect sensitive data**](#protect-sensitive-data), because this email carries a reset link. Write a subject, and a body that uses one variable:

```liquid
Hi {{ variables.first_name }}, use this link to reset your password: {{ variables.reset_link }}
```

Copy the template ID from the email's **API** tab.

</Step>

<Step title="Send the email to yourself">

```bash
export POSTHOG_PROJECT_SECRET_API_KEY="phs_..."

curl -X POST "https://us.posthog.com/api/messaging/send/email/" \
  -H "Authorization: Bearer $POSTHOG_PROJECT_SECRET_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: my-first-email" \
  -d '{
    "template_id": "<template_id>",
    "to": "you@example.com",
    "message_data": {"first_name": "Ada", "reset_link": "https://example.com/reset"}
  }'
```

Use your own address as `to`. If your project is in the EU, use `https://eu.posthog.com`. A `202` with a `message_id` means that PostHog queued the email.

</Step>

<Step title="See it arrive" checkpoint>

Open the email's **Sends** tab to see your send and its status. If the email isn't in your inbox, see [troubleshooting](/docs/messaging/transactional-emails/troubleshooting#an-email-didnt-arrive).

</Step>

</Steps>

Now send it from your app with one of the SDKs above, or with [the API](/docs/messaging/transactional-emails/api).

## Create a transactional email

Each email in [**Transactional**](https://app.posthog.com/transactional) has a **Design**, **Metrics**, **Sends**, **Versions**, and **API** tab. The **API** tab has the template ID and an example send. Use the variables that your code sends as `{{ variables.reset_link }}`.

- **Sender** - On the **Design** tab, click **Edit sender** to choose a different verified sender, or to set a display name, a from address on the sender's verified domain, or reply-to addresses separated by commas.
- **Drafts** - Edits save as a draft. Sends use the live version until you click **Publish**, and each publish adds a version on the **Versions** tab. **Discard draft** throws your edits away.
- **Checks** - PostHog doesn't publish a change that would stop the email from sending, such as an empty subject or body, or a marketing category.

<CalloutBox icon="IconWarning" title="An email stays transactional" type="caution">

Transactional emails ignore marketing opt-outs, so use them only for emails that a person needs, never for marketing. You can't change a transactional email back to a regular template.

</CalloutBox>

### Use an existing template

Open the template in the **Templates** tab, open its **API** tab, and click **Make transactional**. The template needs a subject, a body, a verified sender, and no marketing [message category](/docs/messaging/opt-outs#message-categories). If you still use it for other emails, click **Duplicate** in its menu first, and make the copy transactional. With the API, call `POST /api/projects/:project_id/messaging_templates/:template_id/make_transactional/` with a [personal API key](/docs/api/personal-api-keys) that has the `transactional_email:write` scope. Keys with `hog_flow:write` still work.

## Verify your sending domain

Both paths need a [verified sending domain](/docs/messaging/verify-domain). Verification usually takes a few minutes. Until then, you can try a send by hand from the [sandbox sender](/docs/messaging/sandbox-sender), shown in the app as **PostHog test sender**. It delivers only to members of your PostHog organization, ignores `from` and `reply_to`, and doesn't take `cc`, `bcc`, or `attachments`. To move from another provider, add PostHog's records next to the old ones while it still sends. Transactional email never waits for your sending allowance, so you can move it on day one. See [sending reputation and allowance](/docs/messaging/sending-reputation#move-from-another-provider).

## Create an API key

Send with a [project secret API key](/docs/api/project-secret-api-keys) that has the `transactional_email:write` scope. Keys with `hog_flow:write` still work. The key can send transactional emails and [read their status](/docs/messaging/transactional-emails/api#check-an-emails-status), and nothing else. Keep the key on your server, and never put it in code that runs in the browser.

1. Go to [**Project secret API keys**](https://app.posthog.com/settings/project-secret-api-keys) and click **Create project secret API key**.
2. Give the key a label, and set **Transactional email** to **Write**. For a service that only reads statuses, choose **Read**.
3. Copy the key. It starts with `phs_`, and you can't see it again after you leave the page.

## Protect sensitive data

For emails with sign-in codes, reset links, or other secrets, turn on **Protect sensitive data** when you create the email, or on its **API** tab. PostHog then keeps no copy of the content and doesn't track link clicks, so a token in a link never goes through a tracking redirect. It still tracks deliveries, opens, bounces, and status. You can change this setting at any time. An email from your code takes this setting from the template with the same key, and is sensitive when no template has that key. Set [`sensitive`](/docs/messaging/transactional-emails/api#sensitive-emails) on the send to choose.

## See what happened around an email

Open **Transactional**, go to the **Log** tab, and click an email. **Activity around this email** shows the recipient's events from 7 days before to 7 days after the send, grouped by session and split at the send, and the other emails that person got. Click **Watch** on a session to open its [session replay](/docs/session-replay).

This needs the recipient's [distinct ID](/docs/messaging/transactional-emails/api#link-emails-to-your-users) on the send, and events without a session have no replay. On the **Metrics** tab, **What happened after** shows how many of the people you emailed did an event afterwards, and the revenue they brought in.
