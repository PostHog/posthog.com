Using MCP Analytics doesn't stop you from listing your MCP server in the ChatGPT or Claude directories. Reviewers may flag some of the arguments the SDK adds, though. If you plan to list your server, set it up as shown here before you submit, so you don't lose a review round.

By default, the SDK adds three parameters to every tool: `context`, `llm_model`, and `conversation_id`. They're only used for analytics. They give you deeper insights, but your server doesn't need them to work, so you can turn them off.

<CalloutBox icon="IconInfo" title="Last updated November 24, 2026" type="fyi">

OpenAI and Anthropic make the final call. Their rules are in the [OpenAI app developer guidelines](https://developers.openai.com/apps-sdk/app-developer-guidelines/) and the [Claude Connectors Directory review criteria](https://claude.com/docs/connectors/building/review-criteria).

</CalloutBox>

## Configure the SDK before you submit

With this config, your tools and their results look exactly like they would without the SDK.

<MultiLanguage>

```ts file=TypeScript
instrument(server, posthog, {
  context: false,
  captureModel: false,
  enableConversationId: false,
})
```

```python file=Python
from posthog.mcp.types import MCPAnalyticsOptions

instrument(
    server,
    posthog,
    MCPAnalyticsOptions(
        context=False,
        capture_model=False,
        enable_conversation_id=False,
    ),
)
```

```go file=Go
posthogmcpsdk.Instrument(server, posthogmcp.New(client),
	posthogmcpsdk.WithContextParameter(false),
	posthogmcpsdk.WithCaptureModel(false),
	posthogmcpsdk.WithConversationID(false),
)
```

```ruby file=Ruby
PostHog::MCP.instrument(
  server, posthog,
  context: false,
  capture_model: false,
  enable_conversation_id: false
)
```

```rust file=Rust
let options = McpOptionsBuilder::default()
    .context(false)
    .capture_model(false)
    .conversation_id(false)
    .build()?;
let server = McpAnalytics::new(posthog.clone(), options).instrument(MyServer);
```

</MultiLanguage>

Leave the `get_more_tools` and `send_feedback` tools off.

On a [custom dispatcher](/docs/mcp-analytics/installation/typescript#custom-dispatchers), `context` is an option of `prepareToolList`, not the constructor:

- TypeScript: `captureModel: false` and `enableConversationId: false` on `PostHogMCP`, and `{ context: false }` on `prepareToolList`.
- Python: `capture_model=False` and `enable_conversation_id=False` on `PostHogMCP`, and `context=False` on `prepare_tool_list`.
- Ruby: `capture_model: false` on `PostHog::MCP::Client.new`, and `context: false` on `prepare_tool_list`.

### ChatGPT: keep a short intent field

ChatGPT is a bit more flexible. OpenAI allows a short intent field, so you can keep `context` if you shorten its prompt. Replace `context: false` with:

<MultiLanguage>

```ts file=TypeScript
context: { description: "In a few words, what is the user trying to do? Don't include personal details." },
```

```python file=Python
from posthog.mcp.types import MCPAnalyticsContextOptions

context=MCPAnalyticsContextOptions(
    description="In a few words, what is the user trying to do? Don't include personal details.",
),
```

```ruby file=Ruby
context: { description: "In a few words, what is the user trying to do? Don't include personal details." },
```

```rust file=Rust
.context_description("In a few words, what is the user trying to do? Don't include personal details.")
```

</MultiLanguage>

Go doesn't let you change the prompt, so turn `context` off there. For Claude, turn it off in every SDK.

## What you still get

You keep most of what makes MCP Analytics useful:

- Every tool call, with its outcome, latency, and error type.
- The client, such as ChatGPT or Claude.
- Sessions, when the transport has a session ID. From TypeScript 1.7.0, ChatGPT calls also group by ChatGPT's own conversation ID.
- Users, from your [identify callback](/docs/mcp-analytics/identifying-users).

The biggest loss is intent. You can get some of it back with an [intent fallback](/docs/mcp-analytics/intent#the-intent-fallback-callback), a callback on your server that builds intent from the tool name and arguments.

You also lose the model name, including the one Codex sends. And on a stateless server without a session ID, every call becomes its own session.

## Optional: send less tool data

Tool arguments, results, and error messages only go to PostHog. The model never sees them, so they don't change your tools. We find them really useful for debugging failed calls. If you'd still rather send only usage data, remove `$mcp_parameters`, `$mcp_response`, and `$mcp_error_message`:

- TypeScript, Python, and Ruby: the [before-send hook](/docs/mcp-analytics/privacy#3-your-before-send-hook-optional).
- Go: `posthogmcpsdk.WithCaptureParameters(false)` and `posthogmcpsdk.WithCaptureResponses(false)` on `Instrument`, and `posthogmcp.WithCaptureErrorMessages(false)` on `posthogmcp.New`.
- Rust: `.capture_parameters(false)` and `.capture_responses(false)`, and remove `$mcp_error_message` in `before_send`.

Failed calls also send an `$exception` event with the error message. You can [turn off exception events](/docs/mcp-analytics/privacy#turn-off-exception-events) too.

## Tell users what you collect

Both directories expect your privacy policy to say what you collect. Something like this works:

> We use PostHog to see how AI clients use this server: which tools they call, whether the calls succeed, and how long they take.

If you keep tool arguments and results, mention them too.

## Recheck your tools after upgrading

SDK upgrades can change your tool schemas. OpenAI re-reviews changed tools, and Anthropic asks you to tell them about material changes. So after upgrading, compare your `tools/list` output with what you submitted.
