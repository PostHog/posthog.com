MCP Analytics works with servers listed in the ChatGPT app directory and the Claude Connectors Directory. You need one configuration change before you submit, and you still see which tools agents call, which calls fail, how long they take, and which clients and users they come from.

Directory reviewers check that every tool argument serves the tool's function. By default, the SDK adds a few analytics arguments to your tools so agents can tell you why they called them. Those arguments are what reviewers ask about, so turn them off for a directory listing. Everything that runs on your server keeps working.

<CalloutBox icon="IconInfo" title="Last updated November 24, 2026" type="fyi">

We're working with OpenAI and Anthropic to bring more of the SDK's insights to directory-listed servers. We update this page as their guidance and our defaults change. Each platform makes the final decision under its own policy: the [OpenAI app developer guidelines](https://developers.openai.com/apps-sdk/app-developer-guidelines/) and the [Claude Connectors Directory review criteria](https://claude.com/docs/connectors/building/review-criteria).

</CalloutBox>

## What to change for a directory listing

| What the SDK adds | Why it matters for review | What to do |
| --- | --- | --- |
| A required `context` argument on every tool | It captures intent for analytics, not for the tool's function. | Turn it off. Use an [intent fallback](#what-you-keep) instead. |
| An `llm_model` argument on every tool | It isn't part of the tool's function. | Turn it off. |
| A `conversation_id` argument, and a `{"conversation_id": ...}` block appended to tool results | OpenAI's guidelines don't allow session IDs in tool responses. | Turn it off. ChatGPT sessions still group in TypeScript 1.7.0 and later. |
| The `get_more_tools` and `send_feedback` tools | Reviewers expect every tool to serve the user. | Nothing. They're off by default. |
| Tool arguments, results, and error messages sent to PostHog | The model doesn't see them. Reviewers can ask whether you need them and whether you disclose them. | Your choice. See [drop tool data](#optional-drop-tool-arguments-and-results). |

## Turn off the arguments the model sees

Set these options before you submit. Your server then advertises the same tool schemas and returns the same tool results as it does without the SDK. The SDK still sends an event for every tool call.

<MultiLanguage>

```ts file=TypeScript
instrument(server, posthog, {
  context: false,
  captureModel: false,
  enableConversationId: false,
})
```

```python file=Python
from posthog.mcp.types import MCPAnalyticsOptions

instrument(
    server,
    posthog,
    MCPAnalyticsOptions(
        context=False,
        capture_model=False,
        enable_conversation_id=False,
    ),
)
```

```go file=Go
posthogmcpsdk.Instrument(server, posthogmcp.New(client),
	posthogmcpsdk.WithContextParameter(false),
	posthogmcpsdk.WithCaptureModel(false),
	posthogmcpsdk.WithConversationID(false),
)
```

```ruby file=Ruby
PostHog::MCP.instrument(
  server, posthog,
  context: false,
  capture_model: false,
  enable_conversation_id: false
)
```

```rust file=Rust
let options = McpOptionsBuilder::default()
    .context(false)
    .capture_model(false)
    .conversation_id(false)
    .build()?;
let server = McpAnalytics::new(posthog.clone(), options).instrument(MyServer);
```

</MultiLanguage>

Don't turn on the virtual tools. Leave out `reportMissing` and `collectFeedback` in TypeScript, `report_missing` and `collect_feedback` in Python and Ruby, `WithMissingCapabilityTool` in Go, and `missing_capability_tool` and `feedback_tool` in Rust.

If you use a [custom dispatcher](/docs/mcp-analytics/installation/typescript#custom-dispatchers) (`PostHogMCP`) instead of `instrument()`, pass `captureModel: false` and `enableConversationId: false` to the constructor, and `{ context: false }` to `prepareToolList`. In Python, pass `capture_model=False` and `enable_conversation_id=False` to the constructor, and `context=False` to `prepare_tool_list`. In Ruby, pass `capture_model: false` to `PostHog::MCP::Client.new` and `context: false` to `prepare_tool_list`.

If you submit to one directory and also serve other clients from a separate deployment, you can keep the defaults on that deployment.

### What you keep

With these options off, PostHog still records the data most teams start with:

- The tool name, the outcome, the latency, and the error type of every call.
- The client and harness, such as ChatGPT or Claude.
- Sessions, wherever the transport has a session ID. The TypeScript SDK (1.7.0 and later) also groups ChatGPT calls by ChatGPT's own conversation ID.
- Users, through your [identify callback](/docs/mcp-analytics/identifying-users).
- Intent, if you add an [intent fallback](/docs/mcp-analytics/intent#the-intent-fallback-callback). It derives intent from the tool name and arguments on your server, so the model sees nothing.

What changes:

- Intent comes from your fallback instead of the agent's own words.
- PostHog doesn't record the calling model (`$mcp_llm_model`). This also applies to the model that Codex sends in request metadata.
- On a stateless server with no transport session ID, each call is its own session.

## Optional: drop tool arguments and results

The model never sees what the SDK sends to PostHog, so these properties don't change your tools. They're useful for debugging failed calls. Keep them if you need them, and say so in your privacy policy. If a reviewer asks you to collect less, or you want to send only usage data, remove `$mcp_parameters`, `$mcp_response`, and `$mcp_error_message` from each event:

- In TypeScript, Python, and Ruby, use the [before-send hook](/docs/mcp-analytics/privacy#3-your-before-send-hook-optional).
- In Go, pass `posthogmcpsdk.WithCaptureParameters(false)` and `posthogmcpsdk.WithCaptureResponses(false)` to `Instrument`, and `posthogmcp.WithCaptureErrorMessages(false)` to `posthogmcp.New`.
- In Rust, call `.capture_parameters(false)` and `.capture_responses(false)` on `McpOptionsBuilder`, and remove `$mcp_error_message` in its `before_send` hook.

Failed calls also send an `$exception` event with the error message. To stop it, [turn off exception events](/docs/mcp-analytics/privacy#turn-off-exception-events).

## Disclose analytics in your privacy policy

Both platforms expect you to tell users what your server collects. Add a sentence like this one to your privacy policy, and edit it to match your configuration:

> We use PostHog to record how AI clients use this server: which tool was called, whether it succeeded, how long it took, and which client called it.

If you keep tool arguments and results, say so too.

## Check your tools after each SDK upgrade

An SDK upgrade can change the schemas your server advertises. OpenAI reviews changed tools again, and Anthropic asks you to report material changes to tool descriptions. After you upgrade, compare your server's `tools/list` output with the version you submitted.
