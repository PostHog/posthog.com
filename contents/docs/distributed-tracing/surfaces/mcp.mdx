Connect the [PostHog MCP server](/docs/model-context-protocol) so coding agents can inspect your traces beside your source code. Your agent can check service health, locate regressed operations, read a trace's critical path, and draft a fix in the same session.

This works in any MCP client, including Cursor, Claude Code, Codex, Windsurf, and VS Code.

## Gather what you need

1. **Send traces to PostHog.** Follow [Install tracing](/docs/distributed-tracing/installation) so your project has spans to read.
2. **Connect PostHog MCP.** Install the [PostHog MCP server](/docs/model-context-protocol) in your AI tool and grant `tracing:read` access to your project.

## Read trace summaries first

`apm-trace-get` defaults to `summary: true` and returns a roughly 3 KB summary for traces of any size. The summary includes:

- **Headline timing.** Shows total trace duration, root span, span count, service count, and error count.
- **Top self-time spans.** Lists spans whose own duration isn't covered by children, which often point to uninstrumented work.
- **Critical path.** Traces the chain of spans the end time waits on, collapsing N+1 loops and omitting spans under 1% of root duration.
- **Repeated spans and errors.** Flags repeated span names (potential N+1 queries) and error spans with their exception messages.

Set `summary: false` only when your agent needs every raw span field. Pair it with `excludeAttributes: true` unless you need multi-KB attributes like `db.statement`. Paginate with `offset` (up to `2,000` spans per page).

## Try these prompts

| Goal | Ask your agent |
| --- | --- |
| Triage services | `Check service health over the last hour compared to yesterday` |
| Rank slow operations | `Show the top 10 slowest operations by p95 latency in checkout-api over the last 6 hours` |
| Spot regressions | `Compare checkout-api operations over the last hour against the previous hour` |
| Isolate bad infrastructure | `Break down errored spans in payments by k8s.pod.name and server.address` |
| Find slow child spans | `Find traces in the last day with a clickhouse.query span slower than 1000ms` |
| Inspect one trace | `Summarize trace 4bf92f3577b34da6a3ce929d0e0e4736 and point me to the slow code path` |

## Guide your agent

Point your agent at this sequence, so it doesn't guess attribute keys or blow through its context window:

1. Call `apm-service-health` or `apm-services-list` to find the failing service.
2. Call `apm-attributes-list` and `apm-attribute-values-list` before writing attribute filters.
3. Use `apm-spans-aggregate` or `apm-attribute-breakdown` to isolate the operation or host causing errors.
4. Use `query-apm-spans` (`flatSpans: true` for child attributes) to grab a concrete `trace_id`.
5. Call `apm-trace-get` with the default summary to read the critical path and jump straight to the offending file in your repo.

For full MCP setup and tool scoping options, see the [MCP tools reference](/docs/model-context-protocol/tools).
