With Okta Cross App Access (XAA), your Okta org decides which members can use the PostHog MCP server in Claude, and with which scopes. Members sign in to Claude through Okta and never see a PostHog sign-in prompt.

This is one of the identity sources for [enterprise-managed authorization](/docs/model-context-protocol/enterprise-managed-authorization). If you don't use Okta, [Claude-issued identity](/docs/model-context-protocol/claude-issued-identity) is quicker to set up.

PostHog isn't in the Okta Integration Network yet, so you use the PostHog app you created in Okta for SSO.

## Before you start

- **In Okta:** an org with SSO and Cross App Access, and the super admin role.
- **A PostHog app in Okta for SSO.** Cross App Access builds on SSO, so set up [SAML](/docs/settings/authentication/saml) or [OIDC](/docs/settings/authentication/oidc) with Okta first.
- **In Claude:** a Team or Enterprise plan that signs in through Okta, and permission to manage connectors.
- **In PostHog:** the Scale or Enterprise [platform add-on](/platform-packages), admin access, and members whose Okta email matches their PostHog email. PostHog does not create accounts.

## 1. Turn on Cross App Access for your PostHog app in Okta

1. In the Okta Admin Console, go to **Applications → Applications** and select your PostHog app.
2. Open the **Machine Assignments** tab. In the **Callers** tile, click **Edit** next to **Cross App Access (XAA)**.
3. Select **Enable**, then fill in:
   - **Issuer URL:** `https://oauth.posthog.com`
   - **Audience/tenant ID:** `https://oauth.posthog.com`
   - **Scopes:** the PostHog scopes members may use. See [choosing scopes](#choosing-scopes).
4. Click **Save**.

## 2. Register Claude as an AI agent in Okta

Start Claude's setup first, because it gives you the values Okta needs:

1. In Claude, go to **Organization settings → Connectors**, select the **PostHog** connector, and click **Set up** next to **Managed authorization** on the **Configuration** tab.
2. Under **Identity source**, choose **IdP-managed**, confirm your Okta connection, and follow Claude's setup guide.

In Okta, Claude's guide has you go to **Directory → AI agents**, click **Register AI agent**, link it to the app your members use to sign in to Claude, and enter the client ID Claude shows on the **Client registration** tab. Activate the agent when you're done.

## 3. Connect Claude to PostHog in Okta

1. In **Directory → AI agents**, select the Claude agent and open **Resource connections**.
2. Click **Add resource connection**, then set:
   - **Application instance:** your PostHog app.
   - **Claude client ID registered in PostHog:** the client ID Claude uses with PostHog, which Claude's setup guide shows.
   - **Resource identifier:** `https://mcp.posthog.com/mcp`, or `https://mcp-eu.posthog.com/mcp` if you pin the EU region.
   - **Scopes:** **Allow specific scopes**, and select at least `user:read`, `organization:read`, and `project:read`.
3. Click **Add**.
4. On the agent's **User access** tab, assign the users or groups who should get PostHog in Claude.

## 4. Trust your Okta org in PostHog

1. In PostHog, go to [**Organization settings → Authentication**](https://app.posthog.com/settings/organization-authentication).
2. Under **Authentication domains**, make sure your email domain is verified.
3. Find **XAA authentication** and click **Configure**.
4. Set **Identity provider issuer URL** to your Okta org URL, for example `https://acme.okta.com`. Use the org authorization server, not a custom one such as `/oauth2/default`, because Okta issues these assertions from the org server.
5. Leave **JWKS URL** empty. Optionally, put the Claude client ID from step 3 in **Allowed client IDs**.
6. Under **Domains**, choose your email domain, then click **Save configuration**.

## 5. Test and enable in Claude

1. Back in Claude's setup, click **Run test**. Claude shows which step failed, if any, with what Okta and PostHog returned.
2. Enable the connector and choose which roles get it.

## Choosing scopes

<CalloutBox icon="IconWarning" title="Okta allows 100 scopes per app" type="action">

PostHog offers more than 100 scopes, so you can't list all of them in Okta. Pick the ones your members need.

</CalloutBox>

- Always include `user:read`, `organization:read`, and `project:read`. The MCP server needs them to list your organizations and projects.
- A `:write` scope also grants the matching `:read`, so list only the `:write` scope for products where members need to make changes.
- A read-only start covers most analysis: `insight:read`, `dashboard:read`, `query:read`, `event_definition:read`, `property_definition:read`, `person:read`, `cohort:read`, `session_recording:read`, `error_tracking:read`, `experiment:read`, `feature_flag:read`, `survey:read`, and `logs:read`.
- The full list is in `scopes_supported` at `https://oauth.posthog.com/.well-known/oauth-authorization-server`.

The access token gets only the scopes that both Okta granted and Claude asked for.

## Limits

Okta limits SSO-based Cross App Access to 250 ID-JAGs per user, per resource app, per month. Claude requests a new ID-JAG each time its PostHog access token expires, which is every 2 hours, so heavy daily use can reach that limit. Okta for AI Agents raises it.

## Revoking access

- **In Okta:** unassign a user from the agent, or remove the resource connection. Claude can't get new tokens for them, and a token already issued stays valid for up to 2 hours.
- **In PostHog:** removing a member from your PostHog organization, or deactivating them, stops their access on the next request.
- **For everyone:** disable managed authorization in Claude, or delete the XAA configuration in PostHog.

## Troubleshooting

| Error | Where | What to check |
| --- | --- | --- |
| `invalid_target` | Okta | The resource identifier Claude requested doesn't match the resource connection. |
| `unauthorized_client` | Okta | A scope Claude requested isn't allowed in the resource connection. |
| `invalid_grant` (`ID-JAG could not be verified`) | PostHog | The issuer URL in PostHog isn't your Okta org URL, or the member's email domain isn't selected under **Domains**. |
| `invalid_grant` (`ID-JAG sub is not an active member…`) | PostHog | The member's Okta email doesn't match a member of your PostHog organization. |
| `invalid_grant` (`ID-JAG client_id doesn't match the authenticating client`) | PostHog | The **Claude client ID registered in PostHog** in the resource connection isn't the client ID Claude uses with PostHog. |
| `invalid_client` | PostHog | Claude couldn't authenticate to PostHog, or its client ID isn't in **Allowed client IDs**. |
| `access_denied` | PostHog | Your PostHog organization doesn't have the Scale or Enterprise add-on. |

For every PostHog error code and what PostHog checks, see the [ID-JAG reference](/docs/settings/authentication/id-jag).
