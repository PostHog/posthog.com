# Offline evaluations

Before releasing the support agent, Twig's engineers had tested an ordinary cancellation: a visitor wants a full refund one day before arrival. The support agent explained the seven-day notice rule, and the policy evaluation passed.

That answer is correct. But the heating complaint reveals a gap in the engineers' testing: a broken essential amenity that qualifies for an exception to the cancellation policy.

Twig's engineers need to fix the support agent's refund refusal without breaking the standard cancellation policy answer. They use <Term name="offline evaluations">offline evaluations</Term> to run saved requests through the support agent and evaluate its answers before releasing the change.

## Save the request and expected outcome

Twig's engineers create a <Term name="dataset">dataset</Term>, a collection of test cases they can rerun. In PostHog, they open the recorded heating conversation and add it to the dataset to save it as a test case alongside the ordinary cancellation request.

For the heating complaint, they save two different things:

- `source_output` contains the support agent's original refusal.
- `expected_output` describes what the support agent should do: apply the broken-amenity exception and offer relocation or a refund.

The refusal is evidence of the problem, not the answer the engineers _want_ the evaluation to reward.

Switch between the cancellation and broken-amenity cases to compare their answers with the expected outcomes:

<AioDatasetFigure />

The cancellation case passes because the visitor changed their mind too late to qualify for a full refund. The heating case fails because the support agent refuses a refund that Twig's policy permits.

The engineers save the policy information with each case too. Otherwise, someone rerunning the heating complaint might give the support agent a different policy and end up testing a different situation.

## Change the instructions and compare the answers

Twig's engineers update the support prompt to tell the agent to apply the broken-amenity exception before the ordinary cancellation window.

They keep the visitor's request, policy, model, and evaluation criteria the same. They're trying to find out whether changing this instruction fixes the refusal.

The original prompt is their <Term name="baseline">baseline</Term>: the version they compare the updated prompt against. They can open the captured generation in PostHog's <Term name="playground">playground</Term>, a workspace for trying prompt and model changes against recorded inputs, to inspect a candidate answer.

But one better answer isn't enough. The engineers also run both saved cases through the support agent.

Send the heating complaint with the updated instructions, then inspect the answer and evaluation results:

<AioPromptComparisonFigure />

The support agent now explains that the heating qualifies for the broken-amenity exception because it can't be repaired. It offers relocation or a refund, and the policy evaluation passes.

The ordinary cancellation still passes too. The new instructions haven't made the support agent offer a refund whenever someone cancels at the last minute.

The code evaluation passes for both heating answers because both mention `"7 days"`. Sentiment remains negative because the visitor's complaint hasn't changed. The policy evaluation (LLM judge) is the one that tells Twig's engineers whether this fix worked.

## Run the evaluations before release

Twig's engineers automate both saved cases with a <Term name="test runner">test runner</Term>. It runs the requests through the support agent and its tools, evaluates the answers with the LLM judge, and reports the results to PostHog through the SDK.

They run it locally while editing the prompt, then in continuous integration (CI), the automated tests that run with each application change.

PostHog records each run as an <Term name="offline experiment">experiment</Term>. To compare the original and updated prompts fairly, the engineers keep the same:

- <Term name="dataset revision">Dataset revision</Term>, a fixed version of the saved cases.
- Model, policy, and LLM judge criteria.
- <Term name="scorer">Scorer</Term>, which defines the result's type and passing rule. Their “Policy correctness” scorer records `true` as a pass and `false` as a failure.

The runner performs the evaluation; the scorer tells PostHog how to interpret the reported result.

The cancellation case is a <Term name="regression test">regression test</Term>: it catches the heating fix breaking an answer that already worked. The engineers add more cases as new failures appear.

Errors and `N/A` results stay separate from passes. If the runner couldn't load the policy, it hasn't verified the answer.
