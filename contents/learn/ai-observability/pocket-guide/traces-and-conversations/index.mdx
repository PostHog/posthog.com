# Traces and conversations

One of Twig's AI features is an AI trip planner designed to help visitors find the perfect getaway. One day, a visitor asks for a forest getaway for four.

<AioConversationPreview />

The trip planner responds with a recommendation: Adiron-shack. But the visitor changes their mind, and decides they'd rather go to the beach. They're happy with the beach stay, but they want to make sure the rental has a kitchen.

It's a pretty average conversation with the AI trip planner, nothing really out of the norm. But Twig's engineers need to _see_ conversations like these to understand when things go wrong, or how to improve things even if they're going right.

So they instrument the AI trip planner with PostHog AI Observability (AIO) and start to piece together the stories behind AI conversations happening in their product.

## The data behind an AI answer

Just inspecting the output from a conversation with the trip planner won't tell Twig's engineers:

- Which request produced each answer
- What information the planner used to produce each answer
- Whether the planner remembers visitor's requests from one message to another

So they start with the visitor's first request: a forest stay for four. They open the request's <Term name="trace">trace</Term>, which groups all the elements of that request.

Inside the trace, a <Term name="generation">generation</Term> records the model call: its input, answer, model, cost, and timing. The visitor just sees the recommendation, but Twig's engineers can also see the catalog information the model received to give that recommendation.

Send the forest request, then inspect the information behind the recommendation:

<AioRequestFigure />

Seeing the input lets Twig's engineers check the trip planner's answer against the listing instead of relying on the answer's own claim.

## Check the model's memory

In this conversation, the visitor changed their mind and asked for a beach stay instead. In that request, they said "Actually, I'd prefer somewhere with beach access." The visitor hadn't repeated "for four", but it's likely they're still looking for a stay for four.

Twig's engineers want to know whether the trip planner remembers the visitor wanted a stay for four, across all messages in the conversation. So they inspect the next generation's input. It includes the earlier messages and the group size, with the recommendation of Flamingo's Envy, which does accommodate four.

To follow the related requests together, Twig's engineers open the visitor's <Term name="ai session">AI session</Term>: the conversation containing those requests. Each request still has its own trace inside that session.

Continue the conversation, then ask whether the beach stay has a full kitchen:

<AioConversationFigure />

For the kitchen question, the input identifies Flamingo's Envy and includes "Full kitchen" in its amenities. That connects the answer to the right listing.

## Find the cause of an incorrect answer

Now Twig's engineers have a pretty good understanding of how to understand an AI conversation that results in correct answers. But another visitor uses the trip planner, and reports a bug: they asked for a city stay for four, and were recommended Le Nid Chic, a studio that fits two.

Twig's engineers find the request in AIO and open its trace. A <Term name="span">span</Term> records an operation within a trace. They inspect the span for Twig's catalog-search function called `search_stays`.

Compare the search input with the returned listing, then inspect the same request after the engineers fix the search:

<AioSearchFixFigure />

Twig's engineers update the catalog-search code to filter by the requested guest count. They rerun the request and use the new trace to verify the change. The prompt stays the same, but now search supplies the right result. They weren't filtering by guest count.

Notice the request has `$ai_is_error: false` because the model call _completed_, even if it return the wrong answer. Twig's engineers use the recorded input and output to investigate correctness separately from call failures.

## Keep context to investigate later

The city bug shows Twig's engineers what they need to retain:

- The visitor's request for four people
- The search input that omitted the guest count
- The returned studio's capacity
- The incorrect recommendation.

Without those records, the engineers couldn't tell whether the search or the model caused the problem.

Twig's engineers choose to capture that information for trip planner requests. They configure Twig to remove names, email addresses, and booking references before sending the content to PostHog. They leave <Term name="privacy mode">Privacy mode</Term> off for these calls because it would omit the inputs and answers they need to investigate. Privacy mode prevents that content from being captured – it doesn't selectively redact personal details.

PostHog retains large AI properties, included recorded inputs and answers for [30 days](/docs/ai-observability/data-retention). Before that window expires, Twig's engineers save the city request and its catalog facts as a test case, with the expected outcome: explain that no city stay fits four people. That gives the engineers a lasting way to check whether the same bug returns.
