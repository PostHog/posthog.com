# Exceptions and issues

In an app like [Twig](https://twig.com), guests browse stays, pick their dates, book a stay, and then check the trip from their account. The engineers want to know when any part of that funnel breaks.

When something breaks, Twig's code throws an <Term name="exception" />, such as a `TypeError`. Its <Term name="stack trace" /> shows what led up to it.

To see them, the team uses Error Tracking. It captures each exception and its stack trace as a queryable PostHog event.

## Autocapture exceptions

The engineers run the Error Tracking Wizard on Twig. It installs PostHog and sets up source map uploads for Twig's bundle:

<Setup />

Then they switch on [exception autocapture](https://app.posthog.com/error_tracking/configuration#selectedSetting=error-tracking-exception-autocapture) in the project settings.

Once the SDK loads, it captures uncaught exceptions in Twig.

For example, the **Trip details** button calls `readTripHost` without a `try`/`catch`. This error is uncaught, and the SDK catches it through `window.onerror`.

Click **Trip details** to see what it records:

<AutocapturedExceptionFigure />

On each platform, autocapture catches:

- **Web:** errors that reach `window.onerror`, and unhandled promise rejections
- **Server:** exceptions the process doesn't catch
- **Mobile:** uncaught exceptions and crashes

## Exceptions are just events

Everything in PostHog is an event, including exceptions. The exception event sits alongside Twig's other PostHog events, so we can answer questions like these:

- [Which customers are impacted?](/learn/error-tracking/pocket-guide/querying-exceptions#start-from-one-hosts-errors)
- [Does it impact conversion and retention?](/learn/error-tracking/pocket-guide/querying-exceptions#check-whether-an-error-makes-guests-leave)
- [Can this error be tied to loss in revenue?](/learn/error-tracking/pocket-guide/querying-exceptions#rank-issues-by-bookings-at-risk)
- [Were they part of any feature flag or experiment rollouts?](/learn/error-tracking/pocket-guide/querying-exceptions#catch-new-errors-in-experiments)
- [What's shown on the user's page before and after the exception is thrown?](/learn/error-tracking/pocket-guide/querying-exceptions#watch-what-guests-saw)

See [Querying exceptions](/learn/error-tracking/pocket-guide/querying-exceptions).

## Manual exception capture

Autocapture misses exceptions that Twig catches itself. Catching an exception keeps the app from crashing, but something still went wrong. The engineers want to know, so they send it with `captureException`.

In **Trip details**, they catch the error and add the stay that failed:

<MultiLanguage>

```js file=Web
try {
  setHost(readTripHost(hosts, booking.stay.hostId));
} catch (error) {
  setError("Try to load details again.");
  posthog.captureException(error, {
    surface: "trip_details",
    stay_id: booking.stay.id,
  });
}
```

```js file=Node.js
try {
  host = readTripHost(hosts, stay.hostId);
} catch (error) {
  posthog.captureException(error, distinctId, {
    surface: "trip_details",
    stay_id: stay.id,
  });
}
```

```python
try:
    host = read_trip_host(hosts, stay.host_id)
except Exception as e:
    posthog.capture_exception(
        e,
        distinct_id=distinct_id,
        properties={"surface": "trip_details", "stay_id": stay.id},
    )
```

```ruby
begin
  host = read_trip_host(hosts, stay.host_id)
rescue => e
  posthog.capture_exception(e, distinct_id, { surface: "trip_details", stay_id: stay.id })
end
```

</MultiLanguage>

Some frameworks offer error boundaries as a last resort, to keep the app from visibly crashing. In these cases, capture the exception in the error boundary:

<MultiLanguage>

```tsx file=Next.js
export default function Error({ error, reset }) {
  useEffect(() => {
    posthog.captureException(error, { surface: "vacation_route" });
  }, [error]);
  // Twig shows "Something went wrong" with a Try again button
}
```

```tsx file=React
import { PostHogErrorBoundary } from "@posthog/react";

<PostHogErrorBoundary>
  <App />
</PostHogErrorBoundary>;
```

```tsx file=React&nbsp;Native
<PostHogErrorBoundary fallback={ErrorScreen} additionalProperties={{ screen: "trip_details" }}>
  <App />
</PostHogErrorBoundary>
```

```js file=Fastify
app.setErrorHandler((error, request, reply) => {
  posthog.captureException(error, undefined, {
    $request_path: request.routeOptions.url,
  });
  reply.code(500).send(error);
});
```

```python file=Flask
from posthog.integrations.flask import PosthogFlaskIntegration

PosthogFlaskIntegration(app, client=posthog, capture_exceptions=True)
```

</MultiLanguage>

## Exceptions are grouped into issues

Individual exceptions are numerous and noisy, so PostHog groups similar ones into <Term name="issue">issues</Term> <SeeFig n={1} />.

The Twig engineers work through these issues to diagnose, triage, assign, and fix them, not individual exceptions.

Every **Try again** on **Trip details** adds to the same issue.
