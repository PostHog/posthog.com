# Querying exceptions

Now that Twig's engineers capture high quality exceptions, they can query them for analysis.

Here are ways Twig's engineers use other PostHog events to understand the impact of issues in error tracking.

Each check below has a prompt to give an agent on [Learn Error Tracking with your agent](/learn/error-tracking/agent-prompts-and-mcp).

## Join exceptions to the rest of Twig's data

PostHog keeps Twig's events in one [context warehouse](/docs/self-driving/context) with persons, groups, sessions, and the tables an app can [sync](/docs/data-pipelines/sources) from other tools, like [Zendesk](/docs/data-pipelines/sources/zendesk). [HogQL](/docs/data-warehouse/sql) queries all of it together, so anything sent to PostHog can be joined to Twig's exceptions.

The engineers filter, break down, or join exceptions on these properties:

| To answer | Use | Set up |
| --- | --- | --- |
| Which error is it? | The message in `$exception_list`, or the issue in `$exception_issue_id` | The message is set automatically by every SDK. PostHog assigns the issue |
| Which page did it happen on? | `$current_url` or `$pathname` | Set automatically by the web SDK |
| Is it a crash? | `$exception_level` set to `fatal` | Set automatically for crashes by the <img src="https://res.cloudinary.com/dmukukwp6/image/upload/Android_robot_bec2fb7318.svg" alt="" className="inline-block size-4 align-text-bottom" /> [Android](/docs/error-tracking/installation/android), <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/ios.svg" alt="" className="inline-block size-4 align-text-bottom dark:invert" /> [iOS](/docs/error-tracking/installation/ios), and <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/react.svg" alt="" className="inline-block size-4 align-text-bottom" /> [React Native](/docs/error-tracking/installation/react-native) SDKs |
| Which SDK or app sent it? | `$lib` or `$app_namespace` | `$lib` is set automatically by every SDK, and `$app_namespace` by the mobile SDKs |
| Who hit it? | `distinct_id` and person properties, like email | [Identify your users](/docs/getting-started/identify-users) |
| Which host's stay was it, and what does the host pay? | `$groups` and the host's group properties | [Set up group analytics](/docs/product-analytics/group-analytics) |
| Which flag variant did they see? | `$feature/<flag-key>` | [Send flags with your events](/docs/feature-flags/adding-feature-flag-code), on the server too |
| Which session was it in, and what's in its replay? | `$session_id` | Set automatically by the web and mobile SDKs. On the server, [pass the session ID](/docs/data/sessions#server-sdks-and-sessions) |
| Which LLM trace was it in? | `$ai_trace_id` | [Link exceptions to traces](/docs/ai-observability/link-error-tracking) |
| Which part of the product threw it? | Custom properties | [Add them at capture](/docs/error-tracking/capture#customizing-exception-properties) |
| What do other tools say, like support tickets or billing? | Any property above, joined to a synced table | [Sync a source](/docs/data-pipelines/sources) |

[Issues and exceptions](/docs/error-tracking/issues-and-exceptions) lists every property PostHog sets.

## Rank issues by bookings at risk

<Callout title="Prerequisites">

- Group analytics with hosts as a group, so each exception carries the host of the stay. [Configure group analytics](/docs/product-analytics/group-analytics#set-up-group-analytics)
- An `mrr` property on each host from a warehouse connection with [Stripe](/docs/data-pipelines/sources/stripe). [Connect your payment data](/docs/data-warehouse/warehouse-properties#set-up-a-warehouse-property)

</Callout>

Hosts pay Twig a monthly fee, which the engineers sync from Stripe as each host's `mrr`. They rank issues by the MRR of the hosts they hit. An issue that hits high-MRR hosts can matter more, even with fewer occurrences <SeeFig n={1} />.

This joins exceptions to hosts on `$groups`:

| Source | What it adds |
| --- | --- |
| `$exception` | The hosts each issue hit |
| `groups` | What each host pays, from its `mrr` property |

To build a version of this, give an agent the revenue skill <SeeFig n={5} />.

The [Errors by host value](/learn/error-tracking/pocket-guide/who-it-breaks) scout runs a related check every day. It reports issues concentrated in paying hosts.

## Check whether an error makes guests leave

<Callout title="Prerequisites">

- Session tracking to see what people did after an error. The web and mobile SDKs do this automatically. [Track sessions on your server](/docs/data/sessions#server-sdks-and-sessions)

</Callout>

To see whether an error makes guests leave, the engineers check three things:

- **Funnels.** The engineers build a <Term name="funnel" /> of booking a stay on Twig, with its graph type set to [historical trends](/docs/product-analytics/funnels#graph-type), to see whether conversion fell when the error appeared <SeeFig n={2} />. They [break it down](/docs/product-analytics/funnels#breakdowns) by the issue's cohort, created from the issue page, to compare people who hit the error with people who didn't.
- **Retention.** They filter a [retention insight](/docs/product-analytics/retention) to the issue's cohort and compare it with all users. If people who hit the error come back less, the error is driving churn.
- **Session drop-off.** They check whether people did anything within a minute of each error. Some sessions end anyway, so they compare each issue with the overall drop-off.

The session drop-off check joins exceptions to the events that followed on `$session_id`:

| Source | What it adds |
| --- | --- |
| `$exception` | When the error fired |
| `$pageview` and Twig's named events, like `twig_stay_viewed` | Whether the guest kept going |

## Watch what guests saw

<Callout title="Prerequisites">

- Session replay to watch what people saw when the error happened. [Set up session replay](/docs/session-replay/installation)
- Recordings of every session with an error, so the right one exists. [Record sessions with errors](/docs/session-replay/how-to-control-which-sessions-you-record#event-triggers)

</Callout>

When an error makes guests leave, the engineers watch their sessions to see what happened.

This joins exceptions to recordings on `$session_id`:

| Source | What it adds |
| --- | --- |
| `$exception` | The error and when it fired |
| `session_replay_events` | What the person saw and did |

## Start from one host's errors

<Callout title="Prerequisites">

- Group analytics with hosts as a group. [Configure group analytics](/docs/product-analytics/group-analytics#set-up-group-analytics)

</Callout>

Triage can also start from a host. When a host reports a problem, the engineers rank every issue on that host's stays by how many guests it impacts <SeeFig n={3} />. In the issue list, that's the host as a filter, sorted by **Users**.

This joins exceptions to hosts on `$groups`:

| Source | What it adds |
| --- | --- |
| `$exception` | Each issue and how many guests it impacts |
| `groups` | Which host's stays those guests were on |

## Find the errors behind support tickets

<Callout title="Prerequisites">

- A support tool connected to PostHog, like [Zendesk](/docs/data-pipelines/sources/zendesk) or [Intercom](/docs/data-pipelines/sources/intercom). [Connect your support data](/docs/data-pipelines/sources)
- Replay links in tickets, so each ticket points to a session. [Add replay links to tickets](/docs/session-replay/sharing#method-two-automatically-share-replays-to-intercom-or-crisp)

</Callout>

Guests and hosts reach Twig's support in Zendesk, which the engineers sync to PostHog. A ticket with an error behind it points at a bug they can fix.

This joins tickets to exceptions on the session ID in each ticket's replay link:

| Source | What it adds |
| --- | --- |
| A tickets table, like `zendesk.tickets` | What the customer reported |
| `$exception` | The error behind it |

## Reach the guests an error hit

<Callout title="Prerequisites">

- Identified users, so it's clear who to contact. [Identify your users](/docs/getting-started/identify-users)

</Callout>

Once the engineers fix an issue, they tell the guests it hit, or survey them. They create a <Term name="cohort" /> from the issue page, then [duplicate it as a static cohort](/docs/data/cohorts#can-you-use-a-dynamic-cohort-as-a-feature-flag-target) to target them with a survey or flag.

This joins exceptions to people on `distinct_id`:

| Source | What it adds |
| --- | --- |
| `$exception` | The issue each person hit |
| `persons` | Who they are, so the team can reach them |

## Catch new errors in experiments

<Callout title="Prerequisites">

- Feature flags sent with events, so it's clear which variant each person saw. [Send flags with your events](/docs/feature-flags/adding-feature-flag-code)

</Callout>

When Twig ships a change as an <Term name="experiment" />, the engineers add `$exception` as a [secondary metric](/docs/experiments/metrics#primary-and-secondary-metrics) to compare errors across variants.

To see when errors started, they chart each variant's error rate <SeeFig n={4} />. With an uneven split, they compare a ratio, like exceptions per pageview, so a variant on 5% of traffic compares fairly with one on 95%. The Feature Flags pocket guide covers [running the experiment](/learn/feature-flags/pocket-guide/flag-to-experiment).

This joins exceptions to variants on `$feature/<flag-key>`:

| Source | What it adds |
| --- | --- |
| `$exception` | Errors in each variant |
| `$pageview` | Traffic in each variant, for the rate |

## Track crash-free sessions

<Callout title="Prerequisites">

- Exception autocapture, so unhandled exceptions are captured. On mobile, crash reporting in an <img src="https://res.cloudinary.com/dmukukwp6/image/upload/Android_robot_bec2fb7318.svg" alt="" className="inline-block size-4 align-text-bottom" /> [Android](/docs/error-tracking/installation/android), <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/ios.svg" alt="" className="inline-block size-4 align-text-bottom dark:invert" /> [iOS](/docs/error-tracking/installation/ios), or <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/react.svg" alt="" className="inline-block size-4 align-text-bottom" /> [React Native](/docs/error-tracking/installation/react-native) app.

</Callout>

Twig is a web app, so the engineers track stability as the share of sessions without an unhandled exception.

This joins sessions to unhandled exceptions on `$session_id`:

| Source | What it adds |
| --- | --- |
| `sessions` | Every session |
| `$exception` with `$exception_handled` set to `false` | Which sessions hit an unhandled exception |
