# Querying exceptions

Now that Twig's engineers capture high quality exceptions, they want to know which issue to fix first. The issue list ranks issues by how often they fire, but the noisiest issue isn't always the one that hurts Twig most.

An exception is an event like any other, so PostHog keeps it in the same [context warehouse](/docs/self-driving/context) as Twig's persons, hosts, sessions, and the tables they [sync](/docs/data-pipelines/sources) from other tools. The engineers answer each question by joining exceptions to that data with [HogQL](/docs/data-warehouse/sql).

## Rank issues by bookings at risk

<Callout title="Prerequisites">

- Group analytics with hosts as a group, so each exception carries the host of the stay. [Configure group analytics](/docs/product-analytics/group-analytics#set-up-group-analytics)
- An `mrr` property on each host from a warehouse connection with [Stripe](/docs/data-pipelines/sources/stripe). [Connect your payment data](/docs/data-warehouse/warehouse-properties#set-up-a-warehouse-property)

</Callout>

Hosts pay Twig a monthly fee, which the engineers sync from Stripe as each host's `mrr`. They rank issues by the MRR of the hosts they hit. An issue that hits high-MRR hosts can matter more, even with fewer occurrences <SeeFig n={1} />.

This joins exceptions to hosts on `$groups`:

| Source | What it adds |
| --- | --- |
| `$exception` | The hosts each issue hit |
| `groups` | What each host pays, from its `mrr` property |

The [Errors in paying hosts](/learn/error-tracking/pocket-guide/errors-in-paying-hosts) scout runs a related check every day. It reports issues concentrated in paying hosts.

## Check whether an error makes guests leave

<Callout title="Prerequisites">

- Session tracking to see what people did after an error. The web and mobile SDKs do this automatically. [Track sessions on your server](/docs/data/sessions#server-sdks-and-sessions)

</Callout>

To see whether an error makes guests leave, the engineers check three things:

- **Funnels.** The engineers build a <Term name="funnel" /> of booking a stay on Twig, with its graph type set to [historical trends](/docs/product-analytics/funnels#graph-type), to see whether conversion fell when the error appeared <SeeFig n={2} />. They [break it down](/docs/product-analytics/funnels#breakdowns) by the issue's cohort, created from the issue page, to compare people who hit the error with people who didn't.
- **Retention.** They filter a [retention insight](/docs/product-analytics/retention) to the issue's cohort and compare it with all users. If people who hit the error come back less, the error is driving churn.
- **Session drop-off.** They check whether people did anything within a minute of each error. Some sessions end anyway, so they compare each issue with the overall drop-off.

The session drop-off check joins exceptions to the events that followed on `$session_id`:

| Source | What it adds |
| --- | --- |
| `$exception` | When the error fired |
| `$pageview` and Twig's named events, like `twig_stay_viewed` | Whether the guest kept going |

## Watch what guests saw

<Callout title="Prerequisites">

- Session replay to watch what people saw when the error happened. [Set up session replay](/docs/session-replay/installation)
- Recordings of every session with an error, so the right one exists. [Record sessions with errors](/docs/session-replay/how-to-control-which-sessions-you-record#event-triggers)

</Callout>

When an error makes guests leave, the engineers watch their sessions to see what happened.

This joins exceptions to recordings on `$session_id`:

| Source | What it adds |
| --- | --- |
| `$exception` | The error and when it fired |
| `session_replay_events` | What the person saw and did |

## Start from one host's errors

<Callout title="Prerequisites">

- Group analytics with hosts as a group. [Configure group analytics](/docs/product-analytics/group-analytics#set-up-group-analytics)

</Callout>

Triage can also start from a host. When a host reports a problem, the engineers rank every issue on that host's stays by how many guests it impacts <SeeFig n={3} />. In the issue list, that's the host as a filter, sorted by **Users**.

This joins exceptions to hosts on `$groups`:

| Source | What it adds |
| --- | --- |
| `$exception` | Each issue and how many guests it impacts |
| `groups` | Which host's stays those guests were on |

## More questions to ask

The same joins answer more questions. The engineers also find the errors behind support tickets, contact the guests an error hit, catch new errors in experiments, and track crash-free sessions. Each one has a prompt on [Learn Error Tracking with your agent](/learn/error-tracking/agent-prompts-and-mcp), and [Issues and exceptions](/docs/error-tracking/issues-and-exceptions) lists every property you can join on.
