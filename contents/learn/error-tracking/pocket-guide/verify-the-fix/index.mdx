# Check whether the fix held

The Inbox validation scout checks each fix once it has reached guests, and reports the fixes that didn't hold. It waits and compares rates first, because some browsers keep running the old code for a while.

## What the scout looks at

Yesterday at `10:30` the engineers merged a fix for the Trip details `TypeError`. Today the issue still fires at about the rate it did before the merge, so the scout reports it <SeeFig n={1} />. When the rate fell hard and keeps falling, the fix is still rolling out, and the scout checks again later.

## The report in your inbox

A fix that didn't hold becomes a new <Term name="report" /> in the team's <Term name="inbox" />, linked to the original so the team can see what was already tried <SeeFig n={2} />.

## The scout itself

PostHog maintains this scout, listed as **Inbox validation** in the project's scouts. Its [skill file](https://github.com/PostHog/posthog/blob/master/products/signals/skills/signals-scout-inbox-validation/SKILL.md) is on GitHub. It waits 24 hours after the merge for a server fix, and 72 hours or more for web and mobile. Then it compares the issue's exceptions and affected users with the same window before the merge. It also checks Twig's overall traffic, so a quiet weekend doesn't pass for a fix. For a fix no report links to, the [PR follow-up](/learn/error-tracking/pocket-guide/deploy-regressions) scout runs the same check. It runs every 24 hours by default and stays quiet unless something needs the team's attention.

## Add this to your scout troop

PostHog ships this scout turned on, and the engineers can turn it off for each project. It checks a fix once exceptions reach PostHog and the fix's report resolves, either when its linked pull request merges or when the engineers resolve it themselves.
