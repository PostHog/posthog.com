# Reduce noise

Twig's issue list also fills up with exceptions the engineers will never fix, like errors from browser extensions.

The engineers can drop noisy exceptions in Twig or at ingestion. PostHog doesn't store or bill dropped exceptions, and they can't be recovered.

| Protection | Use it for |
| --- | --- |
| [Filters in the app](#filters-in-the-app) | Dropping exceptions the team never wants, and redacting data that must not leave the app |
| [Burst protection](#burst-protection) | Stopping one client stuck in a loop from flooding the project |
| [Suppression rules](#suppression-rules) | Dropping noise the team will never fix, like errors from browser extensions |
| [Rate limits](#rate-limits) | Capping volume during an outage, for the whole project or for one issue |

## Filters in the app

The `before_send` hook runs in Twig before the SDK sends anything. It returns `null` to drop an exception, or edits its properties to redact sensitive data. Nothing dropped here reaches PostHog, so it's the cheapest place to filter.

```js
posthog.init('<ph_project_token>', {
    before_send: (event) => {
        const exception = event.properties.$exception_list?.[0]
        if (exception?.value?.includes('ResizeObserver loop')) {
            return null
        }
        return event
    },
})
```

## Burst protection

The <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/js.svg" alt="" className="inline-block size-4 align-text-bottom" /> [web](/docs/libraries/js) and <img src="https://res.cloudinary.com/dmukukwp6/image/upload/posthog.com/contents/images/docs/integrate/nodejs.svg" alt="" className="inline-block size-4 align-text-bottom" /> [Node.js](/docs/libraries/node) SDKs cap how many autocaptured exceptions of one type a client sends: 10, then 1 every 10 seconds. It's on by default, so a loop in one browser can't flood Twig's project. Raise the limits if an app throws in legitimate bursts.

Burst protection only runs in those two SDKs, and only in the client. To cap volume from every SDK, use [rate limits](#rate-limits), which PostHog applies at ingestion.

## Suppression rules

A suppression rule drops future exceptions that match its filters, like the exception type or message <SeeFig n={1} />. It fits noise the team can describe, like errors from browser extensions or third-party scripts. The engineers add rules in [Error Tracking settings](https://app.posthog.com/error_tracking/configuration#selectedSetting=error-tracking-suppression-rules). PostHog applies them at ingestion, and some SDKs apply them in the app too.

The engineers can also suppress a single issue, which drops every future exception in it. Each issue has one of three statuses:

- **Active** is the default. The issue needs attention.
- **Resolved** means it's fixed. PostHog keeps the data and reopens the issue if the error comes back.
- **Suppressed** means the team won't fix it. PostHog drops its future exceptions. Exceptions it already stored stay.

The engineers leave a bug they plan to fix active, and assign it.

## Rate limits

Rate limits cap how many exceptions PostHog ingests in a window of 15 minutes, 30 minutes, or an hour. A project-wide limit caps the project's total volume. A per-issue limit gives each issue its own cap, so one noisy issue during an outage can't drown out the rest.

Bypass rules let critical exceptions skip both limits. PostHog still bills the exceptions they let through.
