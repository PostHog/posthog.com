# Triage and alerts

Once the engineers know which issues matter most, each one needs an owner.

## Assignment rules

Assignment rules route each new issue to the team that owns it. A rule matches on the exception's properties and assigns the issue to a role or a teammate <SeeFig n={1} />. To assign issues to a team, the engineers create a role for it in the organization settings.

Rules run at ingestion, after <Term name="source map">source maps</Term> are applied, so they match Twig's unminified <Term name="stack trace" />. For example, the engineers set a rule on the source file that sends issues from `src/trips/` to the Trips role. The first match wins, so they put specific rules first.

To track the fix in another tool, the engineers [connect](/docs/error-tracking/integrations) GitHub, GitLab, Linear, or Jira, and create the issue from the PostHog issue page. It links back to the PostHog issue, with every exception and the people the issue impacts, and they can add the impact before they create it <SeeFig n={2} />.

PostHog AI can group Twig's recent exceptions by source file and URL path, and suggest a rule for each group.

## Alerts

Each alert fires on one of three triggers:

- **Issue created** fires once for every new issue, which can mean many messages a day.
- **Issue reopened** fires when an issue the engineers resolved comes back. Use it to catch regressions.
- **Issue spiking** fires when an issue suddenly gets far more exceptions than usual. Spike detection compares each 5-minute window with the issue's baseline from the past hour, and ignores windows below a minimum count <SeeFig n={3} />.

Each alert pairs one trigger with one destination, like a [Slack](/docs/data-pipelines/destinations/slack) channel or a [webhook](/docs/data-pipelines/destinations/webhook), so to catch both regressions and spikes, the engineers set up two alerts.

The engineers add both in [alerting settings](https://app.posthog.com/error_tracking/configuration#selectedSetting=error-tracking-alerting).
