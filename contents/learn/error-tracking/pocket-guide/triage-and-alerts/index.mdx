# Triage and alerts

Every week at stand-up, Twig's engineers go through the new issues together. At first it takes 5 minutes. As Twig grows, it takes 10, then 20, and eventually the whole meeting. Most of that time goes to the same questions every week: who owns this issue, and does it need attention now?

So the engineers look for ways to send each issue to the people who own it, and to only interrupt someone when an issue needs them.

## Route issues to their owners with assignment rules

Most issues belong to one team. The Trips team owns everything under `src/trips/`, including **Trip details**. Instead of assigning those issues by hand at stand-up, the engineers add an assignment rule that sends issues from `src/trips/` to the Trips team <SeeFig n={1} />.

Rules run at ingestion, after <Term name="source map">source maps</Term> are applied, so they match Twig's unminified <Term name="stack trace" />. The first rule that matches assigns the issue, so specific rules go first.

## Track fixes in GitHub

Stand-up also used to copy issues into GitHub, where the Trips team plans its work. Now the engineers create the GitHub issue from the issue page. It links back to PostHog, with every exception and the guests the issue impacts <SeeFig n={2} />. The [GitLab, Linear, and Jira integrations](/docs/error-tracking/integrations) work the same way.

## Get alerted when an issue spikes

Some issues can't wait for the next stand-up. When **Trip details** breaks for hundreds of guests, the Trips team wants to know right away, without a message for every new issue.

PostHog alerts on three triggers:

- **Issue created** fires for every new issue, which can mean many messages a day.
- **Issue reopened** fires when a resolved issue comes back, which catches regressions.
- **Issue spiking** fires when an issue gets far more exceptions than usual. PostHog compares each 5-minute window with the issue's baseline from the past hour <SeeFig n={3} />.

The engineers only alert on spiking issues. New issues already go to the team that owns them, which grooms them, so an alert for each one would only add noise. Spike alerts go to the Trips team's Slack channel.

When the spike alert fires, someone on the Trips team opens the issue and watches a recording of a guest who hit it. If it's a real bug, they fix it and link the GitHub issue. If it's noise, they suppress it.

Stand-up takes 5 minutes again.

To set up the same for your app, create a role for each team in your organization settings, then add assignment rules and alerts in [Error Tracking settings](https://app.posthog.com/error_tracking/configuration#selectedSetting=error-tracking-alerting).
