# Connect a deploy to an error burst

This creates a <Term name="scout" />, which is a scheduled agent that queries your PostHog events and files a <Term name="report" /> in your <Term name="inbox" /> when it finds something.

This one, PR follow-up, ties a new <Term name="issue" /> after a deploy to the pull request that likely caused it. A deploy often carries several pull requests, so doing this by hand means reading each one against the <Term name="stack trace" />.

## What the scout looks at

Release 1.5.0 went out at 09:10 with five pull requests. Six minutes later, a new `TypeError` started firing on checkout <SeeFig n={1} />. Its stack frames are in a file one of those pull requests changed, so the scout reports it against that pull request. A new issue with no frames in changed files goes to the [spikes and stuck loops](/learn/error-tracking/pocket-guide/errors-as-signals) scout instead.

An older issue counts too if it reopens or fires at a clearly higher rate after the deploy.

## The report in your inbox

The <Term name="report" /> names the pull request, its author, merge time, and deploy time, compares the error before and after, and recommends fixing the code or rolling back <SeeFig n={2} />. Click **Ask AI** on the report to ask who else is affected, whether the problem is new, or what to do next. See [reports](/docs/self-driving/reports#ask-ai-about-a-report).

## The scout itself

PostHog maintains this scout, and you can read [its skill file on GitHub](https://github.com/PostHog/posthog/blob/master/products/signals/skills/signals-scout-pr-follow-up/SKILL.md). It waits for each merged pull request to deploy. Then it matches the stack frames of issues that started in the deploy window against the files the pull request changed. It reads deploy times from GitHub deployments, GitHub releases, or deploy annotations. Without one, it estimates 24 hours after the merge for server code, and 72 hours or more for web and mobile.

## The schedule it runs on

The scout runs on the schedule you set in its **Settings**, but stays quiet unless something needs your attention. Each run judges about eight pull requests.

## Add this to your scout troop

PostHog ships this scout, and you can turn it on or off for each project. It uses:

- **Required:** GitHub connected to PostHog, so the scout can see merged pull requests and the files they changed. See [GitHub](/docs/libraries/github).
- **Recommended:** a deploy signal, like GitHub deployments synced through the [GitHub source](/docs/data-pipelines/sources/github). Without one, the scout estimates deploy times.
- **Recommended:** <Term name="source map">source maps</Term> for bundled code, so stack frames name your files. See [Make stack traces readable](/learn/error-tracking/pocket-guide/stack-traces).
