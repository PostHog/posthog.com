# Connect a deploy to an error burst

A deploy often carries several merged pull requests. When a new <Term name="issue" /> appears minutes later, its first-seen time points at the deploy, and its <Term name="stack trace" /> points at the files that threw. Tying the two together means reading each pull request in the deploy against the stack trace, often after the authors have moved on to other work.

This scout follows up on each merged pull request once it's live and reports a new error whose stack frames are in files that pull request changed.

## What the scout looks at

Release 1.4.2 went out at 09:10 with five merged pull requests. Six minutes later, a `TypeError` that PostHog had never seen started firing on checkout. One of the five could have caused it, or something unrelated could have broken at the same time. Which is it?

- If none of the new issue's stack frames are in a file the deploy changed, the scout stays _quiet_ and leaves the issue to the [error tracking scout](/learn/error-tracking/pocket-guide/errors-as-signals).
- If the issue was first seen after the deploy and its stack frames are in files one of the five changed, it's a side effect of that pull request. The scout _**reports**_.

In <SeeFig n={1} />, checkout exceptions climb after the deploy while sessions hold steady.

A merged pull request isn't live until it deploys, so the scout waits for the deploy. It reads the deploy time from GitHub deployments, GitHub releases, or a deploy annotation that names the commit. Without any of those, it assumes server code is live 24 hours after the merge and web or mobile code 72 hours or more after it. A report built on that assumption says the deploy time is an estimate.

The deploy window runs from that deploy to the next one. An error that starts after a later deploy belongs to the pull requests in that later deploy. An older issue with frames in a file the pull request changed counts too, if it reopens or fires at a clearly higher rate than before the merge.

When one deploy carries several pull requests, including dependency bumps from bots, the scout names the pull request whose files match the stack trace. When more than one matches, it names the whole deploy in one report.

## The report in your inbox

When the scout ties a new error to a pull request, it files a <Term name="report" /> in your <Term name="inbox" />, and <SeeFig n={2} /> breaks the card down part by part. Click **Review** to open the full report.

The report leads with the pull request's number, title, author, merge time, and deploy time. It then compares the error before the merge and after the deploy, over windows of the same length, and recommends a next step, such as fixing the code or rolling the pull request back. It suggests the pull request's author as the reviewer.

A side effect that hits users in volume is P2, and a smaller one is P3. It's P1 only when the error tracking scout would rate the same error P1 and it's still firing. If your inbox already has an open report on the same issue, such as one from the error tracking scout, PR follow-up adds the pull request to that report as evidence instead of filing a second one.

## The pull request you merge

When the stack trace ties the error to one pull request's files, the scout marks the report actionable. PostHog then dispatches an agent to write the fix, with the report and its evidence attached as context. You review and merge it like any other pull request.

If the change shipped behind a <Term name="feature flag" />, switching the flag off stops the errors while the fix is written. [The off switch](/learn/feature-flags/pocket-guide/off-switch) in the Feature Flags pocket guide covers how fast that takes effect.

Once the fix merges and deploys, PR follow-up checks it like any other merged pull request. Merging the fix also resolves the report, and the inbox validation scout then checks whether the error stopped. [Check whether the fix held](/learn/error-tracking/pocket-guide/fix-while-you-sleep) covers that scout.

Reports are free. Pull requests are **$15 each**, with your first three a month **free**. See self-driving [Pricing](/docs/self-driving/pricing).

## The scout itself

A <Term name="scout" /> is a set of instructions an agent follows on a schedule. PR follow-up is one of the canonical scouts PostHog ships, and you can read [its skill file on GitHub](https://github.com/PostHog/posthog/blob/master/products/signals/skills/signals-scout-pr-follow-up/SKILL.md). The [Self-driving pocket guide](/docs/self-driving/pocket-guide/101) explains how scouts work.

It checks whether each merged pull request did what it claimed and whether it broke anything else, such as starting a new error in the files it changed.

Each run reads:

- **Your merged pull requests**, from GitHub connected to PostHog or synced into your data warehouse next to your product data. It reads each one's title, description, and the files it changed.
- **Your deploys**, from GitHub deployments, GitHub releases, or deploy annotations, to find when each merge went live.
- **Error Tracking**, for issues that first appeared or reopened in the deploy window, and the files their stack frames name.
- **The rest of what the pull request touched**, such as the error rate and latency of the service it changed, the volume of the logs it writes, web vitals on the page it renders, and any alerts on them that fired in the deploy window.

## The schedule it runs on

You choose how often PR follow-up runs, from every 30 minutes to every 30 days, or at set times with a cron expression. See [setting a scout's schedule](/docs/self-driving/scouts#setting-a-scouts-schedule).

Each run judges about eight pull requests, starting with the ones earlier runs held back. The scout keeps a verdict on each pull request in its memory, so later runs skip the ones it has already settled. Most pull requests do what they claim, so most runs end without a report.

## Add this to your scout troop

PostHog ships this scout, and you can turn it on or off for each project. It has one requirement and two recommendations:

- **Required:** GitHub connected to PostHog, so the scout can list merged pull requests and the files they changed. See [GitHub](/docs/libraries/github).
- **Recommended:** a deploy signal, such as GitHub deployments synced through the [GitHub source](/docs/cdp/sources/github), GitHub releases, or deploy annotations that name the commit. Without one, the scout estimates when each merge went live.
- **Recommended:** <Term name="source map">source maps</Term> for bundled code, so stack frames name files in your repository. See [Make stack traces readable](/learn/error-tracking/pocket-guide/stack-traces).
