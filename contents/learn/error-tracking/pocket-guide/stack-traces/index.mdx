## Source map uploads

To get full stack traces, the engineers need to upload a <Term name="source map" /> to map minified code to source code <SeeFig n={2} />. PostHog can get the maps three ways:

| Option | Trade-off |
| --- | --- |
| Upload in CI | The default. The source stays private, and each build uploads its own maps. |
| Host them publicly | No upload step, but anyone can read the source. |
| Embed them in the bundle | No upload, but users download larger files and can read the source. |

The engineers link each upload to a [release](/docs/error-tracking/releases). PostHog then shows the version and commit on every trace. With a [GitHub or GitLab integration](/docs/error-tracking/integrations), it also links each frame to the file and line in `twig/web`.

The Wizard's Error Tracking setup already adds uploads where the platform needs them. To add them to an existing setup:

<Setup subcommand="upload-source-maps" />

After uploading, the engineers check the [symbol sets](https://app.posthog.com/error_tracking/configuration#selectedSetting=error-tracking-symbol-sets) in PostHog, which show any failed uploads or missing bundles.

## Breadcrumbs

Breadcrumbs, which PostHog calls exception steps, hold context that only matters if something breaks. The engineers call `addExceptionStep` at checkpoints like a retry or a fallback path. The SDK attaches the steps to the next exception, and they show up in the issue's **Timeline** tab <SeeFig n={3} />.

If no exception happens, the SDK discards the steps, so successful runs cost nothing.

The engineers pick where context goes by when they'll need it:

| Record it as | When |
| --- | --- |
| An exception step | It only matters if this run fails |
| A log | The team wants it kept for every run, failed or not |
| A property on the exception | The team wants to filter, group, assign, or count issues by it |
| An event | The team wants to count the action on its own |
