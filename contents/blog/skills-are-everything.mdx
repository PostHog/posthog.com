When agent skills first came out, I thought they were silly. We are just casting magic spells now are we? Is that where we are?

But over time, I bought into the whole "context engineering" thing (as much as I fought the hype initially) and started using them more. Today, almost every interaction I have with an agent on any surface loads at least one skill from the [PostHog skills store](/docs/skills).

No really, my agent looked it up. Over the last 28 days, 78% of my 578 chats loaded a skill and 47% updated one (shoutout [AI observability](/docs/ai-observability/installation/claude-code) for making this easy as all my Claude Code sessions go there). 

I have about 139 skills in the store. About 100 of them are custom [scouts](/docs/self-driving/scouts), which are skills that run themselves on a schedule. The other 39 are for how I actually work, and those are what this post is about.

*Jake gets it.*

So this post is my attempt to explain what changed my mind, and to show you the actual skills I use every day to keep the charade going. 

Not in a cringe "try my skill bro" sort of way. There is a little cottage industry in this at the moment which i find a bit confusing (even if they do actually work sometimes). I'm not "taking a dependency" on your skill bro, skills can become technical (agent?) debt so we should set the bar very high when considering adopting them.

I'm much more evangelical about various _ways_ to use skills so that you can be as lazy as possible and make your agents fun to work with and get stuff done.

## Skills are magic context bombs

Most people think of skills as better prompts. Something that teaches the agent a trick. They aren't.

You should think of skills as **little portable agentic memory systems**. They are the perfect abstraction for tagging a bundle of context, so an agent (or I) can pull that context in exactly when it's needed and nowhere else. 

The body is typically a thin index. The bundled files hold the detail. The agent reads them and pulls only the files the current task touches. That's [progressive disclosure](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#progressive-disclosure-patterns), and it's mostly the point.

We shouldn't need magical skills to make AI better, and I think that whole category will go away soon. Models will just be good and just "get it" much more while of course using memory and tools to just get what they need.

A lot of the time skills are used to provide the agent with instructions, but this will likely go away as models get better. They will just use their built in memory and tools to get what they need.

What won't go away is the need to **manage context**. This means telling agents what's true right now, what happened last session, what's in-flight, and what bit us before. That's the part I'm skills-pilled on and part that's changed my work the most. Here's some examples. 


(p.s. im not even sorry if this reads like an infomercial for the [PostHog skills store](/docs/skills) if you use PostHog and have the MCP you really should just try it for the skills you want all your agents to have access to)

## 1. Skills as a project tracker

Every meaningful piece of work I do is documented and maintained by my agents in one of two skills: `self-driving-work` and `scouts-work` (these are the two things i work most on at PostHog). 

They're siblings with identical conventions: a numbered `issues/` backlog with an index, an `ideas/` folder, `open-prs.md`, a rolling 14-day `CHANGELOG.md`, `environment-notes.md` for durable gotchas, and a `HANDOVER.md` that each session overwrites its own section of.

At the time I'm writing this, the `self-driving-work` skill is on version 433 with 126 bundled files, including 55 numbered issues, 17 ideas, and 39 pain points. I didn't write most of those. My agents did, at the end of sessions, because the skill tells them to.

```
self-driving-work         v433, 126 bundled files
├── SKILL.md              the thin index
├── HANDOVER.md           one section per thread of work
├── CHANGELOG.md          rolling 14-day window
├── environment-notes.md  durable gotchas
├── open-prs.md
├── roadmap.md
├── dogfooding.md
├── field-feedback.md
├── issues/               55 issues + index
│   ├── 01-reviewer-suggestion-regression.md
│   ├── 02-crowd-fallback-provenance.md
│   └── ...
├── ideas/                17 ideas + index
│   ├── 01-rank-by-author-association.md
│   └── ...
├── pain-points/          39 bad examples + index
├── feedback/             3 + index
└── scripts/
    └── task_summary_sampler.py
```


The loop looks like this:

- I start a session on any surface (local Claude Code, a cloud task, Slack, PostHog AI, Codex) and say "let's check in on /phs self-driving work".
- The agent uses my local `/phs` [bridge skill](/docs/skills#step-3-set-up-a-bridge-skill-optional-shortcut), loads the remote skill, reads `HANDOVER.md`, scans the backlog index, and knows where we left off. We do the work in the repo and the product, not in the skill.
- At the end of the session, the agent logs any new issue or idea, records any PR that opened or merged, adds one changelog line, and overwrites its handover section.

This is the lowest friction and most chill way I have ever found to deliver complex features over long horizons. The skill is the memory, and it's memory I get my agents to intentionally control and maintain.

I don't rely on a model's hidden memory feature that I can't read. The skill in PostHog shows exactly what my agents think is true. If it gets messy, I tell the agent to clean up, or better yet, it knows to follow certain protocols like trimming the changelog after 14 days (all skill edits are version tracked so it's recoverable if I need it).

I liked this pattern enough that I turned it into a template. [`project-template`](https://github.com/PostHog/community-skills/tree/main/skills/project-template) is in the [community skills store](/docs/skills/community). Install it once per area of work, bind the project name and the changelog window, and you have a living hub that any agent on your team can read and write.


My favorite part of the template is a small table the agent has to consult before writing anything down:

| Still true in 30 days? | Has an owner who refreshes it? | Goes in                                   |
| ---------------------- | ------------------------------ | ----------------------------------------- |
| Yes                    | Yes, a tracked work item       | `issues/NN` or `ideas/NN`                 |
| Yes                    | No, durable reference          | `environment-notes.md` or a `references/` file |
| No, but in flight now  | You, this session              | your `HANDOVER.md` section                |
| No, it just happened   | Nobody                         | `CHANGELOG.md`, one line                  |

The most common failure of the skill is durable detail written into the changelog, because the changelog is the file the agent was already editing. That table exists because I watched it happen many times.

You don't need all this structure on day one, though. For a new, messy project, just start a skill and tell your agent to keep its context there. Don't worry much about the layout. Agents do something sensible on their own, and in my experience, skills only starts to get messy at around version 50. The important part is that the context is in a skill you can see, version, and load from anywhere.

Eleven skills, written by several people on the team. A new teammate, or a fresh agent session, can read that list and know where everything lives.

## 3. Skills as a runbook that learns

The alerts skill in section 2 records what exists. A runbook records what went wrong and how we fixed it, so it gets better every time something breaks.

`self-driving-debugging` is our runbook for when self-driving misbehaves in production and users have some issues we need to dig into.

The whole thing hangs off one line in the skill body: **add or extend a reference every time we run down a new class of issue.** When a support ticket turns into a real investigation, the agent writes what it found as a dated file in `investigations/`, then extends the matching reference so the next agent doesn't start from zero. Seven investigations in, it covers duplicate reports, competing PRs for one fix, oversold report titles, unaddressed review comments, and a data import source that emitted nothing.

Its sibling, `scouts-debugging`, does the same job for the scout fleet. Between them, "debug self-driving for team N" is a sentence I can say to an agent on any surface and get a real answer.

## 4. Skills as a daily driver

The `andy-inbox` skill is how I start most days. It pulls every report in the [self-driving inbox](/docs/self-driving/inbox) where I'm a suggested reviewer, maps each one to its GitHub PR and issues, and renders one plain line per report: priority, age, review state, CI, and one next action.

```
In flight with a PR, newest report first

#  Next               Report                                        PR       Signals
1  ENQUEUE (YOUR GO)  fix(signals): give the revenue scout a supp…  #108959  stamp✓ CI✓
2  FIX CI             fix(mcp): paginate large GitHub repository…   #108947  stamp✓ CI2✗
3  ENQUEUE (YOUR GO)  fix(mcp): document the usable --json flag p…  #108934  stamp✓ CI✓
4  ENQUEUE (YOUR GO)  fix(hogql): system schema discovery relapse…  #108866  stamp✓ CI✓
5  FIX CI             fix(inbox): show why follow-up checks failed…  #108829  stamp? CI2✗
6  ENQUEUE (YOUR GO)  fix(mcp): bound health-issues-list payloads…  #108798  stamp✓ CI✓
7  FIX CI             fix(mcp): make execute-sql join errors iden…  #108284  stamp✓ CI2✗
```


The skill bundles Python scripts to do the boring parts: `render_table.py` builds the table from the API and `gh`, `pr_candidates.py` ranks reports that are ready for a Create PR press, `merge_intent.py` finds PRs I've approved that need agent work to get merged, and `draft_task.py` writes the payload to launch a PostHog [task](/docs/posthog-desktop/tasks) for a stalled row. So "get these three PRs green on CI" turns into three async tasks I can check on later.

It also has a `working-set.md` that records only what I've personally chosen to own, with four rules to guide it:

1. **Live first, memory second.**
2. The API is the truth.
3. The file is a list of my commitments.
4. Never report status from the file alone.

There's a whole family of daily driver skills like these:

- `my-github` is what needs my attention across GitHub: open PRs, review requests, assigned issues, recent merges.
- `andy-prs` is every PR I opened, with its size, the issues it closes, the inbox report it came from, and its checks.
- `andy-issues` is every issue I filed, mapped to the inbox report that picked it up and the PR that came out of it, so I can see which of my specs turned into code.
- `andy-approvals` is the bot-authored PRs I approved or sent `/trunk merge` on, and whether the bot has pushed since, because approving an agent's PR and then losing track of it is a real failure mode.

A scout called `signals-scout-andy-github` runs the GitHub one every hour and keeps a single living report current in my inbox, so most mornings the answer is already waiting for me. A generic version, [`my-inbox`](https://github.com/PostHog/community-skills/tree/main/skills/my-inbox), is in the community store.

## 6. Skills that run themselves

Every [scout](/docs/self-driving/scouts) in PostHog [is a skill](/docs/self-driving/whats-in-a-scout). Same format, same store, same version history. The only difference is a schedule and a harness that runs it. Which means when I've built a skill for how I do a job, turning it into a job that does itself is a small step, not a new project.

`signals-scout-agent-feedback` watches what agents complain about in our MCP, `signals-scout-self-driving-logs` watches our production logs, and `signals-scout-canonical-drift` checks the canonical scout fleet against the current harness once a week for any drift and inconsistencies as code evolves.

A few are about skills themselves. `signals-scout-skills-best-practices` checks recently-changed skills in our repo against the [Agent Skills spec](https://agentskills.io/specification). `signals-scout-skills-maintenance` catches merged PRs that make an in-repo skill stale. Both lean on `skills-best-practices`, which gets its own section below.

Yes, I have skills that maintain skills. I did warn you.

## 7. Skills as a place to think

I even used a skill to write this blog. The `andy-blogs` skill has one file per post with the argument, sources, a dated log of every decision, a list of what I cut for being too sensitive, and the open TODOs. 

When I start a new session on the post, the agent already knows which branch the draft is on, which numbers it still has to re-check, and which Slack screenshot I already rejected (it was about scouts, not skills). It's well past 20 versions by now, and this paragraph is in its changelog. It helps with all the annoying stuff about writing blog posts like adding the screenshots. And I also use it to tell the agent how I write blog posts: I need to fire up VSCode to eyeball every diff before we commit as agents are to eager to try add stuff I don't want in the final post.

This isn't just a set of instructions. The skill is a document I'm iterating on with an agent, over weeks, across surfaces. A skill turned out to be a better home for that than a Google Doc, because the agent can read it, edit it with the smallest possible change, and every edit is a version I can diff.

## Why the store, and not a folder of Markdown files

You could do all of this with a local `.claude|agents/skills/` folder but that's just crazy. Vibing your own plumbing and CI to get your skills to every agent is also totally possible but crazy. Using a skill store gives you benefits like:

- **It's on every surface.** The same skill loads in Claude Code on my laptop, in a cloud task, in Slack, in Codex, in Cursor, and in PostHog AI.
- **Agents can write to it.** The `skill-update` tool takes incremental `edits` and `file_edits` with a `base_version` check, so two sessions can maintain the same skill without clobbering each other.
- **It's versioned.** 433 versions of `self-driving-work` means 433 diffs I can read when something looks off. A file on disk gives me one, unless I remember to commit it.
- **It's shared.** A teammate, or their agent, or a scout, reads the same thing I do.
- **Progressive disclosure is built in.** `skill-list` returns names and descriptions. `skill-get` returns the body and a file manifest. `skill-file-get` pulls one file.

## The skill that stops skills slop

There's a catch with all of this. Leave an agent to maintain a skill and it will grow it: a paragraph every session, a changelog line for every fix, until loading the skill costs more than it saves. A mono-skill of slop.

So I wrote `skills-best-practices`. I tell the agent to use it to clean up if needed and also, when I'm making a new project tracker type skill, I tell the agent to follow it. It's in the [community store](https://github.com/PostHog/community-skills/tree/main/skills/skills-best-practices) if you want it. The short version:

1. **Give every skill a convention.** Tell the agent exactly where an issue, a handover, or an investigation goes. If you don't, it makes something up, and it's different every time.
2. **Keep the body small.** About one screen: what this is, the gotchas, and a map of the files. Detail goes in the files.
3. **Stop things growing forever.** The changelog keeps 14 days. The handover gets overwritten, not appended to.
4. **Link, don't copy.** One skill per area, with links to its siblings.
5. **Dogfood them.** Use the skill for its actual job, notice where the agent stumbled, and fix the skill in the same session.

## Try it

- Read the [skills docs](/docs/skills) and connect the [PostHog MCP](/docs/model-context-protocol) to whatever agent you use.
- Then just ask your agent about the PostHog skills store. With the [PostHog AI plugin](https://github.com/PostHog/ai-plugin) installed, it already has the [`skills-store`](https://github.com/PostHog/ai-plugin/tree/main/skills/skills-store) skill and knows how to list, load, and edit your skills.
- Install [`project-template`](https://github.com/PostHog/community-skills/tree/main/skills/project-template) from the [community store](/docs/skills/community) for one area of work you're tired of re-explaining to your agent.
- Install [`skills-best-practices`](https://github.com/PostHog/community-skills/tree/main/skills/skills-best-practices) next to it, and tell your agent to load it before it creates or edits any skill.
- When you have a skill for how you do a job, [turn it into a scout](/docs/self-driving/scouts) and let it do the job for you.

And if you build a skill for something in your life that has no business being a skill, tell me. I have a hedgehog joke scout. I'm not going to judge.
