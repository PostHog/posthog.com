When agent skills first came out, I thought they were silly. We are just casting magic spells now are we? Is that where we are?

But over time I bought into the whole "context engineering" thing (as much as I fought the hype initially) and started to use them more, and now I'm convinced they will change your life!

Here is a blog about all the reasons and ways I use and love skills and how they have changed my life. I hope it changes yours too.

Today, almost every single chat I have with an agent, on any surface, loads at least one skill from the [PostHog skills store](/docs/skills). I own 139 skills in our internal project as I write this. 

About 100 of them are [scouts](/docs/self-driving/scouts), which are skills that run themselves on a schedule. 

The other 35 or so are skills I built for how I actually work, and those are the ones this post is about.

So this post is my attempt to explain what changed my mind, and to show you the actual skills I lean on every day. 

Not in a cringe "hey try my skill bro" sort of way. 

All of that is a bit cringe, and I promise the skills I'm about to show you are not magic prompts that make the model smarter. 

I'm much more evangelical about various _ways_ to use skills so that you can be as lazy as possible and make your agents a joy to work with.

## Skills are magic context bombs

Most people think of skills as better prompts. Something that teaches the agent a trick.

You shouldn't think of skills as tricks. They're **little portable agentic memory systems**. A skill is the perfect abstraction for tagging a bundle of context, so an agent (or I) can pull that context in exactly when it's needed and nowhere else. 

The body is typically a thin index. The bundled files hold the detail. The agent reads them and pulls only the files the current task touches. That's [progressive disclosure](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#progressive-disclosure-patterns) (another buzz phrase), and it's mostly the whole point.

We shouldn't need magical skills to make AI better, and I think that whole category will go away soon. Models will just be good and just "get it" much more while of course using memory and tools to just get what they need.

What won't go away is the need to manage **context**: what's true right now, what happened last session, what's in flight, what bit us before. That's the part I'm skills-pilled on. Eventually the models will probably just learn all this too, but that's a bit further out would be my guess.

Here's how I use the skills store, roughly in order of how much it changed my day.

## 1. Skills as a project tracker

Every meaningful piece of work I do is documented and maintained by my agents in one of two skills: `self-driving-work` and `scouts-work`. They're siblings with identical conventions: a numbered `issues/` backlog with an index, an `ideas/` folder, `open-prs.md`, a rolling 14-day `CHANGELOG.md`, `environment-notes.md` for durable gotchas, and a `HANDOVER.md` that each session overwrites its own section of.

By the time I'm writing this, the `self-driving-work` skill is on version 433 with 126 bundled files, including 55 numbered issues, 17 ideas, and 39 pain points. I didn't write most of those. My agents did, at the end of sessions, because the skill tells them to.

```
self-driving-work         v433, 126 bundled files
├── SKILL.md              the thin index
├── HANDOVER.md           one section per thread of work
├── CHANGELOG.md          rolling 14-day window
├── environment-notes.md  durable gotchas
├── open-prs.md
├── roadmap.md
├── dogfooding.md
├── field-feedback.md
├── issues/               55 issues + index
│   ├── 01-reviewer-suggestion-regression.md
│   ├── 02-crowd-fallback-provenance.md
│   └── ...
├── ideas/                17 ideas + index
│   ├── 01-rank-by-author-association.md
│   └── ...
├── pain-points/          39 bad examples + index
├── feedback/             3 + index
└── scripts/
    └── task_summary_sampler.py
```

*The file tree of a project-tracker skill after two months of agents maintaining it.*

The loop looks like this:

- I start a session on any surface (local Claude Code, a cloud task, Slack, PostHog Desktop, Codex) and say "let's check on /phs self-driving work".
- The agent uses my local `/phs` [bridge skill](/docs/skills#step-3-set-up-a-bridge-skill-optional-shortcut), loads the remote skill, reads `HANDOVER.md`, scans the backlog index, and knows where we left off. We do the work in the repo and the product, not in the skill.
- At the end of the session, the agent logs any new issue or idea, records any PR that opened or merged, adds one changelog line, and overwrites its handover section.

This is the lowest friction and most chill way I have ever found to deliver complex features over long horizons. The skill is the memory, and it's memory I get my agents to intentionally control and maintain.

I don't rely on a model's hidden memory feature that I can't read. I can open the skill in PostHog and see exactly what my agents think is true. Every now and then as things get messy I just tell the agent to clean up or better yet it knows itself to follow certain protocols like trim the changelog after 14 days etc (all skill edits are version tracked anyway so it's all recoverable if I really need it).

I liked the pattern enough that I turned it into a template. [`project-template`](https://github.com/PostHog/community-skills/tree/main/skills/project-template) is in the [community skills store](/docs/skills/community). Install it once per area of work, bind the project name and the changelog window, and you have a living hub that any agent on your team can read and write.

My favorite part of the template is a small table the agent has to consult before writing anything down:

| Still true in 30 days? | Has an owner who refreshes it? | Goes in                                   |
| ---------------------- | ------------------------------ | ----------------------------------------- |
| Yes                    | Yes, a tracked work item       | `issues/NN` or `ideas/NN`                 |
| Yes                    | No, durable reference          | `environment-notes.md` or a `references/` file |
| No, but in flight now  | You, this session              | your `HANDOVER.md` section                |
| No, it just happened   | Nobody                         | `CHANGELOG.md`, one line                  |

The most common failure of the skill is durable detail written into the changelog, because the changelog is the file the agent was already editing. That table exists because I watched it happen many times.

You don't need all this structure on day one, though. For a new, messy project, just start a skill and tell your agent to keep its context there. Don't worry much about the layout. Agents these days do something sensible on their own, and in my experience it only starts to get messy at around version 50. The important part is that the context is in a skill you can see, version, and load from anywhere. As the project matures, you add structure.

That's how `autoresearch`, the skill behind the biggest (side-quest) thing I've built this year, went. It started on April 27 as a single design spec. Over five months and 551 versions it grew whatever the work needed: a decision log, a backlog, a plan to cut a PR stack 31 layers (yes 31 i kid you not) deep into reviewable pieces, a brief for reviewers, and a few one-off scripts for slicing the stack. Once the stack landed, I had the agent refactor it into the same tidy project tracker shape as `self-driving-work`. The messy stack-era files are still in the version history if anyone needs them.

## 3. Skills as a runbook that learns

The alerts skill in section 2 records what exists. A runbook records what went wrong and how we fixed it, so it gets better every time something breaks.

`self-driving-debugging` is our runbook for when self-driving misbehaves in production and users have some issues we need to dig into.

The whole thing hangs off one line in the skill body: **add or extend a reference every time we run down a new class of issue.** When a support ticket turns into a real investigation, the agent writes up what it found as a dated file in `investigations/`, then extends the matching reference so the next agent doesn't start from zero. Seven investigations in, it covers duplicate reports, competing PRs for one fix, oversold report titles, unaddressed review comments, and a data import source that emitted nothing.

Its sibling, `scouts-debugging`, does the same job for the scout fleet. Between them, "debug self-driving for team N" is a sentence I can say to an agent on any surface and get a real answer.

## 4. Skills as a daily driver

The `andy-inbox` skill is how I start most days. It pulls every report in the [self-driving inbox](/docs/self-driving/inbox) where I'm a suggested reviewer, maps each one to its GitHub PR and issues, and renders one plain line per report: priority, age, review state, CI, and one next action.

```
In flight with a PR, newest report first

#  Next               Report                                        PR       Signals
1  ENQUEUE (YOUR GO)  fix(signals): give the revenue scout a supp…  #108959  stamp✓ CI✓
2  FIX CI             fix(mcp): paginate large GitHub repository…   #108947  stamp✓ CI2✗
3  ENQUEUE (YOUR GO)  fix(mcp): document the usable --json flag p…  #108934  stamp✓ CI✓
4  ENQUEUE (YOUR GO)  fix(hogql): system schema discovery relapse…  #108866  stamp✓ CI✓
5  FIX CI             fix(inbox): show why follow-up checks failed…  #108829  stamp? CI2✗
6  ENQUEUE (YOUR GO)  fix(mcp): bound health-issues-list payloads…  #108798  stamp✓ CI✓
7  FIX CI             fix(mcp): make execute-sql join errors iden…  #108284  stamp✓ CI2✗
```

*The in-flight table. One line per report, with the thing I need to do next.*

The skill bundles Python scripts to do the boring parts: `render_table.py` builds the table from the API and `gh`, `pr_candidates.py` ranks reports that are ready for a Create PR press, `merge_intent.py` finds PRs I've approved that need agent work to get merged, and `draft_task.py` writes the payload to launch a PostHog [task](/docs/posthog-desktop/tasks) for a stalled row. So "get these three PRs green on CI" turns into three async tasks I can check on later.

It also has a `working-set.md` that records only what I've personally chosen to own, with four rules to guide it:

1. **Live first, memory second.**
2. The API is the truth.
3. The file is a list of my commitments.
4. Never report status from the file alone.

There's a whole family of these:

- `my-github` is what needs my attention across GitHub: open PRs, review requests, assigned issues, recent merges.
- `andy-prs` is every PR I opened, with its size, the issues it closes, the inbox report it came from, and its checks.
- `andy-issues` is every issue I filed, mapped to the inbox report that picked it up and the PR that came out of it, so I can see which of my specs turned into code.
- `andy-approvals` is the bot-authored PRs I approved or sent `/trunk merge` on, and whether the bot has pushed since, because approving an agent's PR and then losing track of it is a real failure mode.

A scout called `signals-scout-andy-github` runs the GitHub one every hour and keeps a single living report current in my inbox, so most mornings the answer is already waiting for me. A generic version, [`my-inbox`](https://github.com/PostHog/community-skills/tree/main/skills/my-inbox), is in the community store.

## 6. Skills that run themselves

Every scout in PostHog [is a skill](/docs/self-driving/whats-in-a-scout). Same format, same store, same version history. The only difference is a schedule and a harness that runs it. Which means when I've built a skill for how I do a job, turning it into a job that does itself is a small step, not a new project.

`signals-scout-agent-feedback` watches what agents complain about in our MCP, `signals-scout-self-driving-logs` watches our production logs, and `signals-scout-canonical-drift` checks the canonical scout fleet against the current harness once a week.

A few are about skills themselves. `signals-scout-skills-best-practices` checks recently-changed skills in our repo against the [Agent Skills spec](https://agentskills.io/specification). `signals-scout-skills-maintenance` catches merged PRs that make an in-repo skill stale. Both lean on `skills-best-practices`, which gets its own section below.

Yes, I have skills that maintain skills. I did warn you.

## 7. Skills as a place to think

This one surprised me. `andy-hogs-2026q4` is my draft of Hopes, Obstructions, Growth, and Sneak attacks for our quarterly planning.

And `andy-blogs` is the skill that tracked this post. It has one file per post, with the argument, the sources, a dated log of every decision, a list of what I cut for being too sensitive, and the open TODOs. When I start a new session on the post, the agent already knows which branch the draft is on, which numbers it still has to re-check, and which Slack screenshot I already rejected (it was about scouts, and this post is about skills). It's on version 11. This paragraph is in its changelog.

Neither of these is a set of instructions. They're documents I'm iterating on with an agent, over weeks, across surfaces. A skill turned out to be a better home for that than a Google Doc, because the agent can read it, edit it with the smallest possible change, and every edit is a version I can diff.

## Why the store, and not a folder of markdown files

You can do all of this with a `.claude/skills/` folder. I did for a while. Here's why I moved everything into PostHog:

- **It's on every surface.** The same skill loads in Claude Code on my laptop, in a cloud task, in Slack, in Codex, in Cursor, and in PostHog Desktop. If your skills only live in one repo's dotfiles, your agents on every other surface are working from nothing.
- **Agents can write to it.** The `skill-update` tool takes incremental `edits` and `file_edits` with a `base_version` check, so two sessions can maintain the same skill without clobbering each other. That's what makes the project-tracker pattern possible.
- **It's versioned.** 433 versions of `self-driving-work` means 433 diffs I can read when something looks off. A file on disk gives me one.
- **It's shared.** A teammate, or their agent, or a scout, reads the same thing I do. The holiday handover only works because of this.
- **Progressive disclosure is built in.** `skill-list` returns names and descriptions. `skill-get` returns the body and a file manifest. `skill-file-get` pulls one file. Nothing loads that the task doesn't need.

## The skill that stops skills slop

Everything above has a failure mode, and it's the same one. An agent that maintains a skill will, left alone, grow it. Every session adds a paragraph to the body. Every fix gets a sentence in the changelog. The handover becomes a log. Six weeks later you have a mono-skill of slop that no agent loads because loading it costs more than it saves.

I wrote `skills-best-practices` to stop that happening. It's the house style for our store: the compliance floor from the [Agent Skills spec](https://agentskills.io/specification), 16 named patterns lifted from the skills in this post, a smell checklist, a refactoring workflow, and the write mechanics that don't lose content. It eats its own dogfood: the body is a thin index and the substance is in five bundled files. When an agent creates or edits a skill of mine, it loads this one first. It's in the [community store](https://github.com/PostHog/community-skills/tree/main/skills/skills-best-practices) too, alongside [`skills-spec`](https://github.com/PostHog/community-skills/tree/main/skills/skills-spec), which is the spec itself as a skill.

I think this is the crucial and least talked about part of working with skills. The rules are simple. Holding to them across hundreds of agent sessions is the work.

1. **Give every skill a convention or a workflow.** A skill without one is a blank page, and agents will slop all over a blank page. The project tracker says exactly where an issue, an idea, a PR, and a handover go. The debugging runbook says to add an investigation file and extend a reference. The agent doesn't have to decide how to record things, so it records them consistently.
2. **Keep the body small, as a wrapper for everything else.** The body is what an agent reads to get up to speed fast: what this is, the gotchas that bite hardest, a file map, companions, and a maintenance contract. About one screen. New detail goes in a bundled file, and the body only gains a pointer to it.
3. **Set heuristics so nothing grows unbounded.** It's fine for agents to maintain the skill. You just set the rules. The changelog is a rolling 14-day window that gets trimmed as it's appended to, not an archive. `HANDOVER.md` is a clobber file: read first, overwrite last, one section per workstream, deleted when the work lands. The "where does this fact go" table from earlier exists because the most common failure is durable detail written into whichever file the agent was already editing.
4. **Link skills when it makes sense.** `self-driving-work` and `scouts-work` cross-reference each other constantly, and that's fine. Each has a Companions section that says what its siblings own so nothing gets duplicated. One hub per area beats one hub that covers everything, and a link is cheaper than a copy that drifts.
5. **Dogfood them, often.** Take a skill for a spin with your agent. Actually use it for the job it's meant for, notice where the agent stumbled or where you had to fill in context by hand, and fix the skill right there in the same session. The best-practices skill has a version bump every time I audited a skill and learned a new smell. The skills in this post are good because they've been used hundreds of times and improved every time they weren't.

Two mechanical rules sit underneath all of that. Use the smallest edit primitive, because a full-body rewrite for a one-line change silently drops content, and chain `base_version` between writes. And keep every bundled file reachable from the index, because a file no index links is invisible to progressive disclosure and no agent will ever find it.

## Try it

- Read the [skills docs](/docs/skills) and connect the [PostHog MCP](/docs/model-context-protocol) to whatever agent you use.
- Install [`project-template`](https://github.com/PostHog/community-skills/tree/main/skills/project-template) from the [community store](/docs/skills/community) for one area of work you're tired of re-explaining to your agent.
- Install [`skills-best-practices`](https://github.com/PostHog/community-skills/tree/main/skills/skills-best-practices) next to it, and tell your agent to load it before it creates or edits any skill.
- When you have a skill for how you do a job, [turn it into a scout](/docs/self-driving/scouts) and let it do the job for you.

And if you build a skill for something in your life that has no business being a skill, tell me. I have a hedgehog joke scout. I'm not going to judge.
