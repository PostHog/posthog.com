The UI is dead. Or so I keep hearing.

Agents are your users now, software is [losing its head](https://a16z.com/is-software-losing-its-head/), and everyone who learned Figma should start learning Bash.

Maybe the UI is dead in the four square blocks of San Francisco where everyone's running three Mac minis with clawbots. But I'm a regular person at a screen for most of my day, and so are the people I build for.

Here's the tl;dr of my take:

- everything is a user interface if I'm using it
- my agents are the ones using it sometimes
- headless is just a new layer to product building (the same way APIs and the GUI were once new)

If you're a product builder, congratulations! That means your job just doubled: every user of your product is potentially bringing a plus-one, an agent (or several) that doesn't care what font you picked.

At PostHog we've spent the last while building for these new agent party guests, tools like our [MCP server](/docs/model-context-protocol), [CLI](/docs/getting-started/install), and [context mill](https://github.com/PostHog/context-mill). At the same time, we've been shipping more charts, screens, and clicky stuff for humans than ever.

Here's what we've learned building for a hybrid (not headless) future.

## 1. If a human can do it, an agent should too

If you're new to this whole "agentic users" thing, start here. Anything a human can do in your product, [an agent needs a way to do as well](/newsletter/agent-first-product-engineering).

Mostly, agents don't touch your UI. Some can (computer-use agents like Perplexity's Comet will click around a live DOM), but that's the slow, brittle path. Given the choice, an agent would rather work in data, SQL, tool calls, and APIs.

Start by auditing your product's capabilities and ask at each interaction: can an agent do this through an endpoint or an MCP call? Every click-only answer is a dead end for the agent, and dead ends are where [loops](/newsletter/loops) die.

Netlify has a name for getting this right: [agent experience](https://www.netlify.com/agent-experience/), or AX, how easily an agent can discover what you do, call it reliably, and recover when something breaks. The standard way to give it that is [MCP](https://modelcontextprotocol.io). Think of it as an API built for agents instead of developers: the same menu of actions your product already exposes, described in a language an agent can read.

The flip side matters just as much (and it's where the rest of this post is headed). Every action you hand the agent is an action a human now needs a way to see, sign off on, or roll back.

**What this looks like:**

- Salesforce shipped [Headless 360](https://www.salesforce.com/news/stories/salesforce-headless-360-announcement/), exposing its data and workflows as APIs, MCP tools, and CLI commands so agents can act without touching the UI.
- [Vercel's MCP server](https://vercel.com/blog/introducing-vercel-mcp-connect-vercel-to-your-ai-tools) lets an agent inspect deployments, pull runtime logs, and trigger deploys with the same account access a human gets in the dashboard.
- Stripe, Cloudflare, Supabase, and Hugging Face all publish official agent skills that work across Claude Code, Cursor, and Copilot.

<CalloutBox icon="IconTerminal" title="Go build:" type="fyi">

An MCP that covers every action a human can take. Run the dead-end audit. Rewrite your errors as instructions. Make your writes safe to repeat, so an agent that retries a call doesn't create two of everything. And think about your customer's customer: your rate limits were designed for human clicking patterns, not an agent hammering you on someone else's behalf. Then dogfood the whole thing headlessly. If you want a rubric for whether the agent is actually doing the job, [we wrote one](/blog/testing-ai-agents).

</CalloutBox>

## 2. Onboarding might not start on your homepage

If you're building for developers, onboarding increasingly doesn't start from a "get started" button. It starts in a terminal or a chat window. This is less true if your users aren't technical, but the pattern is spreading: if your [AEO](/blog/aeo-advice) game is strong, the user may never see your homepage at all. Claude or ChatGPT recommended you to a person, they said "go for it," and the agent set it up.

The catch is you can't count on the agent to read your install docs. A capable one might go looking, but plenty won't. So the job is to make setup something an agent can finish without a human stepping in. Three things get you most of the way there:

1. **Be discoverable.** Register your MCP server and get listed where agents look for connectors (the Claude and Codex app directories, for a start).
2. **Handle auth on its own terms.** An OAuth device flow or a self-minted scoped key beats a dashboard someone has to click through.
3. **Collapse setup into one call.** One command, not a ten-step guide.

That's the agent handled. Humans still onboard themselves, though. And even when an agent runs the whole setup, a person eventually opens the product and has to work out what it is, whether it worked, and what to do next. That requires UI, baby! The agent gets you wired up in one call, but the human still needs a screen that orients them, shows the state of things, and points at the obvious next step.

**What this looks like:**

- The fastest way to try PostHog today is a single `npx` [command](/docs/getting-started/install) that sets up your account and scans your codebase to work out what to instrument. It also runs a little tutorial in your terminal as it goes, so you can watch it work. Here's [how we built it](/blog/envoy-wizard-llm-agent).
- [AgentMail](https://docs.agentmail.to/agent-onboarding)'s onboarding docs teach the agent to provision an inbox and key itself.
- MCP standardized on OAuth 2.1 so access is scoped, revocable, and granted once. When there's no browser at all (CI, a bare terminal), the device authorization flow does the same job with a short code.

<CalloutBox icon="IconSparkles" title="Go build:" type="fyi">

Build both front doors. For the agent: a signup flow it can finish end to end ([fork ours](https://github.com/PostHog/wizard), our competitors already have), docs it can parse (an llms.txt, pages served as plain Markdown), and auth that's safe when it improvises (short-lived, scoped tokens beat hoping it won't paste a key into a chat). For the human: a first run that orients them in seconds. Adapt it to how they arrived. If an agent already did the setup, drop the person into a working product that shows them what it did and one clear next step. If they're setting up by hand, walk them through it.

</CalloutBox>

## 3. Feed agents context (or they'll invent it)

Your product might be the best toy ever, but if the batteries aren't included, Christmas morning is going to be disappointing. The batteries are context: what the user has done, what's in their account, what state everything is in. Your UI already shows a human all of that. The job is to make the same context reachable to an agent, as data it can query and act on.

More context isn't better context, mind you. Anthropic's [advice on context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) is to keep it informative and tight, curating each turn rather than context dumping. Every token you spend on data that doesn't matter is one not spent thinking.

Get this right, and one pool of context feeds a dozen surfaces. Take PostHog error tracking. The exceptions it captures show up as a [web UI](/docs/error-tracking) a human reads, but the same data can be pulled into an agent over our MCP. Taking it a step further, errors can be acted on automatically by [self-driving](/blog/what-if-your-product-built-itself), and land as a PR with the fix in [Slack](/blog/slack-app-beta). It's the same data, with many front doors, and many ways for humans and agents to manipulate it.

**What this looks like:**

- We rebuilt the context layer behind our own setup wizard and [5x'd paid conversion](/newsletter/context-engineering).
- Linear's agent triages an incoming issue, investigates the code, and opens a PR for an engineer to review in the morning. Their internal agent [merged nearly 700 PRs in a single month](https://linear.app/now/coding-sessions-for-linear-agent).
- Supabase's [MCP server](https://supabase.com/docs/guides/getting-started/mcp) hands an agent your project's live schema and logs and lets it run SQL, so it works from the actual state of your database instead of guessing at it.

<CalloutBox icon="IconDatabase" title="Go build:" type="fyi">

Build one context layer and point both the UI and the agent at it: the dashboard a human reads and the answer an agent pulls come from the same source. Then notice how much of your UI is already context. An error message is a screen a human reads and a signal an agent acts on, so when you make it say exactly what to do next instead of "something went wrong," you've improved the interface and fed the agent in the same move.

</CalloutBox>

## 4. Watch what agents actually do

You've got years of data on what your human users do and almost none on what the agents do. You can't build for a user you can't see (shocker), so the solution is to watch what agents call, what they retry, and where they give up.

It's the same instinct you already have for humans, but the failures look different. A person rage-clicks or bails, and you catch it in [session replays](/session-replay). An agent fails in its own ways: it loops, retries a tool that keeps erroring, hallucinates a parameter, or gives up and hands the job back to the human.

You catch those in [AI observability](/docs/ai-engineering/observability) for the agents you ship, and [MCP analytics](/docs/mcp-analytics) for the ones showing up at your MCP server. Different shapes, same payoff: each one you find is usually a spot where the surface between you and the agent needs work. Last month ours clustered close to 10 million tool calls from 31 different agent clients, real people running things like this:

- Wired PostHog into a text-message assistant so it pings them the moment a metric moves.
- Shipped an A/B test on a "skip the intro" screen – feature flag, 50/50 split, and all.
- Built an activation-to-paid funnel.
- Triaged live production errors like expired magic links and missing auth sessions.

What's missing from those examples is the PostHog UI. What's not missing is UI. Those 31 clients (Claude Code, Cursor, Cowork, Linear, Notion) all have a screen. A terminal is a UI. A chat window is a UI. [Slack is a UI](/blog/slack-app-beta). Your users are still looking at a screen, just not yours.

![MCP Analytics dashboard](https://res.cloudinary.com/dmukukwp6/image/upload/q_auto,f_auto/mcp_dashboard_light_0907967b56.png)

<Caption>How's this for meta: the query I ran to pull those examples showed up, seconds later, as a sample intent in the same dashboard. The tool using the tool.</Caption>

**What this looks like:**

- In June, Cloudflare's [Radar data](https://www.nbcnews.com/tech/tech-news/bot-web-traffic-overtaken-human-web-traffic-data-shows-rcna348522) showed automated requests overtaking human ones on HTML traffic for the first time, 57.5% to 42.5%, about 18 months earlier than its CEO had predicted.
- [Temporal](https://temporal.io/solutions/ai) records every step of an agent's run as a durable event history you can replay and inspect, so you can see exactly where a loop stalled or repeated itself.

<CalloutBox icon="IconGraph" title="Go build:" type="fyi">

Instrument agent traffic the way you already instrument humans: tag every call with the client it came from, then watch where agents retry or give up. And enjoy the irony, because the thing you build to watch a swarm of agents who never touch a UI is a dashboard. A UI. You cannot hold a thousand silent agent runs in your head, so even here the answer is a screen for a human to read.

</CalloutBox>

## 5. Price for two kinds of user

In February 2026, the software industry had a collective panic attack. Around [$300 billion](https://www.forbes.com/sites/donmuir/2026/02/04/300-billion-evaporated-the-saaspocalypse-has-begun/) in market value evaporated in roughly 48 hours, Wall Street named it the SaaSpocalypse (nice branding), and by spring the number was closer to [$2 trillion](https://www.saastr.com/the-saas-rout-of-2026-is-even-worse-than-you-think-for-the-first-time-ever-software-now-trades-at-a-discount-to-the-sp-500/). The logic was that if one agent does the work of ten people, you don't buy ten seats.

PostHog has had [usage-based pricing](/newsletter/pricing-advice) from the beginning, which sidesteps the whole problem: charge for what gets used and it doesn't matter whether a human or an agent used it. Per-seat pricing can't do that. An agent and a human cost you wildly different amounts, so one price for both means you either eat the agent's bill or overcharge the human.

It also clarifies what each side is buying. The agent is paying for raw capability, the tokens and calls it burns to get work done. The human is paying for the experience wrapped around that work: the screen where they see what happened, decide whether to trust it, and steer. Yet another useful reminder that the UI isn't overhead you begrudgingly maintain. It's a thing people actually pay for (are you getting it now?).

**What this looks like:**

- Salesforce keeps a per-seat license for its human reps (Service Cloud Enterprise runs about $165 a seat) but bills [Agentforce](https://www.salesforce.com/agentforce/pricing/) conversations separately at roughly $2 each.
- Stripe ships its own [token and usage meters](https://docs.stripe.com/mcp) so agent traffic gets billed by consumption while the human dashboard stays on its existing plan.

<CalloutBox icon="IconReceipt" title="Go build:" type="fyi">

Put a usage meter on the machine surfaces your customers' agents hit (the API, the MCP server, tokens) and bill those by consumption. Keep humans on a plan that buys access to the product and its interface. Concretely: one line item that scales with agent traffic, one that doesn't. Then earn that second line. Delight me while my agent does the grunt work. Give me a screen I actually want to open.

</CalloutBox>

## 6. Now build the screen worth looking at

Uno reverse. Every one of those five sections produces something a human still has to see, trust, approve, or undo. The agent creates the dashboard, but someone decides whether to ship it. The agent files the fix, but someone reads the diff.

Humans are visual creatures. A good UI gives you a sense of state at a glance, the way a door handle tells you to push or pull (Danilo wrote a [whole thing](/newsletter/good-taste-great-products) on affordances). On screen it's a spinner that means wait, a greyed-out button that means not yet, or a red badge that means "look here!" I take that in ten zillion times faster than I'd skim the equivalent wall of text in a terminal. Your brand, your taste, your whole sense of what the user is trying to do **all live in the user interface**.

If anything, the UI matters _more_ now. When software was hard to build, people had fewer choices (and used crummy products as a result). Now a decent product can be scaffolded in an afternoon, so the thing that makes a human pick yours is how it looks and feels to use, and how well their agent can use it too.

Even the companies furthest down the headless road keep reaching back for the screen. Claude Code lives in the terminal and it's lovely, but Anthropic still built it a UI, shipping Claude Desktop and Cowork.

We made the same call. Our bet with [self-driving](/blog/what-if-your-product-built-itself) is that a product can run its own loop, with agents doing most of the work. But people don't open PostHog to watch agents work. They open it for the outcomes: bugs fixed, PRs merged. [PostHog Desktop](/desktop) is the screen where you see those outcomes, approve them, and steer.

This is the fun part, honestly. You're no longer designing a screen for someone with nothing else to look at. You're designing for moments like:

- **Approval.** The agent has the change ready and needs a yes. Can the human tell what they're saying yes to in two seconds?
- **Review.** Not a summary of what changed. The change itself. A diff beats a paragraph.
- **Undo.** When the agent gets it wrong, there needs to be a way back.
- **Legibility.** A feed you can scan and instantly tell which actions came from a colleague and which came from a bot.
- **Orchestration.** If five agents are running at once, do you watch them on one screen, or open five chats?
- **Interruption.** When you need to steer the agent while it's still moving.

Those are much better design problems than another login page.

**What this looks like:**

- When Intercom built [Fin](https://www.intercom.com/blog/introducing-operator/), one of the first things it shipped was Fin Operator, an agent that supervises the customer-facing agent and serves up its work in a diff-style review UI – a pull request for your support setup.
- Linear has started writing [interaction guidelines](https://linear.app/developers/aig): an agent should always be legible as an agent, and its work should show up somewhere a human can review it.
- GitHub credits both sides now. Bot accounts carry a [bot] badge, and [generated release notes](https://github.blog/changelog/2026-06-18-generated-release-notes-credit-you-for-copilot-pull-requests/) credit the human who kicked off a Copilot PR, not just the agent that typed it.

<CalloutBox icon="IconLaptop" title="Go build:" type="fyi">

Surfaces for reviewing, approving, and overriding agent work. Make agent actions legible _as_ agent actions. Then make the surfaces agents don't touch as delightful as you possibly can.

</CalloutBox>

## The future is hybrid (not headless)

Agents might be the primary users of software soon, by sheer volume. But by _meaning_? There's no agent without me. It's easy to nod along to an agent's output without really reading it, and the screen is what pulls me back in. It's where I catch what the agent got wrong, and where I still feel like I'm holding the wheel.

Good products for agents really are, under the hood, a pile of Markdown, SQL, tools, and resources. Build that. But I'm a human living in a home, not a data center or cyberspace. So build the plumbing for my agent, and build me a screen worth looking at. Give me _and_ my agents a reason to use your thing.
