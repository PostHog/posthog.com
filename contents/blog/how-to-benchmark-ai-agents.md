We spend 2 trillion+ LLM tokens per month, with the lion's share going to running agents. We know what they do and how good they are *most of the time*, but it's way too much money to let them run unattended.

New models keep popping off like mushrooms, and popular LLM benchmarks don't give us nearly enough info. We can "vibe" how well model X or Y will perform in our stack, but it often leads to worse results, as our tasks are pretty specific.

What doesn't make it easier is that agents cheat. They search for leaked context, memory, and DB query logs – to do as little work as possible. Can't blame them, but it makes creating your own benchmarks harder than you would expect.

In this post, I'll explain how we benchmark our agents, what we learned, and where we messed up (so you don't need to), with links to real PRs. I'll focus on agents for data research and code review, since we do a lot of that as part of [self-driving](/self-driving) and 2.4 million+ agentic runs we spawned.

## 1. How to define criteria

Defining what is "good" is the hardest part, in my opinion. If you ask an [LLM judge](/docs/ai-evals) whether an agent's output is "helpful", you'll get polite, useless praise. Especially if it was generated by the same model.

To build benchmarks that actually mean something, criteria have to evolve from simple sanity checks to something measurable. Ideally, based on the real data.

### Simple: Finite list of correct answers

The first approach would be to take a task that has a clear answer (or multiple) and check what combinations of model + effort + harness reach those answers, and which ones fail.

We have our own code review agent, called ReviewHog, that covers a significant part of PostHog PRs. It needs to stay up to date for the best results, so we needed a base benchmark to check against when we change models or prompts.

The best solution we came up with initially was surprisingly effective and mostly simple.

> **Illustration placeholder**
>
> The deck illustration for the simple manual-check approach

The recipe:

- We took one large PR
- Made a frozen copy
- Reviewed it manually
- Had several other review agents review it.
- Got a list of potential bugs from every possible angle.

Meaning, if there are 13 issues worth checking (structure, performance, security, etc.), we can measure the models on a 0/13 scale and time/money spent. Here's an [example](https://github.com/PostHog/posthog/tree/master/products/review_hog/eval/experiments/2026-08-model-glm53-flash) of us testing GLM 5.3 Flash.

It worked well (and still does), but it has an expected limitation: even on a large PR, the scope is limited and doesn't show the whole picture.

### Harder: Golden set

The second approach was to use the same method across more varied examples, covering a larger percentage of real cases.

Let's stick with the code review for a moment longer. First, we need more PRs. Second, what if, instead of synthetic-ish bug cases, we tested searching for bugs that 100% happened? Ideally, if they also caused a mess, like a proper incident.

And that's exactly what we did.

> **Illustration placeholder**
>
> The deck illustration for the harder incident-golden-set approach

We collected a golden set of PostHog incidents built from incident discussions and code. Each incident in the set includes:

- The PR that caused the incident
- The description of the problem
- The PR that was used as a fix for the incident

This means we can review 33 PRs of different sizes, from different repos, and get a clear boolean metric: did the reviewer find the bug that caused the incident?

Here is what the numbers looked like:

> **Illustration placeholder**
>
> Table with golden set experiment results

We got pretty good results with ReviewHog, with this combination showing the best result: `GPT Sol 5.6` (at the time) at `xhigh` for bug search and `Claude Opus 5` (at the time) at `xhigh` for bug validation (here are the [experiment results](https://github.com/PostHog/posthog/tree/master/products/review_hog/eval/experiments/2026-09-incident-golden-set)), both using `pi`.

> It's also a good example of "don't confirm model results with the model of the same family", as having both stages with OpenAI or Anthropic led to miserable results.

That said (and you probably thought this too), the code review tasks are deterministic enough and easier to grade. The next problem we hit was how to grade abstract agents – ones that can, technically, do anything.

### Hardest: Targeted rubrics

The obvious answer is rubrics. But with open-ended tasks, generic rubrics like "Rate accuracy from 1 to 5" fall apart immediately. They mostly measure how confident and fluent the model sounds, not whether it did useful work.

A great example is scouts. If you don't know them yet, [scouts](/docs/self-driving/scouts) are custom agents we use for self-driving to research anything from [Product Analytics](/product-analytics) anomalies to mentions of your brand in social media. As open-ended as it gets.

To evaluate them, we built a rubric generator. You pick the agent you care about, add some context, and let it generate evaluation criteria.

> **Illustration placeholder**
>
> Scout generator screen

Every scout should produce a report covering what it found, how actionable the findings are, and what to do next. To measure this baseline, we stick to a mostly static set of rubrics shared across all scouts.

To make the ranking more meaningful, we also generate rubrics tailored to that specific scout:

- What area it covers (a specific product feature, external data source, etc.)
- What skills and instructions it needs to follow
- What it did in previous runs, what tools it used, and what reports it generated

Based on that, we add agent-specific rubrics. In our case, for a scout analyzing the stability of the [Session Replay](/session-replay) player, we don't just check formatting. We grade whether it spotted actual playback failure symptoms, whether it queried data correctly, and whether the bug it flagged actually affected real users.

> **Illustration placeholder**
>
> Replay player reliability rubrics

Now that we have a defined list of rubrics to track against, we can reliably track success rate through any number of changes. The v1 we work right now allows us to test against:

- Old model vs New model ("Is the new model released work better than the old one?")
- Thinking effort ("Do I actually need it at xhigh, if medium does it just fine with 30% fewer tokens?")
- Prompt changes ("Let's create 5 skills and track which one works the best for the task")

The result is a report with a close-to-clear answer. It's obviously not fully deterministic, but it's way better than just "vibes."

Here's the report I ran while writing this part of the post to check "what is better, Sol vs Opus," and it looks like, for this specific task, we are sticking with Sol. Opus would do a better job on plenty of tasks, but to know that, you need something measurable to rely on.

>
> Report results

Next, after we figure out what is good, we need to make it work and stay objective at scale.

## 2. How to isolate runs

The surprisingly nasty problem you notice when you want to benchmark multiple models against real data is that they learn about each other pretty fast and try to piggyback. This can come from [LLM traces](/docs/ai-observability/traces), DB queries, or any other logs the agentic run generates.

For results to reflect the model's quality, make sure state isn't leaking. With multi-step agents that simulate human-agent conversation, state leaks into places normal test runners don't even check.

You can isolate state in multiple ways, including three approaches we tested.

### Simple: Sequential runs with state cleanup

The simplest approach is to run trials one after another and clear local agent memory between runs. You run a trial, record the output, reset the agent's scratchpad or immediate context, and start the next run.

> **Screenshot placeholder**
>
> Sequential runs

It doesn't mean you need to run one agent at a time – the chain could include hundreds of agents running in sequence or in parallel, if they are all part of the same task. It's also what we used for initial ReviewHog benchmarks against a single frozen PR.

The downsides are clear: you need to clean up the DB and logs after each run, and it's obviously slow, so testing different combinations of agents/efforts/skills will take a while.

### Harder: Parallel runs with shared state

If your agent doesn't generate meaningful artifacts beyond the output, you can probably say you don't care and run multiple variants at the same time anyway. Unironically, I bet plenty of cases could work, and it speeds up the benchmark a lot.

Instead, I'll show the cases where it doesn't.

Back to scouts, here's an example of a data-anomalies scout being benchmarked. Run B4 investigated an anomaly and saved a memory at 15:18:08. When Run B12 ran later in the same workspace, it picked up that memory at 15:18:54 and used it instead of doing the work itself.

> **Screenshot placeholder**
>
> Run B12 retrieving shared memory saved by Run B4

As you could've guessed, the results of such runs are highly questionable because the grading gets contaminated. A fast model like Luna could overperform by copying Opus's homework.

It could work the other way around too. For example, an agent could decide not to cheat and honestly skip the results the other agent already found. During a benchmark run, Run B2 looked at candidate anomalies, saw that an earlier run had already covered the target bug, and skipped the task entirely.

> **Screenshot placeholder**
>
> Run B2 skipping an anomaly due to prior-run context

In this case, a clever model would get a surprisingly low grade for not finding a basic issue. Or you would need to prepare your judges for similar cases, which would affect the benchmarking results anyway.

Meaning, the next obvious step is to make runs of different agents invisible to each other.

### Hardest: Isolate everything

To get clean benchmarks, every trial needs complete isolation across everything the agent can touch:

- Identical starting context across all runs
- Private writable state (scratchpads, memory, vector stores, and DBs)
- Separate evaluation so scoring happens independently

DB state isn't the only leak. If your agent has tools to query ClickHouse, PostHog, logs, and so on, an earlier benchmark run leaves traces in those sources. A subsequent run can find those error spikes or query histories and use them as clues. True isolation means isolating telemetry and log scopes too.

> **Screenshot placeholder**
>
> Isolation illustration

Though there's also a real risk of over-isolating. If the benchmarking agent doesn't have as many tools as the real agent, it can get confused and skew the results.

Here's an example of one of the first dry runs we tested. It differs from the previous two traces – it wasn't cheating, just literal instruction-following.

> **Screenshot placeholder**

The moment it understands it's a dry run, it changes how it executes the intermediate steps, and judging becomes harder. This moves us to offline benchmarks, because agents that know they're running in a benchmark environment behave even stranger.

## 3. How to benchmark offline

You can run hundreds of agents against the current state of the DB pretty reliably. However, if you want to replicate the exact same check a day or a week later, you would need to run a new benchmark as the DB state changes.

Instead, you could decide to create offline evals – ones you can re-run as much as you want with comparable results.

I use the word "offline" loosely here, since you still need to call AI endpoints and so on. The main point is that the state is frozen and you can reset it at any time.

We went through three stages to get this working.

### Simple: Mocked MCP replies

Agents do tool calls when running. We track and store those traces – what the agent asked and what it got back. For example, what query it ran with `execute_query(sql)` and what slice of the DB was in the output.

> **Screenshot placeholder**
>
> MCP mock

It sounds pretty straightforward and worked on basic tech demos (returning static JSON to SQL queries), but it failed miserably on any meaningful production-like work because agents aren't deterministic. Meaning, the query from run 1 doesn't guarantee that run 2 will run the same one.

It's not a big surprise, but it would still be cool if it worked out of the box. Still, the case isn't that desperate, and we tried a couple of tweaks.

### Harder: Trajectory-based mocked MCP replies

The logical next step. Instead of building the mocked data over a single run, we ran ~50 runs, checked every trajectory the agent picked, and mocked those instead.

> **Screenshot placeholder**
>
> Trajectory MCP mock

It has potential, and to make it even more stable, I would suggest adding synthetic (or real) data a bit before and/or after every query (so a 24h query still returns true data if the call is skewed a bit).

On PostHog's side, though, as we mostly focus on benchmarking internal tasks, we decided to go with a hybrid approach. Meaning, it was simpler, but at the same time harder, to use real data.

### Hardest: Restored real-data slices

The solution that actually worked was spinning up an isolated PostHog sandbox seeded with a restored, real-world data slice.

On the surface, the idea is simple: query a couple of DB tables (Postgres, ClickHouse), store them as Parquet files in S3, and then restore them in the VM with a local PostHog instance to make it look like the real deal. The bonus: data never leaves PostHog infra.

> **Illustration placeholder**
>
> Offline sandbox setup showing real data slice, timestamp shifter, and isolated evaluation window

The first problem is obvious: "24h" now and "24h" in two weeks are way different "24h". Meaning, every time we inject data, we need to skew it toward the current timeline.

The second problem is less obvious: even if you skew the data, agents are still non-deterministic. That means testing a new model can make it look into tables and data sources you don't expect it to check.

For example, when preparing data for agent feedback, we can clearly sync tables with actual responses and tables with the scouts those responses were left about. But the moment you get a proper model, it will look inside, see that there aren't many users on this local instance, and get suspicious.

> **Screenshot placeholder**
>
> September 30 trace hitting a dead end due to missing team roster and metadata

On the other hand, you can, as always, overprepare and make it as realistic as possible on the MCP tools side, while the rest of the data in the local instance doesn't match the scale. Then the agent gets even more suspicious and starts thinking the data is synthetic.

> **Screenshot placeholder**
>
> September 23 trace where agent flags data-slice extraction artifacts as suspicious data

Needless to say, both cases will negatively affect your grading, since they cover behavior you don't want to test. And, sadly, there's no silver bullet – you just need to run and tweak it until you don't catch any "agent is suspicious" traces anymore.

## Vibes are cheap, bench

If you take anything away from this, it's that agents will happily exploit whatever mess you leave behind and cheat. If you want to go with vibes instead – it's ok, as they can get you pretty far, don't get me wrong.

However, with enough effort, building benchmarks is properly doable. You would need to watch for unexpected parameters and iterate a lot. But in the end, you'll have a solid system to move faster. Especially if you won't repeat the mistakes we did.
