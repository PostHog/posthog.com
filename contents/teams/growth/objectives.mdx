## Q4 2026 objectives

These are the primary goals the team is prioritizing this quarter.

<details>
<summary>Make agents first-class citizens for onboarding and implementation – <TeamMember name="Matt Brooker" photo /> <TeamMember name="Rafael Audibert" photo /></summary>

**Note:** Rafael will drive this goal while Matt is on parental leave.

**Motivation:** As an agent, it is hard to sign up, to implement PostHog correctly, and to know what to do with it. The wizard exists and it's amazing at installing PostHog. It is, however, hard to use the wizard as an agent because it's a TUI application. Also, agents don't usually use the wizard as their default way to implement PostHog. They prefer to implement it "from memory" rather than running the wizard or checking our docs.

**What we'll ship:**
- A production-ready headless CLI wizard that works with any user's coding agent
- Our skills exposed through a CLI, plus a way to make agents aware of it
- A provisioning API and authorization flows for agent-first onboarding via the wizard, which might include headless signups and a first-party OAuth app for the wizard
- Extensions to the wizard platform that the headless and cloud wizards need
- Broader evals of agents attempting to install PostHog when exposed to different scenarios (with/without Wizard/MCP/CLI/docs)

**We'll know we're successful when:**
- Agents can sign up, provision a project, and implement PostHog without a human opening a browser
- Agents reach for the wizard or our skills instead of implementing PostHog "from memory"
- We can compare how well agents implement PostHog depending on the scenario they are exposed to

**Synergy:**
- <SmallTeam slug="wizard-and-docs" /> owns the underlying wizard platform and agent library, and the TUI wizard. We build the headless wizard on top of it and contribute platform extensions back
- <SmallTeam slug="wizard-and-docs" /> is building an official benchmark for agents using our docs. Our evals cover MCP, CLI, and SDKs, and both teams will try Gauge if the pricing makes sense
- <SmallTeam slug="context-and-mcp" /> is choosing the MCP architecture. The CLI and the MCP should expose the same skills and give agents the same experience
- <SmallTeam slug="client-libraries" /> is rebuilding the SDKs around shared specifications. New SDKs (`@posthog/browser` v2, `@posthog/next` v1, and others) should be easy for agents to implement, and our evals should catch regressions in how agents use them

</details>

<details>
<summary>Improve the human journey through their time using PostHog – <TeamMember name="Fernando Gomes" photo /></summary>

**Motivation:** As a human, it is hard to know how to get set up and what you can do with PostHog. We have solved some of our onboarding issues and also our complicated sidebar, BUT PostHog is still rooted in a world where we portray our product in the same way we organize our teams internally. This is not how customers want to use the product. They want it to be organized the way **their own product** is organized instead.

**What we'll ship:**
- User-centric, task-oriented onboarding for the parts of your product you care about, instead of setting up each PostHog tool one by one
- A cloud in-app wizard for point implementations, such as adding a new product
- Handoffs between the wizard and the PostHog app, so users can start a task in one and finish it in the other. For example, the wizard detects data warehouse sources and users complete source creation in the app
- A review of the onboarding email flow for the current stage of PostHog
- A more careful onboarding flow for each new product you add

**We'll know we're successful when:**
- More new users reach their first meaningful use of PostHog, and they get there faster
- Users add a new product from the app with the cloud wizard instead of writing the code themselves
- Tasks that start in the wizard finish in the app (and the other way around) without users getting lost

**Synergy:**
- <SmallTeam slug="wizard-and-docs" /> and Growth both own the handoffs between the wizard and the PostHog app
- <SmallTeam slug="self-driving" /> wants a UI-first onboarding and runs the CLI wizard in a cloud sandbox. We share the cloud wizard infrastructure and the handoff from PostHog onboarding to Self-Driving onboarding
- <SmallTeam slug="platform-ux" /> is working to make PostHog web simple again. Together, we want to introduce spaces: customers split PostHog into the parts of their own product (e.g. checkout, onboarding, mobile app), and each space brings together the insights, replays, flags, and errors for that part. Spaces should become the default way to view PostHog, instead of the per-product split that mirrors how our teams are organized
- <SmallTeam slug="error-tracking" />, <SmallTeam slug="web-analytics" />, <SmallTeam slug="feature-flags" />, and <SmallTeam slug="experiments" /> all want wizard-guided setup for their products. The cloud wizard should make that easy for them

</details>

<details>
<summary>Cross-sell PostHog products via agents – <TeamMember name="Rafael Audibert" photo /></summary>

**Motivation:** After a codebase uses one product, how do we make sure agents suggest and implement the other PostHog products that go with it? We have a lot of products, and we have found different ways to cross-sell them to customers: in-app exposition, email campaigns, social media awareness posts, etc. Some of these methods, specifically the ones that happen in our UI, don't translate to a world where the main way customers interact with PostHog is via an agent. This goal is more abstract than the others, so we must try many things to see what sticks.

**What we'll ship:**
- New product and tool suggestions in MCP and CLI tool call responses
- Incremental skill surfacing that guides users to new products
- Cross-sell and incremental upgrade opportunities in the cloud in-app wizard
- Wizard signals (product and tech stack metadata from user codebases) used to enrich customer profiles and create opportunities for activation, cross-sell, and upgrades in the PostHog app
- More docs that agents can index

**We'll know we're successful when:**
- Agents suggest a second PostHog product without being asked, and users accept the suggestion
- Codebase signals from the wizard turn into in-app cross-sell and upgrade opportunities that convert

**Synergy:**
- <SmallTeam slug="wizard-and-docs" /> is building a Jev / Decisions API wizard feature that tags user codebases with product and tech stack metadata. We use those signals downstream
- <SmallTeam slug="wizard-and-docs" /> is turning docs into a skill library. Incremental skill surfacing builds on it
- <SmallTeam slug="context-and-mcp" /> owns the MCP, where tool call responses can suggest new products
- <SmallTeam slug="self-driving" /> reports already find problems in a customer's product. They are a natural place to suggest the PostHog product that solves them
- <SmallTeam slug="surfaces" /> runs agent sessions in PostHog Desktop, which is another place where agents can suggest new products
- <SmallTeam slug="feature-flags" /> is shipping a "flag by default" skill that the wizard installs. It's a good model for how other products can cross-sell through agents

</details>
